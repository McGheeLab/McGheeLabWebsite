## Project Overview

**Project Name:** McGheeLab Website
**Current version:** V1.0
**Description:** Single Page Application (SPA) for the McGhee Lab at the University of Arizona. Showcases research in microfluidics, 3D bioprinting, and traction force microscopy. The site covers mission, research areas, projects, team, classes, and contact information.

## Conventions

- **Architecture:** Vanilla HTML/CSS/JS — no frameworks, no build step
- **Routing:** Hash-based SPA routing (#/mission, #/research, #/projects, #/team, #/classes, #/contact)
- **Content (V3.302 correction):** `content.json` holds only static seed
  content (mission sections, contact info, classes intro). Research
  stories, news posts, project packages, and team members live in
  **Firestore** (`stories`, `newsPosts`, `projectPackages`, `users` /
  `teamProfiles`) and are authored through the in-site dashboard editors
  in `user-system.js` (login → `#/dashboard`), with contributor
  submissions reviewed by admins. Editing content.json still requires an
  FTP redeploy; Firestore content does not.
- **Images:** Static site images go in `Images/`; story/news media is
  uploaded through the editors to Firebase Storage as webp thumb/medium/full sets
- **Icons (V3.861): monochrome only, never colour emoji.** Site code uses
  `ICON.svg(name)` / `ICON.label(el, name, text)` / `ICON.render(value)` /
  `ICON.draw(ctx, …)` and static HTML `<i data-hi="name"></i>`; course
  modules use their inline sprite (`<use href="#hi-name"/>`, `HI.svg()`,
  regenerated by `python3 scripts/module_icons.py <file>`). Icons are
  Heroicons v2 plus Lucide for the gaps, listed in
  `scripts/icons.manifest.json` → `node scripts/gen-icons.mjs`. Text-only
  channels (tooltips, placeholders, `<option>`, toasts, exports) get words,
  not emoji. `node scripts/gen-icons.mjs --check --scan --emoji` must pass;
  it is a release gate. Only the chat reaction set is exempt (`emoji-ok`).
- **Naming:** camelCase for JS functions and variables
- **Mobile:** All layouts must be responsive; touch interactions supported

## Key Technical Decisions

- **Vanilla JS SPA** — No framework dependencies; deployed as GitHub Pages static site
- **Hash routing** — Works with GitHub Pages without server-side config
- **content.json** — Separates content from presentation logic for easy updates
- **Persistent header/footer** — Only page content swaps on navigation

## Release Batching (V3.604+)

Small changes are **collected, not individually announced**. The per-change
ritual (CHANGELOG entry, plan doc, sw.js CACHE_VERSION bump) is unchanged.
Since V3.818 the upload itself is automatic: a Claude Code `Stop` hook runs
`python3 scripts/deploy.py autodeploy` at the end of every turn, which
syntax-checks the changed site files, uploads them, verifies them, and
reports the result as a system message ("Deployed N file(s)…", or "HELD:
file: error"). A change is therefore live when the turn ends, so the `sw.js`
bump belongs in the same turn, and rules/indexes/functions go out before the
client edit that needs them. Pause with `"autoDeploy": false` in
`deploy/site.json` (for example during a live lecture, V3.775). Only the
announcement and the phone build wait for a batch:

1. **After every small change**, append ONE plain-language entry to
   [CodeLog/Updates/PENDING_RELEASE.md](CodeLog/Updates/PENDING_RELEASE.md)
   — written for lab members, not developers ("You can now…", "Fixed:…").
2. **When the ledger reaches 5+ entries, tell Alex it's ready to push.**
   Alex saying **"push"** overrides the threshold at any count.
3. **At push time, run the release script** — it ships the web AND the phone
   app from the ledger, so the two can't drift:

   ```bash
   python3 scripts/release_push.py            # --force to push under 5
   python3 scripts/release_push.py --dry-run  # show everything, change nothing
   ```

   It writes the Ourlab mobile changelog entry (generated from the ledger),
   bumps `CURRENT_PROJECT_VERSION`, runs `sync-rm` + `cap sync`, gates on
   device verification, archives/exports/uploads the TestFlight build, prints
   the ready-to-paste announcement block, and rolls the ledger into
   **Shipped**. Run it from a real terminal — codesign fails under a sandbox.

4. **One step remains:** the site is already live (V3.818 auto-deploy at
   the end of each turn; if the hook reported HELD or FAILED, fix the named
   file, or run `python3 scripts/deploy.py ftp`, or `stage` → Cyberduck →
   `verify`). Then open `mcgheelab.com/rm/pages/whats-new.html` as admin, paste the
   printed block (including the app build), and press "Send to all lab
   members" — one click writes the `releases` history doc AND sends a single
   push + My Week feed item to every lab member via the `releaseAnnounce`
   Cloud Function. **Never drag the repo or all of `rm/` into Cyberduck
   again**: `deploy/site.json` is the only definition of what the site is,
   and everything outside it (CodeLog, functions, scripts, Data, keys) must
   never reach the server. `python3 scripts/deploy.py audit` checks.

**Why the app ships with every batch:** Ourlab mobile is not a URL wrapper —
`OurlabMobile/scripts/sync-rm.mjs` bundles the whole `rm/` tree into the app
at build time. An FTP-only push updates browser users and silently leaves
phone users on old code, so each batch cuts a matching TestFlight build and
the announcement names the build that carries the changes. The mobile repo
keeps its own `m-vX.Y.Z` version line and its own
`CodeLog/Updates/CHANGELOG.md` — **don't hand-author that entry**, the script
generates it (patch bump for a bundle refresh, minor when native/Swift/config
files changed; `--minor` / `--patch` override).

Exception: changes needing `firebase deploy` (rules/indexes/functions) still
deploy their backend parts immediately in the documented order — only the
FTP + notification are batched.

## Version Control Workflow (V3.868)

Git keeps up with the site the same way the site keeps up with the turn: the Claude Code `Stop` hook runs
`python3 scripts/git_autopush.py` **before** `deploy.py autodeploy`. It commits the turn (subject from the CHANGELOG
head), rebases onto `origin/main` (so a change Gabe merged reaches this computer and the deploy that follows), runs the
push gate, and pushes. Nothing to do per turn; the hook's `systemMessage` says what happened. A batch above
`autoPushMaxFiles` (deploy/site.json, 80) waits for a person: `python3 scripts/git_autopush.py --batch`. Secrets and
confidential files (keys, `.env`, payroll, ledgers, grant documents) are never staged — **the GitHub repo is public.**
Pause with `"autoPush": false`.

**Every push runs `scripts/merge_check.py`** (the tracked `.githooks/pre-push`, installed once per clone by
`python3 scripts/merge_check.py install`; the same check runs on GitHub for every PR): a new module must be registered in
`CodeLog/features.json`, a change that looks like a feature we already have must say how it relates (`extends` /
`merges_into` / `related` / `distinct_from`), the branch must merge with `origin/main`, and the release gates must pass.
Preview with `python3 scripts/merge_check.py worktree`. Gabe's Scientia work comes in on `scientia/<topic>` branches by
pull request — see [scientia/CLAUDE.md](scientia/CLAUDE.md). `scripts/version_push.py` remains for a hand-made release.
