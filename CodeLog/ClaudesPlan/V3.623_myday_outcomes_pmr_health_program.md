# V3.623 — My Day outcomes → PMR ledger → project health (program)

**Program plan, releases 1–4** (Alex, 2026-08-12): "currently for my day
everything is bound to a single week and that's it. We need a way to take
that entry and make an outcome… All of this goes into the PMR. A main
section of the PMR should actually be a ledger of the myday plans and
outcomes… keep track of project health from this perspective… At the top
of the PMR the student should know their projects and see the health score
for each… The PMR should basically not be something they fill out but
really just a report of everything they have been doing on all of the
other input surfaces."

Program: **V3.623** item outcomes + follow-up on My Day → **V3.624**
mentor-read rules + PMR ledger section → **V3.625** project-health engine
+ "My projects" header + mentor barrier-accept → **V3.626** new activity
signals (annotations, comments, task completion) + presence strips.

This doc is the plan for V3.623 and the program spec for V3.624–626; each
later release gets its own plan doc at build time per the normal ritual.
(V3.619–V3.622 are claimed by the concurrent paper-reader
highlight→comment program — do not renumber into them.)

## Decisions locked with Alex (2026-08-12 grill)

| Question | Decision |
|---|---|
| Where outcomes are recorded | On My Day, anytime — inline affordance per item + standing nudge for blanks. PMR only *reads* the ledger. |
| Mentor barrier acceptance | Explicit **Accept** button on the PMR (with note); accepted barriers stop counting against health. |
| Health display | Traffic-light status + trend arrow + one-line "why" per project. No raw number shown. |
| Project unit | **Research-roadmap output cards** (`researchFoci`, `level=='output'`). |
| Cross-user access | Relax Firestore read: `dayPlans` and `trackerEntries` gain `isMentorOf ∥ isAdmin` read (V3.517 notebook precedent). Writes stay owner-only. |
| Result payload | Text summary + optional image upload + optional notebook-entry / figure links. Barrier = reason text. No-result = optional note. |
| Health inputs | All four: unaccepted barrier chains (core, escalating), silence/inactivity, no-result streaks, overdue (missing) outcomes. |
| PMR project_overview block | **Replaced** by the health header (kept renderable for old docs; dropped from default order). Student keeps an editable description line per project. |
| Follow-up mechanics | "↻ Follow up next week" creates a **new** planned item next Monday (editable) with a `follow_up_of` backref chain. Never re-dates the original (the `→ Today` move destroys history; outcomes must not). |
| Visibility | Owner + `mentor_uids` + admin — same model as focusAreas/PMR. No lab-wide surface this program. |
| Phasing | 4 releases, each independently shippable. |

## Problem

1. **My Day items die without a verdict.** `status` is
   `planned|done|skipped|cancelled` ([rm/js/day-distribute.js:17]) — done
   is a bare checkmark, `✗ Skipped` writes no reason and doesn't cascade
   (huddle/booking copies keep saying "planned",
   [rm/js/my-day.js:1381-1386]), and after 7 days unconfirmed items
   silently fall off the pending list. Nothing records *what came of the
   plan* — the result, the blocker, or the fizzle — and nothing carries it
   into next week except the history-destroying `→ Today` re-date.
2. **The PMR is hand-assembled.** The student curates weekly entries
   (`⤓ Assemble` is a one-shot human-curated import,
   [rm/js/pmr-week-assemble.js]); `project_overview` status is a manual
   dropdown that `autoFillProjectRows` hardcodes to `'good'`
   ([rm/js/pmr.js:2340]). Nothing computes project state from what
   actually happened.
3. **Mentors can't see the raw work.** `dayPlans`, `buckets`, and
   `trackerEntries` are owner-only ([firestore.rules:1864-1867], [:793]),
   which is why `loadOpenTasks` no-ops cross-user
   ([rm/js/pmr.js:447-455]). A mentor reviewing a PMR sees focus areas and
   notebook but not the plans, outcomes, or activity that explain them.
4. **No health signal.** A barrier that persists 4 weeks looks identical
   to one that appeared yesterday. The only "how is it going" rollup is
   [rm/js/research-progress.js] (per-thrust weekly icons) — not stored,
   not escalating, not on the PMR.

## Data model (whole program)

### 1. Outcome on the dayPlan doc — additive, owner-written (R1)

`userData/{uid}/dayPlans/{itemId}` gains:

```js
outcome: null | {
  kind: 'result' | 'barrier' | 'no_result',
  summary: '',                          // result: what came of it · barrier: the reason · no_result: optional
  image: null | { storage_path, download_url },   // single webp, optional
  notebook_entry_ids: [],               // links into userData/{uid}/notebook
  links: [],                            // [{kind,label,url}] — roadmap figure / paper deep links
  follow_up_item_id: null,              // set when a follow-up item is spawned
  recorded_at: ISO, recorded_by: uid,
},
follow_up_of: null | { item_id, date } // ON THE NEW ITEM: backref to the item it follows up
```

New vocab in day-distribute.js (do NOT overload `FOCUS_AREAS.OUTCOME_META`
— `success/partial/failure` is the *focus-week* verdict; this is the
*item* verdict):

```js
ITEM_OUTCOME_META = {
  result:    { icon:'✅', label:'Result' },
  barrier:   { icon:'🚧', label:'Barrier' },
  no_result: { icon:'◌',  label:'No result' },
}
```

Week grouping is **derived** (`mondayOf(item.date)`, [rm/js/my-day.js:102])
— no `weekId` stamped on dayPlans. Bridge to focusAreas' `'YYYY-Wnn'` only
via the existing `FOCUS_AREAS.weekIdFor()`; do not add a 4th copy of that
function.

### 2. Barrier acceptance — new subcollection (R3)

`userData/{studentUid}/healthReviews/{reviewId}`:

```js
{ id: 'hr-<ts36>-<rand4>',
  item_id,                    // the barrier-outcome dayPlan item being accepted
  foci_id,                    // denormalized project attribution at accept time
  note: '',                   // mentor's reason ("vendor backorder — fine")
  reviewer_uid, reviewer_name,
  week_monday: 'YYYY-MM-DD',  // week of the accepted barrier
  created_at: ISO }
```

Acceptance is per barrier item; the health engine treats accepted items as
neutral, which resets that chain's escalation from the acceptance week
forward.

### 3. PMR doc — additive fields (R3)

`project_health: [{ foci_id, description }]` — the student-editable
one-liner under each project card. Backfilled by the `hydrateDoc` pattern
([rm/js/pmr.js:1188-1217]); no migration.

### 4. firestore.rules (R2 + R3)

```
// R2 — mentor read on raw work surfaces (V3.517 notebook precedent)
match /userData/{userId}/dayPlans/{itemId} {
  allow read:  if isOwner(userId) || isMentorOf(userId) || isAdmin();
  allow write: if isOwner(userId);
}
// R2 — trackerEntries read (firestore.rules:793): add `|| isMentorOf(userId)`

// R3 — barrier acceptance: mentor-written, owner-readable
match /userData/{userId}/healthReviews/{reviewId} {
  allow read:   if isOwner(userId) || isMentorOf(userId) || isAdmin();
  allow create: if (isMentorOf(userId) || isAdmin())
                && request.resource.data.reviewer_uid == request.auth.uid;
  allow update, delete: if (request.auth != null
                && resource.data.reviewer_uid == request.auth.uid) || isAdmin();
}
```

No composite indexes: all new queries are single-field ranges on `date`
within a subcollection (same shape as `DD.listRange`,
[rm/js/day-distribute.js:882-888]).

### 5. Storage (R1)

One webp per outcome image at `dayPlanMedia/{uid}/{itemId}-{ts}.webp`.
Needs a `storage.rules` block (owner write, owner+mentor+admin read —
check the notebook-attachment block for the exact idiom at impl time). If
notebook attachments already expose a reusable upload helper, reuse it.

## R1 — V3.623: outcomes + follow-up on My Day (FTP + storage:rules)

The student-facing capture loop. Owner-only visibility until R2.

### day-distribute.js
- `ITEM_OUTCOME_META` export.
- `saveOutcome(item, outcome)` — plain doc update (no distribution
  cascade), stamps `recorded_at/by`, fires a tracker `kind:'work'` signal
  only if the item wasn't already `done` (avoid double-count with
  `recordDoneWork`, [day-distribute.js:334-343]).
- `createFollowUp(item, {date, title})` — builds a fresh item (new id,
  `status:'planned'`, copies `type`, `details` — critically `focusId`, so
  project attribution survives the chain — and sets
  `follow_up_of:{item_id, date: item.date}`), saves it, sets
  `outcome.follow_up_item_id` on the original. **No auto-distribute** —
  the student can edit/distribute it from My Day like any planned item.
- **Bug fix:** the skip path gets `cascadeUpdate()` so distributed copies
  stop claiming "planned" after a skip.

### my-day.js
- `openOutcomeDialog(item, presetKind)` — modeled on `openReportDialog`
  ([my-day.js:1099-1180]): kind radios (from `ITEM_OUTCOME_META`), summary
  textarea (placeholder varies by kind: "What did you get?" / "What's
  blocking you?" / "What happened?"), image attach → webp compress →
  Storage, notebook-entry checkboxes (reuse the report dialog's
  week-filtered list), links row, and a "↻ Follow up next week" block
  (checkbox + date input defaulting to next Monday + title prefilled
  `Follow up: <title>`).
- Affordances (all via the existing `data-act` delegation, so they work
  from every horizon for free — `findItem`, [my-day.js:1192-1199]):
  - `✓` stays one-tap done. Done/skipped items without an outcome render a
    `◇ Add outcome` chip; with one, the outcome icon + first line of
    summary (+ `↻ follows last week` tag when `follow_up_of`).
  - Pending-card `✗ Skipped` now opens the outcome dialog (barrier
    preselected — skip-with-no-reason is today's dead end) and then writes
    `status:'skipped'`.
  - Timeline/mini/month renderers get the outcome icon dot.
- **Standing nudge:** on load, count done/skipped/past-planned items from
  this week + last week with `outcome == null`; if >0, banner
  "🧾 N items need outcomes" above the timeline → tapping steps through
  the outcome dialog queue one item at a time. Renders every day (capture
  is "anytime"), not just Fridays.

## R3 — V3.625: health engine + "My projects" header + accept (rules THEN FTP)

### New module [rm/js/project-health.js] (`window.PROJECT_HEALTH`)
Pure compute, no DOM — pmr.js renders. All tunables in one
`PROJECT_HEALTH.CONFIG` object.

- `projectsForStudent(uid)` — union, deduped by foci id: output cards
  with `member_uids` ∋ uid; outputs whose `roadmap.experiments[].analyses[]
  .owner_uids` ∋ uid (flatten via `ROADMAP_DATA`); foci ids appearing in
  the student's `focusAreas[].focus_ref` inside the window. (Loads via
  `RESEARCH_DATA` list — lab-readable.)
- `attributeItem(item, focusDocsById)` — `item.details.focusId →
  focusAreas/{id}.focus_ref.{id, analysis_id}`. Unattributed items stay in
  the ledger but never touch health.
- `computeHealth({items, focusAreas, reviews, window=8 weeks})` → per
  project `{ foci_id, title, status, trend, why, weekStrip, factors }`.
  Week-by-week factors, oldest→newest:
  - **Barrier chain (core):** consecutive weeks with ≥1 *unaccepted*
    barrier on the project (linked by `follow_up_of` or simple
    same-project adjacency) contribute −1 × current chain length —
    escalation is built in. A `healthReviews` accept neutralizes that item
    from its week forward; a fully-accepted chain resets to zero.
  - **No-result streak:** weeks whose attributed outcomes are all
    `no_result` → −0.5 × streak length.
  - **Overdue outcomes:** any attributed item ≥1 week old with
    `outcome == null` (status ≠ cancelled) → −0.5 that week, capped −2.
  - **Silence:** owner of an analysis/card but a week with zero attributed
    items AND zero focusAreas pointing at the project → from the 2nd
    consecutive silent week, −1 per week, capped −3.
  - **Results:** a week with ≥1 `result` → +1 (cap +2 across window).
  - Health = sum over the last 4 weeks; buckets: `healthy ≥ −1`,
    `attention −1…−3`, `stuck < −3`. Trend = last-2-weeks sum vs the 2
    prior (↑/→/↓). `why` = dominant factor, phrased humanly:
    "barrier 'PDMS backorder' — 3 weeks, not yet accepted" /
    "no activity 3 weeks" / "4 items missing outcomes".

### pmr.js — `project_health` header section
- New section at the **top** of `DEFAULT_SECTION_ORDER`;
  `project_overview` drops out of the default order (still renderable for
  old docs that pinned it in `section_order`; label gains "(legacy)").
- Card per project: color dot + title (links to
  `research.html?id=<foci_id>`) + trend arrow + why line + 8-week outcome
  strip (per-week dominant icon) + student-editable description
  (`doc.project_health[]`, owner-only, normal `scheduleSave`).
- Expand → that project's rows filtered out of the R2 ledger.
- **Accept:** on barrier rows (header expand + ledger section), mentors
  (`state.viewAsUid` ≠ me ∧ `isMentorOf`/admin — the one deliberate write
  from the reviewer view, alongside comments) get `Accept reason…` →
  note prompt → `healthReviews` create. Accepted rows show
  `✔ accepted by <name> — <note>`; health recomputes on the spot.

## Out of scope (this program)
- Health anywhere but the PMR (My Day/research-hub badges, push alerts on
  health drops — future).
- Auto-writing `weekly_entries` narrative; `⤓ Assemble` stays curated.
- Lab-wide health visibility (would need a roadmapClaims-style mirror).
- Buckets/tasks mentor read (only dayPlans + trackerEntries relax).
- Editing outcomes from the PMR (capture lives on My Day).
- Retro-backfill of outcomes for past weeks.

## Release ritual
- Order: R1 → R2 → R3 → R4; each independently shippable; per-release
  sw.js `CACHE_VERSION` bump + CHANGELOG + one plain-language
  PENDING_RELEASE line (batch FTP per V3.604 — `release_push.py` at 5+ or
  on Alex's "push"; the app ships from the same batch).
- Backend deploys are immediate, never batched: R1 `storage:rules` (if the
  new path needs it), R2 + R3 `firestore:rules` — **always before their
  FTP**, or mentor views 403 / uploads fail.
- No functions, no indexes anywhere in the program.

## Rollback
- Any release: `git revert` + re-FTP (+ redeploy the previous
  `firestore.rules` / `storage.rules` from git for R1/R2/R3).
- All schema is additive: old clients ignore `outcome`/`follow_up_of`/
  `project_health`; orphaned `healthReviews` docs are inert. Reverting R2
  rules simply blanks mentor ledgers again. No destructive writes, no
  migrations.
