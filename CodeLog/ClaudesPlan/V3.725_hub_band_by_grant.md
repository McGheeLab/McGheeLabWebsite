# V3.725 — "How the lab moves forward" collapses, and its first column is grants

## Goal

Alex: *"the first section 'How the lab moves forward' should start collapsed.
There are three columns 'What we're driving forward' this has multiple cards for
each grant when I click on one of these grant cards information related to it
populates in the next two columns. The middle column is 'open work you could pick
up' currently all of these are attributed to the CAREER grant Aim 1 and that
should be a grant card in the first column, the 'who's on what this week' just
shows which of these cards are active by students."*

## What was wrong with the old band

Column 1 listed every **output card that happened to own a roadmap**. So the
lab's top-level orientation panel was a list of papers, and columns 2 and 3
poured every grant's analyses into one undifferentiated stream. With one paper
carrying all five analyses, the middle column read as one thing's work rather
than the lab's.

A grant is the unit work is actually spent against — that is the whole premise
of V3.717 — so it is the unit here too.

## Shape

Three columns that read left to right as one sentence: **which grant we are
driving forward → what is unclaimed under the one you picked → who is on it this
week.** Column 1 is the selector; the other two follow it and each carries an
explicit "in &lt;grant&gt;" line so the scoping is never ambiguous.

Column 1 shows one card per grant with roadmap work beneath it, aggregating
across all its aims and outputs: `n of m analyses done · k open · j being
worked`. Work reaching no grant gets a "Not under a grant" bucket rather than
vanishing — the same rule the aims band follows.

## Collapsed, carefully

The panel is wrapped in a `<details>` that starts closed. The open flag is
**module state (`_bandOpen`), not markup**: claiming an analysis re-renders the
whole hub, and honouring only the markup would slam the panel shut in the middle
of the action that opened it. "Starts collapsed" means per page load, which is
what was asked; it does not fight the user within a session.

## Also fixed

The band's filter was still `level === 'output'`, left over from before V3.719
widened roadmaps to aims — so an aim's roadmap could never appear. Now
`aim || output`, matching `sectionRoadmap` and `listRoadmapCards`.

## Verified

Against live data plus a synthetic second bucket (an ONR aim given a roadmap, to
exercise selection):

- starts collapsed, toggle reads "show";
- column 1 lists both grants, the first selected;
- clicking the second moves the selection, flips both scope lines to "in ONR",
  and repopulates the open column with that grant's two analyses;
- the panel stays open across a selection.

## The debugging lesson

The band rendered empty for several passes while I read and re-read the new
grouping code, which was correct the whole time. The cause was the **test
harness**: its `FOCUS_AREAS` stub defined `weekIdForOffset` but not `weekIdFor`,
which `renderHubBand` calls — so the function threw inside an `async` and the
rejection surfaced as neither a console error nor a visible failure, just an
empty host indistinguishable from "no data".

That is the second time in this session a stub rather than the subject produced
the symptom. **When a headless render comes back empty, verify the harness's own
contract against the code under test before reading that code.** A node-side
replay of the same logic (which passed immediately) is the cheapest way to split
"my logic is wrong" from "my rig is wrong".
