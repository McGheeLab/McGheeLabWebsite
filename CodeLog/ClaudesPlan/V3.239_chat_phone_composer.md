# V3.239 — Chat phone composer keyboard fix (Phase 3b of mobile compatibility)

> Phase 3b continued. V3.237 fixed calendar rows; V3.238 fixed tasks inbox rows. V3.239 fixes the **chat composer** so it stays above the iOS keyboard. User listed chat as a must-have phone use case ("Chat / huddle / quick reads").

## Problem

The chat-layout at ≤700px (`rm/css/chat.css:1933`) sets `overflow: visible` on `.chat-layout` so chat content flows into the document scroll. The composer (`.chat-input-area`) sits at the bottom of `.chat-main` in normal flow. When the user taps the textarea:

1. iOS Safari shows the on-screen keyboard.
2. The visual viewport shrinks by ~270px.
3. The composer, being part of the document flow, stays at its original position — now hidden behind the keyboard.
4. The user can't see what they're typing.

The send button has the same problem — and at 38px × 38px sits below the 44px Apple HIG tap-target minimum.

## Approach

CSS-only `@media (max-width: 640px)` block in `rm/css/chat.css`:

- **`.chat-input-area`** gets `position: fixed; bottom: 0; left: 0; right: 0`. iOS Safari 15+ tracks the visual viewport for fixed-positioned elements when the keyboard opens, so the composer floats above the keyboard automatically. No JS, no `visualViewport` resize handler needed.
- **`.chat-main`** gets `padding-bottom: 80px` so the last messages in the list aren't hidden behind the fixed composer.
- **Safe-area** — `.chat-input-area` adds `padding-bottom: calc(.5rem + var(--safe-bottom))` so the composer clears the iOS home indicator on notched phones.
- **Tap targets** — `.chat-input` bumps to `min-height: 44px`; `.chat-send-btn` bumps to `min-width: 44px; min-height: 44px`.
- **Thread overlay composer** — `.chat-thread-input` (full-screen thread view, already `position: fixed; inset: 0` from the existing 700px block) also gets the safe-area bottom padding.

## Why `position: fixed` over `visualViewport` JS

iOS Safari 15+ (March 2022) correctly tracks the visual viewport for `position: fixed` elements when the keyboard opens — the fixed composer rides up with the keyboard, no JS needed. A `visualViewport.resize` + `translateY` JS handler was the standard fix before iOS 15, but adds complexity and a transient mis-positioning during transition. The McGhee Lab's user base is on iOS 15+, so the CSS-only approach wins.

If the lab ever supports an older iOS, the fallback would be: add a `visualViewport.resize` listener in `chat.js` that writes `--chat-keyboard-offset` to a CSS custom property and translates `.chat-input-area` by that amount.

## Verification

1. **Desktop ≥1024px** — `/rm/pages/chat.html`: pixel-identical to V3.238. New rules are scoped inside `(max-width: 640px)`.
2. **Tablet 641–1024px** — existing V3.237 700px mobile-tweaks block applies (thread fullscreen, action bar compact, etc.) but composer stays in normal flex flow — no fixed-position interference.
3. **iPhone 14 Pro (390px) emulation** — composer pinned to bottom of viewport. Last messages have room above the composer.
4. **Real iPhone test (required)** — DevTools doesn't faithfully simulate the iOS keyboard. Test on a real device: tap textarea, type, verify composer + textarea stay visible above the keyboard; verify the messages list scrolls to the bottom and the last message is readable above the composer.
5. **Thread overlay** — tap a message to open a thread (mobile shows it full-screen via the existing 700px rule); composer at the bottom of the thread is also safe-area-padded.
6. **Notched phone** — composer doesn't get hidden under the iOS home indicator (`var(--safe-bottom)` padding).
