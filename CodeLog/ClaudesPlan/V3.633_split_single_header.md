# V3.633 — Split view gets ONE header

## Context

Alex, twice: *"when I split, there is a second header on the split pages"*, then
after V3.618 shipped only half of it, *"each page still has its own navigation
bar."*

Splitting **outside a workflow** rendered **three** navigation bars: the
parent's `.top-nav`, plus a full `.top-nav` inside each of the two iframe panes.

This was not a regression. It was V3.75's deliberate trade, stated in the
comment at `rm/js/split-view.js:98-102`: with no workflow strip on the parent,
the pane's own nav was the only way to retarget that pane. V3.618 fixed the
*in-workflow* reload case and explicitly deferred this one; this is that
follow-up.

Alex chose the end state: **one bar drives both panes**, the same relationship
the workflow strip already has.

## Root cause

`_HAS_WORKFLOW` gated embedding in two places — `_embedHref` (no `?embed=1`)
and `paneHTML` (no `name="rm-embed-<side>"`). With neither signal, `nav.js`'s
`isEmbed` check was false inside each pane, so the pane built the regular nav.

## What changed

### `rm/js/split-view.js` — panes always embed

- `_embedHref` and the iframe `name` attribute are now unconditional.
- The `_HAS_WORKFLOW` IIFE became `_adoptWorkflowFromUrl()`, kept **only** for
  its side effect: adopting `?workflow=<id>` into sessionStorage. That is
  load-bearing (V3.618) — this IIFE runs at parse time, and `writeState()`
  strips the param from the URL before nav.js's DOMContentLoaded
  `_wfAdoptFromUrl` could ever see it.

### `rm/js/nav.js` — pane pickers on the parent bar

Only on `/rm/pages/split-view.html`, and only outside a workflow (the strip
branch returns long before this):

- `⊟ Split` (meaningless on the split shell) is replaced by two `.nav-dropdown`
  pane pickers — `◧ Left: <page> ▾` / `◨ Right: <page> ▾` — plus `× Close split`.
- Pickers dispatch the **existing** `rm:split:swap` / `rm:split:set-active` /
  `rm:split:close` events, so `split-view.js` needed no new listeners.
- Labels seed synchronously from `window.__SPLIT_STATE` and refresh on
  `rm:split:state-change`, so a pane navigating by an in-page link relabels its
  picker. `_splitRefreshPickers` never rebuilds a menu, so an open dropdown
  survives the refresh.
- `_wfBuildPageMap()` now also records `gate`, with children inheriting the
  group's gate. `_splitMatch` was hoisted to module scope (it closed over
  nothing) so the strip and the pickers share one matcher.

### `rm/css/split-view.css`

Split-specific rules only — `.nav-dropdown` / `.dropdown-menu` styling already
comes from `style.css`. Added group headers (`.dropdown-divider` is scoped to
`.nav-dropdown-pinned` in workflow.css, so it could not be reused), a label
clamp, the active-pane ring mirroring `.split-pane.active`, and the
`· other pane` marker.

## Key decisions

- **Gate checked in addition to `canAccessPage`, not instead.** A non-admin
  whose `allowedPageIds` happens to include an admin page would otherwise see
  Permissions in the picker, and `canAccessPage` is permissive when the page
  registry has not loaded. The `lab-member` branch reproduces `applyNavGates`'s
  V3.605 escape hatch so capability-granted collaborators keep their pages.
- **Filter at build time; do NOT stamp `data-gate` on the menu links.**
  `applyNavGates` sets `style.display` on `.top-nav [data-gate]` and collapses a
  dropdown whose links are all hidden — it would fight the picker.
- **`.tab-bar` hub tabs are left alone.** They are in-page tabs, not chrome, and
  on `settings.html` / `people.html` they have no `?tab=` URL at all, so hiding
  them would strand a pane with no way to switch section. The embed CSS is also
  shared with workflow-shell and popouts — three shells changed to fix one.

## Verification (headless, all passed)

| Check | Result |
|---|---|
| Out-of-workflow split | 1 `.top-nav` on parent, **0 navs in both panes** |
| Both panes | `?embed=1` + `name="rm-embed-<side>"` + `data-rm-embed="1"` |
| Picker as admin | 56 options, 7 groups in nav order |
| Picker as non-admin lab member | 50 options; Permissions / Guests / API Usage / Teachers **absent** |
| Open/active markers | left picker marks "Library" active, "Tasks" as other pane |
| `split-view` in its own picker | excluded |
| Opening a picker | fires `set-active`; parent URL flips to `active=right` |
| In-workflow split | 1 strip, 0 pane navs |
| **Reload** in-workflow (the V3.618 case) | still 1 strip, 0 pane navs |
| `× Close split` | survivor loads top-level, `window.name` empty, normal nav back |

A real bug was caught this way: the async fill checked
`document.body.contains(navEl)` while the nav was still detached, leaving both
menus stuck on "Loading pages…". The fill is now invoked from `renderNav` after
`document.body.prepend(nav)`.
