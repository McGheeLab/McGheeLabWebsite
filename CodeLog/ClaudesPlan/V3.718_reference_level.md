# V3.718 — A grant's bibliography becomes a card of its own

## Goal

Alex: *"under the grants, i want one more card and that is all of the references
used in the proposal."*

## The decision that mattered

A grant's children were `aim` (a target result) and `output` (a paper or patent
the lab produced). A bibliography is neither, and V3.717 exists precisely to
keep those two apart — *"for book keeping we will keep these separated."*
Filing 103 references as an "output" would have undone that distinction on the
first card that used it.

Three options were put to Alex; he chose the honest one: **a sixth level,
`reference`.** It hangs off a grant (`PARENTS.reference = ['grant']`) and
belongs to **no band**, which is what keeps it off the hub — one bibliography
per grant would be noise in a lab-wide band. It shows on its grant's review and
on its own page.

## The key design: a pointer, not a copy

The 103 references were already in the lab library (`items`, `type:'paper'`,
`meta.library.is_library_entry`), each carrying
`meta.library.cited_in_drafts: [<grant draft id>]` — stamped when the
`.paperbundle` was imported. Nothing needed copying.

So the card stores only:

```js
ref_source: { kind: 'draft_citations', draft_id: 'career-understanding-…' }
```

`research-references.js` reads the list live through the registered
`library/papers.json` route. Consequences worth having: the lab keeps exactly
one copy of every reference, citing something new in the builder appears on the
card with no re-sync, and there is no second bibliography to drift.

## Files

**New**
- `rm/js/research-references.js` — `RESEARCH_REFS.render/load/count`. Grouped by
  year, newest first (how a bibliography is actually scanned); each row links to
  the library reader and to `doi.org`. Entries with no DOI/PMID/arXiv id are
  **flagged, not hidden** — a bibliography that quietly drops its weakest rows is
  worse than one that points at them. `load()` returns `[]` on any failure.
- `scripts/seed_gels_career_references.js` — one-shot, `--commit`-gated,
  idempotent.

**Changed** — `research-data.js` (the level, `ref_source` in hydrate/create),
`research.js` (the card's main-column body), `research-grant-review.js` (a
References section per attached card, count filled after paint),
`rm/css/research.css`, `rm/pages/research.html`,
`scripts/tests/research-graph.test.mjs` (+7 cases).

`grantIdsForCard`'s aim branch was generalized to *any* level whose only parent
is `grant`, so `reference` resolves with no new branch — and the next level of
that shape needs none either. `cardsUnderGrant` still excludes references: they
are what the grant was built on, not work being done under it.

## The bug this shipped with, and the fix

Alex, on first look: *"why did you put references sited in concepts? this should go in
the grant as a card at the end."*

The card was never in a concept — `level:'reference'`, `links.grant_ids:['gels-career']`,
`concept_ids:[]`. But `hydrate()` had coerced any unrecognized level to `'concept'` since
V3.544, and his browser was still on V3.717 JS, which has no `reference` level. **I wrote
data carrying a new level before the code that understood it reached the browser**, and
the fallback filed it under Concepts.

Two fixes:

1. **Placement**, as asked: References now renders LAST on the grant review, after the
   per-person roll-up. It is reference material to look something up in, not a status
   anyone scans the page for.
2. **The fallback**, so this cannot recur: an unknown level now KEEPS its own name.
   Because `BANDS` drives the hub by exact level, a card from a newer build renders
   **nowhere** instead of in the wrong band — the safe failure for forward-dated data.
   `RD.levelMeta(level)` never returns undefined, and every renderer that used to index
   `LEVELS` directly goes through it.

The general lesson, worth more than the fix: **when data and code ship separately, the
data will arrive first at least once.** Any enum with a "coerce unknown to X" fallback
turns that into a silent misfiling rather than a visible gap. Prefer rendering nothing.

## Verified

Rendered against the real 15 cards and the real 202-paper library: 103 rows in
24 year-groups, 100 DOI links, the 2 predicted thin entries flagged (FDA
Modernization Act 2.0; the GELLS-DEM software), the grant review showing
"📚 References Cited 103", and the hub still showing four bands with no
reference card anywhere. 32 + 17 node assertions green.

**One lesson from the test rig, not the code:** the first render came back with
zero rows. The cause was a 1 MB library fixture inlined into a `<script>` in the
harness page, not the module — serving it as a real file and `fetch`ing it fixed
it instantly. Assert through the DOM and keep fixtures out of inline script tags.

## Not changed

No `firebase deploy` — the reference card lives in `researchFoci`, already
covered by `read: isLabMember` / `write: isAdmin`, and the library route it reads
is long-established. FTP-only; sw.js → 692.
