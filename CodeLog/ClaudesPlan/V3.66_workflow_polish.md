# V3.66 — Workflow polish

## Goal

Three quality-of-life additions to the V3.63–V3.65 workflow feature:

1. **Drag-to-reorder** strip chips (with reorder persisted to sessionStorage and saved to Firestore for custom workflows).
2. **Pin custom workflows** to the regular nav as a `⭐ My Workflows ▾` dropdown so users can enter their custom workflows in one click without going through the chooser.
3. **Per-workflow default landing page** — workflow doc gets a `landingPageId` field; the chooser, admin matrix, and custom-workflow builder respect it.

## Why

After V3.65 shipped, the strip didn't let users reorder; the chooser was always one extra click away even for daily-use workflows; and clicking a workflow always landed on the first chip — surprising when the user wanted a different page (e.g. Paper Writing should open in the editor, not the library).

## What ships

### 1. Drag-to-reorder

Each `.ws-page` chip is `draggable=true`. HTML5 dragstart/dragover/drop fire. The drop handler computes the new ordering from the DOM (after splicing the dragged chip into the right position based on horizontal midpoint of the drop target), writes it to `state.orderOverride: [...]` in sessionStorage, and refreshes the strip in place.

`_wfEffectivePageIds(basePageIds, state)` honors `orderOverride` when present:
1. Emits ids from the override that still exist in source (filtered by `removedPageIds`)
2. Appends any added/base ids not yet in the override

So reorder doesn't hide subsequent additions — when the user clicks `+ Add page`, the new chip slots into the strip at the end (after the override).

The `× remove` button is excluded from drag — its mousedown stopPropagation prevents the parent chip's dragstart from firing, and its own dragstart preventDefault keeps it inert when grabbed directly.

CSS adds three drag states: `.ws-page-dragging` (dragged chip, opacity .4), `.ws-page-drop-before` and `.ws-page-drop-after` (insertion-side amber inset shadow on the target chip).

For custom workflows, "Save changes" treats reorder as dirty and folds `orderOverride` into the doc's `pageIds` field on save.

### 2. Pinned custom workflows

When no workflow is active and the user is signed in, after the regular six-group nav renders, `_wfPinCustomWorkflows()` fires. It:

- Awaits `firebridge.whenAuthResolved()` and `firebridge.loadAccessGrant()`.
- Fetches `userData/{uid}/customWorkflows` (cached in `_wfCustomCache` for the page lifetime).
- For each workflow, picks a landing page (`landingPageId` if accessible, else first accessible) using the inline `_wfBuildPageMap` + `firebridge.canAccessPage`.
- Renders a `⭐ My Workflows ▾` dropdown after the existing nav items, with one entry per workflow (icon + label, href = decorated landing page) and a `Manage workflows…` link at the bottom.

Workflows with zero accessible pages are silently skipped. Users with zero custom workflows see no dropdown.

CSS `.nav-dropdown-pinned` and `.dropdown-divider` (in `workflow.css`, dynamically injected by nav.js).

### 3. Per-workflow landing page

A new `landingPageId` field on the workflow record. Five places consume / produce it:

- **`page-registry.js` seeds** — each of the 5 default workflows declares a `landingPageId`:
  - Lab Research → `activity-overview__tab__tracker` (open daily logging immediately)
  - Paper Writing → `paper-builder` (jump into the editor list)
  - Certification & Training → `compliance`
  - Task Scheduling & Activity Reports → `tasks`
  - Meetings → `meetings`
- **Workflow chooser** — `pickLandingPage(wf, accessiblePages)` returns `landingPageId` if accessible, else `accessiblePages[0]`. Both default-card and custom-card click handlers use it.
- **Admin matrix** (`/rm/pages/admin-permissions.html?tab=workflows`) — each workflow row's label cell grew a `Landing` dropdown showing the workflow's currently-checked pages. Auto-refreshes when checkboxes toggle (via `refreshLandingSelect`). Pending edits tracked with `type: 'workflow-landing'`; save flushes `landingPageId` to the doc.
- **Custom workflow builder** (`+ New custom workflow` modal on the chooser) — a `Landing page` dropdown below the page picker. Defaults to "First selected page" (empty string). Auto-populates from selected pages as the user toggles checkboxes.
- **Save as custom** (strip → modal) — inherits the source workflow's `landingPageId` when it's still in the effective page list; otherwise empty.
- **Pinned-nav dropdown** — entries decorated to point at `landingPageId`.

## Untouched (intentionally)

- **`firestore.rules`** — `landingPageId` rides on the existing `labConfig/defaultWorkflows` and `userData/{uid}/customWorkflows/*` writes. No new fields require new rules.
- **`firestore.indexes.json`** — no new queries.
- **Firebase Functions** — none affected.
- **Existing renderers across all RM pages** — none touched. Workflow strip continues to be purely additive in `nav.js`.

## Trade-offs

- **HTML5 drag-and-drop falls back to nothing on touch devices** that don't fire dragstart. Acceptable for V3.66; pointer-events polyfill could ship later.
- **Pinned-nav fetches `customWorkflows` on every page load** (cached for the page lifetime). One small read per RM page hit; trade-off vs requiring an explicit refresh after creating a workflow. Could be cached longer in IndexedDB if it shows up in profiling.
- **Landing select is in the row label cell**, not as a dedicated column. Keeps the matrix from getting wider, at the cost of slightly busier row labels.
- **Saved custom workflows can have `landingPageId: ''`** (empty string) — chooser falls back to first page, identical to the default behavior.

## Verification

```bash
RM_WRITE_ALLOWLIST=mcgheealex@gmail.com python3 rm/server.py
```

1. Sign in. `/rm/` → click "Lab Research" → strip appears on Activity Tracker (because `landingPageId='activity-overview__tab__tracker'`), not on Library.
2. Drag a chip in the strip — drop indicator shows on hover; release reorders. Refresh the page → order persisted (sessionStorage).
3. Click "Save changes" (custom workflow) or "Save as custom" (default workflow with reorder) → reload → reorder is now baseline, no dirty indicator.
4. Click `× Leave workflow` → six-group nav. After the regular groups, `⭐ My Workflows ▾` dropdown lists every saved custom workflow. Click an entry → enters the workflow at its landing page.
5. As admin: `/rm/pages/admin-permissions.html?tab=workflows` → each row's label area has a `Landing` dropdown. Pick one → save → reload → persists.
6. Build a new custom workflow via `+ New custom workflow` card → pick pages → pick a landing → save → enter the workflow → strip opens at the picked landing page.
7. DevTools → Application → Cache Storage shows `mcgheelab-shell-v41`.
