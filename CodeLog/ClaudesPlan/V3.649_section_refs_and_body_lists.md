# V3.649 — Section cross-references, and lists inside a paragraph

Two asks, both about the paragraph you are writing:

> "in the paper writer I want to be able to add references to various sections
> in the paper"

> "I need the ability to add lists to the write version of the paragraph,
> either bullet or numbers"

## 1. Section cross-references

**What was already there.** `[!sec:label]` shipped in V3.432 and works end to
end: `renderSecRefChip` draws it, the Document view upgrades it to "Section N"
post-mount via `data-secref-label`, and the exporter emits `\label{}` on the
heading and `\ref{}` at the reference.

**What was missing.** Any way to *make* one. `getSectionRefTargets()` — the
only listing function — returns just the anchors that already carry a
hand-typed `ref_label`, so there was nothing to show in a picker until the
writer had already visited each section header, invented a label, and typed
the raw token into their prose. The toolbar's REFERENCE group had `+ Eq`,
`+ Fig`, `+ Table` and a conspicuous hole where `+ Section` belonged.

**Built:**
- `PaperEditor.getSectionRefChoices()` — every anchor a `[!sec:]` could point
  at, in document order, labelled or not: sections plus the subheadings nested
  under them, each with `{id, kind, title, refLabel, sectionId,
  appendixBoundary}`.
- `PaperEditor.ensureSectionRefLabel(id)` — returns the anchor's label,
  minting one from its title if absent, the way `_autoAssignFloatLabel` does
  for figures. **Uniqueness is enforced against every label in the document**:
  slugs collide (two subheadings both called "Statistics"), and a collision
  would silently repoint an existing reference at the wrong heading.
- `+ Section` in the toolbar's REFERENCE group and `§ Insert section
  reference` on the paragraph right-click menu, both opening a picker that
  lists sections with their subheadings indented under them. The section the
  caret is currently in is sorted last and marked *"you are here"* — "see
  Section 2" written inside Section 2 is a mistake worth making hard.

## 2. Lists in the paragraph body

"The write version of the paragraph" is the body Y.Text — the editor's own
mode toggle labels it **Write** (vs Skeleton).

A list *block* already existed, but it is a sibling of the paragraph: you had
to leave the prose you were writing, add a block, and come back.

**Syntax**, deliberately the same convention the list block already uses so
the two cannot drift: `- ` or `* ` for a bullet, `1. ` / `1) ` for a number,
two leading spaces per nesting level. A run of consecutive item lines is one
list; switching marker starts a new one; a blank line ends it.

**One parser, four consumers.** `PaperSchemas.parseBodyRuns(text)` returns
`[{type:'prose'|'list', …}]`. A second implementation anywhere is a guarantee
that the PDF and the screen eventually disagree, so the editor, the Document
view, the exporter and the toolbar all read it:

- **Editor** — new `renderParagraphBodyHtml`. This is a *block-level wrapper*,
  not a change to `renderParagraphHtml`: that function is the INLINE contract
  and is reused for captions, table cells, subheadings and list-block items —
  a list item's own text runs back through it, so parsing markers there would
  make an item re-parse its own marker. Prose bodies fall straight through, so
  ordinary paragraphs render byte-identically to before (asserted).
- **Document view** — same renderer. The emitted list carries **both**
  `pe-body-list` and `pdv-list`, because `pdv-list` is what the doc view
  styles *and* names in `SPLIT_GUARD_SEL` — without it the column packer would
  be free to break a page mid-list, which it deliberately avoids for the list
  block.
- **LaTeX export** — `paragraphBodyToTex` splits the same way; prose runs go
  through the inline contract, list runs through `listItemsToTex`, which the
  list BLOCK now also calls so the two can never nest or indent differently.
- **Toolbar** — `• List` / `1. List` in the FORMAT group. These are LINE
  toggles, not selection wraps: `PaperEditor.toggleListAtSelection(type)`
  grows the selection to whole lines, runs `PaperSchemas.toggleListLines`, and
  writes back through `replaceParagraphRange` (which already maps source
  offsets across atomic chips, so a line containing a citation survives being
  turned into an item). Pressing the same button again strips the markers.

While the body is focused you see and edit the raw `- item` source, exactly as
you do for `**bold**` — chip mode is unchanged.

### A latent bug this surfaced

`replaceParagraphRange` inserted `tpl.content.firstChild` — **only the first
node** of the rendered replacement. Invisible for its entire life, because
every caller replaced a single token (a footnote or a citation group renders
to exactly one chip node). A multi-line replacement renders to
text/`<br>`/text/`<br>`/text, and everything after the first node was silently
dropped: three list lines collapsed into one. It now inserts the whole
fragment, capturing `lastChild` before `insertNode` empties it. Caught by the
first harness run of the list toggle, not by reading.

## Follow-up in the same release — "a bunch of - in line"

Alex, on first use: *"the list does not display correctly, the list need to be
per line not a bunch of - in line. it should look right in the write view."*

**The list feature exposed a much older bug.** `serializeChipDom` turned
`- a<div>- b</div>` into `- a- b`. Pressing Enter in a contenteditable does not
produce a `<br>` in Chrome or Safari — it wraps the new line in a `<div>` — and
the serializer only knew about `<br>`, recursing into every other element with
no separator. **So every newline typed into a paragraph body has always been
silently dropped on the way back into the Y.Text.** Multi-line prose collapsed
to one line; it only became obvious with a list, where the collapse reads as
`- a- b- c`.

There was a second, quieter consequence: `readCaretCharOffset` and
`_rangeFromCharOffset` count a `<br>` as one source character but a `<div>`
boundary as zero, so every caret offset past the first line was short by one
per line — silently misplacing inserted citations and values in any multi-line
paragraph.

Three fixes:
1. **`serializeChipDom` is block-aware** — a block element (`DIV`, `P`, `LI`,
   `UL`, `H1`-`H6`, …) starts a new line, unless it is at the very start or the
   previous node already ended one (`text<br><div>x</div>` must not produce a
   blank line). Needed regardless of fix 2, for content typed before this
   landed and for paste.
2. **Enter inserts a `<br>`** (`insertLineBreak`, with a Range fallback), so
   the live DOM is identical to what the chip renderer would produce for the
   same source — which is what keeps the caret walkers honest.
3. **The Write view lays lists out** — `renderChipsOnlyBodyHtml` wraps each
   list line in an inline-block span with a hanging indent, so a wrapped item
   aligns under its own text instead of falling back to the margin. The marker
   stays visible and editable (source, like `**bold**`). Reached through a new
   `opts.renderChipsHtml` on the binding, so only paragraph bodies get it.

   One trap found by screenshot: `text-indent` **inherits**, and the citation
   chip is inline-block — so it applied the negative indent to its own text and
   `smith2024` rendered as `mith2024`, slid out of its own background box.
   `.pe-src-li * { text-indent: 0 }` resets it below the line.

The wrapper is invisible to every source-mapping walker (it is not a block tag,
and the walkers recurse through non-chip elements), which is asserted directly:
the Write view round-trips to byte-identical source, and a caret placed on the
last list line reads back the exact source offset.

## Second follow-up — real bullets and standard list keys (V3.650)

> "it still looks bad it needs to display as bullet points. if i press enter at
> the end the next bullet point shows up. All the standard rules apply, this is
> standard stuff. figure it out."

Showing the raw `- ` marker was the wrong call. The Write view now renders a
real list and behaves like one.

**The move that made it safe: the marker IS a chip.** The editor already has
exactly one atomic-token contract — `contenteditable="false"` plus `data-src`
holding the exact source text — and every source-mapping walker already speaks
it: `serializeChipDom` contributes `data-src`, `readCaretCharOffset` counts
`data-src.length`, `setCaretCharOffset` / `_rangeFromCharOffset` treat it as
indivisible, `replaceParagraphRange` aligns ranges to it. Rendering the marker
as `<span class="pe-li-mark" contenteditable="false" data-src="  - ">•</span>`
therefore buys a real bullet, an uneditable marker, and a byte-exact
round-trip **with zero changes to the caret machinery** — the part of this
editor least safe to touch, and the part I have already had to repair twice
this week.

**The standard keys** (`handleListKey`), all applied in SOURCE space and then
repainted through the same renderer, so the DOM the walkers see is always the
DOM the renderer would have produced:

| Key | Behaviour |
|---|---|
| `Enter` at end of item | new item, same depth and marker type |
| `Enter` mid-item | splits, remainder moves to the new item |
| `Enter` on an empty item | leaves the list |
| `Tab` / `Shift+Tab` | indent / outdent one level (capped at the parser's 3) |
| `Backspace` at start of item | outdent; when flush left, strip the marker |
| `Shift+Enter` | plain line break, no list logic |

Ordered lists renumber themselves: `PaperSchemas.renumberOrderedRuns` rewrites
the **source** after every structural edit, restarting per run and per depth.
Displaying a number that differed from the stored one would serialize back
wrong, so the source is made canonical instead.

The caret is carried across that renumber as `(line, column)` rather than an
absolute offset, because renumbering changes marker widths (`9. ` → `10. `).

### Verified

The harness grew to **85 assertions**. Beyond the round-trip and caret-offset
guarantees: markers render as chips with real glyphs (`•`, `◦`, `1.`), no raw
`- ` survives in the visible text, and each key above is driven through the
real binding and asserted against the resulting **source string** — including
that Enter in ordinary prose is untouched by the list handler.
