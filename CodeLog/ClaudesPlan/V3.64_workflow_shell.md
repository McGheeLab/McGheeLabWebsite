# V3.64 — Workflow-driven UX redesign · PR 2: workflow chooser + workflow-aware nav strip

## Goal

Second of three workflow-redesign PRs. After V3.63 shipped the data
model + admin tooling, V3.64 makes workflows visible to non-admin
users:

- `rm/index.html` becomes the **workflow chooser** (replacing the V3.62 stats dashboard).
- `nav.js` learns to render a focused **workflow strip** when a workflow is active.

V3.65 adds custom workflows + builder UI on top.

## What ships

### Workflow chooser at `rm/index.html`

Card grid showing the 5 default workflows from V3.63's `labConfig/defaultWorkflows` Firestore doc (or seeded constants if not yet seeded). Each card:

- Icon + label + description
- Page count + first 6 page chips (with "+N more" if more)
- Filtered: workflows with zero accessible pages (per V3.63 `canAccessPage`) are silently dropped — a user with restricted access only sees the workflows they can use

Top-right link `Lab Overview Stats →` goes to `rm/pages/lab-overview.html` — the new home for the V3.62 14-card summary grid (renderer `dashboard.js` unchanged). Lets users still reach the at-a-glance numbers without making them the front page.

Click a card → `WorkflowState.setActive(id, kind)` writes sessionStorage → navigate to the workflow's first accessible page with `?workflow=<id>` query.

### sessionStorage state — `rm/js/workflow-state.js`

Active workflow held in sessionStorage as:

```js
{
  id:             'paper-writing',
  kind:           'default'  | 'custom',
  addedPageIds:   [],        // user added these via "+ Add page" (V3.65)
  removedPageIds: [],        // user removed via the chip's × button (V3.65)
}
```

Why sessionStorage over URL: in-page navigations (`location.href = '/rm/pages/X.html'`) don't carry query params automatically. sessionStorage means workflow context persists across all navigations within a tab without needing every existing renderer to add `?workflow=`.

URL `?workflow=<id>` is a **one-time entry signal**: `WorkflowState.adoptFromUrl()` writes it to sessionStorage and `history.replaceState` strips it from the URL. Bookmarks of `library.html?workflow=paper-writing` enter the workflow cleanly.

**Effective page list** at render time: `workflow.pageIds ∪ addedPageIds − removedPageIds` (de-duped, ordered). Computed by `WorkflowState.effectivePageIds()`.

`workflow-state.js` exports `window.WorkflowState` — used by the chooser and (V3.65) the builder. **Not loaded on every page**; nav.js has its own inline read logic for the strip.

### Workflow strip — `nav.js` fork

When `_wfAdoptFromUrl()` returns an active state at `renderNav()` time, `renderWorkflowStrip(state)` runs instead of the six-group dropdown nav.

Strip layout:

```
🗂 Paper Writing  | [Library] [Comments] [Paper editor] [Tasks] [PMR] [Chat]   + Add page  ⊟ Split   × Leave workflow
```

- **Brand link (workflow icon + label)** → `/rm/index.html` (workflow chooser; functions as "Switch workflow").
- **Page chips** — ordered by the workflow's pageIds, filtered by `firebridge.canAccessPage()`. Active chip (the current page) gets a white-background highlight. Each chip's link is decorated with `?workflow=<id>` so cmd-click-to-new-tab still lands in the workflow.
- **`+ Add page`** — placeholder button, disabled with V3.65 tooltip.
- **`⊟ Split`** — opens the V3.56 split-view shell with `?workflow=<id>` so the strip persists in both panes' iframes (same-origin Firebase IndexedDB sharing makes auth automatic).
- **`Save as custom`** — placeholder button, only rendered when `addedPageIds.length || removedPageIds.length` (workflow is dirty). Wired in V3.65.
- **`× Leave workflow`** — clears sessionStorage and `location.reload()`s → six-group nav returns.

The strip's read logic (`_wfReadState`, `_wfAdoptFromUrl`, `_wfPageIdFromHref`, `_wfBuildPageMap`, `_wfFetchWorkflow`, `_wfEffectivePageIds`, `_wfDecorateHref`) is **inlined into `nav.js`** rather than depending on `workflow-state.js` + `page-registry.js`. This way every page that already loads nav.js gets the strip without per-page edits — none of the ~38 existing pages need updating.

The strip awaits `firebridge.whenAuthResolved()` + `firebridge.loadAccessGrant()` before rendering chips so the access filter is correct. During the brief await window, the brand label shows "Loading…".

`workflow.css` is injected dynamically by nav.js the first time the strip renders. Idempotent — browser deduplicates by href. Pages without an active workflow never load it.

### CSS — `rm/css/workflow.css`

Two style families:
- **`.wf-*`** — workflow chooser cards (used by `rm/index.html`)
- **`.workflow-strip`, `.ws-*`** — workflow strip (used by `nav.js`)
- **`.ws-modal-*`** — V3.65 add-page picker modal (markup defined now, behavior in V3.65)

## Risks and edge cases

- **Strip overlays the page on first paint** because nav.js renders at `DOMContentLoaded` — no flash because `position: sticky; top: 0; z-index: 50;` on `.workflow-strip` lays it on top of everything. The strip's chip filter waits for auth+grant — during that ~50–200ms window, "Loading…" is shown in the brand area; the chips area is empty. Acceptable.
- **Cmd-click into new tab** on a strip chip preserves the `?workflow=<id>` query in the new tab's URL → nav.js adopts it into the new tab's sessionStorage → strip renders. Works.
- **A user lands on a page that's NOT in their active workflow** (e.g., they Cmd-click a non-workflow link from inside a workflow tab) → strip still renders, none of its chips match the current page → no chip is active. The user can still click any chip to jump back into the workflow flow. Acceptable.
- **Browser back/forward** with stripped `?workflow=<id>` URL still works because sessionStorage persists across history navigations within a tab.
- **First-run when admin hasn't seeded `labConfig/defaultWorkflows`** — nav.js's `_wfFetchWorkflow` returns null → strip shows "Workflow not found". The chooser renders the seeded constants (since `WorkflowState.loadDefaultWorkflows` falls back to PAGE_REGISTRY.DEFAULT_WORKFLOWS) — so the chooser still works. To fix the strip-side fallback would require duplicating the seed constants into nav.js; deferred to V3.65 once we know the rough edges.
