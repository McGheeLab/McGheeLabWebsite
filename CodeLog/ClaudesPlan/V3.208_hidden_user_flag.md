# V3.208 — Hidden user flag (keep any lab member out of public + internal directories)

## Goal

Admin wants the ability to mark **any** lab member — PI, postdoc, grad,
undergrad, highschool, alumni — as `hidden` so they're a full RM lab
member (sign in, use the dashboard, get assigned tasks) **without
appearing on**:

1. The **public website Team page** (mcgheelab.com `#/team`).
2. **Internal RM people directories**: people page, PMR left rail,
   task-assign picker, chat sidebar, sharing picker, meeting attendee
   pickers, dashboard "active members" tiles, CV overview, etc.

Admins (signed-in users with `role: 'admin'`) must still see the hidden
user in every internal directory so they can manage them. The public
website Team page never shows hidden users to anyone.

## Approach

Add a single boolean `hidden` (default falsy) on `users/{uid}`. Filter it
in every people-list rendering site through a shared helper:

```js
// In firebase-bridge.js, exposed globally as window.LAB_USERS:
LAB_USERS.isVisible = function (u) {
  if (!u || !u.role || u.role === 'guest') return false;
  if (u.hidden && !(typeof firebridge !== 'undefined' && firebridge.isAdmin && firebridge.isAdmin())) return false;
  return true;
};
```

Each of the ~14 sites that currently filter `u.role && u.role !== 'guest'`
swaps to `LAB_USERS.isVisible(u)`. The helper composes the existing
guest-filter with the new hidden-filter and the admin-bypass in one
place, so future people-lists pick up the policy by using the helper.

The public website Team page in `app.js` does **not** load
firebase-bridge.js, and is never admin (it's the marketing site). It
inlines its own filter: `u.role !== 'guest' && !u.hidden`.

The `hidden` flag is set/cleared from the **admin-only Role form** in
`rm/js/people.js` (changeRole) — added as a third field alongside role +
category. Also added to the LAB_FIELDS edit form so it can be toggled
later. A subtle "Hidden" chip on the people page row signals the state
to admins (admins are the only ones who see the row at all once hidden).

## Why a helper instead of inline `&& !u.hidden`?

- 14 call sites. Inlining the new clause invites drift the next time
  someone adds a 15th people-list. The helper makes the policy explicit
  and centralized.
- The admin-bypass rule (`!firebridge.isAdmin()`) is non-trivial — it
  needs to read the live signed-in profile. Putting that in 14 places
  hides the rule.
- Future-friendly: if "private" needs to become finer-grained (e.g.
  per-project visibility), the change happens in one helper.

## Non-goals (deferred)

- **Firestore rules tightening.** `users/{uid}` stays publicly readable.
  If the user later wants `hidden` to be a real privacy boundary (not
  just UI), the rule becomes
  `allow read: if !resource.data.hidden || isLabMember()` — but that
  breaks the public Team page render and needs a separate path for the
  public site. Out of scope for this version.
- **Activity / story feeds.** A hidden postdoc could still authored a
  published `stories` doc; that doc would still surface their name. If
  needed, a follow-up filter on `stories.authorUid` against `users.hidden`
  can be added — but the user's ask is "don't release them on people
  pages and lists," not "never mention their name anywhere."
- **Invitation token carries `hidden`.** Could add `hidden: true` on the
  invitations doc and propagate at profile-bootstrap time. Deferred —
  the admin flips `hidden` at the same time they promote role from
  guest, so the manual step is already there.

## Done when

- A new user with `role: 'contributor'`, `category: 'postdoc'`,
  `hidden: true` on their users doc is:
  - Absent from the public `#/team` page on mcgheelab.com.
  - Absent from the RM people page when viewed by a non-admin lab member.
  - Absent from the PMR left rail, task-assign assignee picker, chat
    sidebar, sharing picker, meeting attendee pickers when viewed by
    non-admins.
  - Present in all of the above when viewed by an admin (with a small
    "hidden" chip on the people page for admin clarity).
- The user themselves can sign in, use the RM dashboard, get assigned
  tasks, and have full lab-member access — `isLabMember()` still returns
  true because their `role !== 'guest'`.
- `sw.js` CACHE_VERSION is 178, CHANGELOG and ARCHITECTURE are updated.
