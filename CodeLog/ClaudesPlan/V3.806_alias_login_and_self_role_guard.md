# V3.806 — One person, two Google logins + nobody changes their own role

## Goal

Alex, after V3.805: *"lets make the backup account mcgheealex@arizona.edu. can we make both accounts
mirror each other so anything done on one account is done on the other, this makes it so that there
is a backup admin account."*

## Decision

There were three models, and Alex chose **same account, either login**:

| Model | Mirrors? | Independent backup? |
|---|---|---|
| **Alias login (chosen)** | yes, it's literally one uid | no; covered by the rules guard below |
| Separate backup admin | no, its RM data is empty | yes |
| Data sync between two uids | — | rejected: uids are embedded in other people's records (authorUids, presenters maps, schedules.ownerUid, chat membership), so a sync can't be made correct |

Accepted cost: `mcgheealex@arizona.edu` stops being Alex's student-view test account. V3.679 had
deliberately kept it non-admin for that.

## Approach

1. **`functions/auth-alias.js` → `aliasSignIn`** (HTTPS, `cors: true`). It verifies the ID token
   (`checkRevoked`) and runs the pure `resolveAlias()`: mapped email + `google.com` provider +
   `email_verified` + not already the target. Then it calls `createCustomToken(targetUid)`. The map
   is a code constant. The runtime SA `665438582202-compute@` already holds
   `roles/iam.serviceAccountTokenCreator` on itself (checked).
2. **Client swap.** `_aliasSwap(user)` runs at the top of `onAuthStateChanged` in
   `rm/js/firebase-bridge.js` (RM + the Ourlab app) and `user-system.js` (main site). It returns true
   after `signInWithCustomToken`, and the listener re-fires with the primary account. Alias emails
   are a client hint list kept in sync by hand; the server is authoritative.
3. **Rules guard.** `users/{userId}` update becomes `(isAdmin() && request.auth.uid != userId) ||
   (owner && role unchanged)`. The V3.805 incident write is now denied even for an admin. Admins
   still manage everyone else's role and their own other fields.
