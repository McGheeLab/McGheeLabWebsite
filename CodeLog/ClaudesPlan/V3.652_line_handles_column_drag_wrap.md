# V3.652 — Table builder: controls on the lines, drag-to-resize, wrap by default

## The asks (Alex, 2026-08-20, on V3.650/651)

1. *"i need to be able to drag the boarders of the cells to custom widths."*
2. *"the +- should only pop up when i mouse over the line."*
3. *"the +- should be per line not per cell."*
4. *"in the middle of the +- shuld be a ||| drag indicator."*
5. *"the text should be wrapped by default."*

## (1–4) The controls belong to the line

V3.650 pinned each `＋` to a gutter head cell's edge and put each `−` in the
middle of its band. That reads as "controls attached to cells" and it revealed
everything at once on any hover of the grid. What Alex wants is the model every
spreadsheet uses: **one cluster per grid line, revealed only when the pointer is
on that line**.

So each line — every column border and every row border, including both outer
edges — gets one invisible **11 px hit strip running its full length**, in a new
`.pe-tbl-lines` overlay. Hovering anywhere along the strip highlights the line
and raises a single cluster:

```
column line:   ［ ＋  |||  − ］        row line:   ［ ＋ ］
                                                   ［ − ］
```

- `＋` inserts a row/column **at** that line.
- `|||` drags to resize (below).
- `−` deletes the band the line sits against — the one **after** it, except on
  the closing edge, whose only neighbour is the one before. Arming on a band with
  text is unchanged from V3.650 (`−` → `✓`, red for 4 s, no `confirm()`), and
  merely *hovering* a line now previews which band the `−` would take.

The gutter row and column stay. They are still the band-selection surface
(V3.651), they reserve the margin — and because there is exactly one head per
row and one per column and **they are never merged**, they are the only cells
whose edges are reliably the grid's lines. That is what the strips measure
against.

This is the one place measurement replaces V3.650's pin-to-a-cell trick, and it
is justified twice over: a hit zone has to span the whole line, and dragging a
width is pixel maths anyway. Geometry is re-read (not cached) on mount, on the
next frame, and from a `ResizeObserver` on the table — a wrapped cell changes
row heights as you type.

Only column lines carry the `|||`. Row height in LaTeX is `\arraystretch`, a
property of the whole table (the "rows:" control in the style bar), so a per-row
drag would be a handle for something with nowhere to be stored.

### Drag-to-resize
Dragging line *i* sizes the column to its left, as a **fraction of the table's
content width** — the same `widths_json` the width dropdown already writes and
the export already turns into `p{…\linewidth}`. Clamped to 5–90 % so a drag past
the edge cannot collapse a column, live-previewed on the colgroup during the
drag, and committed on mouse-up only if the pointer actually moved (so a click
on the grip is not a silent resize).

## (5) Wrap by default

`wrap` joins the shared style model, **defaulting to true**. A cell of prose in
an `l` column runs off the page in LaTeX and blows the column out in the
browser, which is never what the writer meant.

**Browser:** wrapping means `table-layout: fixed` — that, not `white-space`, is
what makes a long cell wrap instead of widening its column. Fixed layout takes
its widths from the first row unless there is a `colgroup`, and the first row is
exactly where a merge can hide a column, so the editor grid now **always** emits
a colgroup (leading `<col>` for the gutter). Same in the doc-side preview and
Document view.

**LaTeX:** wrapping means `p{width}`, and `p{}` needs a *number* — `tabular` has
no "auto but wrapping" column type. So the columns the writer has not sized
share whatever fraction of the line is left over, via a new shared
`PaperLayout.tableColShares(widths, cols)` — the same helper that fills the
editor's colgroup, so **what you drag is what compiles**.

Two things the emitter has to get right:

- `\dimexpr <share>\linewidth-2\tabcolsep\relax`. Without the subtraction, N
  columns of `1/N\linewidth` overrun the line by `2N\tabcolsep` and LaTeX
  reports an overfull hbox on a table that looked right on screen.
- `>{\raggedright\arraybackslash}p{…}` for left-aligned columns. A `p{}` column
  is **justified** by default, which in a narrow column gives the rivers of
  whitespace that make a wrapped table look broken; `\arraybackslash` puts `\\`
  back to meaning "end of row".

### This changes existing tables on purpose
V3.651 held the line that an untouched table's `.tex` was byte-identical.
Defaulting `wrap` on breaks that deliberately — an existing table now compiles
with `p{}` columns instead of `l`. **`wrap text` is a visible toggle in the style
bar**, and turning it off restores the old output exactly; the self-test asserts
that (`wrap:false` matches no `p{`). Everything else about the byte-identical
property still holds: `wrap: true` counts as default, so `style_json` is still
deleted from a table nobody has styled.
