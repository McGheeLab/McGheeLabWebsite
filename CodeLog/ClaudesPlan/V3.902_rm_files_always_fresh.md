# V3.902 — RM and Scientia always load the newest version after a deploy

## Goal

When a change goes live, the next page load shows it. Today a browser can keep opening the previous version of an RM
page, script or stylesheet (and the notebook's Scientia app) for half an hour after a deploy, or for days when the file
had not changed in weeks.

## Problem

Alex, right after V3.901 went live (2026-10-24): "i dont see the changes live on the website". The server had the new
build (`BUILD = '… Read beside the note, clip figures and equations'`, uploaded 01:40 UTC). The browser didn't ask for it:

- The host (Apache) sends `Last-Modified` and `ETag` but no `Cache-Control`. A browser then picks its own freshness:
  ~10% of the file's age when fetched. V3.900's Scientia had been up ~5 h, so a copy fetched before the deploy stayed
  "fresh" for ~30 min. `rm/js/notebook-scientia.js` (last changed a day earlier) gets ~2.4 h.
- `sw.js` routes `/rm/` network-first, but `networkFirst` called a plain `fetch(request)`. That goes through the browser's
  HTTP cache, which answered with the old copy without asking the server. The V3.738 comment already reports the
  same masking for `/modules/`.
- The Scientia iframe's address never changes (`/rm/scientia/scientia.html`), so nothing marks a new build as new.

Reproduced locally (`python3 -m http.server` also sends no `Cache-Control`). An iframe page and its script were fetched,
the files were changed on disk, and the page was opened again:

| | iframe page | its script |
|---|---|---|
| old `sw.js` | old | old |
| new `sw.js` | **new** | old |
| old `sw.js` + `Cache-Control: no-cache` | new | new |
| new `sw.js` + `Cache-Control: no-cache` | new | new |

The script that stays old under the new worker never reached the worker or the server: Chrome's in-memory cache
reused it. That cache only stops reusing when the response itself says `no-cache`.

## Approach

Both halves, because each covers what the other can't:

1. **`rm/.htaccess`** (new): `Header set Cache-Control "no-cache"` for `html?|js|mjs|css|json|webmanifest` under `/rm/`,
   inside `<IfModule mod_headers.c>`. "no-cache" means check every time. An unchanged file is a 304 with no body
   (measured live: `scientia.html` 304, 0 bytes). Images, PDFs and fonts keep normal caching. Covers every browser,
   with or without the worker, and Chrome's memory cache, but only for copies fetched after it is live.
2. **`sw.js` `revalidating(request)`**: `networkFirst` (`/rm/`, `/modules/`, `whiteboard-*.js|css`) fetches with
   `cache: 'no-cache'`. A navigation Request (RM pages, the Scientia iframe) is asked for again by URL with
   `credentials: 'same-origin'` and `redirect: 'manual'`, because re-making a `mode: 'navigate'` Request with options
   throws in some browsers (Workbox issue 1796). This reaches copies browsers saved **before** the header existed: the
   worker script is always fetched fresh, so the next visit installs it (`skipWaiting` → `controllerchange` reload) and
   it re-checks the Scientia page. CACHE_VERSION 881.
3. **`scripts/deploy.py`**:
   - `_verify_set(…, uploaded=True)` accepts a 403 for a `.ht*` file that was just uploaded. Apache never serves those,
     so `l/.htaccess` was re-uploaded and reported "not verified" on every deploy, and `rm/.htaccess` would have been too.
   - `scientia_build_if_stale` also watches `rm/js/page-layout.js` and `rm/js/page-regions.js`, which V3.901's build
     copies into the app.

## Files

- `rm/.htaccess` — new.
- `sw.js` — `revalidating()`, `networkFirst` uses it; CACHE_VERSION 880 → 881.
- `scripts/deploy.py` — `_verify_set` `uploaded`, `scientia_build_if_stale` sources.

## Checked before it went live

- The `.htaccess` was run in this Mac's Apache with `AllowOverride FileInfo` only. That is the class the host demonstrably
  allows, since `l/.htaccess`'s RewriteRule works. `httpd -t` passes; html/js/css get `no-cache`, png doesn't, an
  unchanged file answers 304, the error log is empty. (A directive the host doesn't allow would be a 500 for all of
  `/rm/`, hence the rehearsal.)
- The worker was checked with the table above. A real RM page and the Scientia page both load through it.
- Live after upload: `/rm/` pages, scripts and styles answer 200 with `cache-control: no-cache`; `sw.js` is the new one.

## Release

No Firebase change. Uploaded in the turn, so the result could be checked live. `sw.js` reloads open tabs when it takes
over (the V3.775 lecture rule applies: not during a recording).

## Rollback

Delete or empty `rm/.htaccess` on the server (an empty or comment-only file is valid). Revert `revalidating()` in `sw.js`
and bump CACHE_VERSION.

## Not done
