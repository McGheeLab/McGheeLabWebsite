# V4.111 — Scientia: the iPad pen — strokes that never started or were lost

## Why
Gabe, 23 Nov: "Get a fix for an iPad pen. As of now, it seems like the pen does not write well. The fix might be universal SVG strokes for all pencil modes. Do research on that and find the best way to tackle this." Then: "sometimes, the pen won't write on the screen"

## What the research found (sources in the PR)
- **Scribble** (iPadOS handwriting → typed text) can take Apple Pencil strokes from a web page, even off text fields (WebKit bug 217430). Then no `pointerdown` arrives at all. A page cannot turn Scribble off.
  - Both tldraw (`useCanvasEvents.ts`) and Excalidraw (`App.tsx`, "fix for Apple Pencil Scribble") stop the touch's default as it starts: `touchstart` with `{passive:false}`, `preventDefault()`. `pointerdown.preventDefault()` alone is not known to be enough.
- **Safari's pen events:** Safari sends Pencil `pointermove` at up to 240 Hz and drops pointer events when frames run late (Apple forums). `getCoalescedEvents` came only in Safari 18.2.
- **Cancels:** a stroke the system cancels (`pointercancel`) should be kept as if lifted.
- **Palms:** iPadOS delivers one pointer type at a time, so a resting palm can stop the Pencil before the page hears it. No page can change that.
- **"One SVG pipeline for every pen mode"** is not the fix by itself. The apps that work share careful input handling and keep a renderer per mode. The notes' strokes are already SVG, and so is ink on HTML pages; the whiteboard is the lab's own engine (kept unchanged).

## What was wrong here
- **On a note:**
  - nothing stopped Scribble where the pen writes ink;
  - the live stroke's whole path was recomputed on every pen event;
  - since V4.105 (ink you can click through), the pen starting on the empty part of ink lying over a component found the component's text, so it wrote nothing. Before, the ink took the pen there.
- **On an HTML page:** a cancelled stroke was thrown away, nothing stopped Scribble, and the line was rebuilt on every event.
- **On the whiteboard:** nothing stopped Scribble.

## What changed
- **`13zf-ink.js`:**
  - `INK.writeWhy(paper, target, x, y)` is the one rule for where the pen writes: '' or the reason why not. The rules are the same as before, plus one put back: on an ink component's rectangle the pen writes (`INK.inkUnder`). `penDown` uses it.
  - **The Scribble guard:** on every paper, a stylus `touchstart` (`touchType 'stylus'`) where the pen writes ink has its default stopped, and so do its `touchmove`s during a stroke. In a component's text it is left to Scribble, as before. Fingers are untouched.
  - **The live stroke:** every sample is kept as it comes, but the line on screen is drawn once a frame (`requestAnimationFrame`).
  - **`#touchlog`** (the existing touch log) also says why a pen touch did or did not write, a stroke's points, moves and time, a cancel (the stroke kept), and a stylus touch that came with no pen `pointerdown` (Scribble or the system took it).
- **`13zze-html.js` (the script in an HTML page's frame):** a cancelled stroke is kept and sent like a lifted one; the stylus touch is stopped as it starts (except on a note pinned to the page); the line is drawn once a frame.
- **`board/pen.js` (the app's part of the whiteboard):** a stylus touch on the drawing surface (its canvas) is stopped as it starts; buttons and cards keep theirs.
- **`MANUAL.md`:** where the pen writes over components, and what to do if it does not write (`#touchlog`; try once with Scribble and the Quick Note corner gesture off).

## Not done, and why
- **No rewrite into one SVG pipeline,** for the reasons above.
- **The whiteboard's engine is the lab's,** run unchanged, so only the app's adapter changed.
- **Not tested on an iPad here.** The tests use real pen events (CDP), and stylus touches made in the page. Chrome has no `touchType`, so the tests give the touch one.
