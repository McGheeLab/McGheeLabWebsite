# V3.634 — Students belong to their teacher (association, classification, and the road to teacher-authored material)

## The ask

> "Any student invited by a teacher should be assigned the role of student on
> the site, and should have an association with that teacher that persists.
> Students by default only get access to the class they need, and the teacher
> will build the material that drops into that class."

Four requirements. Two were already true or are now shipped; one is a decision
that has to be made deliberately because of what `role` controls; one is a new
feature that needs its own scope.

| # | Requirement | Status |
|---|---|---|
| 1 | Invited students are classified as students | **Shipped (R1)** — was already automatic, now unconditional + linked |
| 2 | A persistent association with the inviting teacher | **Shipped (R1)** |
| 3 | Students only get the class they need | **Already true** — verified in the emulator suite |
| 4 | Teacher builds material that drops into the class | **Needs R3** — new feature, scoped below |

---

## R1 — SHIPPED: classification + durable association

### What changed

`joinClassWithCode` ([teacher-classes.js](../../teacher-classes.js)) previously
flipped `category:'student'` **only if** the user's category was exactly
`'guest'`, inside a `try/catch` that swallowed failures to a `console.warn`. So
a user who had been recategorized (or whose write failed) stayed an
unclassified guest forever, invisible as a student in the Guests panel.

Now, on every successful join by a non-teacher, `TC_DB.linkStudentToTeacher`
writes:

```js
{
  category:    'student',
  teacherUids: FieldValue.arrayUnion(teacherUid),   // durable, multi-teacher
  studentSchool: schedule.school,
  studentSince:  serverTimestamp()
}
```

`teacherUids` is an array on purpose: a student can be invited by more than one
teacher (two classes, two schools) and joining the second must not erase the
first.

**The association survives what the enrollment doesn't.** `enrollments`
already denormalizes `teacherUid`, but the *display* only looked at
`status:'active'` rows. `contextFor` in
[rm/js/admin-guests.js](../../rm/js/admin-guests.js) now reads **every**
enrollment regardless of status and falls back to `users/{uid}.teacherUids`, so
the Guests panel shows "invited by Dana Ruiz" even after the teacher removes
the student or you delete the class.

### Trust boundary (important)

`users/{uid}` owner-writes are allowed for every field except `role`
(V3.304 hardening), so **a student can write their own `teacherUids`**. These
fields are a denormalized convenience for the admin panels — never a gate.
`enrollments` remains authoritative: its create is rules-gated on a live join
code, and that is what `tcCanViewModules` and every rule check reads. The code
carries this as a comment so nobody later mistakes it for a permission.

### Deploy

FTP-only. No rules change (the fields are already owner-writable), no index
(nothing queries `teacherUids` yet — the panels join client-side over the
whole `users` collection they already load).

## R2 — DECISION NEEDED: what "role of student" means

The literal reading — set `users/{uid}.role = 'student'` — **must not ship as
is.** `role` is the single capability axis for the entire platform, and every
gate in it is written as "not a guest", not as an allow-list. Grepping
`role !== 'guest'` / `role === 'guest'` finds **38 call sites**:

| Where | What a non-guest role grants today |
|---|---|
| [firestore.rules:31](../../firestore.rules#L31) `isLabMember()` | read/write access to the RM data layer |
| [rm/js/firebase-bridge.js:314,1016](../../rm/js/firebase-bridge.js) | clears the RM pending-access overlay — RM opens |
| [app.js:660](../../app.js#L660) | **puts the person on the public People page** |
| `functions/release-announce.js:110` | push notification + My Day item on every release |
| 9 Cloud Functions (`fetch-paper-pdf`, `equation-ocr`, `paper-compile-proxy`, `library-lookup`, `semantic-scholar`, `upload-paper-pdf`, `restore-paper-comments`, `paper-pdf-fetch-proxy`, `paper-compile/server`) | paid/privileged lab tooling |
| `cv-builder.js:1702`, `rm/js/chat*`, `rm/js/people.js`, … | CV suite, chat, rosters |

So `role:'student'` on a high-school student would open the lab's research
management system to them, list them on the McGhee Lab People page, and send
them release notifications. That is the opposite of "only get access to the
class they need".

Two coherent options:

**Option A — keep `role:'guest'`, treat `category:'student'` as the student
role (status quo + R1).** Zero risk, already shipped, and the taxonomy is
already student-aware everywhere it matters (Guests panel buckets, admin
recategorize, teacher/student dashboard dispatch). The word "role" in the UI
would mean `category`.

**Option B — make `student` a first-class role value.** Then, in one version:
add `'student'` to the `ROLES` map and `CATEGORY_DEFAULT_ROLE`; rewrite
`isLabMember()` as an explicit deny-list
(`role != 'guest' && role != 'student'`, i.e. add `role != 'student'` to the
rules helper); audit and patch **all 38 sites**, most importantly the 9
Cloud Functions and the People-page filter; then verify with the emulator suite
(`scripts/tests/teacher-rules.test.mjs` gains a `role:'student'` persona whose
every RM read must be denied). Buys a cleaner mental model and per-role
capabilities later (`hasCap()` already exists from V3.605); costs a careful
sweep and a rules + functions deploy.

**Recommendation: A now, B only if you want students to have capabilities that
`category` can't express.** R1 already delivers the visible behavior — students
are labelled students and tied to their teacher.

## R3 — TO BUILD: teacher-authored material

Today a teacher's class is **read-only from their side**: the admin approve
modal expands `grantedFolders` into `schedules.modules[]` from
`modules/manifest.json`, and the V3.304 plan explicitly ruled out giving
teachers the tabs/widgets editor. "The teacher will build the material that
drops into that class" is therefore a new capability, and the interesting
question is *what* they author — which is a scoping decision, not an
implementation detail:

1. **Assignments / instructions** — text blocks with due dates that appear
   between the lab's modules. Cheapest, no file handling.
2. **Uploads** — worksheets, slides, handouts (PDF) attached to a module or to
   the class. Needs a storage path + rules (`classFiles` exists but is
   `create: if request.auth != null` and admin-only update — usable, needs a
   teacher-scoped variant).
3. **Their own module pages** — teacher-written HTML/rich text rendered in the
   class shell. Most powerful, most sanitization work, and it means teacher
   content renders under the lab's brand — a review/publish gate is then not
   optional.
4. **Reordering / hiding the lab's modules** — arguably the highest
   value-per-line: `schedules.modules[]` already carries `order` and
   `published`, and the update rule already lets an owner write the doc while
   pinning `grantedFolders`. A teacher-facing reorder/hide UI needs **no rules
   change at all**.

Suggested sequencing: **(4) then (1) then (2)**, leaving (3) for after there is
a real teacher asking for it. (4) is a UI-only release against rules that
already permit it; (1) and (2) are additive fields plus one storage-rules
clause.

Two things to settle before writing that plan:
- **Does teacher-authored content need your approval before students see it?**
  (Reviews and public profiles are moderated; class-internal material arguably
  isn't, but (3) changes that calculus.)
- **Does it need to be reusable across their classes** (a teacher's own
  library) or is per-class enough for now?

Prerequisite either way: fix **issue 1** from
[V3.632_teacher_rules_findings.md](V3.632_teacher_rules_findings.md) — while any
signed-in user can create a `kind:'teacher-class'` schedule doc, giving
teachers *more* write surface on that doc compounds an already-open gate.
