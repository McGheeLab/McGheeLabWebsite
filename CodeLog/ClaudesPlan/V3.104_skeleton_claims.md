# V3.103 — Paper builder: skeleton bullet outlining + per-bullet claim flag

## Goal

Two coupled gaps in the paper-builder authoring surface:

1. **Skeleton has no list structure.** Today every paragraph block has
   `skeleton: Y.Text` (line-broken plain text, see
   [paper-blocks.js:121-148](../../rm/js/paper-blocks.js)) — there's no
   indent, no nesting, no per-bullet metadata. The skeleton is supposed
   to be the *argument structure* of the paragraph; it should render as
   a real bullet outline with depth.
2. **Claim flagging needs an anchor.** The lab already has full claims +
   evidence infrastructure ([rm/js/claims.js](../../rm/js/claims.js),
   `drafts/{draftId}/claims/{claimId}` Firestore collection,
   `window.CLAIMS` namespace with `subscribe`/`create`/`addEvidence`/
   `removeEvidence`), and the reader-side annotation panel
   ([rm/js/annotation-panel.js](../../rm/js/annotation-panel.js)) already
   has a draft+claim picker that mirror-writes to both sides. What's
   missing is the *write* surface in the paper builder — a place where
   the writer marks "this assertion needs a literature pass."

The natural home for that surface is the skeleton bullet: each bullet
*can* (but does not have to) be flagged as a claim. Most bullets stay
as plain outline scaffolding. Flagged bullets carry a `claim_id` linking
to a claim doc and surface a status pill that tracks lit-review progress.

This is the second of four planned wishlist items
([rm/wishlist.md](../../rm/wishlist.md) "paper builder"). V3.102 shipped
figures; V3.103 ships skeleton + claims; V3.104 ships body rich text;
V3.105 ships equation refs. Master plan:
`/Users/alexmcghee/.claude/plans/we-need-to-make-expressive-turing.md`.

## Approach

### Schema migration: skeleton from `Y.Text` → `Y.Array<Y.Map>`

Each paragraph block gains `skeleton_items: Y.Array<Y.Map>`. Each
Y.Map item carries:

| Key | Type | Purpose |
|---|---|---|
| `id` | string | `sk-` shortId |
| `depth` | number | `0..3` (capped) |
| `text` | Y.Text | Bullet content; uses paragraph render contract (math + cite) |
| `claim_id` | string\|null | Optional pointer to `drafts/{paperId}/claims/{claimId}` |

Per-bullet `text` Y.Text means two coauthors editing different bullets
never conflict at the character level (vs. one shared Y.Text with line
breaks).

The legacy `skeleton: Y.Text` is read once at first render post-deploy
in `migrateSkeletonToItems(yBlock, Y)` — split on `\n`, parse leading
spaces (`/^ */ ` length / 2, capped at 3) for depth, strip leading
`- ` if present, push one Y.Map per non-empty line. The legacy field
is **kept** (not deleted) so a one-version rollback is safe; renderers
prefer `skeleton_items` whenever it's non-empty. Idempotent: re-running
the migration on an already-migrated block no-ops.

### Bullet outline UI

Replaces the old flat `skEl` contenteditable in `renderParagraph` (line
121 of [paper-blocks.js](../../rm/js/paper-blocks.js)) with
`renderSkeletonOutline(yBlock, ctx)`. The outline mounts a `<ul>` with
nested `<ul>` for items at greater depth than their parent. Each `<li>`
has:

- Drag handle (decorative for V3.103 — actual reorder lands in V3.106)
- contenteditable bullet text (bound via existing
  [`bindYTextToContentEditable`](../../rm/js/paper-editor.js#L1934) so
  `$math$` and `[@cite]` tokens work inside bullets)
- `⚑` flag-as-claim button (visible on hover when bullet has no claim_id)
- Claim status pill (visible only when `claim_id` is set)

Keyboard handling on the bullet contenteditable:

- **Tab / Shift+Tab**: indent / outdent the focused bullet (cap depth 3,
  floor depth 0). Updates `depth` via `yDoc.transact`.
- **Enter**: split current bullet at caret. New item inherits depth.
- **Backspace at start of empty bullet**: delete the item.
- **Cmd/Ctrl+Shift+L**: open the flag-as-claim modal for the focused
  bullet.

### Claim flag flow (reuses `window.CLAIMS`)

Clicking `⚑` (or pressing `Cmd+Shift+L`) opens a small modal:

- Statement (prefilled from bullet text, editable)
- Save button → calls `CLAIMS.create(paperId, {statement, ...})`,
  receives a `claimId`, then writes `claim_id: claimId` into the
  bullet's Y.Map inside a Yjs transaction.

Once flagged, the bullet renders a status pill (developing / supported
/ needs-more-evidence / abandoned) sourced from a per-paper
`CLAIMS.subscribe(paperId, ...)` snapshot.

Click pill → side panel listing the claim's `supporting_evidence_ids`
and `counter_evidence_ids` with deep links to
`/rm/pages/library-paper.html?id=<paperId>#ann-<annId>`.

### Reader-side bridge — already built

The annotation panel at [rm/js/annotation-panel.js](../../rm/js/annotation-panel.js)
already exposes the "Tag as evidence" form (lines 335-380) with a
draft + claim picker that calls `CLAIMS.addEvidence(draftId, claimId,
paperId, annId, stance)`. No changes needed there — the writer's flagged
bullets simply appear in the existing claim picker once the user enters
the paper's draftId.

The existing `drafts/{paperId}/` Firestore path matches the
paper-builder's paper id (the paper's `id` slug is the draftId), so
no schema bridging is required.

### Export

`paper-export-tex.js` reads `skeleton_items` (falling back to legacy
`skeleton` text) and emits each bullet as a comment line above the
section's body content:

```
% Skeleton:
%   - top-level bullet
%     - nested bullet
%       - deeper bullet
\section{Introduction}

The first paragraph body...
```

Skeleton bullets are authoring scaffold, not publication content, so
they emit as LaTeX comments. Claim ids are **not** emitted (they're a
process-tracking artifact, not part of the manuscript).

## Out of scope (deferred)

- **Drag-reorder of bullets across depth.** Drag handle is decorative
  for V3.103. Implementing a depth-aware drag (move a bullet plus its
  visually-nested children to a new position) takes a chunk of code
  and isn't blocking authoring. Lands in V3.106 alongside paragraph
  block reorder.
- **Inline `[!claim:id]` token in body prose.** The flag's primary home
  is the bullet pill; a body-prose claim chip is a secondary surface
  the master plan mentioned but isn't load-bearing for the writer's
  workflow. Add only if a concrete need surfaces.
- **Auto-create claim when typing `?` at end of bullet.** Considered as
  a discoverability shortcut; rejected because typing `?` is too easy
  to do accidentally and the modal flow gives the user a chance to
  refine the statement before the claim doc is created.
