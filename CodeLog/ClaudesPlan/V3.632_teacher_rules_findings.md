# V3.632 — Teacher-account stress test: findings + how to run your own

Two things live in this doc:

1. **[Part 1](#part-1--what-the-machine-found)** — the result of an automated
   stress test of the V3.304 teacher/student platform: 62 permission checks run
   against the real `firestore.rules` in the Firestore emulator, plus a
   code-path audit. **7 real issues**, none of them cosmetic.
2. **[Part 2](#part-2--the-test-you-should-run)** — the 20-minute manual pass
   only a human can do, using the new demo mode (`#/demo`) for the screens and
   a second Google account for the permissions.

Companion: `V3.632_teacher_demo_mode.md` (the demo-mode build).

---

## Part 1 — what the machine found

### How it was run

`@firebase/rules-unit-testing` against `firebase emulators:exec --only
firestore`, loading this repo's `firestore.rules` verbatim, with six personas:
admin, teacher A, teacher B, an enrolled student, a removed student, an
unrelated signed-in guest, and a signed-out visitor. Every check declares the
result the V3.304 plan intends, so the report distinguishes *hole* (allowed
what should be denied) from *break* (denied what a legitimate user needs).

**Re-run it** (test file kept at `scripts/tests/teacher-rules.test.mjs`):

```bash
cd scripts/tests
npm install --legacy-peer-deps @firebase/rules-unit-testing@5 firebase@11
JAVA_HOME=/opt/homebrew/opt/openjdk@21 PATH=$JAVA_HOME/bin:$PATH \
  firebase emulators:exec --only firestore --project demo-mcgheelab-tc \
  "node teacher-rules.test.mjs"
```

(firebase-tools ≥ 15 refuses Java < 21; the Corretto 8 that `java -version`
reports on this Mac is not enough, hence the explicit `JAVA_HOME`.)

Result: **62 checks · 52 as intended · 10 deviations** covering 7 distinct
issues. What already works is worth stating plainly, because it's the majority:
granted-module pinning, class ownership, code secrecy (`list` is owner-only),
enrollment self-service with a live code, roster isolation between teachers,
review participation gating, self-approval blocks on reviews and profiles,
`role` hardening, and every admin-panel query.

### The issues, worst first

#### 1. The admin approval gate is client-side only 🔴 — ✅ FIXED in V3.635

`firestore.rules:386` — `match /schedules/{scheduleId} { allow create: if
request.auth != null; }`

Any signed-in user can create a schedules doc with arbitrary fields. Verified:
teacher A created `schedules/tc-selfmade` with `kind:'teacher-class'`,
`ownerUid:` self, and **every** `grantedFolders` entry — then (legitimately,
since they own it) minted a join code for it and could hand it to students. So
"admin approves each class" is enforced only by the UI. The `grantedFolders`
pin on *update* is airtight; it's `create` that's open.

The self-made class does show up in your Teachers panel (it queries
`kind == 'teacher-class'`), so this is bypass-then-visible, not invisible.

Proposed fix — let anyone keep creating a normal class (which is how the lab's
own classes are made), but make the `teacher-class` marker admin-only:

```
allow create: if request.auth != null
              && (isAdmin() || request.resource.data.get('kind', '') != 'teacher-class');
```

Check before deploying that nothing in `class-builder.js` creates a doc *with*
`kind:'teacher-class'` as a non-admin — the only writer today is the admin
approve modal (`rm/js/admin-teachers.js`), so this should be free.

#### 2. A teacher can repoint their own join code at another teacher's class 🟠 — ✅ FIXED in V3.635

`firestore.rules:523` — `allow update, delete: if isAdmin() ||
resource.data.teacherUid == request.auth.uid;`

Ownership is checked on the *existing* doc, so every field including
`scheduleId` and `teacherUid` is rewritable. Verified: teacher A repointed
`joinCodes/AAA111` at teacher B's class, after which a student redeeming A's
code landed in **B's roster** and could read B's modules. Cross-tenant, and B
sees an unexplained student appear.

Proposed fix — allow the only update the UI actually performs (deactivation):

```
allow update: if isAdmin()
              || (resource.data.teacherUid == request.auth.uid
                  && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['active']));
allow delete: if isAdmin() || resource.data.teacherUid == request.auth.uid;
```

`TC_DB.deactivateCode` writes exactly `{active:false}`, and regeneration
creates a *new* doc, so this matches the client.

#### 3. A removed student can re-add themselves 🟠 — ✅ FIXED in V3.635

`firestore.rules:549` — the student self-update carve-out is
`hasOnly(['status','studentName','updatedAt'])`, which permits `status:
'removed' → 'active'` with no code check. Verified. `joinClassWithCode` demands
a live code, but the rule doesn't, so a student who opens the console (or keeps
a fetch handy) undoes your Remove. Also note the roster keeps the removed row
forever, so re-adding is a one-field write.

Proposed fix — let a student *leave*, not re-join:

```
|| (request.auth != null
    && resource.data.studentUid == request.auth.uid
    && request.resource.data.status == 'removed'
    && request.resource.data.diff(resource.data).affectedKeys()
         .hasOnly(['status', 'studentName', 'updatedAt']))
```

Re-joining then goes through create/`setEnrollmentStatus`… which is also an
update, so if you want re-join-with-a-live-code to keep working, add a second
clause gated on `get(joinCodes/…).active == true` exactly like create does.

**What actually shipped is stronger,** because the code check alone turned out
to be insufficient: `request.resource.data` is the **merged** document, so an
update that doesn't touch `joinCode` still presents the code the student
originally joined with — which is live, so they'd pass. The shipped rule
therefore also requires `resource.data.get('removedBy','') != 'teacher'`, with
`removedBy` outside the student-writable key set and stamped by
`TC_DB.removeStudent` / the RM roster Remove. Net semantics: a student may
leave and re-join with a live code, but a **teacher's** removal is final until
the teacher re-activates them. `setEnrollmentStatus` gained a `joinCode`
argument so a re-join proves itself against a currently-live code rather than
a possibly-regenerated stored one.

#### 4. "Enrollment closed" doesn't actually close enrollment 🟡 — ✅ FIXED in V3.637

Verified: with `enrollmentOpen:false` on the class, a student redeeming the
still-active code enrolled successfully. Only `joinClassWithCode` checks the
flag; rules don't. The teacher-facing toggle therefore promises more than it
delivers — the real off switch is **Disable code**, which is enforced.

Cheapest honest fix is UI, not rules: when a teacher switches Enrollment off,
deactivate the active code too (and re-mint on switching back on). Otherwise
add `get(schedules/$(scheduleId)).data.get('enrollmentOpen', true) == true` to
the enrollment-create rule.

#### 5. The whole `users` collection is world-readable 🟠 — ✅ FIXED in V3.637 (guests closed; lab-member docs stay public for the team page)

`firestore.rules:229` — `match /users/{userId} { allow read: if true; }`

Verified: a **signed-out** visitor can list every user document, and an
external student can read any lab member's profile. Predates V3.304 (the public
team page reads it), but V3.304 is what makes it matter: you're now inviting
outside teachers and their students into the same collection that holds every
lab member's name, email, role, and bio. One `getDocs(collection(db,'users'))`
from any browser console dumps the lab directory.

This one is not a one-line fix — the public team page and several RM surfaces
read `users` — so it wants its own version. Sketch: keep public read for the
fields the team page needs by moving them to the already-existing
`teamProfiles`, then narrow `users` to `isOwner || isAdmin || isLabMember`.
Worth scoping before the first outside class goes live.

#### 6. Deleting a class blocks its participants from reviewing it 🟡 — ✅ FIXED in V3.637

`firestore.rules:563` — review-create does
`get(schedules/$(scheduleId)).data.ownerUid == …`. After "Delete class" the
schedule doc is gone, the `get()` returns null, dereferencing it errors, and
the rule denies — even for a student whose enrollment doc still exists.
Verified (`Null value error` in the emulator log). So the testimonial you'd
most want ("the class is over, tell us how it went") is exactly the one that
can't be written.

Fix: check the enrollment first, and guard the schedule read with `exists()`:

```
&& (exists(/databases/$(database)/documents/enrollments/$(request.resource.data.scheduleId + '_' + request.auth.uid))
    || (exists(/databases/$(database)/documents/schedules/$(request.resource.data.scheduleId))
        && get(/databases/$(database)/documents/schedules/$(request.resource.data.scheduleId)).data.ownerUid == request.auth.uid))
```

#### 7. You can't approve a class request from the phone app 🟡 — ✅ FIXED in V3.637

Not a rules issue — a bundling one. `rm/js/admin-teachers.js:133` fetches
`/modules/manifest.json`, an absolute site-root path. `OurlabMobile`'s
`scripts/sync-rm.mjs` copies only the `rm/` tree plus a hand-listed
`['scheduler.js']`, so that URL 404s inside the app. The catch sets
`manifest = {}`, and the approve modal then renders **zero** module-set
checkboxes and refuses to submit ("Grant at least one module set"). The
Teachers tab also shows raw folder keys instead of labels.

Fix: add `modules/manifest.json` to the copy list in `sync-rm.mjs` (it's 6 KB),
or have `admin-teachers.js` fall back to the folder keys with a visible warning.

### Two design notes, not bugs

- **The request form offers the lab's own courses.** `modules/manifest.json`
  exposes `bme295c` and `bme576` alongside the general sets, so an outside
  teacher can request — and you can accidentally grant — your actual UA course
  material. There's no "offerable to outside schools" flag in the manifest.
- **Module HTML stays publicly fetchable** by direct URL. That was an explicit
  V3.304 trade-off ("soft gating"), and the gate on the *viewer* works; just
  don't describe the modules as private to a teacher.

## Part 2 — the test you should run

Two halves, because they prove different things. Demo mode covers **screens and
wiring**; the second account covers **permissions**. Neither substitutes for
the other.

### A. Screens — 10 minutes, no accounts needed

Sign in as yourself (admin) and open **`mcgheelab.com/#/demo`** — or click
**🎭 Demo mode** in the toolbar on the RM Teachers page. Pick a persona; the
real teacher/student screens render against fake data. Nothing is written to
Firestore and no accounts are created. The strip at the top switches persona,
resets the fixtures, and lists every write your clicks *would* have made.

Walk these and look for anything that reads wrong to an outsider — copy,
empty-state wording, a button that does nothing:

| Persona | What to check |
|---|---|
| Signed-out visitor | The sign-in gate names the teacher and the school. |
| Brand-new sign-in | Are the two CTAs ("Are you a teacher?" / class code) clear to someone who has never heard of the lab? |
| Nothing requested yet | The request form's module-set list — **7 checkboxes, including bme295c and bme576.** Decide whether outsiders should see your UA courses (design note above). |
| Request awaiting review | Does the wait feel acknowledged? A teacher may sit here for days. |
| Request denied | Your deny reason is shown verbatim. Write one in the panel and check it reads like something you'd send a stranger. |
| Approved, no students yet | The most common real state. Big code, "Copy", roster empty. Is it obvious what to tell students to do? |
| Approved, 2 classes, 15 students | Click **Regenerate**, **Disable**, **Remove** on a student, and the **Enrollment open** toggle — then open the Actions log and confirm each did what you expected. |
| Not in a class yet | Type `BADBAD` (should be refused), then `K7M4PQ` (should join). |
| Enrolled in a class | Open a module from the class page — the iframe loads the real module HTML. |
| Review awaiting moderation | A student can see and edit their own unpublished review. |
| Removed from the class | Falls back to the code gate, not the module list. |

Then, with a demo still running, open **`#/classes`** and **`#/team`** — the
reviews strip and the featured-teacher cards read the fake data, so you can
proof the outward-facing copy. Click **✕ Exit demo** when done (or just close
the tab; the persona lives in `sessionStorage`).

### B. Permissions — 10 minutes, needs a second Google account

Demo mode runs as you, so every read succeeds. To see what a real teacher's
browser can and can't do, use a throwaway Google account in a private window
(any Gmail works; it lands as `role:'guest'`, which is what teachers stay).

1. **Private window → mcgheelab.com → sign in with the second account.**
   You should land on the guest dashboard with the two CTAs.
2. Click **"I'm a teacher"**, fill the request form, submit. In your own
   window, the RM **Teachers → Class Requests** tab should show it as pending.
3. **Deny it** with a reason. Refresh the teacher window — reason visible,
   fresh form offered.
4. Submit again, then **Approve** it: pick the module sets and confirm. Watch
   for the class id and code in the green status line.
5. Back in the teacher window, reload. The class, the code, and an empty roster
   should appear **without** you touching anything else. (This is the step most
   likely to expose a rules gap, because the teacher — not the admin — is now
   doing the reading.)
6. **Third account (or the same private window signed into another Gmail)** →
   `#/classes/<the class id>` → enter the code → confirm the module list opens.
   The teacher's roster should show that student.
7. As the teacher, **Remove** the student, then reload the student window: they
   should hit the code gate. (Issue 3 above says a determined student can undo
   this from a console — that's the fix to decide on, not a test failure.)
8. Both accounts: write a review from the dashboard. As admin, moderate them in
   **Teachers → Reviews**, feature one, then check `#/classes` and `#/team`.
9. **Try the things that should fail** in the teacher's console — this is the
   part demo mode can't do:
   ```js
   // must be denied
   firebase.firestore().collection('users').doc(YOUR_TEACHER_UID).update({role:'admin'})
   // must be denied
   firebase.firestore().collection('schedules').doc(SOMEONE_ELSES_CLASS).update({title:'x'})
   // currently SUCCEEDS — issue 1
   firebase.firestore().collection('schedules').doc('tc-test-selfmade')
     .set({kind:'teacher-class', ownerUid: YOUR_TEACHER_UID, grantedFolders:['bme295c'], modules:[]})
   ```
   If step 9's third call still succeeds, issue 1 hasn't been fixed yet. Delete
   the doc afterwards.
10. **Clean up:** delete the demo class, its codes, the enrollments, the
    reviews, the request, and the `users/{uid}` docs for the throwaway accounts
    (RM **Guests** panel). The Firebase Auth accounts themselves survive —
    deleting those needs a callable function that doesn't exist yet.

### What to do with the results

All seven shipped: 1-3 in V3.635, 4-7 in V3.637. The batch deploys **FTP
first, then rules**. What's left is not on this list — it's the two design
notes above (the manifest offering your own UA courses to outside teachers,
and module HTML staying publicly fetchable), plus two documented residuals:
lab-member profiles still readable publicly (needs the `teamProfiles` split),
and an owning teacher not being able to review a class after it's deleted
(needs soft-delete). All the proposed rule edits above
are small, but they all need `firebase deploy --only firestore:rules` and a
smoke test of both sign-in paths right after — the V3.304 release ritual warns
about exactly that interaction.
