# V3.803 — Learning Modules get a type; homework/keys and reports/tests get their own tabs

## The ask

Alex: *"when i add a new learning module to the learning module stack, i want to
set a type. Homework, Homework key, report, test, module, pretest. Homeworks and
keys should automatically be added to the homework tab. Make another tab for
reports and tests."*

The immediate trigger is `modules/bme466/HW1-student-key.html` ("HW1 — Worked
solutions"): it is in the manifest, it needs to be reachable from the class page,
and the only place it could go today is the numbered lesson stack next to Week 1.

## Goal

Every entry in a Learning Modules section carries a **type**. The stack is still
where entries are managed (add, reorder, retype, visible, delete). The public
page lists each entry by type:

| type | where students see it | starts |
|---|---|---|
| `module` (default, every pre-V3.803 entry) | its Learning Modules section, numbered | visible |
| `pretest` | its Learning Modules section, PRETEST badge, no lesson number | visible |
| `homework` | the **Homeworks** tab | visible |
| `homework_key` | the **Homeworks** tab, KEY badge | **hidden** |
| `report` | the **Reports & Tests** tab | visible |
| `test` | the **Reports & Tests** tab | **hidden** |

Keys and tests start hidden because a key visible the moment it is added is the
one mistake this field must not make easy. Everything else keeps the old default.

## Approach

**Data.** One new optional field on `schedules/{id}.modules[]` entries: `type`.
Absent = `'module'`, so nothing existing moves until Alex retypes it. Notes
(`kind:'notes'`, V3.660) never carry a listing type — they always stay in the
stack. No rules change (a new field in an existing array on a doc admins already
write), no index, no migration script.

**Two new section components, created on demand.** `SECTION_REG` gains
`homeworkModules` ("Homework & Keys", types homework + homework_key) and
`reportTestModules` ("Reports & Tests", types report + test), both
`component: 'typedModules'`. They are *derived lists*: `renderTypedModulesBody`
reads `modulesForTypedSection(key)` — every entry in the class whose
`moduleHomeKey()` is that key, in stack order (section tab order, then `order`).
Nothing is copied, so there is nothing to drift.

`ensureTypedModuleTabs()` is the "automatically" in the ask. In the mould of
V3.716's `ensureModulePlacements()`, it runs after placements at load and on
every `refreshCanvas()`, never `markDirty()`s, and bails when the class has no
modules section (teacher-classes stay untouched). For each typed section key
with at least one entry and no section yet:
- **Homeworks:** append the section to an existing Homeworks tab — BME 466's
  `hwList466` tab (below the Assignments & Due Dates table), or any tab named
  like one. Otherwise create a public "Homeworks" tab.
- **Reports & Tests:** create a public "Reports & Tests" tab after the Homeworks
  tab when there is one, else before the first gated (student/staff/admin) tab.

Because it runs on every refresh, deleting the tab while typed entries exist
brings it back; the hint in the section says so. The way to remove it is to
retype or delete the entries.

**Typing is automatic (added mid-build).** Alex: *"any module i upload should
have a type attached to it to autosort them upon load."* `guessModuleType(htmlFile,
title)` reads the type off the file name and title — this catalog carries it
(`hw-01-…`, `HW1-student-key.html`, `report-01-…`, `hw-00-pretest.html`).
Keyword-only, most specific first (solutions / answer key / key+hw → key;
pretest; hw / homework / assignment / problem set; report; test / exam /
midterm / final / quiz, word-bounded so "Pretest" is not a test); anything else
is a module. `moduleType()` returns the explicit type when valid and the guess
otherwise, so an untyped entry reads the same on the class page, in the viewer
and in the module header before the doc is ever re-saved. `ensureModuleTypes()`
stamps the guess onto untyped entries at load (same in-memory, no-markDirty
mould), so the editor's select shows it and it persists on the next save. The
picker prefills Type from the picked file until the user changes it. Scanned
over all 80 manifest files: only the BME 466 hw-*/key/report files and the
pretest leave `module`. Consequence: the live BME 466 page re-sorts itself the
moment the FTP lands, with no editor visit.

**Editor.** The Add Module modal gains a Type select (not for notes). Every
stack card gains a Type select and, for listed types, a "Listed on the X tab"
note; the numbered circle counts only plain modules so the editor numbering
matches the public page. The modal's "Please select a file" `alert()` becomes an
inline error beside the field (no browser popups — see memory). A tab/section
created on add or retype is announced with a toast, not an alert.

**Viewer.** `wireModuleViewer` (and the in-page `module-header.js`) walk prev/next
within the LIST the student came from: a homework's siblings are the other
homeworks and keys in Homeworks-tab order, and the lesson stack's prev/next skip
listed entries. Progress reads "Lesson N of M" for modules (counting only
modules), "Pretest" / "Instructor notes" for those, and "Homework key · 2 of 5"
style for listed types.

## Files

  `renderTypedModulesBody`, modal, card select, viewer siblings, `cbToast`.
- `modules/shared/module-header.js` — the same sibling rule inside the iframe.
- `user-styles.css` — type tag + circle + select styles.
- `scripts/tests/module-placements.test.mjs` — new section 7: types.
- `sw.js` 788 → 789. CHANGELOG, ARCHITECTURE, PENDING_RELEASE.

## Not done, on purpose

- The BME 466 `assignments` subcollection (due dates, audiences, kinds) is
  untouched. The Homeworks tab shows both: the due-date table it already had,
  and below it the typed module list. Linking a key to its assignment row is a
  later step if Alex wants it.
- `prompt()`/`confirm()` in `addTab`/`addSection`/module-delete are still there;
  only the modal's own alert was converted, since this release touches it.
- Teacher-classes (`tabs: []`) render `schedule.modules` straight and have no
  type UI; the field is additive and ignored there.

## Deploy

FTP only (class-builder.js, module-header.js, user-styles.css, sw.js). No
`firebase deploy`. The live BME 466 page re-sorts itself on load (no retyping);
the next editor save persists the types. Then add `HW1-student-key.html` (the
picker chooses Homework key) and tick Visible when it is time; glance at each
row's Type select for a wrong guess.
