# V3.932 — Computer ↔ cloud merges in context; a deletion in a share waits for the other person

## Goal (Alex)
"we need a merge computer to cloud especially for shared documents. if one user deleted something, the other has to
approve it for example. if both have edited the same block, then the merge will attempt to keep the users edits together
but in the same context. for example if there is a list of items, and there was an edit to the list or an addition to
the list then those changes are made to that list, but if there are non contextual changes then they just go at the end
of the card."

## What was there
- `merge3` (hub-core) merged a record field by field. A card's `body` (`{text, marks}`) is one field, so two edits to the
  same card were always a conflict: one person's text or the other's, decided under the warning triangle.
- The desktop bridge merged a row both sides changed on the computer (the app's Python merge), then sent the result up.
- On a first connect with notes on both sides, one side replaced the other (V3.931: this is what lost shared projects).
- In a share, a collaborator's deletion went through if they were the last to write the record (V3.923). An owner's
  deletion went straight to everyone.

## Approach

### 1. Contextual merge — `functions/scientia-merge.js` (pure, used by `planPush`)
- Text is lines (list items, paragraphs, steps). Each side's edit is diffed against the common version (LCS, diff3).
  - An edit only one side made goes where it was made.
  - Both adding at the same place (two new list items): both go in, the one already there first.
  - Both changing the same lines differently: both versions, side by side, in that place.
  - An edit to lines the other side removed has no context left. It goes at the end of the card, under
    "<name>'s edit (its place was removed):".
  - With no common version (two notebooks meeting), the lines both hold count as common, so nothing is lost.
- Marks (`{id, type, from, to, ref}`) follow their lines, remapped through each side's line map. A mark either side
  removed stays removed.
- `settle(store, prev, mine, cur, merged, bad)` runs on the fields `merge3` couldn't settle:
  - Text bodies and multi-line strings merge as above. Plain objects merge field by field.
  - A card's place (`x, y, w, h, z, collapsed`) stays where it is now.
  - A card name both changed: the other name goes at the end of the card.
  - Anything left is a conflict, as before.

### 2. Computer ↔ cloud — `rm/scientia/scientia-cloud.py` (+ the vendor copy), `scientia/labsync.py`
- `Bridge.exchange()`: the computer's changes go to the cloud first, so a row both changed merges there (one merge,
  the lab's). The computer takes the result as it is.
- `Bridge.unite()`: when both sides hold notes and share no history, they become one notebook. What one side lacks
  goes to it; a row both hold differently goes to the cloud with no common version (`base 0, prev null`). The hub now
  merges such a push instead of overwriting (`planPush`). Nothing is removed. `--prefer` still replaces, by name only.
- `labsync.realign()` uses `exchange()`.

### 3. Deletions wait for the other person — `functions/scientia-share-core.js`, lab-mode §17
- `holdDeletes(env, idx, uid, role, dels)`:
  - A note, card, theme, aim, structure or project removed from a share is held.
  - A collaborator's deletion waits for the owner (or another collaborator). The owner's waits for a collaborator.
  - Grouping: one decision per note (with its cards, structures and wires), one per card otherwise.
  - Not held: an empty card, or a record only the deleter ever wrote (`who/`: its sole author since it was shared, or
    `'*'` once someone else changed it). Wires, media and terms aren't decided on alone.
- Pending entries live in `scientiaShares/{id}/pending/{pid}`. While one waits:
  - the deleter's copy stays gone;
  - everyone else keeps theirs (`fanOut` skips held keys);
  - the hourly pass neither restores, re-asks nor removes;
  - an owner who deletes the project itself does not end the share.
- `decide(env, uid, share, pid, 'delete'|'keep')`: only an approver decides. It applies to the owner's hub (the
  collaborator's delete, or the owner's records back from the keeper's copy), then runs the share pass so every copy
  follows.
- Hub routes: `GET /api/rm/shares/pending`, `POST /api/rm/shares/decide` (FirestoreHub `sharesPending` /
  `sharesDecide`; stubs on MemoryHub). The desktop reaches them through `serve.py`'s `rm_proxy`.
- Lab layer §17: a chip at the top ("2 deletions to approve") and a panel with *Keep it* / *Delete it*, plus your own
  deletions waiting for someone else. It works on the web and in the installed app.

## Not done / follow-ups
- The app's own conflict dialog and the local Python merge (`sisync.py`, Gabe's) are unchanged. Two devices on one
  computer still merge field by field there.
- Approvals are polled every minute and on return to the window. They don't arrive by push.
- A deletion in a shared lit review (a note, not a project) follows the same rules. Its root, the review itself, is
  never deleted by a collaborator (V3.923).

end-of-turn deploy. Until the function is deployed, the approvals chip simply finds nothing.
