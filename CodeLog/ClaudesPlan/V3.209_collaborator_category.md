# V3.209 — New `collaborator` user category

## Goal

Add a new lab-tier category, `collaborator`, for external partners who
get access to a curated subset of RM pages via the admin page-allow
matrix but are kept out of every public-facing surface and every
internal directory.

Semantics:

- **Page access is explicit-only.** A collaborator with no
  `userPermissions/{uid}.allowedPageIds` entry sees **nothing** through
  `canAccessPage` — no implicit "default workflow baseline" like normal
  lab members get. The admin uses the existing page-allow matrix at
  `/rm/pages/admin-permissions.html` to grant specific pages.
- **Invisible by default.** Collaborators never appear on
  - the public website Team page (`#/team`),
  - the RM People page (for non-admin viewers),
  - PMR left rail, task-assign picker, chat sidebar, sharing picker,
    meeting attendee picker, dashboard active-members tile,
    procurement requester picker, CV overview, etc.
- **Admin sees them.** Admins still see collaborators in the People
  page (with a "collaborator" category chip), in the page-allow matrix
  to assign pages, and in any other admin-only directory.

## Why a category, not just the V3.208 `hidden` flag?

The V3.208 `hidden` boolean lets admins toggle visibility for any user.
A category goes further:

1. **Distinct page-access semantics.** Lab members have the
   default-workflow implicit baseline; collaborators don't. That's a
   category-level policy, not a per-user toggle.
2. **Organizational clarity.** "Collaborator" appears in the People
   page filter tabs and on the row chip, so admins can see at a glance
   which users are external. A `hidden: true` postdoc is still
   *categorically* a postdoc; an external partner shouldn't be filed as
   "postdoc + hidden."
3. **Future-proof.** Other places that key off category (sorting,
   rank-checks in equipment.js, conditional UI) will already exclude
   collaborators from lab-only flows.

## Implementation

### Category enum updates

- **`rm/js/people.js`** — add `'collaborator'` to:
  - `PEOPLE_CAT_ORDER` (positioned after `alumni`, before `guest`)
  - `PEOPLE_CAT_LABEL`
  - `LAB_FIELDS[0].options` (Edit Lab Profile form)
  - `changeRole` form category options
  - `openInviteForm` category options
- **`rm/js/equipment.js`** — add `'collaborator'` to `CATEGORY_ORDER`
  at the same position (rank near alumni/guest, so equipment-borrowing
  rank checks treat collaborators as low-priority by default).

### Visibility filter

- **`rm/js/firebase-bridge.js`** — extend `LAB_USERS.isVisible(u)`:
  ```js
  if (!u || !u.role || u.role === 'guest') return false;
  var hideByCategory = u.category === 'collaborator';
  if ((u.hidden || hideByCategory) && !(typeof firebridge !== 'undefined' && firebridge.isAdmin && firebridge.isAdmin())) return false;
  return true;
  ```
  Auto-hides collaborators from non-admin viewers without needing the
  per-user `hidden` flag. The 14 internal people-lists already swap to
  this helper in V3.208, so no per-site change is needed.

### Public team page

- **`app.js`** — line 567 filter gains `&& u.category !== 'collaborator'`:
  ```js
  const teamUsers = users.filter(u => u.role !== 'guest' && !u.hidden && u.category !== 'collaborator');
  ```

### Page access (the "enhanced access via matrix" semantic)

- **`rm/js/firebase-bridge.js`** `canAccessPage(pageId)` — between the
  explicit-grant check and the implicit-baseline fallback, deny baseline
  for collaborators:
  ```js
  if (_accessGrant.allowedPageIds && _accessGrant.allowedPageIds.length) {
    return _accessGrant.allowedPageIds.indexOf(pageId) >= 0;
  }
  // Collaborators have no implicit baseline — admin grants explicitly.
  if (_profile && _profile.category === 'collaborator') return false;
  // Lab-member implicit baseline:
  var REG = window.PAGE_REGISTRY;
  if (REG && REG.defaultPageIdSet) return REG.defaultPageIdSet.has(pageId);
  return true;
  ```
  This is the core "enhanced access via the matrix" rule: a collaborator
  sees only what `allowedPageIds` lists. Admin uses the existing
  admin-permissions.html matrix to tick the pages they get.

### Limits of this change (read before relying on it as a security boundary)

`canAccessPage` gates the **workflow chip strip** and **page discovery
UI** — it does **not** prevent a collaborator from typing a URL into
the address bar and loading a page. The real security boundary is
`firestore.rules`, which currently gates by role (`isLabMember()` etc.)
and not by category or `userPermissions`. Tightening firestore.rules to
honor `userPermissions/{uid}.allowedPageIds` per collection is a
separate, larger lift — out of scope here. Treat V3.209 as a strong UI
gate, not a data-layer gate. For collections containing sensitive
material (paper drafts, grant drafts, PMR), the existing per-doc rules
(authorUids, owner-only, admin-only) already restrict reads
independently of category.

## Done when

- Admin can invite a new user with category `collaborator` (in either
  the invite form or via `changeRole`).
- That user signs in, has `role !== 'guest'` (so they're past the
  pending-access overlay), and can navigate to RM pages explicitly
  granted via the page-allow matrix.
- Without any `userPermissions/{uid}.allowedPageIds` entry, the
  collaborator sees zero pages in workflow chip strips and page-discovery
  surfaces (no implicit baseline).
- Public website `#/team` does not list the collaborator regardless of
  signed-in state.
- Non-admin RM users do not see the collaborator in any internal
  directory (people page, PMR left rail, task-assign, chat, etc.).
- Admin sees them everywhere with a `collaborator` chip on the people
  page row.
