# V3.143 — Caret persistence rewrite (real fix for the toolbar button silent-fail)

## The bug, this time understood properly

User: "still doesnt work" — V3.140's fix didn't address the actual root
cause.

When the user:
1. Clicks into a paragraph + types text.
2. Clicks a toolbar reference button (e.g. `+ Inline Eq`, `+ Cite`,
   `+ Eq`, `+ Fig`, `+ Table`).
3. mousedown fires, `_saveCaretFromCurrentFocus()` saves the live
   `Range` object on `_state.savedRange`.
4. Picker opens. ~30 ms later, the picker's `setTimeout(input.focus(),
   30)` grabs focus. The paragraph contenteditable **blurs**.
5. The contenteditable's blur handler runs `applyRendered(el,
   sourceText, renderFn)` ([rm/js/paper-editor.js:2959](rm/js/paper-editor.js#L2959))
   which does `el.innerHTML = renderFn(sourceText)` — replacing every
   child node with a fresh DOM tree (so chips render, math renders,
   etc.).
6. The user picks an item from the picker. `_insertAtSavedCaret` runs.
7. `sel.addRange(_state.savedRange)` is called. **The Range's
   startContainer / endContainer are now detached text nodes** — they
   were destroyed in step 5. `addRange` silently produces a
   non-functional selection.
8. `document.execCommand('insertText', false, text)` no-ops because
   there's no live selection inside the contenteditable.
9. From the user's perspective: nothing happens.

V3.140's fix populated `_state.savedEl` more reliably, but never
addressed the stale Range. The Range was the actual broken piece all
along.

## The fix

Caret persistence model:

| Before V3.143 | V3.143 |
|---|---|
| `_state.savedEl: Element` | `_state.savedEl: Element` |
| `_state.savedRange: Range` (goes stale) | `_state.savedCaret: number` (char-offset, never goes stale) |

Two save-sites updated:

- `_saveCaretFromCurrentFocus()` (toolbar `mousedown` path) — also
  records the char-offset via the new `_readCharOffset(el,
  endContainer, endOffset)` helper.
- `_saveCaretFromEvent(e, el)` (right-click context-menu path) —
  records char-offset too.

Insertion site rewritten:

- `_insertAtSavedCaret(text)` no longer trusts `_state.savedRange`. It
  always rebuilds a fresh Range from `_state.savedEl` +
  `_state.savedCaret` against the **current** (post-re-render) DOM via
  the V3.140 `_rangeFromCharOffset(el, offset)` walker. The fresh
  Range references the live text nodes that exist now.
- After successful insertion, `_state.savedCaret += text.length` so
  successive picks stack rather than overwrite each other.
- Final-final fallback: if even `range.insertNode` fails (e.g. the
  Selection API has no rangeCount after `addRange`), `el.textContent +=
  text` + dispatch a synthetic `input` event so the Y.Text observer
  picks up the change. Never silent.

## Why V3.140 wasn't enough

V3.140 fixed *one* failure mode (the user clicking the button without
having focused into a paragraph), and added an alert for the truly
empty case. But the most common path — user typing in a paragraph,
clicking a toolbar button, picker opens, picking does nothing — was
unaffected because:

- `_state.savedEl` was correctly set.
- `_state.savedRange` was correctly cloned.
- The Range went stale 30 ms later when the picker stole focus and the
  blur handler swapped innerHTML.
- All the V3.140 fallback paths still trusted the cached Range.

Only by abandoning Range-caching can the bug actually be fixed.

   `[!eqi:<id>]` inserts at the caret position; on blur it renders as

   alert ("Place your cursor in a paragraph first…") still surfaces.
7. Hard-reload to evict SW cache `mcgheelab-shell-v118`.

## Same root cause as V3.142

V3.142 shipped the same shape of fix for lab-notebook chip insertion:
`document.execCommand('insertHTML')` no-ops because the contenteditable
was just re-rendered. Different module, same root issue: trying to
operate on a Range that points at detached nodes. The notebook fix
added a Selection-API fallback. The paper-builder fix abandons
Range-caching entirely (because the prose-token insertion goes through
`execCommand('insertText')`, not `insertHTML`, so a different fallback
matters).
