## Context

The live whiteboard (V3.677–683) works, but it lives on its own page. Alex's actual
lecture setup is **two devices at once**: a laptop driving the learning module onto the
classroom projector, and an iPad where he draws. Today, showing the board to the room
means navigating the laptop *away* from the module — so teaching alternates between
"the module" and "the board" instead of using both together.

The goal is a whiteboard **popout inside the module page**, modeled on the calculator
button already in the homework modules: open/collapse/resize/reposition it beside the
lesson, never leaving the page. On the laptop it shows the live board Alex is drawing on
from the tablet, so the projector shows lesson and board together. He can also **snap a
simulation from the lesson straight onto the board** and annotate it while talking.

This plan covers **R1 only — the instructor teaching workflow**. Two later releases
(student private boards + homework export; classmate sharing) are sketched at the end so
R1 doesn't paint them into a corner. Staging was chosen deliberately: R1 is testable in a
real lecture within one cycle.

## Decisions locked with Alex

| Decision | Choice |
|---|---|
| Popout source | One panel, toggle at top: **[My notes] / [Live class board]**. R1 implements the Live side; My notes is a stubbed seam. |
| Zoom/pan | **Viewer-local lens, never synced.** Strokes stay in the fixed 16:10 board space; the projector keeps the whole board. |
| Snapped images | **Movable, resizable items** on the current page (not page backgrounds) — needs an image-item layer beside strokes. |
| Capture method | **Canvas-direct only in R1** (`canvas.toDataURL()`), no DOM rasterizer vendored. Marquee-over-anything is deferred. |
| Staging | Split. R1 = teaching workflow. R2 = student boards + export. R3 = sharing. |

## What R1 delivers

1. A **whiteboard popout** in the weekly learning modules — drag by its header, resize
   from the corner, collapse to the title bar, close; reopens exactly where and how it
   was left. Survives Present mode.
2. The popout renders the **live instructor board**, updating stroke-by-stroke as Alex
   draws on the tablet.
3. **Pinch-zoom + two-finger pan**, plus manual **− / ⌂ / +** buttons top-right. Local to
   that screen only.
4. **"→ Whiteboard" on every simulation canvas** — snaps it onto the live board as a
   movable, resizable image that Alex can then annotate from the tablet.

## Verified findings that shape the design

- **All 32 canvases in `modules/bme466/01-diffusion-why-anything-moves.html` are pure 2D
  draws** — zero `drawImage`, zero external `Image()` sources, zero WebGL. So
  `canvas.toDataURL()` cannot taint and cannot return blank. Canvas-direct snap is
  genuinely near-free and pixel-perfect. (Verified by grep this session.)
- **The iframe src carries no class id.** `class-builder.js:4085` sets
  `iframe.src = modules/{folder}/{file}` with no query string, and no call site anywhere
  builds `?class=`; the only producer is `module-header.js:52`, for its own nav links.
  A module currently has **no reliable way to know its classId** — R1 must fix this.
- **Two iframe height regimes** (`class-builder.js:4092-4097`): modules with `#rail`
  (the weekly learning modules) get `calc(100vh - 120px)` and scroll internally, so
  `position:fixed` behaves. Everything else is stretched to full `scrollHeight` and the
  *parent* scrolls, so a fixed panel scrolls away. **R1's learning modules are in the
  safe regime**; this is an R2 problem — and it means the existing calculator panel in
  `hw-00`/`hw-01` is *already* broken inside the viewer (pre-existing bug, noted for R2).
- **Live board strokes are world-readable** (`firestore.rules`, `allow read: if true` on
  `whiteboards` and `strokes`). So the R1 panel needs **no authentication at all** — just
  a Firestore handle. This removes the auth bridge from R1's critical path entirely.
- **`whiteboard.js` is a closed IIFE with singleton state**: one module-level `S`, and
  **20 hardcoded `getElementById('wb-*')` lookups** across 11 distinct ids. It can host
  exactly one board, in one fixed DOM shape. Mounting a second board in a panel requires
  a refactor, not a wrapper.
- **Modules can run their own Firebase**: `modules/bme466/hw-00-pretest.html:1029-1195`
  (the `ML-CLOUD-SAVE v1` block) loads the gstatic compat SDK and calls
  `firebase.initializeApp()` with an inline config. Proven precedent for a self-contained
  module reaching Firestore, consistent with `modules/AUTHORING.md` §0/§7.
- **An origin-checked module→parent channel already exists**:
  `modules/shared/module-header.js:181-197` posts `{source:'ml-module', type:'section', id}`
  to `window.location.origin`; the parent listener is `class-builder.js:~4278`, which
  currently drops anything that isn't `type === 'section'`.
- Learning modules have **no tool dock**. Their only chrome slot is `.rail-head` in
  `<nav id="rail">` (`01-…:324-334`), beside `#rail-present` / `#rail-fminus` / `#rail-fplus`.

## Design corrections (verified after approval — these supersede details below)

1. **No auth bridge is needed at all.** `firebase-config.js:16` and
   `hw-00-pretest.html:1042` use the **same apiKey** and both init the **default**
   app. Firebase Auth persists per-origin at `firebase:authUser:{apiKey}:[DEFAULT]`,
   and the iframe is same-origin with `allow-same-origin` — so an in-iframe app
   **silently restores the parent's signed-in user**. The `lab-apps.js` bridge is the
   wrong precedent (it ships `token: null` — identity metadata, not a credential).
   Only `classId`/`boardId` need the postMessage handshake.
2. **Don't load `user-system.js` in the iframe** to reach `processImage`/`uploadImageSet`
   — it's 263 KB and renders site chrome. Ship a ~25-line local `wbProcessImage` in the
   panel producing only **medium (800px) + full (1600px)** webp; a board item never needs
   a 300px thumb.
3. **AUTHORING.md §7.4 already sanctions shared includes** for modules "surfaced in site
   navigation" (`modules/AUTHORING.md:199-200`) — which these two are. No rule is being
   bent; §7 just needs the new component documented.
4. **Height detection uses a `<meta name="ml-module-viewport" content="1">`**, not element
   sniffing: a panel built from deferred JS *races* the iframe `load` handler, while
   `<meta>` is parsed with the head and always present. Branch becomes
   `cdoc.querySelector('meta[...]') || cdoc.getElementById('rail')` — all 47 existing
   modules match neither, so the fall-through is byte-for-byte today's path.
5. **No pinch/drag arbitration is required.** `inksHere()` already excludes
   `pointerType === 'touch'`, so touch and pen are *already disjoint input classes*:
   route touch → pan/zoom, pen/mouse → ink. This falls out of the existing palm-rejection
   design and is simpler than lifting paper-figure-board's arbitration.
6. **`?class=` is missing in three places**, not one: `iframe.src` (`:4076`), "Open module"
   (`:10149`), and the module list (`:2111`).
7. **Capture inside `requestAnimationFrame`** — these canvases are animated, and a bare
   synchronous `toDataURL` can land between clear and draw and return blank.
8. **Snap targets `S.board.activePageId`, not the panel's viewed page** (they differ if
   Alex scrolled the panel away), and toasts "Sent to page N" so it's never silent.
9. **Key snap buttons off the `<canvas>`, not `.canvas-wrap`** — module 01 has 35 wraps
   for 32 canvases.
10. **Storage is not the gate; Firestore is.** Any authed user can write under
    `classes/{classId}/**`; an image is only *visible* if an `items` doc points at it, and
    `items` writes are class-admin-only.
11. **Copy `firebase-config.js:32-42`'s `experimentalAutoDetectLongPolling` settings block**
    into the panel's init — the iframe's `firebase` is a separate script instance and does
    not inherit the Chrome/QUIC WebChannel workaround.
12. **`ERASE_TOL / scale` and `MIN_SEG / scale`** so the eraser stays a constant *screen*
    size and zooming in captures finer detail. Both no-op at scale 1.
13. Extract the shared board-geometry CSS into **`whiteboard-board.css`** loaded by both
    `index.html` and the modules, rather than duplicating ~120 lines of `wb-*` into the
    panel stylesheet where it would drift.

## Architecture

### The engine gets extracted; nothing forks

`whiteboard.js` cannot host a second board (singleton `S`, hardcoded ids). R1 extracts
the **pure** engine into a new shared file, loaded by both the parent SPA and the module
iframe, so there is exactly one inking implementation:

- **`whiteboard-core.js` (NEW, repo root)** — no Firestore, no auth, no fixed ids.
  Exports a factory `WhiteboardCore.mount(rootEl, opts) → instance`. Moves in the pure
  geometry/render/input already written and measured in V3.683: `crControls`,
  `paintStrokeRange`, `paintStroke`, `paintActiveSegment`, `pressF`, `simplifyPts`,
  `simplifyToBudget`, `segDist2`, `strokeHit`, `normPoint`, `sizeCanvases`,
  `drawBackground`, `repaint`, the pointer handlers, and the `COLORS` / `PEN_WIDTHS` /
  `BACKGROUNDS` / `MIN_SEG` / `SIMPLIFY_EPS` / `WIRE_MAX_PTS` / `BOARD_AR` constants.
  Per-instance state replaces `S`; element lookups become `root.querySelector('.wb-…')`.
  The instance exposes `setStrokes/upsertStroke/removeStroke`, `setPage`, `setView`,
  `destroy`, and callbacks (`onStrokeFlush`, `onErase`) so the *host* owns persistence.
- **`whiteboard.js` (parent)** keeps every Firestore concern — board/stroke listeners,
  the live flag, the class-admin gate, the board list, the banner — and becomes a
  consumer of the core. Its three exports and both routes (class-page section, full-page
  board, `?projector=1`) must behave identically afterward; that is the regression bar.

**Viewer-local zoom composes cleanly** because the core keeps strokes in normalized board
space and applies the view only at paint time: `repaint` multiplies by `W` today, so the
lens is one extra `ctx.setTransform(scale,0,0,scale,tx,ty)` before painting, and
`normPoint` gains the inverse mapping. Nothing about the stored coordinates changes, so
projector parity is preserved by construction.

### The panel lives inside the iframe

A parent-side panel would get Firebase for free, but modules are **also opened outside
the viewer** (direct links, and the Homeworks tab's "Open module" button — the V3.682
note records that both bypass the iframe), and those students would silently get no
whiteboard. In-iframe is the only placement that works in every context, and it matches
AUTHORING.md's self-contained rule.

- **`modules/shared/whiteboard-panel.js` + `.css` (NEW)** — the second shared module
  component after `module-header`. Ports the proven context-panel engine from
  `hw-00-pretest.html:1222-1287` (drag by `.cpanel-head`, CSS `resize:both` +
  ResizeObserver, `.min` collapse, ≤700px bottom sheet, geometry persisted in
  localStorage), and mounts a `WhiteboardCore` instance in its body. Keeps the
  `#tool-{k}` ⇄ `#panel-{k}` ⇄ `PANEL_DEFS[k]` naming convention so homework modules can
  adopt it in R2 by adding one key.
- Reads the live board with the module's **own Firebase app**, read-only and
  unauthenticated (strokes are world-readable), following the `hw-00` precedent. One
  `onSnapshot orderBy('seq')` feeds `instance.upsertStroke`.
- Learning modules mount the toggle button in `.rail-head`; the panel must survive
  `body.present` (rail collapses to 62px, root font 19–28px).

### Snapping goes through the parent

The module posts the dataURL up; the **parent** — already signed in as class admin with
`McgheeLab.db` — does the upload and the write. No auth in the iframe, and it reuses the
established origin-checked channel.

1. Panel adds a **"→ Whiteboard"** affordance to each `<canvas>` in the module.
2. On click: `canvas.toDataURL('image/webp')` → `postMessage({source:'ml-module',
   type:'wb-snap', dataUrl, title}, window.location.origin)`.
3. The parent handles it in a **separate listener added in `wireModuleViewer`** — *not* by
   extending the existing one at `class-builder.js:4278`, which lives inside
   `setupModuleEngagement`'s closure with its own flush/teardown lifecycle tied to
   scroll-beacon batching. A snap must not be coupled to that.
4. Parent converts to a Blob, runs it through the canonical
   `McgheeLab.processImage` + `uploadImageSet` (`user-system.js:262/270`, webp
   thumb/medium/full) to `classes/{classId}/whiteboard/{boardId}/{itemId}`, then writes
   the item doc.
5. The tablet's existing board listener picks it up — **no new sync path**.

Standalone (no parent) hides the snap button in R1.

### Image items

New subcollection `schedules/{classId}/whiteboards/{boardId}/items/{itemId}`, sibling to
`strokes`, so nothing about the stroke pipeline changes:

```
{ pageId, kind:'image', x, y, w, z,          // normalized board space, as strokes are
  url, thumbUrl, storagePath,
  source: { module, canvasId, title },       // provenance back to the lesson
  createdAt, createdBy }
```

Rendered as **absolutely-positioned DOM under the ink canvas** (the `paper-figure-board`
card model), so drag/resize hit-testing is free and ink always composites on top.
`sharedWithUids`-style fields are deliberately absent here — R3 adds sharing on the
*board* doc, not per item.

Rules: a new `match /items/{itemId}` block inside the existing `whiteboards` block,
mirroring the strokes gate verbatim — **rules do not cascade into subcollections**, so
the class-admin `get()` must be re-declared.

Storage needs **no rules change**: `storage.rules`'s `classes/{classId}/{allPaths=**}`
already grants public read and any-authenticated write up to 50 MB, which covers the
snap path. Note a tighter sibling rule would be **security theatre** — Storage rules, like
Firestore's, grant when *any* match allows, so a narrower block cannot take away what the
broad one already gives. Genuinely constraining snaps to `image/*` would mean narrowing
the existing broad rule, which also governs class-file and widget uploads
(`class-builder.js:3268`, `:3328`) — out of scope for R1, and flagged here as a
pre-existing looseness rather than something this feature introduces.

### Pan / zoom

Lift wholesale from `rm/js/paper-figure-board.js`: `_view = {tx,ty,scale}` (~54),
`_toWorld`/`_applyView` (~138-147), `_zoomAt` (~343-351 — note it re-derives the factor
from the *clamped* scale, without which the view drifts at the limits), `_onWheel`
(~334-341, ctrl/meta = zoom, bare wheel = pan), pinch as a ratio against a captured
baseline routed through the same `_zoomAt` (~428-436), and second-finger-kills-drag
arbitration (~382-392). All verified present at those lines. The − / + buttons map
directly onto the centred-zoom helper already there (`:355`,
`_zoomAt(factor, r.width/2, r.height/2)`) and ⌂ onto `_zoomFit` (`:356`), so pinch,
wheel, and all three buttons share one code path.

**Gesture split inside the panel:** pen draws (unchanged, admin only), one finger pans,
two fingers zoom. This does not disturb V3.678's `.wb-draw-mode` guards, which only apply
when the drawing tools are active.

## Verification

Ship order: **`firebase deploy --only firestore:rules,storage:rules` BEFORE FTP** (rules
don't cascade; without them the item writes 403).

1. **Refactor regression first** — the extraction must be invisible. Before touching
   anything else: class-page whiteboard section, full-page board route, `?projector=1`,
   draw/erase/undo/clear/page-flip/go-live all behave as today. Re-run the V3.683 ink
   harness (extract-the-real-functions Node assertions + the browser geometric
   measurement) against `whiteboard-core.js`.
2. **Headless** (`browser-automation` skill): learning module renders with 0 console
   errors; panel opens, drags, resizes, collapses, and restores geometry after reload;
   panel survives `?present=1`. Assert **in the page** and read results from the DOM —
   `--eval` runs in an isolated world and cannot see page globals.
3. **Two-device, the real test** (device testing is non-negotiable for this repo): iPad
   goes live and draws → laptop's module popout shows strokes < 1 s. Snap a simulation on
   the laptop → it appears on the iPad board → annotate it → the annotation shows on the
   laptop. Pinch-zoom on the iPad and confirm the **laptop/projector view does not move**.
4. **− / ⌂ / +** match pinch behavior; ⌂ restores fit.
5. **Negative:** a signed-out viewer sees the live board but gets no drawing tools and no
   snap button; a non-admin cannot write an item doc (console attempt → permission-denied).

## Known costs and risks

- **The refactor is the risk, not the feature.** Extracting the engine touches the one
  thing that already works and that Alex teaches from. Mitigation: do it first, ship
  nothing else until the R1 regression list above is green, and reuse the existing V3.683
  ink harness as the correctness bar.
- **Learning modules gain Firebase.** Both weekly modules currently contain *zero*
  Firebase (verified) and are already 287 KB and 210 KB. The panel adds three gstatic SDK
  tags (~300 KB, CDN-cached, `defer`red). Acceptable, but it makes a previously
  dependency-free lesson page depend on the network for one panel — the panel must fail
  soft to "live board unavailable" and leave the lesson fully usable, exactly as
  `hw-00`'s cloud-save block fails soft to localStorage.
- **`?class=` must be threaded in two places** — the iframe src *and* the class page's
  module links — or the panel works embedded and not standalone (or vice versa).
- **Snap is parent-mediated, so it only works inside the viewer** in R1. That matches
  Alex's laptop workflow, but the button must be hidden (not broken) standalone.
- **Panel vs. Present mode** is the most likely visual surprise: Present collapses the
  rail to 62 px and pushes root font to 19–28 px. The panel is `position:fixed` in px, so
  it should be checked at both font extremes.
