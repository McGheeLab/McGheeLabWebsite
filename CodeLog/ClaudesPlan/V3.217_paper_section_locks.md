# V3.217 — Paper editor: soft per-block section locking

Wishlist item from `rm/wishlist.md` (Paper editor section).

## Goal

Two coauthors editing the same block at the same time is technically
safe under Yjs (the CRDT merges every keystroke) but produces a
confusing keystroke-fight in the UI. Promote `focusBlockId` presence
into a soft per-block lock: the first user to focus a block holds it;
everyone else sees the block visibly locked-by-name and cannot place a
cursor / type into it. The holder also sees their own self-lock badge
so it's obvious *they* are the one blocking the other side.

## Approach

1. **Holder = deterministic presence pick.** `paper-editor.js` exposes
   `ctx.getLockHolderForBlock(blockId)` to the block renderer.
   Implementation: filter `state.presenceList` to entries whose
   `focusBlockId === blockId`, then sort by `uid` ascending and return
   the first. Both clients agree under contention because the
   tie-breaker is deterministic.
2. **Lock badge.** Every paragraph block toolbar gains a `<span
   class="pe-block-lock-badge">` after the presence dots. Refreshed in
   `refreshBlockLock(blockWrap, bdEl, badgeEl, ctx, blockId)` on
   initial mount + on every `paper-presence-changed` event:
   - No holder → badge hidden; `data-locked=""`; nested
     contenteditables stay editable.
   - Holder is self → green "You" badge; `data-locked="self"`;
     contenteditables editable; click the badge to release the lock
     immediately.
   - Holder is someone else → red "Locked by Alex" badge with their
     presence color in the dot; `data-locked="other"`; every nested
     contenteditable inside the block goes `contenteditable="false"`.
3. **Non-holder click → transient toast.** A delegated click handler
   on the block wrapper (installed once per block via a
   `_pe_lockClickInstalled` flag) fires `_showLockToast(x, y, holder)`
   when the wrapper is `data-locked="other"` and the click isn't on a
   toolbar control. Single shared `.pe-lock-toast` DOM element reused
   across blocks; auto-hides after 1.8s.
4. **Lock release paths.** All four cases from the wishlist:
   - **Blur the body.** Wrap-level delegated `focusout` listener
     schedules a 250ms-delayed `setFocusBlock(null)` whenever any
     contenteditable inside the block loses focus AND
     `e.relatedTarget` isn't another element inside the same block.
     That second check avoids dropping the lock when the user clicks
     a toolbar button (status pill, comment button, etc.) on the same
     block.
   - **Navigate away.** Existing `disconnect()` in `paper-yjs.js`
     deletes the presence doc; lock auto-clears for every other
     client.
   - **Idle ≥ 30s.** A per-block `IDLE_RELEASE_MS = 30000` timer in
     `paper-blocks.js`'s `renderParagraph` closure. Reset on every
     `focusin` / `input` event delegated through the block's wrap; on
     fire it calls `ctx.releaseLock()`. Guarded by `_selfOwnsThisBlock()`
     (queries `ctx.getSelfFocusBlockId()`) so a stale closure can't
     stomp on a lock the user has since moved to a sibling block.
   - **Manual release.** Clicking the self-badge calls
     `ctx.releaseLock()` → `setFocusBlock(null)` immediately.
   - **Re-acquire after idle release.** If the idle timer fires and
     releases the lock but the user is still focused in the body, the
     `wrap.input` listener detects "no holder" + active focus and
     calls `ctx.onFocusBlock(blockId)` to re-claim before bumping the
     idle timer.
5. **Stale lock auto-clear.** No code change needed — `paper-yjs.js`'s
   `presenceUnsub` `onSnapshot` already filters out records older than
   `PRESENCE_STALE_MS` (30s). When a holder's tab disconnects, their
   heartbeat stops; 30s later their presence record falls out of the
   cache and the lock clears for everyone.
6. **Skeleton bullets share the lock.** The skeleton-bullet bind in
   `renderSkeletonOutline` calls `ctx.onFocusBlock(blockId)` on focus
   too, so focusing any bullet inside a block claims the lock. The
   per-block-wrapper contentEditable toggle (point 2) walks every
   `[contenteditable]` descendant, so bullets are locked too when the
   block is held by someone else.

## Open question resolutions

> Can a non-holder forcibly steal a stale lock, or only wait it out?

Only wait. The 30s presence-stale check and the 30s idle release are
both fast enough that stale locks self-clear before they become
annoying. No "force-steal" affordance in this version — it would
create UX surprise for the holder ("why did my edit just stop?"). If
this becomes a pain point we can add it later.

> What happens if a non-holder is mid-keystroke when a lock from
> another user arrives — silently drop their input, or grant them
> the lock because they typed first?

Silently drop: the contentEditable flips to `'false'` and any pending
keystrokes have nowhere to land. We rely on the deterministic
smallest-uid tie-breaker plus the fact that *both clients* see the
same lock holder simultaneously, so neither side can race past the
other. The losing side sees their keystroke land in the body for a
single frame at worst, then the contentEditable flip on the next
presence tick drops further input. The amount of "lost" typing is
bounded by the 200ms Yjs flush window, which the holder receives via
`update` and integrates losslessly anyway.

## Done when

- User A focuses block X. A sees green "You" badge on block X; user B
  sees red "Locked by A" badge on block X with A's color dot.
- B clicks into block X's body or skeleton bullet. The
  `contenteditable="false"` prevents the cursor from landing; a
  transient "🔒 Locked by A" toast appears near the click point and
  fades after ~1.8s.
- B can freely edit block Y while X is locked.
- A blurs block X (Tab away, click block Y, etc.). After a 250ms
  debounce the lock releases; B's block X immediately becomes
  editable again.
- A goes idle on block X for 30s (no keystrokes). The lock
  auto-releases via the paper-yjs idle timer; B can claim it.
- A closes the tab without releasing. After ~30s the presence-stale
  filter drops A's record; B's block X becomes editable.
- A clicks A's own self-badge to manually release.
