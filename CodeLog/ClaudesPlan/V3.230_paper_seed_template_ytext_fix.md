# V3.230 — Paper editor crashes seeding a fresh paper from template

## What broke

V3.229 added a one-click "+ Add Item" type=paper flow from the research
view → paper-builder modal → editor. Going through that flow on a brand
new paper threw:

```
[paper-editor] connect failed: TypeError: Cannot read properties of
undefined (reading 'insert')
    at appendSectionFromTree (paper-editor.js:352:34)
    at paper-editor.js:386:9
    at seedFromTemplate (paper-editor.js:382:21)
    at connectAndRender (paper-editor.js:242:7)
```

This crash is on the seed-from-template path that runs once, the first
time a new paper-builder paper is opened. The path:

1. `connectAndRender()` initializes `paperMap` with empty `sections`,
   `meta`, `equation_library`, etc.
2. `state.sectionsArr = paperMap.get('sections')` (a fresh Y.Array).
3. `seedFromTemplate()` opens a transact and pushes the template's
   starter sections via `appendSectionFromTree(state.sectionsArr, sec)`.
4. Inside `appendSectionFromTree`:

   ```js
   var m = new Y.Map();
   sectionsArr.push([m]);
   m.set('id', ...);
   m.set('kind', ...);
   m.set('label', new Y.Text(''));
   if (sec.label) m.get('label').insert(0, String(sec.label)); // ← undefined.insert
   ```

   `m.get('label')` returned `undefined`. Same pattern in
   `appendBlockFromTree` for `skeleton` / `body`, and same risk on
   `m.set('children', new Y.Array()); var children = m.get('children')`.

## Why

In Yjs 13, when `m` was just integrated within the same transact (via
`sectionsArr.push([m])`), the subsequent `m.set(key, yType)` integration
of a child Y.Text isn't guaranteed to be visible to a follow-up
`m.get(key)` *inside the same transact*. The comment block above the
function already acknowledged this attach-then-mutate requirement at the
Y.Map level — but the code still tried to round-trip Y.Text content via
get-after-set on a freshly-integrated parent. The init transact at
[rm/js/paper-editor.js:199](../../rm/js/paper-editor.js#L199) already
uses the correct pattern (`metaMap.set('title', new conn.Y.Text(initial))`),
which is why the title field doesn't blow up.

Pre-existing latent bug — it's been broken since V3.60 merge. V3.229's
one-click new-paper flow just made it routine to hit.

## Fix

Pass the initial string to the Y.Text constructor instead of doing
`set('', empty Y.Text)` followed by `get(...).insert(0, content)`. Same
fix on `appendBlockFromTree`'s `skeleton` and `body`. For the children
Y.Array, keep a local reference to the `new Y.Array()` instance rather
than calling `m.get('children')` immediately after `m.set('children', ...)`.

```js
m.set('label', new Y.Text(sec.label ? String(sec.label) : ''));
// ...
var childrenArr = new Y.Array();
m.set('children', childrenArr);
(sec.children || []).forEach(function (blk) {
  appendBlockFromTree(childrenArr, blk);
});
```

The Y.Text + Y.Array still become integrated when `.set` runs on the
already-integrated `m`; we just don't depend on the get-after-set
round-trip inside the same transact.

## Files modified

- [rm/js/paper-editor.js](../../rm/js/paper-editor.js) —
  `appendSectionFromTree` and `appendBlockFromTree` rewritten as above.
- [sw.js](../../sw.js) — `CACHE_VERSION` 198 → 199.

## Notes

- The same get-after-set risk exists on `attrs` (Y.Map) in
  `appendBlockFromTree` — fixed by holding the reference locally only if
  callers needed it. Today nothing reads it inside the same transact, so
  the existing `m.set('attrs', new Y.Map())` stays.
- This unblocks the V3.229 flow. The crash silently rolled back the
  transact, so any half-written `sections` were discarded — there's no
  data cleanup needed.
