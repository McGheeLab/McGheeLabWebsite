# V3.227 — Calendar ratings + category overrides: title/start_at sidecar so re-keying can't break ratings

## Goal

Prevent the V3.225 incident from recurring. On 2026-05-15 the user found
that the Calendar page's History tab showed no star ratings or category
overrides — even though Firestore still held 153 ratings + 201 overrides
+ 12 trash entries. The root cause was an event-id mismatch: the
`backfill_email_calendar_to_firestore.py` one-shot prefixed every legacy
event id with `archive-` when uploading to Firestore, while the bulk of
the user's ratings/overrides were stored under the raw 16-char hex id
the original `server.py` `/api/calendar/outlook-events` endpoint
emitted. The id-keyed join `by_event[event.id]` silently misses on
ID-format change, so all previously-rated events looked unrated.

The on-the-fly recovery (per V3.225 conversation) successfully remapped
146 of 153 ratings and 195 of 201 overrides by trying `archive-{id}` /
`{id}` prefix variations. But this only recovers from the specific
`archive-` prefix mismatch — any future event-id reshape (a different
backfill, a Google → ICS source switch, a Cloud Function id-generator
change) would silently break the join again.

## Approach

Add a `event_meta` sidecar map to the `ratings` and `categoryOverrides`
Firestore docs. For every event that gets rated or recategorized, also
record `{title, start_at}` under the same id key. At render time, if the
id-keyed lookup misses, fall back to matching by `(title, start_date)`
against the entries in `event_meta`. The fallback transparently
re-attaches a rating/override to whatever the event's current id happens
to be, **without rewriting the doc** (so no double-write storm on page
load).

The mismatch is silent today because the schema gives the renderer no
way to know "this rating belongs to *this* event" beyond the id itself.
Adding the sidecar gives the renderer a fingerprint that survives id
changes — much like a content-addressed key, but cheap and local.

## Schema additions

### `userData/{uid}/calendarArchive/ratings`

```jsonc
{
  "by_event": { "<id>": 4, ... },             // existing
  "by_sub_category": { "<sub>": 3, ... },     // existing
  "event_meta": {                              // NEW — V3.227
    "<id>": { "title": "Lab meeting", "start_at": "2026-01-15T15:00:00-07:00" }
  },
  "updatedAt": <timestamp>
}
```

### `userData/{uid}/calendarArchive/categoryOverrides`

```jsonc
{
  "overrides": { "<id>": { "category": "research", "sub_category": "tfm" }, ... },
  "event_meta": {                              // NEW — V3.227
    "<id>": { "title": "Lab meeting", "start_at": "2026-01-15T15:00:00-07:00" }
  },
  "updatedAt": <timestamp>
}
```

Backward-compatible: docs without `event_meta` continue to render via
the id-keyed direct path. Old ratings won't have the fallback until the
user re-saves them (or a one-shot migration backfills `event_meta` —
out of scope here).

## Key decisions

- **Render-time fallback, NOT auto-rewrite.** On a missed id lookup we
  return the meta-matched rating/override but do NOT rewrite the doc to
  the new id. Reason: a page-load auto-rewrite would (1) require write
  permission for read paths, (2) generate noise on every cold load even
  when nothing changed, and (3) make the doc churn in step with whatever
  the most recent sync was. Lazy migration via "user re-rates the event"
  catches the long tail; explicit migration is a one-shot script (per
  V3.225 recovery).
- **Reverse index is derived, not stored.** Rebuilt on load. Cheap
  (~hundreds of entries) and keeps the doc schema clean.
- **Signature is `title|YYYY-MM-DD`.** Coarse enough to absorb timezone
  differences in `start_at` (Google API emits `+00:00`, ICS emits
  `+TZID`, the old endpoint emitted naked ISO). Title is the dominant
  discriminator and is stable across the sources we use.
- **`event_meta` lives in both docs.** Duplicates `{title, start_at}`
  per id between ratings and overrides. Worth it — each doc stays
  self-contained, no cross-doc dependency on load order.
- **year-review.js not touched.** It also writes `ratings.by_event` and
  `overrides` via `loadOrEmpty` + `api.save`. Same fix applies but the
  write paths are 30+ lines away from the read paths in a more deeply
  nested helper structure. Calendar page is where the user actually
  rates events most of the time; year-review re-uses the same Firestore
  docs so old ratings still appear there via the id-keyed path. Follow
  up if needed.

  some others. Check Firestore Console at

  still works.
