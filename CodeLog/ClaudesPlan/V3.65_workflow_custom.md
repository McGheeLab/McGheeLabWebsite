# V3.65 — Workflow-driven UX redesign · PR 3: custom workflows + builder

## Goal

Final PR of the V3.63–V3.65 workflow redesign. Wires up the V3.64
placeholder buttons (`+ Add page`, `Save as custom`) and adds a My
Workflows section + builder on the chooser. After this release every
user can:

1. Enter a default workflow → page strip appears.
2. Add or remove pages from the strip → state persists in sessionStorage.
3. Save the modified workflow as a personal custom workflow.
4. Build a fresh custom workflow from scratch via the builder card.
5. Rename + delete custom workflows from the chooser.

## What ships

### Strip mutations in `nav.js`

Three new code paths added to the workflow strip (functions prefixed
`_wf*` to avoid colliding with `WorkflowState.*` which is loaded only
on the chooser):

- **`_wfRemovePage(pageId)` / `_wfAddPage(pageId)`** — sessionStorage
  mutations. Symmetric: removing a previously-added page un-adds (no
  negative-removed entry); re-adding a previously-removed page
  un-removes.
- **Page chip × button** — appended to each `.ws-page` chip in
  `renderWorkflowStrip()`. Click → `_wfRemovePage` →
  `_wfRefreshStrip()` (removes existing strip + renders fresh).
- **`+ Add page` modal (`_wfOpenAddPageModal`)** — picker of
  accessible pages NOT already in the workflow. Grouped by
  `NAV_ITEMS` section, sorted alphabetically. Search filter at top.
  Click row → `_wfAddPage` + close + refresh strip.
- **`Save as custom` (`_wfSaveCurrent`, `_wfOpenSaveAsModal`)** — when
  the workflow is dirty (`addedPageIds.length || removedPageIds.length`
  for a default workflow). Opens a name modal with
  `<workflow label> (mine)` pre-filled. Slugifies the name; writes
  `userData/{uid}/customWorkflows/{slug}` with the effective page
  list. Switches active state to `kind='custom', id=<slug>` so the
  strip continues to operate.
- **`Save changes`** (custom workflows when dirty) — direct save back
  to the existing custom doc; resets `addedPageIds`/`removedPageIds`.

### Chooser My Workflows section in `workflow-chooser.js`

Two new card types:

- **Custom workflow card** (`renderCustomCard`): same layout as
  default cards but with a left-border accent (`.wf-custom-card`)
  and Rename + Delete buttons in the header. Body click → enter
  workflow. Buttons stop propagation.
- **+ New custom workflow card** (`renderNewCustomCard`): dashed
  border, primary-tinted "+" icon. Click → opens the builder modal.

The builder modal (`openBuilder`):

- Name input
- Search filter
- Scrollable list of every accessible page, grouped by section, with
  a checkbox per page. Selection is order-preserving (Set insertion
  order).
- "Selected: N" counter
- Cancel / Create buttons
- On Create: slugify name → `userData/{uid}/customWorkflows/{slug}`
  doc → re-render chooser

Rename uses `prompt()` (simple). Delete uses `confirm()`.

### CSS additions in `rm/css/workflow.css`

- `.wf-card-actions` — header-row buttons cluster
- `.wf-custom-card` — left-border accent
- `.wf-new-card` — dashed border + primary-tinted icon (hover →
  solid)

## Untouched (intentionally)

- `firestore.rules` — `userData/{uid}/{document=**}` owner-only rule
  already covers `customWorkflows/*` reads + writes.
- `firestore.indexes.json` — no new queries; `customWorkflows` is
  read as a flat list (no orderBy or where).
- Cloud Functions — none affected.
- All existing RM page renderers — none modified. The strip is
  purely additive on every page that loads nav.js.

## Trade-offs

- **`prompt()` for rename** — quick path. A modal could ship in
  V3.66 if needed.
- **No undo on delete** — confirm dialog is the only safety net.
  Custom workflows are cheap to recreate, but a 24-hour soft-delete
  could be added later if users hit this.
- **Slug collisions** — if the user picks a name that slugifies to
  an existing custom workflow id, the create silently overwrites
  (we use `set()` not `set(..., { merge: false })`). For the rare
  collision case this is acceptable; the user can see an existing
  workflow already has the name and rename it first.
- **Strip size** — the strip can wrap to 2+ rows when the workflow
  has many pages. That's fine on desktop; on mobile (<700px) it
  could get tall. CSS uses flex-wrap; future enhancement could add
  a "More…" overflow menu.

- New Firestore paths: `labConfig/defaultWorkflows`, `userPermissions/{uid}`, `userData/{uid}/customWorkflows/*`.

- New helpers: `firebridge.canAccessPage`, `firebridge.loadAccessGrant`.
- New pages: `rm/pages/admin-permissions.html` (admin matrix), `rm/pages/lab-overview.html` (preserved V3.62 stats).
- Rewritten: `rm/index.html` is now a workflow chooser.
- `rm/js/nav.js`: 230 LOC → ~640 LOC. Workflow strip fork inlined into nav.js so every page that loads nav.js gets the strip without per-page edits.
- 5 default workflows seeded; users can create unlimited custom workflows under their account.
