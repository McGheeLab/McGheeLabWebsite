# V3.986 — Protocols on the lab website

## Goal

Alex, 2026-11-13, in three messages:

1. "On the mcgheelabwebsite under research i want a link to a protocols page where we can post our protocols for
   public use."
2. "Protocols should have ties to the research members in the lab. For example when we post a new protocol, it
   should have an option to select all those who helped make it. Then on the team page, lab members get an extra
   icon for protocols that they made."
3. "I want the protocols to be loaded in through rm, but on the public facing (non rm) research page, i want a
   protocols page. So users load in and tag meta data to protocols via rm, but we display these protocols via the
   main public facing website."

So: RM is where a protocol comes in (written, imported, tagged, summarised, credited, posted). The public site is
where it is shown. Nothing public is served from RM.

## What existed

- RM's Protocols builder (`rm/pages/protocols.html`, `rm/js/protocol*.js`): a status menu Draft / Published /
  Archived, tags and summary in the editor sidebar, an author byline, versions.
- `firestore.rules` since V3.113 let **anyone** read a protocol (and its version snapshots) whose status was
  `published` — the "Phase 5 public share" that was never built. No protocol had that status (checked anonymously
  against the live database: 0).
- The public Team page already had a protocols badge, counting `users/{uid}.protocols` — a list people typed into
  their own profile by hand (title + URL).

## Approach

### A copy, not the working doc

"Post to website" copies a snapshot, the way Research Foci publish to `publicFoci` (V3.553):

- `publicProtocols/{id}` — the card: title, summary, category, tags, `contributors [{uid, name}]`,
  `contributor_uids`, `byline`, version, step count, `created_at`, `published_at` (first posted), `updated_at`.
- `publicProtocols/{id}/content/current` — `{ tree }`, the document.

Two docs so the Protocols list and the Team page read the cards without downloading every protocol.

Why a copy: (1) the working doc is edited live (Yjs) — a visitor should read what was posted, not a half-typed
step; (2) the working doc carries lab-only things — the owner uid, forks, linked buckets, and **inventory links**.
In the copy a linked materials row becomes the item's label (name, vendor, catalog number, CAS) and an `[!inv:id]`
chip becomes the item's name; stock levels never leave the lab; an id the inventory no longer has reads `?`, as it
already does in the lab's own document view. Figure storage paths and block review status are dropped.

`status: 'published'` on the working doc now means exactly "on the lab website". The editor's status menu goes
through the posting dialog for both directions, so the two can't disagree.

### Rules

- `protocols/{id}` and `versions/` become lab-only whatever the status (the old public branch is removed — the
  public reads the copy).
- `publicProtocols/{id}` + `content/{docId}`: public read; create / update / delete by the protocol's owner or an
  admin (`get(protocols/{id}).ownerUid`); the card's `id` is pinned to its doc id. A non-admin cannot post a
  protocol that does not exist (the `get` of a missing doc denies). An admin can clear an orphaned copy.
- `scripts/tests/protocols-public-rules.test.mjs`: 38 cases, emulator, 0 HOLE / 0 BREAK. Added to `run-all.sh`.

### RM: `rm/js/protocol-publish.js` (new)

- `buildPublic` / `inspect` (pure apart from the inventory lookup), `publish`, `unpublish`, `removePublicCopy`.
- `attachEditor({...})` — the topbar button (**Post to website** → green **On website** → amber **Update website**
  once edited since) and the dialog: who helped make it (lab roster checkboxes, author first and ticked the first
  time, the last post's people ticked after; members with no display name are left out — a public page never falls
  back to an email), **How it will be listed** (title, summary, tags as a visitor will see them, with a warning when
  the summary or tags are empty), the inventory note, Remove from website, and the share address
  `https://mcgheelab.com/#/protocols/{id}`.
- Pending sidebar / tree edits are flushed before a post, and the debounced flush is cancelled, so the copy never
  trails the editor and a post doesn't immediately read as "edited since".
- Contributors are saved on the working doc too (`protocols/{id}.contributors`) so the next post remembers them.
- `protocols.js`: deleting a posted protocol takes the public copy down **first** (the rules check ownership on the
  working doc, so it must still exist), and a failure stops the delete.

### The public site

- `index.html`: **Protocols** under Research in the desktop menu, the phone sheet, the drawer, and the footer.
- `app.js`:
  - `#/protocols` — the list: search (appears once there are more than three, or more than one tag), up to 12 tag
    chips by use, cards (title, summary, "By …", tags, steps · updated). `?by={uid}` = one person's.
  - `#/protocols/{id}` — one protocol, as a page of the site (menus, back link, Print / PDF). The document is drawn
    by `protocol-view.html` in a frame that sizes itself to its content, so the page scrolls, not the frame.
  - Team page: a member's protocols are the posted ones they helped make (linked to the protocol) plus any they
    listed on their profile by hand (a hand-listed one with the same title as a posted one is dropped). With a
    posted protocol, the badge becomes a link to `#/protocols?by={uid}`.
- `user-system.js`: `DB.getPublicProtocols()`, `DB.getPublicProtocol(id)`.
- `protocol-view.html` + `protocol-view.js` (new, site root): loads the lab's own renderer (`protocol-schemas`,
  `-formulas`, `-graph`, `-widgets`, `-doc-render` from `/rm/js/`) and `protocol-doc.css`, no database, no sign-in;
  the site hands it `(card, tree)`. Calculators, builders and plate maps are live for visitors (nothing is saved).
  Ctrl/Cmd+P and the Print button print the sheet itself. Opened on its own it redirects to `/#/protocols/{id}`.

**Why a frame:** the protocol must look the way every lab protocol prints (`protocol-doc.css`, light, navy
masthead) on a dark site whose `styles.css` styles bare `h1`/`table`/`a`. A frame keeps each stylesheet out of the
other's way, and printing the frame prints just the document with correct pagination. Same pattern as
`#/data/{vizId}`.

**Shared renderer:** the document assembly (masthead, numbered sections, footer) moved from `protocol-doc.js` into
`ProtocolDocRender.renderDocument(docEl, {doc, tree, brand, ctx, metaBits?, footerText?})`, so the lab's doc view
and the public page are the same code. The public page passes `metaBits` (contributors, updated, version) instead of
the lab's author / created / version chips.

### Changed course mid-session

The first version put the public page in RM (`rm/pages/protocol-public.html`, like `library-public.html`). After
message 3 it moved to the public site; those two files were deleted before anything shipped.

## Deploy order

1. **Rules** — `firebase deploy --only firestore:rules`. Needed before anyone can post.
2. Site files — the end-of-turn auto-deploy.

Shipping the site before the rules is safe: the list shows "No protocols posted yet." (the database answers
permission-denied for an unknown collection, read as none), the Team page ignores the failed read, and Post to
website explains that the rules may not be live. No protocol has status `published`, so the delete flow never
needs the new collection until the rules are out.
