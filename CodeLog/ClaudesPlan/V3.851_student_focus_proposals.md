# V3.851 — Grad students propose a research focus; the PI or their advisor approves

**Date:** 2026-10-23
**Alex:** *"grad students should be able to add a focus by themselves, the PI or direct advisor should approve."*

## Goal

Any lab member can add a card to the research map (`rm/pages/research.html`) without waiting for the
PI. The card sits on the map marked **Proposed** until the PI (admin) or the proposer's direct advisor
(a uid in `users/{proposer}.mentor_uids` — the same relationship Team Focus, PMR and the grant review
already use) approves or declines it. Until then the proposer can keep editing it. The approvers are
told when a proposal lands; the proposer is told the decision.

## What was there

- `researchFoci/{id}` was `read: isLabMember(), write: isAdmin()` since V3.544 — "the PI authors all
  cards". Every authoring affordance in `research.js`, the composer, the links editor, the roadmap
  editor and the grant review keyed off `state.isAdmin`; `RESEARCH_DATA.create/update/remove` threw
  `Only the PI can edit research foci.` for anyone else.
- The weekly / semester focus loop (`userData/{uid}/focusAreas`) already had proposed → confirmed with
  mentor sign-off, so this request is specifically about the **map cards** those foci align to.
- Cross-user notification feed writes are owner-only by the `userData/{uid}/**` wildcard, so a
  proposal cannot notify the advisor from the browser (the class-notify / bme466-notify precedent).

## Approach

**One doc shape, one new field.** A proposal is an ordinary card with
`approval: { status: 'proposed' | 'approved' | 'declined', proposed_by, proposed_at, decided_by,
decided_at, note }`. A legacy card has no `approval` key and reads as **approved** — nothing is
backfilled, no renderer branches on a missing key. The proposer is auto-attached as a member
(`member_uids` + `member_roles[uid] = 'lead'`), so the card shows up under "Your foci".

**Rules (`firestore.rules`, deployed first).**
- create: admin, OR a lab member whose `created_by` and `approval.proposed_by` are their own uid, with
  `approval.status == 'proposed'` and `published == false`.
- update: admin, OR (card is `proposed`/`declined`, `created_by` unchanged, `published` stays false) AND
  either the proposer re-asserting `proposed` in their own name (edit, or re-propose after a decline —
  never a decision) or a mentor of the proposer (`isMentorOf(created_by)`) either editing while it is
  open or deciding `approved`/`declined` **in their own name** (`decided_by == request.auth.uid`,
  `proposed_by` unchanged).
- delete: admin, OR proposer / mentor while the card is `proposed`/`declined`.
- Once approved the card is admin-write, exactly like every card before this release.
- `resource.data.get('approval', {}).get('status', 'approved')` is resource-free for the legacy case
  so a non-admin write to a legacy card short-circuits to false before `isMentorOf` is reached.
- ★ Deployed from a scratch copy = LIVE ruleset + only this block, because the repo file carries two
  hunks that are not yet live and are not mine (the V3.806 `users` self-role guard and the V3.835
  inventory `use_mode` line). The repo file keeps all three.

**Client.**
- `research-data.js`: `approvalStatus / isProposed / isDeclined / isApproved / proposerOf`,
  `loadMentees()` (one `users where mentor_uids array-contains me` query, memoised; admins skip it),
  `mayEdit(card)`, `mayDecide(card)`, `canPropose()`. `create()` for a non-admin stamps the proposal
  shape itself (the rule's shape, so the only way a write fails is a real permission problem);
  `update()`/`remove()` for a non-admin fetch the card and check `mayEdit` for a clean error, and
  strip `published`. New `approve(card)`, `decline(card, note)`, `repropose(card)`.
- `research.js`: `state.all` (every card) vs `state.foci` (declined cards hidden from everyone but
  their proposer and admins); the status pill reads **Proposed** / **Declined** while a card is
  undecided; hub toolbar **＋ Propose a focus** and per-band **＋ Propose** for non-admin members;
  an **Awaiting your approval** strip for deciders with inline Approve / Decline (the decline note is
  a textarea in the row — no browser prompt); a **Your proposals** strip for the proposer; the detail
  page gets an approval banner (who proposed, when; Approve / Decline for deciders; Withdraw and —
  after a decline — Edit & re-propose for the proposer). `canEdit` becomes `RD.mayEdit(f)`; publish
  controls require admin AND approved.
- `research-composer.js`: title "Propose a new … card", button **Propose**, a one-line hint, and a
  **Builds on** parent picker in create mode (the most specific parent level that has cards; seeded
  links pre-checked) so a proposed aim names its grant and a proposed output names its aim without a
  second trip to the links editor.
- `research-publish.js` refuses to publish an unapproved card; `research-roadmap.js` /
  `roadmap-data.js` replace their admin-only roadmap guard (and a `window.alert`) with `mayEdit`;
  `research-grant-review.js` reads `pageState.canEditCard(grant)`.

**Notifications (`functions/research-foci-notify.js`, `onResearchFocusWritten`).** On the transition
into `proposed` (first time or re-proposed after a decline) → the proposer's `mentor_uids` ∪ every
admin, minus the proposer: *"Research focus proposed"*. Into `approved` / `declined` → the proposer,
with the decline note. `approval.notified_status` is stamped so a retried trigger never re-sends. The
transition logic is a pure function with node fixtures.

## Deliberately not done

- After approval the card is admin-write, as before. Letting the proposer keep editing an approved
  card is a one-clause change in the rule if Alex wants it.
- Proposed cards appear unmarked in the My Week / Team Focus / PMR alignment pickers (they are real
  cards a student may already plan against; a declined one leaves the week "Unattributed", the
  V3.715 behaviour).
- Any lab member may propose, not only grad students — the approval gate is the control.
