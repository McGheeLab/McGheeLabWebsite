# V3.243 — Mentor assignments on the permissions page

## Goal

Admin can designate one or more lab members as **mentors** for another lab
member. Mentors then gain the same cross-user PMR access an admin has when
viewing another student's PMR: read every block, post comments, assign
tasks — but cannot edit the mentee's barriers, weekly entries, or
projects (the existing `isReadOnlyView()` gate covers that).

Driven by: a grad student supervising a rotation student / undergrad
mentee should be able to read + comment on their mentee's PMR without
giving them blanket admin rights.

## Data model

One new field on the existing user profile:

```
users/{menteeUid}.mentor_uids: string[]   // UIDs that mentor this user
```

No new collection. No composite index — `mentor_uids array-contains <uid>`
is a single-field query.

## Approach

### Firestore rules

[firestore.rules](../../firestore.rules) gets one new helper plus two
clause extensions:

```
function isMentorOf(menteeUid) {
  return request.auth != null &&
    exists(/databases/$(database)/documents/users/$(menteeUid)) &&
    get(/databases/$(database)/documents/users/$(menteeUid))
      .data.get('mentor_uids', []).hasAny([request.auth.uid]);
}
```

Then in the PMR doc + comments match blocks, add `|| isMentorOf(userId)`
to the read/write (or read/create) conditions. One extra `get()` per
rule evaluation when a non-owner / non-admin user tries the path — costs
the same as the existing `researcher_uids` check.

### Admin permissions page

[rm/pages/admin-permissions.html](../../rm/pages/admin-permissions.html)
gets a 4th hub tab "Mentors". CSS for `.perm-mentor-row` /
`.perm-mentor-chip` / `.perm-mentor-add`. The existing tab-visibility
selectors get a parallel `tab-mentors` rule per `data-perm-tab` value.

[rm/js/admin-permissions.js](../../rm/js/admin-permissions.js):

- `loadUsers()` extends to capture each user's `mentor_uids` into
  `initialState.mentor` + `mentorAssignments` (Map<menteeUid, Set<mentorUid>>).
- `renderMentorList()` renders one row per non-admin user, showing
  current mentor chips + an "Add mentor" select. Rows changed since
  load get the `is-changed` amber tint.
- `onMentorAdd` / `onMentorRemove` mutate the in-memory map and
  recompute a single pending edit per mentee (`pendingEdits` key
  `mentor:<menteeUid>`).
- `saveAll` adds a section that batches one `.set(..., merge:true)` per
  changed mentee, writing `users/{menteeUid}.mentor_uids` + `updatedAt`.
- `revertAll` restores `mentorAssignments` from `initialState.mentor`
  and re-renders.
- `applySearchFilter` extends to filter mentor rows on the mentors tab.

### PMR page

[rm/js/pmr.js](../../rm/js/pmr.js):

- New `state.menteeUids: Set<uid>`, populated at boot via
  `users where mentor_uids array-contains <my uid>`. Single read.
- `loadMyMentees()` runs in the boot `Promise.all` for non-admins; admins
  skip (they see everyone anyway).
- `canViewUid(uid)` → true if self, admin, or uid in menteeUids.
- `renderRail()` extends: render the rail if the user is admin OR has
  ≥1 mentee. Non-admin mentor view filters labMembers to self + mentees
  only. Heading label becomes "Mentees" in mentor mode.
- `switchToUser()`'s defensive bounce-to-self uses `canViewUid()`
  instead of the old `!isAdmin && uid !== me` check.

The existing `isReadOnlyView()` (returns true whenever `viewAsUid !==
me`) automatically applies to mentors — they get the same gated UX
admins do today.

## Deploy

1. `firebase deploy --only firestore:rules` from the repo root to ship
   the new `isMentorOf()` helper + rule extensions. Without this, admin
   can save assignments but mentors won't actually be able to read
   their mentees' PMR docs.
2. Cyberduck-FTP the repo so the updated `rm/` + `sw.js` land on godaddy.

## Open questions / non-goals

- **Mentor → tasks/buckets/etc**: this version only opens PMR access.
  Mentor doesn't get to see the mentee's tasks queue, lab notebook,
  etc. — those collections stay owner-only / admin-only. If we want
  mentor access to those, it's a follow-up plan.
- **UI affordance for mentees to see who their mentors are**: no
  surface for that yet. The mentee doesn't see anything change in their
  PMR; the mentor just shows up as a new commenter when they engage.
  Could add a `Mentors: Alex, Suraj` chip in the PMR header in a
  follow-up.
- **Notifications**: a mentor doesn't get pinged when their mentee
  updates the PMR. Follow-up if needed.
