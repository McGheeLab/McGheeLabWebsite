# V3.729 — Permissions: category pills + "Create papers" grant

## Goal

Two admin-permissions asks from Alex (2026-09-03):

1. **Users × Pages and Per-user tabs:** quick pills at the top of the page to
   filter the list by *grad student / undergrad / high school / guest*.
2. **Per-user → Papers section:** a per-user permission to **create a paper**.

## Findings that shaped the design

- `users/{uid}` carries two axes: `role` (admin/editor/contributor/guest —
  the RM access gate) and `category` (pi/postdoc/grad/masters/undergrad/
  highschool/alumni/teacher/student/guest — from `user-system.js`
  `CATEGORIES`). The pills Alex named are the **category** axis; the page
  today only groups by `role`, so a category filter is new information.
- Firestore already lets any lab member create a paper row
  (`projects` create: `isLabMember() && type=='paper' && lead_author_uid ==
  uid`). But `paper-builder.js createPaper()` does a **full-collection**
  `api.save('projects/papers.json')` — the adapter re-`set`s every existing
  row with a fresh `updatedAt`, and the update rule denies rows the caller
  doesn't own, so the whole batch fails for non-admins. The bundle-import
  path (`db.collection('projects').doc(slug).set(row)`) writes one doc and
  works. So in practice only admins can press "+ New paper" today.
- The per-user capability system (V3.605: `userPermissions/{uid}.caps`,
  `hasCap()` in rules, `CAPABILITY_REGISTRY` in the admin UI) is the right
  primitive for "grant this user the power to create papers" — and a cap on
  the `paper-builder` page slug already suppresses the guest overlay and
  opens the page (`canAccessPage` → `hasAnyCapabilityFor(slug)`).
- The paper subcollections (`blocks`, `yjs_updates`, `comments`, …) gate on
  `isPaperAuthor()` (materialized `authorUids`), not `isLabMember()`, so a
  guest who owns a paper can actually edit it once the row exists.

## Approach

### 1. Category pills (admin-permissions.html + admin-permissions.js)

- A pill strip in the shared toolbar (visible on the `users` and `user`
  tabs only): **All · Grad students · Undergrads · High school · Guests**,
  each with a live count.
- Matching is by `category`, with `grad` = `grad` ∪ `masters`, and
  `guest` = `category === 'guest' || role === 'guest'` (a high-school
  student still on a guest role matches both — that's correct).
- The filter composes with the existing text search: `applySearchFilter`
  (matrix, group-aware) and `filterUserRail` (per-user rail) both consult
  `_userMatchesCategory(u)` via the row's `data-uid`.

### 2. "Create papers" capability

- `capability-registry.js`: new page entry `paper-builder` with one cap
  `paper-builder:create` ("Create papers"), flagged `section: 'papers'` so
  the generic Capabilities section skips it and the **Papers** section
  renders it as its first row.
- `admin-permissions.js renderUserPapersInto`: a checkbox row wired through
  the existing `_setCapEdit` / `pendingEdits` / `saveAll` pipeline (no new
  save path). Hint text says what it does for whom. Derived actions gain a
  "Can create papers" line (implicit for lab members, granted for cap
  holders).
- `firestore.rules /projects`: `read` also allows
  `hasCap('paper-builder:create') && resource.data.type == 'paper'`
  (provable from the list query's `where type=='paper'`); `create` accepts
  `(isLabMember() || hasCap('paper-builder:create'))` in place of
  `isLabMember()`. Update/delete unchanged (owner-by-uid already).
- `paper-builder.js`:
  - `createPaper()` writes **one** `projects/{id}` doc (`type:'paper'`
    stamped, as the import path does) + `api.invalidate` — this is what
    makes the button work for non-admins at all.
  - "+ New paper" / "Import paper" buttons are shown only when
    `isLabMember() || hasCapability('paper-builder:create')`; a guest
    without the grant sees the list (empty for them) and no create button.

## Files

- `rm/pages/admin-permissions.html` — pill strip + CSS
- `rm/js/admin-permissions.js` — category filter, Papers-section create row,
  derived line
- `rm/js/capability-registry.js` — `paper-builder:create`
- `firestore.rules` — `/projects` read + create clauses
- `rm/js/paper-builder.js` — single-doc create, button gating

## Deploy

`firebase deploy --only firestore:rules` **before** FTP (a granted guest
would otherwise hit permission-denied on the list read). No indexes or
functions change. FTP batched per the release ledger.

## Not done here (flagged)

`paper-editor.js` title/status sync, `research-create.js`, and
`outputs-manager.js` still use the full-collection `api.save` on
`projects/papers.json`, which fails for non-admins whenever another
person's paper exists. Fixing that belongs in the adapter (skip unchanged
rows) or in each call site (single-doc merge) — separate change.
