# V3.792 — "Request a class" lists only published module sets

**Date:** 2026-09-30
**Reported by Alex:** "When I click on the For teachers button in the classes
page, it takes me to a page to request access, and on this page are all the
'Module sets you're interested in'. The problem is that this is showing all of
the modules even the ones that I have not marked as available."

## Goal

The `#/teachers` request form (`loadTeachersRequestCard` in `teacher-teach.js`)
should offer the same set of courses an approved teacher sees in the Modules
tab: the `teacherCatalog` rows the admin has ticked as `published`.

## What was wrong

The form built its checkbox list from `ML.tcManifestFolders()`, which is
`modules/manifest.json` — every folder on disk, with a module count of every
file in the folder. The Modules tab (`renderModulesTab`) reads
`src().publishedCatalog()` (`teacherCatalog where published == true`) and groups
by folder, so the two surfaces disagreed. In production on 2026-09-30 the
manifest had 12 folders and the published catalog covered 4 of them (Cell
Culture Foundations, Heat Transfer, Solid Mechanics Foundations, TFM).

## Approach

- New pure helper `requestFolderOptions(folders, catalog)` in `teacher-teach.js`
  → `[{ key, label, count }]`, sorted by label:
  - counts published catalog rows per folder (`published === false` rows are
    skipped defensively, though `publishedCatalog()` already filters);
  - drops folders the manifest no longer knows (stale catalog docs) — unless the
    manifest failed to load, in which case the catalog keys stand in as labels;
  - the count is *published* modules, not files on disk.
- `loadTeachersRequestCard` fetches `src().publishedCatalog()` alongside the
  manifest and the teacher's requests (all three in one `Promise.all`, each
  with its own `catch`). A catalog read failure hides the checkbox block rather
  than falling back to the manifest, so a failure can never re-show unpublished
  courses. The form still submits without it.
- Exposed as `ML.tcRequestFolderOptions` so the filtering can be asserted in
  node without a browser (the demo world publishes every module, so a headless
  run alone cannot prove the filter).
- `requestedFolders` written on the request is unchanged (folder keys), so the
  admin tab needs nothing.

## Rules

`teacherCatalog` read is already `request.auth != null`, and the request card
only renders for a signed-in user, so a not-yet-approved applicant can run the
same query the Modules tab runs. No rules change, no deploy.
