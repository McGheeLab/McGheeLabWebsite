# V3.674–675 — BME466 homework cloud-save (hwProgress), usage dashboard, class roster

Date: 2026-08-27 · Pilot vehicle: the HW0 pretest module
(`modules/bme466/hw-00-pretest.html`, authored in the course repo's
`local-test/`, synced here for FTP deploy).

## What shipped

1. **`hwProgress/{assignment}_{uid}`** — new Firestore collection. Students
   sign in with their UA NetID (the existing Google provider; UA is Google
   Workspace on arizona.edu) inside a homework module, and the module's
   `ML-CLOUD-SAVE v1` block autosaves their in-progress work (answers, time
   on page — never a grade) to their own doc. In the HW0 pilot the sign-in
   also **assigns the dataset** — seeded from the NetID (email local part);
   there is no course ID in HW0 at all. (`sid_norm`/`code` on the doc record
   that NetID-derived seed for cross-referencing the D2L export.)
   - Rules block in `firestore.rules` (after moduleStats): own-doc
     get/create/update; writes require `email == request.auth.token.email`
     matching `.*@arizona[.]edu`; field whitelist incl. dashboard summary
     fields (`answeredCount,totalQuestions,runCount,secondsActive,
     lastActiveAt`); assignment enum `bme466-pretest|posttest|hw1..hw7`;
     `state` string < 900k; `updatedAt == request.time`; list/delete only
     `isAdmin() || bme466ClassAdmin()` (new helper: email in
     `schedules/bme466.classAdminEmails`).
   - Emulator test `scripts/tests/hw-progress-rules.test.mjs` (25 checks,
     all green; teacher-rules 84 + inventory-rules 49 rerun clean).
     Registered in `run-all.sh` layer 4.
2. **BME466 usage dashboard** — new admin-only `Dashboard` tab on
   `#/classes/bme466` (section key `hwDash466` in class-builder.js), NOT a
   `kind:'teacher-class'` conversion (that would replace the class page and
   require sign-in for everyone). Assignment dropdown → `hwProgress`
   where('assignment','==',…) → per-student rows (name/email, dataset code,
   progress bar, active minutes, last active) + stat cards + CSV export.
   Reuses `.cb295-dash-*` and `.teach-eng-bar` CSS. V3.674 migrations append
   the tab and the published pretest module row to an already-seeded bme466
   schedule doc on the next admin visit.
   **Pre-release testing** (instructor directive): the dashboard's
   "Test an assignment" card lists every module on the schedule doc with its
   release status and an "Open & test" button that opens the raw file
   (unpublished only hides the listing, not the file), optionally appending
   `?ds=<netid>` from the card's input to preview a student's seeded numbers —
   the module honors `?ds` through a class-admin sign-in (it checks
   `schedules/bme466.classAdminEmails`; previews can't export or cloud-save).
   Staff's own signed-in runs are tagged **STAFF TEST** in the progress table,
   and every row has a 🗑 delete (rules: admin/classAdmin) for cleanup.
3. **Module registration**: `modules/bme466/hw-00-pretest.html` +
   `modules/manifest.json` (regenerated via `scripts/scan_modules.py` —
   note it also picked up `02-gradients-and-encounters.html`, which was on
   disk but previously unlisted).

## V3.675 — class roster: invite by CSV, add/drop, assign TAs

Instructor directives: *"invite a csv file of students"*, *"add or drop students
afterwards individually"*, *"assign a user to be a TA"* (this term's TA is a lab
member, but *"this wont always be the case"* — so TA-ness is per-class, not lab
membership).

- **`schedules/{scheduleId}/roster/{email}`** (new subcollection, doc id = the
  LOWERCASED email so rules can `exists()` on `request.auth.token.email`).
  Fields: `name, email, netid, role ('student'|'ta'), source ('csv'|'manual'),
  addedAt`. FERPA: the parent `schedules` doc is world-readable, so the roster
  deliberately lives in a subcollection whose rules grant read/write ONLY to
  `isAdmin()` or the schedule's `classAdminEmails` — students never read it.
- **Roster is access control, opt-in so it can't lock a class out.**
  `hwProgress` create/update now also requires roster membership — but only
  once `schedules/bme466.rosterEnforced == true`. The dashboard's first CSV
  import sets that flag (and a "Turn off"/"Turn on" toggle in the roster card
  flips it). While the flag is absent/false the rule is exactly the pre-roster
  behavior (any `@arizona.edu` may save), which is what keeps a
  not-yet-imported roster from blocking every student the moment the rules
  deploy. Dropping a student revokes their cloud-save immediately; their
  existing progress docs and exported files are untouched.
- **TA assignment** = adding the address to `schedules/bme466.classAdminEmails`
  (the existing staff gate: this dashboard, the roster, `hwProgress`
  list/delete, module staff previews). Works for any `@arizona.edu` account,
  lab member or not — Gabriel (`gabrieldeclercq@arizona.edu`) is a lab member
  this term, but nothing depends on that. The roster row's `role` field is
  just the label; `classAdminEmails` is the authority. Dropping a staff member
  removes their TA access first, then the roster row.
- **Dashboard roster card** (`class-builder.js`): "Import D2L classlist (CSV)"
  (hidden file input behind a real `<button>` so it styles like its siblings),
  Refresh, add-one (name + `netid@arizona.edu`, validated + lowercased),
  Make TA field, per-row **Make TA / Remove TA** and **Drop**, counts, an
  enforcement row, and a note listing any staff not on the roster (their
  access comes from `classAdminEmails`, so that is informational). The
  progress card gained a **"N invited student(s) have not started"** line —
  the roster supplies the denominator the dashboard otherwise can't know.
- **CSV parsing** is a self-contained `hw466ParseCSV` (quoted fields, embedded
  commas, CRLF, BOM) + a D2L mapping: only `Role == Student` rows, `"Last,
  First"` → `"First Last"`, email lowercased as the doc id, writes batched
  (400/commit) with `merge: true` so re-importing updates instead of
  duplicating and never auto-drops. Verified against the real FA26 export
  (51 rows → 50 students, the Instructor row skipped, all unique).
- **Tests:** `hw-progress-rules.test.mjs` now 39 cases (roster read/write
  gating, student self-add denied, the opt-in flag off→on→off transitions,
  non-arizona.edu still denied with the flag off, who may flip the flag);
  teacher-rules 84 and inventory-rules 49 rerun clean. The render + wire path
  was exercised in a node harness and a real DOM (extracted verbatim from
  `class-builder.js`, since its internals sit inside an IIFE) with production
  CSS and screenshots.

## Client contract (for HW1..HW7 adoption)

Copy the `/* ═══ ML-CLOUD-SAVE v1 ═══ */` block from the pretest module, set
`CLOUD_CFG.assignment`, add the 3 gstatic compat-SDK script tags (10.14.0 —
same pins as index.html) and the 4 hooks: `Cloud.init()` on window load,
`Cloud.onDataset(norm)` in setDataset, `Cloud.onLocalSave()` in saveLocal,
`Cloud.flush()` in exportResults. Fails soft to localStorage-only when the
SDK is unreachable (file://, offline) or the student doesn't sign in.
Conflict policy: newer `clientSavedAt` wins; confirm() only when the cloud
copy is newer than local work.

## Deploy

- `firebase deploy --only firestore:rules`  (rules can land before the FTP —
  the roster gate is opt-in, so deploying rules before any roster exists
  changes nothing for students)
- Cyberduck FTP: `modules/bme466/hw-00-pretest.html`, `modules/manifest.json`,
  `class-builder.js`
- No Firebase console changes (Google provider already enabled).
- Then, in the browser at `#/classes/bme466` → **Dashboard**: import the D2L
  classlist (that also switches on roster enforcement), and Make TA for
  `gabrieldeclercq@arizona.edu`.

## Rollback

Independent levers: re-FTP previous class-builder.js/module · delete the
V3.674 rules block + redeploy (modules fail soft to localStorage/export) ·
admin-delete the hwProgress collection. Nothing else references hwProgress.
For the roster specifically: set `rosterEnforced: false` (the card's "Turn
off") to drop back to "any @arizona.edu may save" without touching rules or
deleting anybody; the `roster` subcollection can then be deleted at leisure.
