# Plan — ELN Protocol Calculator (V3.135)

## Context

The Protocols Builder has a working formula scaffold (V3.117): each
`formula` block on a protocol carries `variables[]` (typed inputs with
labels + units + defaults) and an `output` (a computed value resolved
by mathjs against the running symbol table — chained, so a later
formula sees an earlier formula's output). [rm/js/protocol-formulas.js](rm/js/protocol-formulas.js)
exposes the entire scaffold as `window.ProtocolFormulas.{ ensureMathjs,
collectFormulas, buildSymbolTable, renderTextWithTokens, formatSymbolValue,
textHasTokens }`. Step / note / safety / figure-caption block bodies
already render `[!var:name]` tokens through the same scaffold.

**The user ask**: when a notebook entry references a protocol, treat
that protocol AS A CALCULATOR. Inputs (booleans, unitless numbers,
numbers with units) are the protocol's variable scope; outputs are
the protocol's formula outputs. The result inserts into the body as
either (a) **steps with values substituted** — the canonical use, e.g.
"Weigh **56.25 g** NaCl"; (b) a **snippet** for users who already
know the protocol; or (c) a **table** for paste-into-thesis.

**The architectural constraint** the user explicitly added: the
calculator is *protocol-driven*. Lab notebook reuses the protocol's
existing scaffold instead of duplicating it. No new schema in the
protocol; the lab notebook just calls into `protocol-formulas.js`.

The user also chose: calc reachable from **both** the protocol picker
(third sub-action alongside "ref only") and the V3.116
Protocols-followed panel (per-row `🧮 calc` button); inserts are
**editable** (clicking the inserted block re-opens the calc pre-filled
with previous inputs); default format is **steps**.

### Schema additions (entry doc)

```js
state.doc.calc_runs = [{
  id: 'calc-' + ts36 + '-' + nonce,    // matches data-calc-id on the inserted block
  protocol_id: '<protocol id>',
  protocol_title: '<snapshot at insert time>',
  inputs: {                            // user-provided values (per variable name)
    targetVol: { value: 250, unit: 'mL' },
    use_pH_buffer: { value: true },
    ...
  },
  outputs: {                           // computed at the same compute pass
    nacl_mass: { value: 56.25, unit: 'g', label: 'NaCl mass' },
    kcl_mass:  { value: 1.25,  unit: 'g', label: 'KCl mass' },
    ...
  },
  format: 'steps' | 'snippet' | 'table',
  created_at: ISO,
  updated_at: ISO,
}]
```

`notebookHydrate()` defensively coerces `calc_runs` to `[]` on load.
`notebookIndexRow()` projects `calc_count: entry.calc_runs.length` so the
rail can show a `🧮 N` count alongside `📎 / 🧪 / 📋` (analogous to V3.114
inventory + V3.116 protocol counts).

### The calculator modal

Built fresh on every open (no DOM caching) so re-opening on a different
protocol always reflects the current scaffold. Reuses the V3.118
`.ln-modal-back` / `.ln-modal-{head,body,foot}` chrome.

```
┌─ Calculator · 5x PBS prep ──────────────────────[×]┐
│                                                    │
│ Inputs                                             │
│  targetVol   [_____] mL    (target volume)        │
│  use_buffer  [✓]            (include buffer)      │
│  pH_target   [_____]        (pH)                  │
│                                                    │
│              [▶ Compute]                           │
│                                                    │
│ Outputs                                            │
│  NaCl mass    56.25 g                              │
│  KCl mass     1.25 g                               │
│  buffer_vol   12.50 mL                             │
│                                                    │
│ Output format                                      │
│  ◉ Steps    ○ Snippet    ○ Table                  │
│                                                    │
│  Cancel                            Insert into entry │
└────────────────────────────────────────────────────┘
```

**Input row types** are inferred from the variable's metadata:

- `unit` populated → numeric input + unit suffix
- `default` is `true` / `false` → checkbox
- otherwise → text input (treated numeric if it parses)

The `Compute` button re-runs `ProtocolFormulas.buildSymbolTable(formulas, math)`
with the user's inputs merged over defaults. Output rows refresh; if any
formula throws, the relevant output row shows `⚠ <error message>` instead
of a value.

### Three render formats

All three render into a `<div class="ln-calc" data-calc-id="..." data-calc-protocol-id="..." data-calc-format="..." contenteditable="false">…</div>` container. The container is a non-editable atom — clicking anywhere inside it re-opens the calc modal pre-filled with the saved `calc_run.inputs`.

1. **Steps** *(default)* — walk the protocol tree (already loaded by V3.134's `_loadProtocolTree`), call `ProtocolFormulas.renderTextWithTokens(block.body, symbolTable)` on each step / note / safety / materials body. Materials rows with `[!var:name]` tokens in their `qty` field substitute too. Result is a sequence of `<p>` / `<blockquote>` / `<ul>` with values inlined where tokens were.

2. **Snippet** — one-line summary `<strong>Protocol</strong> @ inputs → outputs`. Compact; for users who already know the protocol.

3. **Table** — HTML `<table class="ln-calc-table">` with rows `[var label, value, unit]`. Inputs first (with a header row), outputs after a divider.

A small `<span class="ln-calc-edit-hint">click to re-edit</span>` floats top-right of the container on hover so the editable affordance is discoverable.

### Sanitizer extensions

The body sanitizer's class-name allowlist (V3.114, V3.121) is extended for two cases:

1. **DIV** — currently allowed-tag with no attr allowlist; extend `ALLOWED_ATTRS.DIV = ['class', 'data-calc-id', 'data-calc-protocol-id', 'data-calc-format', 'contenteditable']`. Class restricted to the literal `ln-calc` (with optional `ln-calc-{snippet,table,steps}` modifier — `^ln-calc( ln-calc-(snippet|table|steps))?$`). Force `contenteditable=false` on `ln-calc` containers.
2. **SPAN** — extend the existing allowlist regex to also accept `proto-var(\s+proto-var-(computed|unknown|error))?`. Plus allow `data-var` and `title` attributes on these spans (plain values, no URL safety risk).

Without the sanitizer extensions the chips would survive insert but lose their class on the next save round-trip and degrade to plain spans on reload.

### Click-to-re-edit flow

The body sanitizer keeps `<div class="ln-calc" data-calc-id="...">…</div>` as a single non-editable atom. The pane-level click delegator gets a new branch:

```
pane.click → if target.closest('.ln-calc'):
  calcId = target.closest('.ln-calc').getAttribute('data-calc-id')
  run = state.doc.calc_runs.find(r => r.id === calcId)
  if (run) openProtocolCalculator(run.protocol_id, { editingCalcId: calcId })
```

When the modal is opened with `editingCalcId`, it pre-fills inputs from `run.inputs` and the format radio from `run.format`. On Insert:

- Re-render the chosen format as HTML
- Find the existing `<div class="ln-calc" data-calc-id="...">` in the body
- Replace its content (preserving the same data-calc-id)
- Update `calc_runs[i].inputs / outputs / format / updated_at`
- `scheduleSave()`

If the existing div is missing (user manually deleted the rendered block), insert at the caret as a fresh block.

## Phase 3 (queued, deferred — separate plan when picked up)

> **The plan→execute→complete bench workflow.** A new top-level field `phase: 'plan' | 'running' | 'complete'` on the entry doc, defaulting to `'plan'` for new entries (legacy entries silently default to `'complete'`). One-button pivot from "I'm planning at my desk" to "I'm at the bench, recording actuals." In running mode: each Materials chip's planned qty pairs with an actual-qty + actual-lot input (default ✓ "same as planned"); each protocol gets a "✓ followed as written" + a deviations log; each DOE run gets per-output recording cards + per-run notes; a chronological Observations log with sticky photo + observation FABs; voice-memo per observation. End-of-run drops a plan-vs-actual diff + summary textarea + `↻ Spawn next iteration` that pre-fills tomorrow's entry from today's design + summary. Schema additions: `phase`, `run_started_at`, `run_ended_at`, `summary`, `derived_from`, `observations[]`; per-chip `planned_qty / actual_qty / actual_lot / same_as_planned`; per-protocol `followed_as_written / deviations[]`; per-DOE-run `actuals: {started_at, ended_at, outputs, notes, attachment_paths}`. Mobile-optimised (big tap targets, sticky FABs). Templates (cell culture day / microscopy / bioprinting / reagent prep / DOE screening) prefill the planned skeleton.

This is a sizeable feature on its own. Current plan: ship V3.135 calculator first (it's a tool-use feature, fits cleanly into today's notebook), then come back to Phase 3.

## Beyond Phase 3 — additional features (ranked, ship as needs surface)

1. **Inline calculators** for ad-hoc math (molarity / dilution / pH / unit conversion) — these are *not* protocol-driven (V3.135's scope is the protocol's formula scaffold). A general-purpose calc could share the same `<div class="ln-calc">` container with a different format kind.
2. **Lot number + expiry on chemical chip** — at picker insert time, prompt for lot/expiry, store on `inventory_refs[i]`. Provides forensic traceability.
3. **Templates** — cell culture day / microscopy / bioprinting / reagent prep. Pairs with Phase 3 to prefill the planned skeleton.
4. **Timer / stopwatch widgets** — embed countdown timers in the body. Pairs with Phase 3 recording mode.
5. **CSV / data import → inline preview** — paste a CSV, get a sortable table + small auto-chart.
6. **Sample lineage tree** — render `derived_from: [entryId]` chain as a graph.
7. **Equipment booking shortcut** — link a calendar booking from `/rm/pages/scheduler.html`.
8. **Barcode / QR scan** — phone camera → auto-fill inventory chip. Pairs with Phase 3 bench workflow.
9. **Failed-experiment archive view** — filter by `phase === 'complete'` AND `summary contains "fail"`.
10. **AI summarize last N entries on Project X** — Anthropic API; lab already has the auth path.
11. **Pre-registration / hypothesis lock** — soft-locked plan section, hard locks on opt-in.
