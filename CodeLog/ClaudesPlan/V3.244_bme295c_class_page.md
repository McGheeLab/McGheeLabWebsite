# V3.244 — BME 295C class page

## Goal

Build the public class page for **BME 295C — Challenges in Biomedical
Engineering** (Summer 2026, one-week summer course for rising high-school
juniors/seniors at UA Tucson + UA Phoenix campuses, June 8–12 2026).
The page must:

1. Reuse the existing tab/section class-builder infrastructure at
   `#/classes/bme295c` (no new top-level route).
2. Surface three tabs: **Syllabus**, **Schedule**, **Learning Modules**.
3. Let pre-registered students sign in with the email they used to
   register for the course, edit a short bio + BME-interest note +
   profile photo, and see their pre-assigned discussion group.
4. Let the admin assign students to a campus + group number from an
   in-page admin table (auto-assign in groups of 3–4 with a button).

## Approach

**Reuse, don't replace.** Extend [`class-builder.js`](../../class-builder.js)
with five new class-specific section component types instead of writing a
separate static page. Tab/section persistence, autosave, and the public-
read-admin-write Firestore rules are already wired up for `schedules/{id}`.

Content split:

- **Static** (in-repo) — syllabus copy, speakers + abstracts, discussion
  points, photos. Single source of truth at
  [`modules/bme295c/content.json`](../../modules/bme295c/content.json),
  hand-derived from the source markdowns (`Speaker_details.md`,
  `discussion_points.md`, the Summer 2026 syllabus markdown).
  Photos live at `modules/bme295c/speaker-photos/<First_Last>.{jpg,png,webp}`
  (folder renamed from `speaker photos` to drop the space in URLs).
- **Dynamic** (Firestore `schedules/bme295c`) — pre-seeded 20-student
  roster + admin-edited email/campus/groupNumber per student.
- **Per-student** (Firestore `users/{uid}.bme295c`) — bio, interest,
  photoUrl. Student writes own user doc (existing rule), no new
  collection.

### New `SECTION_REG` entries

```js
checkin295c:   { label: 'Student Check-in (BME 295C)',     component: 'checkin295c' },
syllabus295c:  { label: 'Syllabus (BME 295C)',             component: 'syllabus295c' },
schedule295c:  { label: 'Speaker Schedule (BME 295C)',     component: 'schedule295c' },
modules295c:   { label: 'Discussion Modules (BME 295C)',   component: 'modules295c' },
roster295c:    { label: 'Student Roster (BME 295C, admin)', component: 'roster295c' }
```

These are deliberately class-specific (hard-coded against the bme295c
content.json). If a future cohort needs a similar page, generalize then.

### Tab layout (seeded into `DEFAULT_SCHEDULES['bme295c']`)

| Tab              | Sections                                              |
|------------------|-------------------------------------------------------|
| Syllabus         | `checkin295c` (top), `syllabus295c`                   |
| Schedule         | `schedule295c`                                        |
| Learning Modules | `modules295c`, `roster295c` (admin-only, hidden)      |

`buildSectionBlockHTML` returns empty string for `roster295c` when the
viewer is not admin, so non-admin students never see the section frame.

### Auth & gating

- Tabs themselves are public.
- Tab 1's Check-in card renders three states based on the email join:
  signed out → Google sign-in CTA; signed in + roster match → preallocated
  info + editable bio/interest/photo form; signed in + no match → "contact
  the instructor" notice.
- Tab 3's per-speaker discussion cards always show prompts; the "Your
  group" chip resolves only when the signed-in user's email matches a
  roster entry that has a campus + group assigned.
- No invitation tokens, no new role, no per-cohort Firestore collection.

### Group auto-assign

`autoAssignBme295cGroups()` shuffles each campus pool (Fisher-Yates) and
picks the group count via `Math.round(n / 3.5)` so groups are 3–4 students.
Always-editable — no lock state. Stored as `roster[i].groupNumber`.

### Photo upload + storage rule

- Path: `class-profile-photos/bme295c/{uid}/photo.{ext}`.
- New [`storage.rules`](../../storage.rules) entry restricts writes so
  `request.auth.uid == {userId}` — students can only overwrite their own
  photo. 5 MB cap, image MIME only. Reads public.

### One-time migration

If a pre-V3.244 `schedules/bme295c` doc exists from earlier admin testing
(old `sections: ['overview','speakers','files']` shape), `wireClassPage`
detects the missing `checkin295c` section in `schedule.tabs` and on the
next admin visit overlays the doc with the new layout — preserving
`ownerUid` and any populated `studentRoster`.

## Out of scope

- Per-student invitation tokens (admin emails the URL; email-in-roster
  match gates the chip).
- Photo cropping/resize on the client (upload-as-is; browser scales).
- Lab-tour mini-grid as a separate component (handled inline in Tab 2).
- Recording uploads / post-course Q&A.

## Verification

1. `python3 -m http.server 8000` → open `http://localhost:8000/#/classes/bme295c`.
2. Public visit (signed out): three tabs render from `DEFAULT_SCHEDULES`
   fallback; Tab 1 shows Sign-in CTA; Tab 2 shows day grid + speaker
   lineup with photos; Tab 3 shows expandable discussion cards.
3. Admin sign-in: triggers DEFAULT_SCHEDULES write to Firestore; roster
   section shows under Learning Modules tab. Fill in a few emails + click
   Auto-assign — groups populate.
4. Student sign-in (non-admin Google account whose email is in roster):
   Check-in card shows preallocated info + editable bio/interest; photo
   uploads to Storage; Tab 3 group chip shows correct group # and
   groupmates.
5. Mobile width (375 px): grids wrap, roster scrolls horizontally,
   check-in card stacks.
6. Deploy: Cyberduck FTP to godaddy + `firebase deploy --only storage:rules`.
