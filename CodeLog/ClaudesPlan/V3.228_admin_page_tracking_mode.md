# V3.228 — Admin-configurable per-page tracking mode

**Date:** 2026-05-15
**Branch:** Version-3.228 (planned)

## Problem

V3.226 ships a silent page-time tracker that writes one pending entry per page per day for any RM page where the user has user activity in a 10-minute window. The hardcoded skip list (`SKIP_SLUGS = {'activity-overview', 'pmr', ''}`) is the only escape hatch, and there's no way to say "lump time on this page into a single shared bucket." The user asked for a per-page admin control with three modes:

1. **Activity tracked** — current behavior.
2. **Never tracked** — page-time-tracker skips activity on this page entirely.
3. **Lumped into one category called admin work** — activity on this page rolls into a single shared "Admin work" entry per day instead of a per-page entry. Use case: chrome / browsing pages where the user wants the time counted toward something, but doesn't want a row per page on their tracker.

## Decision

- Store as `labConfig/pageTracking` (authenticated read + admin write via the existing labConfig rule).
- Doc shape: `{modes: {[slug]: 'never' | 'admin'}, updatedAt}`. `'tracked'` is the default; we omit those entries so the doc stays compact and "missing slug = tracked" is the invariant.
- Slug = pathname-derived slug the page-time-tracker already uses (e.g. `lab-notebook`, `dashboard`). Tab-suffixed registry ids (`activity-overview__tab__tracker`) collapse to their base slug because the tracker is unaware of `?tab=...`.
- UI is a third tab on `/rm/pages/admin-permissions.html?tab=tracking`. Each page is a row with a `<select>` (Tracked / Never / Admin work).
- Page-time-tracker fetches the config once after `firebridge.onAuth` resolves. No `onSnapshot` — stale mode for one page session is acceptable; admin re-configurations are rare.

### `rm/js/admin-permissions.js`

- New module-level state: `trackingModes: Map<slug, mode>`, `initialState.tracking: Map<slug, mode>`, `TRACKING_HARD_SKIP = {'activity-overview': true}` (same hard-skip rule the tracker enforces).
- `loadTrackingConfig()` reads `labConfig/pageTracking` and populates the two maps.
- `trackerSlugForHref(href)` derives the page-time-tracker's slug from a registry `href`. Dashboard maps to `'dashboard'`; `/rm/pages/foo.html?tab=bar` maps to `'foo'`.
- `distinctTrackingPages()` walks `PAGE_REGISTRY.list`, applies `trackerSlugForHref`, dedupes by base slug (first occurrence wins for label + group), drops `TRACKING_HARD_SKIP` slugs.
- `renderTrackingList()` paints group-headed rows with one `<select>` per page. Selected option pulled from `trackingModes` (defaulting to `'tracked'`).
- `onTrackingChange(e)` pushes a `{type:'tracking', slug, mode}` pending edit when the value differs from `initialState.tracking`; deletes the edit when restored to initial. Toggles `.is-changed` on the row. Updates `trackingModes` for in-memory consistency.
- `saveAll`: when any tracking edit is pending, build a fresh `modes` map (skip `'tracked'`) and write `labConfig/pageTracking` with `{merge:false}` so removed entries actually drop.
- `revertAll`: clears `trackingModes`, reseeds from `initialState.tracking`, re-renders the tracking list.
- `boot()`: adds `loadTrackingConfig()` to the load `Promise.all` + `renderTrackingList()` to the post-load render.

## What this doesn't do

- No client-side cache invalidation when admin re-saves the config — open tabs keep their session-loaded mode until next reload. Acceptable since the tracker only matters for newly-opened pages from that point on.
- No Firestore index changes; `labConfig/pageTracking` is a single doc.
- No data migration for already-written `auto-pagetime-<slug>-<date>` entries when admin flips a page to `admin` mode. The legacy per-page entries stay; only future windows route into `auto-pagetime-admin-work-<date>`.
- No support for time-of-day or per-user overrides — the config is lab-wide.

## Risks + mitigations

- **Slug mismatch between admin UI and tracker.** The admin UI uses `trackerSlugForHref()` which is independent of `pageIdFromHref()` in `page-registry.js`. Both map base pages to the same slug (e.g., `lab-notebook`); the difference is that the tracker is unaware of `?tab=X`. Tab-suffixed registry entries collapse to their base slug in the UI, so a single config entry for `library` controls both `library` and any `library__tab__*` variants.
- **Race between config load and first user input.** If the user types within milliseconds of page load and beats the Firestore fetch, the first window logs under the default `tracked` mode. We accept the seam — the second window onward uses the configured mode, and the first window is at most 10 minutes of activity on the "wrong" doc.
- **Admin-mode aggregation across days.** The shared `auto-pagetime-admin-work-<date>` doc id is per-date, so cross-day rollover behaves correctly. Multiple admin-flagged pages share one entry within the day.
- **`{merge:false}` overwrites the doc entirely.** Intentional — it lets admin remove a slug from the config by flipping back to `tracked` (which omits it from the saved map). Other lab-wide config docs use `{merge:true}` but those have additive fields; this one is just `modes` + `updatedAt`, so a full replace is the cleanest semantic for "the new map IS the truth."

## Deploy

1. FTP `rm/`, `sw.js`, `CodeLog/` to godaddy.
2. No firestore.rules / indexes changes.
3. Admin: visit `/rm/pages/admin-permissions.html?tab=tracking`, configure a couple of pages, click Save.
4. Verify: in `labConfig/pageTracking` Firestore doc, `modes` contains the non-tracked entries. Open a `never`-mode page in a different tab; confirm `auto-pagetime-<slug>-<date>` doc is NOT created on activity. Open an `admin`-mode page; confirm `auto-pagetime-admin-work-<date>` IS created with `text: 'Admin work'`.
