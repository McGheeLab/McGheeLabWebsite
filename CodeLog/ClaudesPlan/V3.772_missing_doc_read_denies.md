# V3.772 — Joining a class was impossible: a rule that reads a document that isn't there

**Alex:** *"I just logged in as mcgheelabadmin@gmail.com to be added as a
student to `#/classes/tc-tuc-gnr8` with join code N9PYKR and it denied me."*

## What was actually wrong

Not the code, not the data — the **read rule on `enrollments`**.

`joinClassWithCode()` reads the student's own enrollment doc first, to decide
join-versus-rejoin:

```js
const existing = await src().getEnrollment(scheduleId, uid);   // enrollments/{sid}_{uid}
```

On a first join that document **does not exist**. A `get` of a missing
document is evaluated with no readable `resource`, so every clause in

```
allow read: if request.auth != null
            && (isAdmin()
                || resource.data.studentUid == request.auth.uid
                || resource.data.teacherUid == request.auth.uid);
```

either raises (`resource.data…`) or is false (`isAdmin()` for a guest). Rules
use three-valued logic: **an `||` that is nothing but errors and falses is an
error, and an error denies.** The SDK surfaced that as *"Missing or
insufficient permissions."* — and the class page printed it verbatim.

So the very first read of the join flow threw, and the join write — which the
rules would have allowed — was never attempted. **Zero enrollments existed in
the project**: no student has ever been able to join a class since the feature
shipped in V3.304.

## The fix, and why it is not `resource == null`

First attempt was the obvious `resource == null ||` guard. The rules engine
rejected it the same way — so I probed the engine with a throwaway ruleset to
get ground truth instead of guessing:

| probe (document missing) | result |
|---|---|
| `resource == null` | **error** |
| `resource != null` | error |
| `resource is map` / `!(resource is map)` | error |
| `resource.data == null` | error |
| `resource == null \|\| true` | **ALLOW** |
| `true \|\| resource == null` | ALLOW |

Two things fall out. **Any mention of `resource` on a missing document
raises** — there is no null-test that works. But **`error || true` is
allow**: a resource-free clause that is true for the legitimate caller
rescues the whole expression.

The composite doc id is exactly such a clause. `enrollments/{scheduleId}_{uid}`
always ends in the caller's own uid, so:

```
allow read: if request.auth != null
            && (enrollmentId.matches('.*_' + request.auth.uid)
                || isAdmin()
                || resource.data.studentUid == request.auth.uid
                || resource.data.teacherUid == request.auth.uid);
```

A student may always ask about **their own id**, present or not, and learns
nothing about anyone else's. This is strictly tighter than `resource == null`
would have been (which would have answered "not found" for *any* id and made
an existence oracle out of the rule).

Applied to all four members of the composite-id family:

| Collection | Client path that reads a doc that may not exist |
|---|---|
| `enrollments/{sid}_{uid}` | `getEnrollment()` — **the reported bug** |
| `submissions/{aid}_{uid}` | `mySubmission()` — a student's first look at an assignment |
| `moduleStats/{sid}_{uid}` | the V3.672 beacon's doc (no get today; same family) |
| `teacherProfiles/{uid}` | a teacher opening the profile editor for the first time — fixed by putting `isAdmin() \|\| isOwner(uid)` **before** the `resource.data.status` check and guarding it with `resource != null` |

## Verification

**19 cases against the real rules engine, all as expected** — the four fixed
reads of missing docs ALLOW; and every guard still DENY: a stranger reading
someone else's enrollment (existing *or* missing), a signed-out read, a
stranger creating an enrollment for someone else, a student forging a join
code, a stranger reading an existing submission or moduleStats, a stranger
reading a pending teacherProfile. Teacher roster `list` and student
`myEnrollments` list both still ALLOW.

Then **end-to-end against live production**, as a real signed-in user (a
throwaway password account created with the Admin SDK, Firestore REST with its
ID token):

| Live request | Before | After |
|---|---|---|
| read my own **missing** enrollment | 403 PERMISSION_DENIED | **404 NOT_FOUND** ✓ |
| read another user's enrollment id | 403 | **403** ✓ (guard holds) |
| **create** the enrollment with code N9PYKR | never reached | **200 — enrolled** ✓ |
| read it back | — | **200, status: active** ✓ |

The test enrollment and the throwaway account were then deleted; the
collection is back to 0 rows. No Cloud Function triggers on enrollment writes,
so nothing was notified.

## The lesson worth keeping

Rules are three-valued. An error is not a false — it denies the whole `||`
unless some other operand is *true*. So a rule that can only answer by reading
the document is a rule that cannot say "it isn't there". **Every "my doc"
get on a composite id needs a clause that proves the caller from the id or
the auth token alone.** This is the second time this family has bitten: V3.684
was `isAdmin()` raising with no `users` doc and taking a whole `||` down with
it.
