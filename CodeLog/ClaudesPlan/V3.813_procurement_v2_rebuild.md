# V3.813 — Procurement v2: the purchase pipeline rebuilt so it actually runs

Alex: *"we need to make the procurement workflow work, redo the entire system
then run opus agents to test it fully end to end."*

## Why the V3.44 page did not work

Driving the shipped page and reading the code turned up six reasons a request
never made it round the loop:

| # | What was wrong | Consequence |
|---|---|---|
| 1 | Every decision (approve, deny, cancel, delete) went through `window.prompt` / `window.confirm` | Alex's standing rule since V3.648: no browser input popups, ever. The headless harness hangs on them. |
| 2 | **Nobody was told anything.** No Cloud Function, no feed item, no push | The PI never learned a request came in; the student never learned it was approved, ordered or had arrived. The only way to find out was to open the page and click through seven tabs. |
| 3 | The Project dropdown read `labConfig/projects`, a doc nothing has ever written | Always empty. Funding read `labConfig/fundingSources`, which only exists after the website "Sync Config" button has been pressed. |
| 4 | `userName(uid)` matched `u.uid`, but the `users` rows the adapter returns carry `id` (profile-bootstrap never writes a `uid` field) | Every "Approved by / Received by" stamp without a stored name rendered as six hex characters. |
| 5 | The rules were `allow update: if isLabMember()` | Anyone could approve their own request, mark anything ordered, or rewrite another person's ticket. The UI hid the buttons; the server allowed the writes. |
| 6 | `firebridge.loadAccessGrant()` was never awaited and no caps existed | A lab manager could not be given "place orders" without being made an admin. The "Open in Inventory" link pointed at `inventory.html#id`, which inventory.js ignores. |

Plus the things that make a procurement page useful at all were absent: a
reorder path from the inventory item itself, a question-and-answer loop
between PI and requester, batching several approved items onto one PO, an
audit trail, restocking an existing item instead of creating a duplicate, any
report of what was spent on which account, and a way to withdraw a request
that is not "denied".

## What ships

One collection, the same `procurementTickets/{id}` (old tickets stay readable
and keep working — every v2 field is additive and `status` values are a
superset), with the whole system around it rebuilt:

### 1. Pure state machine — `rm/js/procurement-core.js` (new)

Framework-free, DOM-free, exported as `window.PROC_CORE` in the browser and
`module.exports` in node so the same bytes run in the page, the emulator E2E
suite and the node fixtures.

Statuses: `requested → needs_info ⇄ requested → approved → ordered → received
→ placed`, terminal `denied` and `cancelled`. Actions and who may take them:

| action | from → to | who |
|---|---|---|
| submit | — → requested | any lab member (own) |
| edit | requested / needs_info → requested; approved → requested (requester) or approved (approver) | requester, approver |
| ask | requested → needs_info (note required) | approver |
| answer | needs_info → requested (note required) | requester |
| approve | requested / needs_info → approved | approver |
| deny | requested / needs_info / approved → denied (reason required) | approver |
| unapprove | approved → requested | approver |
| order | approved → ordered (PO/method/date/ETA/file; batch siblings) | purchaser |
| edit_order | ordered → ordered | purchaser |
| unorder | ordered → approved | purchaser |
| receive | ordered → received (qty, actual cost, receipt, note) | any lab member |
| unreceive | received → ordered | purchaser |
| place | received → placed (location; new item OR restock) | any lab member |
| cancel | requested / needs_info / approved → cancelled | requester |
| reopen | cancelled → requested (requester); denied / cancelled → requested (approver) | — |
| note | any → same | any lab member |
| flag / clear_issue | ordered / received → same (`issue`) | any member / purchaser |
| delete | — | admin |

`approver` = admin or `procurement:approve`; `purchaser` = admin or
`procurement:order` (both new caps in `capability-registry.js`). `can()`,
`availableActions()`, `buildCreate()`, `buildPatch()` (validates and returns
`{patch}` or `{error, field}`), `inboxFor()`, `filterTickets()`,
`summarize()`, `toCSV()`, `fundingOptions()`, `projectOptions()`,
`prefillFromInventory()`, `restockPlan()`, `batchCandidates()`.

Every write stamps `lastActorUid`, `updatedAt`, appends a `history[]` entry
`{id, at (ISO), by, byName, action, from, to, note}` via `arrayUnion`, and
keeps `watcherUids[]` (requester + everyone who acted or commented) so the
function knows whom to tell.

### 2. Page — `rm/js/procurement.js` + `rm/css/procurement.css` (rewritten)

- **No popups.** Every action is an inline form that opens inside the
  ticket's own card (approve note, deny reason, question, PO details, receipt,
  put-away, edit, withdraw-confirm strip, delete-confirm strip). Errors render
  beside the field. `window.prompt/confirm/alert` are never called; the
  self-test stubs them to throw.
- **Views:** *Inbox* (what needs *you*: approvals if you approve, orders if you
  purchase, arrivals to put away for everyone, your own questions to answer),
  *Active*, *Mine*, *Archive*, *Report* (approver/purchaser). Status chips,
  search, sort. Compact rows expand in place; `?ticket=ID` opens one (every
  notification links here).
- **Composer** at the top (`+ New request` / `?new=1` / `?reorder=INVENTORY_ID`
  prefilled from the inventory item). Funding is a select built from active
  awards ∪ accounts ∪ `labConfig/fundingSources` with an *Other…* row that
  reveals a text field; Project is a text field with a datalist of project
  titles and previously used values. Unit cost × qty → estimated total.
- **Batch ordering:** the order form lists the other approved tickets from the
  same vendor; ticked ones get the same PO in one Firestore batch and share
  an `orderGroupId`.
- **Put away:** location gets a datalist (inventory boxes + previous
  locations); choose *New inventory item* or *Restock an existing item*
  (search by name / cat#; preselected when the request came from Reorder).
  Restock appends the location, bumps `quantity`, records price history and
  reorder info; `qty_remaining` on a tracked item is raised only when the
  placer is an inventory manager (rules forbid it otherwise) and then an
  `inventoryUsage` 'add' row is written for the ledger.
- **Timeline + notes** on every card; a question from the PI shows as the
  ticket's banner until answered.
- Renders are deferred while an input inside the page is focused (meetings
  pattern), so a live-sync refresh never wipes a half-typed form.
- Inventory detail gains **Request reorder →** (`inventory.js`); the dashboard
  gains a Procurement card; Settings gains a *Purchasing* push toggle.

### 3. Rules — `firestore.rules`

The transition table above, enforced: `requestedBy` and `createdAt` cannot
change; each `from → to` pair is allowed only for its role; a same-status
update by anyone may touch only `notes / history / updatedAt / issue /
watcherUids / lastActorUid / lastActivityAt`; admins may do anything; delete is
admin-only. Read stays `isLabMember()`. `isRequester()` reads
`resource.data` only in `update` (where the doc exists), so the missing-doc
trap does not apply. Deploy BEFORE FTP, with the live-vs-local diff first.

### 4. Cloud Function — `functions/procurement-notify.js` (new)

`onProcurementTicketWritten` (`procurementTickets/{id}`): decision logic in
`_internal.plan(before, after)` (node-tested), audiences resolved server-side
(admins ∪ `procurement:approve` holders, admins ∪ `procurement:order`
holders, requester, watchers) minus the actor (`lastActorUid`). Uses
`notifyUsers` (push + My Week feed), `appKey: 'procurement'`, tag
`proc:{ticketId}` so an unread older state collapses into the newer one.

`procurementDailySweep` 08:00 Phoenix: requests waiting > 5 days →
approvers; orders past ETA + 2 days → purchasers; arrivals unplaced > 3 days →
receiver + requester. Each one collapsing feed item.

## Key decisions

- **Same collection, additive fields.** No migration; the three legacy tickets
  in production render and transition under v2 (`history` absent → timeline
  built from the stamp fields).
- **Rules enforce the transition table.** V3.44 argued "trust is high, the UI
  gates it". The cost was that the page could not be trusted by anyone
  reading the data, and the function cannot tell who did what. The table is
  small enough to be rules.
- **Core split out.** A DOM-free module is the only way the emulator E2E can
  exercise the page's real write paths, and the only way node tests pin the
  state machine. The DOM file is rendering + wiring only.
- **ISO strings in `history[]`.** `serverTimestamp()` cannot sit inside
  `arrayUnion`; `updatedAt` keeps the server stamp.
- **Caps instead of a new role.** `procurement:approve` / `procurement:order`
  follow V3.605 exactly, so the Permissions page grants them with no new UI.
- **Restock respects the V3.646 ledger.** A member may append a location and
  bump `quantity`; raising `qty_remaining` is a manager act and stays one.

## What the Opus agents found (and what changed)

Three agents in parallel after the first green run: a rules/core adversary (334
emulator + node cases), a UI explorer (five personas, every seeded state, phone
width) and an integration reviewer. Headlines, all fixed and pinned:

- `esc()` left quotes alone → attribute breakout through a product link (XSS).
- Rules were still too loose for trusted roles and for same-status writes;
  the audit trail and `lastActorUid` were forgeable; create accepted forged
  content. Now: exact per-role moves, append-only trail, self-signed actor,
  receive/place field lists, born-now creates.
- A requester could not edit during a question (core said yes, rules no) —
  an edit during a question is now the answer.
- Receiving 0 still put the ordered quantity away; price divided by the wrong
  quantity; `price_history` used a key inventory never read.
- Page: deleted-ticket links crashed the page; stale ticket objects after a
  live refresh; batch mirrored before commit; put-away was not atomic; counts
  went stale; drafts were thrown away; numbers were accepted silently; report
  table clipped on phones.

The explorer's working notes live in the session scratchpad; the adversary's
scratch suites were folded into `procurement-rules.test.mjs` and deleted.

## Addendum — the project decides the funding string

Alex: *"users should specify which project this purchase is for, this way the
correct funding string is used."* Production already had the mapping — the
admin's Grant Accounts list (`userData/{admin}/financeProjects`: four projects
with strings like `1101917-MCMI`) — but per-user, so students could not read
it, and the form asked for a project tag and an account separately.

Now: Grant Accounts publishes its active projects to `labConfig/fundedProjects`
(auth-read) on every save; the request form has one required **Project** select
whose choice fills **Charged to**; *Other* leaves the string blank and the
approver must assign a project before approving. Purchasers see the funding
string on the card, in the order form and in their push. `funding_string` is a
new optional field on a Grant Accounts project for when purchasing needs more
than the account number.
