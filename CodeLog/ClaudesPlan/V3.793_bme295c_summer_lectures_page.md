## The page

One self-contained HTML file (module convention), dark palette from
`module-header.css`, no build step. Order on the page, top to bottom:

1. **Header** — the shared module header. New: `<header id="module-header"
   data-class="bme295c">` gives a *direct link* (no `?class=`) the full header with the
   class back-link; and a page the class doc's `modules[]` doesn't list shows its own
   `<title>` instead of `lesson-01.html`. Both changes are in `module-header.js` and are
   backward compatible (query string still wins; listed modules still show their title).
2. **"Want to take BME 295C next summer?"** — the interest form, at the top as asked.
   Name, email, high-school graduation year (2027–2030 / other), closer campus
   (Tucson / Phoenix / Either), optional note. Inline errors under the fields (no
   popups). Writes one doc to the new **`courseInterest`** collection. Success replaces
   the form with a thank-you and remembers it in `localStorage` (with "Fill it in
   again"). If the visitor is already signed in on this origin (the class page shares
   Firebase auth persistence), name and email pre-fill.
3. **The week at a glance** — five day cards from `content.json.schedule`: talks link
   to their cards, lab tours listed per day.
4. **The lectures** — one card per talk in the order they happened: Day pill, date /
   time / campus, speaker thumbnail (new 320-px webp thumbs, falling back to the
   original photo), talk title, speaker + title, the recording as a **poster that
   becomes a `youtube-nocookie` embed on tap** (so ten players don't load at once) with
   "Open on YouTube", then collapsible *About this talk* (abstract; hidden when TBD) and
   *Discussion questions* (prompts + follow-ups). A talk with no video shows "Recording
   not available"; a notice above the cards says "9 of 10 recordings are available".
5. **About the course** — description, dates/times/rooms, instructors with emails.
6. **Fine print** — the syllabus recordings policy (personal study only).

`<meta name="robots" content="noindex">`: the recordings are for the class, and the
class doc already treats the link as the gate.

## Data: `courseInterest/{autoId}`

`{ course:'bme295c', name, email, gradYear:'2027'|…|'other', campus:'tucson'|'phoenix'|'either',
note?, source:'lesson-01', uid?, createdAt: serverTimestamp }`.

**Rules.** The page is public with no sign-in UI, so **create is open to anyone**, but
only for a tightly-shaped doc: `hasOnly`/`hasAll` on the key set, `course in
['bme295c']`, name 2–120 chars, email ≤ 200 matching `^[^@\s]+@[^@\s]+\.[^@\s]+$`,
enum gradYear/campus, note ≤ 1000, source ≤ 40, `uid` only if it equals the caller's
uid, `createdAt == request.time`. Read: admin, or a signed-in user whose email is in
that course's `schedules/{course}.classAdminEmails` (the get is guarded by a non-empty
string `course`, so the missing-doc trap denies a bogus course rather than raising into
an allow). Update/delete: admin. No indexes: the admin query is a single equality.

Trade-off, stated: an unauthenticated create means a bot that finds the collection name
can add junk rows. The shape rules bound the blast radius (no free-form keys, short
strings) and the admin card has Remove. Requiring Google sign-in would cost the very
students the form is for.

## V3.796 addendum (2026-10-01) — it's a waitlist, with the student's own email

**Alex:** "for a student to sign up for the BME 295C waitlist, they need their own email in the
form. Then we should collect all students interested into our website's database, and later when
the opportunity is available that list will be able to be pushed out."

Three changes follow from that.

### 1. The email is the student's own: Google sign-in, read-only email

The V3.793 form let anyone type any address. Now the card asks the student to **sign in with
Google** (popup, redirect fallback, `prompt: 'select_account'`); the email field is **read-only
from the account** with a *Switch account* link; name pre-fills from the profile and stays
editable. The rules make the client's promise binding: `email == request.auth.token.email.lower()`.

Auth persistence is shared with the class page (same origin), so a student already signed in
there lands straight on the form or on their entry.

### 2. One entry per student, kept in the site's database

`courseWaitlist/{course}_{uid}` replaces the anonymous `courseInterest` (deleted from the rules;
it never held a real row). Deterministic id → no duplicates, and the page can answer "are you on
the list?" with a `get` by id on every auth change (no `localStorage`). Students can **update**
their details (only `name/gradYear/campus/note/source/updatedAt` may change) and **leave** (delete
their own entry, two-click arm). Owner clauses are ordered before `isAdmin()` in every rule,
because a student who has only ever signed in on this page has no `users/{uid}` doc and
`isAdmin()` would raise and kill the `||`.

### 3. "Pushed out" = written to from the dashboard

The site has no mail server (by design) and the only Gmail OAuth scope on file is
`gmail.readonly`, so nothing can be sent by the site itself. `notifyUsers` (push + the My Week
feed) only reaches lab members with tokens. So the admin card gets **Write to the waitlist**: a
compose box with an applications-are-open template → *Open email to everyone (N)* is a `mailto:`
with every address in **BCC** (batched at 50, Gmail's comfort zone and well under URL limits) →
*Record as sent* writes `courseAnnouncements/{autoId}` so the card shows "Written to N times ·
last {date}" and the history. Copy emails and CSV (now with `uid`) remain.

If Alex later wants the site to send the email itself, that is a new Gmail `send` scope on the
existing OAuth flow plus a callable function — a separate decision (bulk mail to minors from a
personal account has deliverability and policy implications), not a gap in this change.
