# V3.604 — Release batching + "What's New" broadcast

## Goal

Stop pushing (FTP + notify) for every small change. Instead:

1. **Collect** — each small change appends one user-facing line to a
   pending-release ledger (`CodeLog/Updates/PENDING_RELEASE.md`) alongside
   the normal CHANGELOG entry.
2. **Threshold** — when the ledger holds **5+ changes**, or whenever Alex
   says "push", the batch ships as one release.
3. **Announce** — at push time, ONE notification goes to every lab member
   (push + in-app feed) with a summary of what changed, linking to a new
   **What's New** page that keeps the release history.

## Why this shape

- The ledger is a **repo file**, not Firestore — it's authored by Claude
  during coding sessions, reviewed in the working tree like everything
  else, and costs nothing until push time. Storage shape chosen by who
  writes it.
- The announcement is a **Cloud Function** (`releaseAnnounce`) because
  broadcast push needs the Admin SDK (`notifyUsers` in
  `functions/helpers/notify.js` — the exact plumbing chat/equipment
  already use: settings check → presence gate → FCM web+native → feed
  fallback). No new notification machinery.
- The release history is a **`releases` Firestore collection** written
  server-side only (Admin SDK), lab-member read. The notification's
  `url` points at the What's New page, so tapping it lands on the full
  release notes — push is transient, the page is the catch-up surface.

## Components

| File | What |
|---|---|
| `CodeLog/Updates/PENDING_RELEASE.md` | The ledger. One entry per small change: user-facing one-liner + version ref. Reset after each announce. |
| `functions/release-announce.js` | `releaseAnnounce` — onRequest, CORS, Bearer-token verified, **admin-only**. GET = health probe (UI gates the send button on it, same as equationOcr). POST `{version, title, summary, changes[]}` → writes `releases/{id}` → `notifyUsers()` to all non-guest users, appKey `releases`, kind `release`, tag `release-v{version}`. |
| `functions/index.js` | require + export `releaseAnnounce`. |
| `firestore.rules` | `releases`: read `isLabMember()`, delete `isAdmin()`, create/update denied (server-only writes). |
| `rm/pages/whats-new.html` + `rm/js/whats-new.js` | Release history list (newest first). Admin-only compose card on top: version, title, summary, changes (one per line), pre-fill hint from ledger format, confirm dialog stating it notifies the whole lab. |
| `rm/js/nav.js` | "What's New" link under Settings group. |
| `rm/js/settings.js` | New per-app push toggle `releases` ("App updates"), default ON. |
| `CLAUDE.md` | New "Release batching" workflow section so every future session appends to the ledger and knows the push ritual. |

## Key decisions

- **onRequest, not onCall** — matches the proven static-client pattern
  (equationOcr / paperCompile): Bearer ID token + role check server-side,
  GET health probe so the UI self-detects an undeployed function
  (deploy-order safety).
- **Recipients = all `users` where `role != 'guest'`** — fetched
  server-side; the sender is included (they want the confirmation buzz;
  presence gate suppresses anyone already on the What's New page).
- **Per-change sw bump stays.** CACHE_VERSION keeps bumping with each
  change in the working tree; only the FTP (and therefore the user-visible
  update) is batched. Nothing about the existing version ritual changes
  except that FTP + notification wait for the batch.
- **Tag collapse** — `release-v{version}` means a re-send of the same
  version replaces the unread feed item instead of stacking.

## Deploy order

1. `firebase deploy --only functions:releaseAnnounce`
2. `firebase deploy --only firestore:rules`
3. FTP (client self-detects the function via health probe, so order is
   safe either way — but do functions first so the button works
   immediately).
