# V3.669 — Teacher Dashboard v2 + Engagement Hub program (R1: catalog + #/teach)

Master plan for a 4-release program; V3.669 ships R1. Approved by Alex 2026-08-26
after a full grill (see decisions below). R2–R4 will reference this doc.

## Program goal

Deepen HS / community-college outreach on top of the V3.304 teacher platform:

- **R1 (V3.669, this release)** — global admin-curated module catalog
  (`teacherCatalog`) + the teacher dashboard moves to its own `#/teach` route
  (new `teacher-teach.js`) with module assignment (class-wide order + due
  dates, per-student overrides) and the join-code/roster controls.
- **R2** — assignments + student submissions (mark-done / text) + gradebook
  (`assignments`, `submissions/{assignmentId}_{uid}`), notify functions.
- **R3** — engagement tracking (viewer-side beacon; `moduleStats/{scheduleId}_{uid}`
  pre-aggregated docs) + teacher engagement tab.
- **R4** — public `#/engage` hub: teacher availability (weekly + dated slots),
  capability-gated PI browsing (`engage:browse`/`engage:request`),
  request → teacher confirms, admin oversight tab.

## Decisions locked with Alex

- Extend the existing TC_DB data layer; dashboard moves to `#/teach` linked
  from `#/classes`. `#/dashboard` keeps a slim teacher view.
- Demo personas suffice for admin view-as; fixtures extended per phase.
- Keep per-class 6-char join codes + Google sign-in. No email infra, ever.
- Global per-module catalog replaces per-class `grantedFolders` for NEW
  classes (legacy data left in place, deprecated).
- Submissions = mark-done + text only. PI hub access = sign-in + caps.
  Booking flow = request → teacher confirms, admin can intervene.
- Phased releases, one plan doc.

## R1 approach

- `teacherCatalog/{folder--basename}` (doc id matches the existing
  `modules[].id` convention): `{folder, file, title, description?, subjects[],
  gradeLevels[], published, order, updatedAt, updatedBy}`. Read: any signed-in
  user; write: admin. New 5th tab `?tab=catalog` on admin-teachers.
- Class-wide module assignment stays on `schedules.modules[]` (teacher may
  already update it; `grantedFolders` stays pinned). Entries gain
  `dueDate?: 'YYYY-MM-DD'` (repo date convention).
- Per-student overrides on the enrollment doc:
  `enrollments/{sid}_{uid}.moduleOverrides: { [moduleId]: {hidden?, dueDate?} }`
  — teacher-writable (teacher branch of the update rule is unrestricted);
  the student self-update key-set already excludes it.
- New `teacher-teach.js`: `#/teach` (class list) and `#/teach/{id}/{tab}`
  (tabs: modules | students). Inline confirms + toasts, NO
  prompt/alert/confirm (project rule). Approve modal drops the mandatory
  folder grant: checkboxes become an optional "pre-fill from catalog"
  (falls back to manifest while the catalog is empty), new classes get
  `grantedFolders: []`.
- Rules add `isClassTeacher(scheduleId)` helper (used from R2 on).
- Demo: `w.catalog`, DEMO_DB mirrors (`publishedCatalog`, `saveClassModules`,
  `setModuleOverride`), a due-dated module + one student override fixture.

## Release ritual (R1)

`firebase deploy --only firestore:rules` BEFORE FTP. sw.js 644 → 645.
CHANGELOG + PENDING_RELEASE entries. FTP batched via release_push.py.

## Rollback

Previous JS + previous rules. `teacherCatalog` docs orphan harmlessly;
`modules[].dueDate` ignored by old code; new classes with empty
`grantedFolders` still render (folder chips just absent).

## Verification (R1)

1. Demo → teacher persona → `#/teach` renders classes; module picker lists
   only catalog-published modules; reorder + due date persist in the world log.
2. Real teacher: `#/dashboard` slim view links to `#/teach`; code
   create/regenerate/disable + enrollment toggle work there.
3. Rules: teacher cannot write `teacherCatalog`; teacher CAN update own
   schedule `modules[]`; student cannot write `moduleOverrides`.
4. Student class page hides overridden modules and shows due dates.
5. Admin `?tab=catalog` toggle flips a module's visibility in the picker.
