# V3.213 — Page→collection map audit + fill (collaborator data-layer phase 1.5)

## Context

V3.212 shipped the foundation for collaborator data-layer enforcement.
The post-deploy migration's dry-run surfaced ~26 pageIds in the wild
that weren't in `PAGE_COLLECTIONS` — every existing `userPermissions`
doc carried at least some of them. Harmless under V3.212 (no rule
clause uses `collabMay` yet), but **must be fixed before any rule
gating ships in V3.214** because granting an unmapped page resolves to
zero data access.

This is a pure expansion of the page → collection map. No new code, no
new rules, no schema change.

## What's mapped (V3.213)

Audited each unmapped pageId's JS for `db().collection(...)` /
`api.load(...)` / `getAll(...)` / `setDoc / updateDoc` references. Per
the existing policy, **owner-locked subcollections** (`userData/{uid}/*`,
`cvData/{uid}`, `userSettings/{uid}`, `huddleSettings/{uid}`, etc.)
remain excluded since their rules already gate by `isOwner`. **Public-read**
collections (`users`) also excluded.

### Activity overview tabs
- `activity-overview__tab__tracker` → `[labConfig]` — `trackerData` / `trackerEntries` are owner-locked
- `activity-overview__tab__email` → `[labConfig]` — `userData/{uid}/emailArchive` is owner-locked

### User-scoped utilities (own-data-only pages)
- `cv-editor` → `[labConfig]` — `cvData/{uid}` owner-locked
- `profile` → `[labConfig]` — no Firestore
- `settings` → `[labConfig]` — `userSettings/{uid}` owner-locked
- `finance` → `[labConfig]` — `userData/{uid}/finance*` owner-locked

### Standup / huddle (shared lab data)
- `huddle` → `[huddleConfig, huddleHelpRequests, huddlePlans, huddleRundown, labConfig]`
  - `huddleSettings/{uid}` excluded (owner-locked)

### Misc
- `chemicals` → `[inventory, labConfig]` — filtered view of inventory
- `split-view` → `[labConfig]` — shell only, iframes own their data

### Training curriculum (V3.162) — all static modules
17 entries, each `[labConfig]`:
`training, training-paper-writing, training-phd-triangle,
training-scientific-communication, training-microscope-basics,
training-image-analysis-basic, training-image-analysis-intermediate,
training-image-analysis-advanced, training-spheroid-sizes,
training-image-train, training-cell-tracker, training-confocal,
training-imagej-fiji, training-epifluorescence,
training-rm-essentials, training-rm-papers, training-rm-tasks-pmr,
training-rm-daily-research`.

Per `rm/CLAUDE.md`: "training-phd-triangle.html is implemented today,
the other eight slugs are placeholders." The implemented training pages
use canvas / DOM-local state — no Firestore reads. If a future training
module adds Firestore, the mapping needs an update + a "Recompute all
collaborator grants" run.

## Migration outcome

Re-ran `node scripts/migrate_user_permissions_add_collections.js --commit`
after the map fill. Result: **14 docs touched, 0 unchanged, 0 skipped,
0 unmapped warnings.** Every existing `userPermissions/{uid}` doc that
held the `huddle` pageId now also gets `huddleConfig, huddleHelpRequests,
huddlePlans, huddleRundown` added to its `allowedCollections`. The
training / activity-tabs / utility-page entries are all `[labConfig]`
so they didn't add anything to the union for the existing docs.

## Files NOT changed

- `firestore.rules` — unchanged. V3.213 ships zero rule changes.
  V3.214 will start the gating pass.
- `rm/js/admin-permissions.js`, `rm/js/firebase-bridge.js` — unchanged.
  The save path and access-grant reader already pick up the new
  mappings on next save / page load.
