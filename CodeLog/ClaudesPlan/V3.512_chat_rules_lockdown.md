# V3.512 — Chat: rules lockdown

**Release 4 of 7** in the chat upgrade program (R2 = V3.507 moved
mention fan-out + counters server-side, which is what makes this
lockdown possible).

## ⚠ Deploy timing

`firebase deploy --only firestore:rules` **only after V3.507 clients
have saturated** (~2–3 days after the R2/R3 FTP, or check that recent
`chatMessages` docs carry `fanout: 'v2'`). Worst stale-tab break: the
old client's cross-user mention write throws AFTER the message doc is
created — the message still sends and badges still arrive via the Cloud
Function; the user sees a console error until refresh. Re-run the
Settings → "Backfill subscriber lists" button first to be sure every
channel has `subscriberUids`.

## Rules changes (firestore.rules, Lab Chat section)

- **`chatReadState` — owner-only writes** (the headline fix). Was
  `read, write: if request.auth != null` — any signed-in user could
  zero anyone's mention counts (and the pre-V3.507 client *depended* on
  that hole for its mention fan-out). Now: create requires
  `data.uid == auth.uid && docId == auth.uid + '_' + data.channelId`;
  update/delete owner-only. Reads stay open to signed-in users —
  cross-user `lastReadAt` becomes the read-receipt source in R7. The
  server fan-out is Admin SDK (rules-exempt).
- **`chatMessages`** — create pins `authorUid` to the caller AND
  enforces `chatRole() != 'readonly'` + announcement-channel admin-only
  (both previously UI-only; `chatRole()` reads `chatConfig.userRoles`,
  same doc `isChatAdmin()` gets, so it's cached per evaluation). Update
  is field-scoped: author-edit-own with `authorUid`/`channelId`/
  `createdAt` frozen, OR `msgChanged().hasOnly(['reactions','readBy',
  'pinned','pinnedBy','pinnedAt'])` for any member — **this FIXES
  non-author reactions/receipts/pins, which the old author-only update
  rule technically forbade** — OR the thread-counter transition
  carve-out (`threadReplyCount`/`threadLastReplyAt`, stale clients;
  remove in R7), OR chat-admin.
- **`chatChannels`** — create requires `createdBy == auth.uid`; DMs
  allowed for anyone signed-in, regular channels require non-readonly
  and announcement→admin. Update: chat-admin, OR self-only
  subscriberUids toggle (`onlySelfSubToggle` set-difference check —
  only YOUR uid may enter/leave the list) + memberCount, OR the
  `lastMessage/lastActivityAt/messageCount` transition carve-out
  (stale clients; remove in R7). Delete stays chat-admin.
- `chatConfig` / `chatUserMeta` unchanged (already correct).

## Client changes (rm/js/chat.js)

- **`createDM` no longer writes other members' `chatUserMeta`** — those
  cross-user get/update calls have ALWAYS violated the owner-only rule
  (the await threw mid-loop; DM creation limped through only when the
  creator's uid sorted first). Now it subscribes self only, and each
  other member adopts the DM via new **`healDmMemberships()`**: when the
  channels snapshot shows a DM listing me as a member that my own meta
  doesn't track, I arrayUnion it into my own `dmChannelIds` +
  `subscribedChannels`. Runs on every channels snapshot; idempotent.
- **Removed the dead `subscribeThread` unordered fallback** — the
  `(threadParentId ASC, createdAt ASC)` index ships with V3.507, so the
  primary ordered query is always served.
- UI pre-checks (`isChatReadOnly`, announcement toast) stay as friendly
  errors; rules are now the backstop.

## Verification (as a NON-admin)

Send / edit own / react to someone else's / pin / mark channel read /
subscribe+unsubscribe toggle — all succeed. Post to announcement channel
→ denied (toast). Readonly-role user: send denied at rules even with
devtools. From console: `update()` on another user's chatReadState →
permission-denied; adding someone ELSE's uid to subscriberUids →
permission-denied. Create DM from account A → account B sees it appear
and B's own meta gains the id (healDmMemberships). Author edit keeps
working; editing your own message's `authorUid` via console → denied.
