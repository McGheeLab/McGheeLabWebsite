# V3.647 — Bug fixes from `CodeLog/Feature requests/BugFixes_081923.md`

Five bugs Alex reported after using the paper writer and the library for real
work. Four of the five turned out to be the *same shape*: a piece of code
rebuilding a DOM subtree, or serving a cache, that nobody had told it was
holding something the user was in the middle of.

## The bugs, and what each one actually was

### 1. "Creating a table, I can only type one letter at a time"

**Root cause.** Table cells on the Tables page are real collaborative
editors — `bindYTextToContentEditable` on a per-cell `Y.Text`
([paper-equations.js `_buildTableEditorBody`](../../rm/js/paper-equations.js)).
Every keystroke commits through `yText.doc.transact(…, 'local-input')`, which
fires the `sections.observeDeep` registered in `_installSubscriptions`, which
calls `_refreshPanel()` → `_refreshTablesSection()` → `listEl.innerHTML = ''`.
The contenteditable holding the caret is destroyed by the very keystroke that
was typed into it. One character in, focus gone, click back in, repeat.

**Fix.** `_deferWhileEditing(listIds, refreshFn)` — when focus is inside a
list the refresh would replace, park the refresh on the list element and run
it on `focusout` (settled a tick later, so tabbing cell→cell doesn't rebuild
in the gap). Remote edits still land, at the next natural pause instead of
mid-word. Applied to the Tables **and** Figures pages — figure captions are
the same kind of live editor in the same kind of wholesale-rebuilt list.

### 2. "Adding a citation bumps me off the spot I'm inserting at"

Two independent causes, and Alex's two clues each name one of them.

**Cause A — "it happens when the citation I just placed is still in its key
form."** A citation renders as its key precisely *because* the citation index
hasn't loaded yet. The load that converts it to its short number form fired
`paper-citations-loaded`, whose handler called `render()` — a full teardown
and rebuild of every section. The paragraph the user was aiming at becomes a
detached node; `lastFocusedEditable` and paper-equations' `_state.savedEl`
both point at it, the `document.body.contains()` guard fails, and the next
"Insert citation" alerts or silently no-ops. The trigger is the same event
that produces the visible symptom, which is why the two always coincided.

*Fix:* repaint chips in place instead. Broadcast
`paper-equations-changed` / `paper-panel-changed`; every binding already
re-renders any source containing `[@` and already skips focused elements.
The visible work happens; the DOM the caret lives in is never touched.

**Cause B — "it also happens when I click on the text area for the first
time."** The `focus` handler replaces the element's innerHTML with chip-mode
HTML (V3.159). That destroys the caret the browser had just placed from the
click. What survives is a selection collapsed at offset 0 — or none at all,
in which case `_saveCaretFromCurrentFocus` falls back to the **end** of the
paragraph. Both pre-fix failure modes are reproduced in the harness.

*Fix:* the click **point** survives the re-render even though the caret
doesn't. `mousedown` stashes it; the focus handler re-derives the caret from
it against the fresh DOM via `setCaretFromPoint`, and `mouseup` re-applies it
after the browser's own selection handling. A point landing inside an atomic
chip is nudged to just after it — chips are `contenteditable=false` and
`readCaretCharOffset` counts them as `data-src.length` without walking in, so
a caret parked inside one reads back as the wrong source offset. The focus
handler also calls `rememberFocus` now, so a Tab into a paragraph registers.

### 3. "I want to write and add a new value reference inline"

Not a defect — a missing half of V3.645. `PaperValues.openInsertPicker` could
only insert keys that already existed, so a key that didn't yet dead-ended the
writer: leave the sentence, open the Values page, define it, come back, find
the spot again (and by then bug 2 had eaten the caret).

**Fix.** Defining and referencing become one action:
- Two `＋ New …` rows (text, number & unit) in the picker, plus the inventory
  search, all marked `always: true` so they survive filtering — they matter
  *most* when the search box matches nothing.
- Rows may render their label from the typed query, so the row reads
  `＋ New number & unit "N2TError"…`, and `onPick` receives the raw query,
  which seeds the key prompt. Typing a key and pressing Enter is the whole
  interaction.
- `editEntry` gained a `seedKey` argument and now **returns** the key it
  settled on, so the caller can insert that key's token at the caret.
- A `🔑 Insert value or inventory item` item on the paragraph right-click
  menu, opened at the click point — the inline entry point Alex asked for.

### 4. "Bulk DOI import says N added; they're not there"

**Three layers, all in `commitToLibrary`.**

1. `if (window.api && api.invalidate)` is a **dead check**. `util.js` declares
   `api` with a top-level `const`, which is a lexical global and never a
   property of `window`, so `window.api` is *always* undefined. The cache-bust
   added in V3.493 had never run once. (Same class as the V3.392/V3.577
   `window.firebridge` dead-checks; `tab-lifecycle.js:52` already documents
   the trap.)
2. Even fixed, it busted the wrong route. The library list reads
   `library/papers.json` (the V3.206 `type=='paper'` fast path);
   `items.json` is only its fallback.
3. The writes carried **no `updatedAt`**. The adapter's cheap freshness probe
   is `orderBy('updatedAt','desc').limit(1)`, and Firestore ORDER BY *excludes
   documents missing the field*. So the probe read the old top doc, saw
   `updatedAt <= savedAt`, declared the cache fresh and re-leased it. On
   `library/papers.json` (LONG TTL) that kept imported references invisible
   **indefinitely** — not merely until the TTL expired.

The rows were in Firestore the whole time. `library.js` even pushed them into
`_libraryPapers` before calling `_load()`, which then overwrote the array with
the untouched cache.

**Fix.** `typeof api`, both routes invalidated, `updatedAt` server timestamp
stamped on every write (mirroring `library.js _saveOne`).

**Blast radius.** The dead check was copy-pasted to 13 sites. Each was read in
context and fixed individually (never search-replaced — the V3.392 lesson):
`library.js` (a deleted paper could return from cache), `library-paper.js`
(the reader's bust-and-retry for a freshly-imported paper had never run, so it
read "not found"), `paper-import-engine.js` ×2, `paper-export.js`,
`paper-builder.js` ×2, `outputs-manager.js` ×2, `research.js`, `my-week.js`
(the protocol picker's list had never loaded on that page at all), and
`explorer-detail.js` ×2 — where it was not a guard but a bare
`window.api.load(...)` call that **threw a TypeError**.

### 5. "Cited by keeps refreshing and moving my scroll"

**Root cause.** `.lp-side-inner` is ONE scroll container holding
`#lp-citations` directly above `#lp-cited-by`. The citations panel repaints on
every PDF page change (`_onPageChange` → `refreshForPage`, plus once more per
page from `onPageReady`) and comes back a different height, shoving cited-by
under the reader. And cited-by's own repaint is a full `innerHTML` swap, so it
goes zero-height for an instant and the container clamps `scrollTop` — which
is why pressing "+ Add" (which routes back through `onLibraryChanged` →
*both* panels) made it worse.

**Fix.** `rerenderPreservingScroll(el, renderFn)` in `util.js`. Once the panel
has scrolled off the top, hold its **bottom** edge so the panels below it —
what the reader is looking at — don't move; while it's still on screen, hold
its **top** edge. Measurements are taken after `renderFn` as well as before,
so a `scrollTop` the browser clamped mid-render is corrected rather than
compounded.

## Verification

Two harnesses under `scripts/tests/`, wired into `run-all.sh`'s browser layer.
They live outside `rm/` on purpose: `OurlabMobile/scripts/sync-rm.mjs` rsyncs
the whole `rm/` tree into the phone app, so a test page there would ship.

- **`v3647-selftest.html`** (30 assertions) — the scroll anchor against a real
  scroll container (including a **control** proving a bare `innerHTML` wipe
  really does move the rail); the picker's always-rows, query-driven labels and
  raw-query `onPick`; the value picker's row set and its create-then-insert
  path; and `commitToLibrary`'s writes (server-timestamp stamped, both routes
  busted). It also asserts `typeof window.api === 'undefined'` — the dead-check
  trap, pinned so it can't quietly come back.
- **`v3647-caret.html`** (10 assertions) — loads the **real**
  `bindYTextToContentEditable` (Y.Text faked to its five-method surface; the
  thing under test is the caret, not the CRDT) and drives the actual first-click
  sequence: mousedown at a measured pixel → focus → mouseup.

**Negative control run.** With only the caret restore neutered, 4 assertions
fail and the caret reads exactly **0** — the predicted pre-fix failure mode.
Restored: 10/10.

Regression: V3.646 selftest 18/0, V3.646 UI journey 42/0, label-id parity
35/0, `gen-icons --scan` clean.

**Not covered headlessly:** `_deferWhileEditing` needs a live Yjs document and
an attached panel, so the table-cell fix is verified by reading rather than by
harness. Drive one table on a real paper before the batch ships.
