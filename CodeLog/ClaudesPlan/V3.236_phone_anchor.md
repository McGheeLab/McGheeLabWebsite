# V3.236 — Anchor the page on phone (Phase 3a polish)

> Polish on top of V3.235. User report: "*the pages on the phone feel loose, if i move to the left or the right the page moves around loose as well.*"

## Diagnosis

Two mobile-browser defaults make full-bleed phone layouts feel like they're floating:

1. **Horizontal page scroll.** If any descendant of `<body>` is even one pixel wider than the viewport, browsers add a horizontal scroll the user can drag through. The drawer pattern's `transform: translateX(±100%)` panes (positioned off-screen) plus subpixel rounding from KaTeX equations and PDF canvas elements were enough to open this scroll on real iPhones.
2. **Rubber-band vertical scroll.** iOS Safari (and Chrome on iOS) bounce the page past its content edges by default. Combined with the horizontal drag, the page feels disconnected from the viewport.

Both effects were dramatically worse on the drawer-host pages because they're full-bleed (`.lp-page { padding: 0; max-width: none }`, `.pe-page { height: 100vh }`) with no peripheral page chrome to anchor against.

## Fix

In [rm/css/tokens.css](../../rm/css/tokens.css), add a single ≤640px block that locks the page axis on the `<html>` + `<body>` elements:

```css
@media (max-width: 640px) {
  html,
  body {
    overflow-x: hidden;
    overscroll-behavior: none;
  }
  body {
    max-width: 100vw;
  }
}
```

- `overflow-x: hidden` clips any horizontal overflow from descendants — drawer transforms, wide PDFs, math, anything. The body can no longer be dragged horizontally.
- `overscroll-behavior: none` kills the vertical rubber-band so swiping past the content edges no longer makes the page bounce.
- `max-width: 100vw` on body is belt-and-suspenders: ensures the body box never exceeds viewport width even if some legacy CSS sets a wider `min-width` somewhere.

Internal scroll containers (the PDF viewer, comment lists, chat threads, the paragraph editor) keep their own overflow — they're free to scroll within their box without dragging the body.

The `.rm-mobile-drawer-locked` body class from V3.235 still wins when a drawer is open (it adds `position: fixed; width: 100%` for full scroll arrest, with the iOS-friendly scroll-position save).

Tablet + desktop are unaffected — the rules are scoped to `@media (max-width: 640px)`.

## Why on `<html>` AND `<body>`

iOS Safari historically split scroll behavior between `<html>` and `<body>`: some properties only take effect when applied to the root element, others only on body. Setting `overflow-x: hidden` and `overscroll-behavior: none` on both is the documented cross-browser-safe form.

## Why `overflow-x: hidden` doesn't break `position: sticky` on `.top-nav`

The well-known "overflow on ancestor breaks sticky" trap applies when an ancestor has `overflow: hidden` and the sticky element is supposed to scroll within that ancestor. Here the sticky element (`.top-nav`) is sticking to the viewport via the document scroll, not to an inner scroll container — and `overflow-x: hidden` doesn't create a new vertical scroll context (the vertical axis stays visible/auto, owned by the viewport).

Tested by re-loading the dashboard, tasks, calendar pages at 390px — sticky top nav still pins to the top edge.

## Verification

1. **Phone 390px (Chrome DevTools iPhone 14 Pro), paper-builder editor.** Tap on the title input area and drag finger left/right — page no longer slides horizontally. Drag finger up past the topbar — page no longer bounces.
2. **Phone 390px, library-paper reader.** Same horizontal-drag + bottom-edge-bounce test. PDF still pans inside `.lp-viewer` for zoomed-in pages (internal scroll preserved).
3. **Drawers still work.** Open ☰ Outline / 💬 Comments / ℹ️ Info / 📝 Notes — drawers slide in cleanly. Tap backdrop / Escape — they retract. Body scroll lock still engages while a drawer is open.
4. **Sticky top nav still pins.** Dashboard / tasks / calendar at 390px — `.top-nav` stays at the top edge while content scrolls.
5. **Tablet + desktop unchanged.** 1024px and 1440px — no visual or scroll behavior change vs V3.235.

## Out of scope

- **Per-page `touch-action` tuning.** Some pages (PDF viewer, chat) might benefit from explicit `touch-action: pan-y pan-x pinch-zoom` rules to better choreograph their internal pan/zoom with the body lock. Wait until a specific page surfaces a complaint.
- **iOS pinch-zoom prevention.** The viewport meta still allows pinch-zoom (V3.232 default) for accessibility. Not changing this.

## Rollback

`git revert` of this commit restores V3.235 behavior. The rule is additive in a `@media` block — removing it just restores default browser horizontal scroll + rubber-band on phones.
