# V3.497 — Attach an uploaded/fetched PDF to an existing PDF-less library entry (no more duplicates)

## Goal

When a paper is already in the library **without a PDF** and the user then
loads a PDF for it, the PDF should attach to the *existing* entry — not spawn a
second copy that has the PDF while the metadata-only original lingers.

## Root cause

There are three ways a paper enters the library, and each has a weak/absent
"is this already here?" check:

1. **Manual PDF drop / file-picker** — `_ingestOne` in
   [rm/js/library.js](../../rm/js/library.js). Its only dedupe is a **PDF
   content-hash** comparison via `LIBRARY_UPLOAD.findDuplicate`, and that
   helper *skips every entry that has no PDF* (`if (!pdf) continue`). So a
   metadata-only entry is invisible to it → a new copy (with PDF) is created.
   **This is the reported bug.**
2. **"Add by identifier" button** — `_wireDoiAdd` in library.js. Dedupes only
   on an **id-slug collision** (`_libraryPapers.some(x => x.id === item.id)`).
   A legacy entry whose slug differs slips through → duplicate.
3. **"Add" in citation / cited-by panels** — `LIBRARY_UPLOAD.fromDoi` in
   [rm/js/library-upload.js](../../rm/js/library-upload.js). Dedupes on **exact
   normalized DOI only**; when it *does* find the dup it returns early and never
   attaches a PDF, so a PDF-less entry stays PDF-less.

## Approach

### 1. One shared matcher (`library-upload.js`)

`LIBRARY_UPLOAD.findExistingEntry(meta, items) → { item, matchedBy } | null`

Priority order, considering only `meta.library.is_library_entry` rows:

- `doi` → `pmid` → `arxiv_id` (exact after normalization) → `matchedBy` in
  `{'doi','pmid','arxiv'}` — **safe, auto-attach**.
- normalized **title** (+ year when both present) → `matchedBy: 'title'` —
  **fuzzy, caller confirms**.

Normalizers (also exported): `_normDoi` (strip `doi.org/`, `doi:`, trailing
punctuation, lowercase), `_normArxiv` (strip `arxiv:` + `vN` version suffix),
`_normTitle` (lowercase, non-alphanumerics → single spaces, trim).

### 2. Wire the matcher into all three flows (per user: "all entry points")

- **`_ingestOne`** (library.js): after metadata resolves, before building a new
  item, call `findExistingEntry`. Title matches prompt via new `_confirmAttach`.
  - existing entry **has a PDF** → toast "already in library with a PDF", skip
    (no dup, no clobber).
  - existing entry **has no PDF** → `uploadPdf(match.id, file)`, stamp
    `meta.library.pdf` (`source:'manual_attach'`), clear `pdf_status`,
    `_saveItems()`, re-parse refs + SS-enrich in the background. Return early.
  - title match **declined** → fall through to today's new-entry path.
- **`_wireDoiAdd`** (library.js): replace the id-collision check with
  `findExistingEntry` (identifier → block; title → confirm-then-block). Keep the
  slug-collision line as a backstop for genuinely distinct papers.
- **`fromDoi`** (library-upload.js): replace the DOI-only dedupe with
  `findExistingEntry` (identifier matches only — this path is non-interactive so
  a fuzzy title match is *not* auto-merged). On an identifier match with no PDF,
  run the Unpaywall OA pipeline and attach to the existing row via a **targeted
  `items/{id}.set(..., {merge:true})`** (fullRefresh pattern — never rewrites the
  whole items array). Return `{item, alreadyExisted:true, attached, pdfInfo}`.

## Key decisions

- **Identifier auto, title-with-confirm** (user choice). `fromDoi` skips title
  matches entirely because it cannot prompt.
- **Existing-has-a-PDF → skip, never overwrite.** The content-hash dedupe still
  catches byte-identical re-uploads; a *different* PDF for the same paper is left
  alone (user can replace it from the reader page).
- **Save patterns stay native to each flow.** library.js mutates the in-memory
  `_libraryPapers` object and calls `_saveItems()` (its whole-array route, then
  `_load()`+`_render()`); `fromDoi` uses a targeted merge-set.
- **No new Firestore rules / indexes / functions.** FTP + sw bump only.

## Out of scope (noted for later)
