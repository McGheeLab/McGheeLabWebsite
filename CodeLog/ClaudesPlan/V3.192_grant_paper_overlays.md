# V3.192 — Grant ↔ Paper integration via the overlay system

(Originally planned as V3.187 → V3.188 → V3.189 three-phase rollout —
those slots were taken by today's concurrent ships, so all three slices
land as V3.192. Internal references below preserve **slice A / B / C**
to reflect the conceptual phasing.)

Shipped together as one bundle because the surfaces are tightly coupled
(grant editor → upload → paper reader).

## Goal

Connect the V3.179 grant writer to the lab's existing paper-overlay
infrastructure so the user's "Claude in the sibling repo runs a lit
review → highlights show up on the paper" workflow extends to grants.
Concretely:

1. **A grant has a sibling git repo** (`repo_path`) where lit reviews
   happen. AI-generated `.paper-overlay.md` files in that repo carry the
   grant id, get uploaded to the grant card, and materialize as
   annotations on the relevant library papers.
2. **Annotations gain a `type` field** (closed enum: evidence / method /
   result / limitation / claim / note / question) for cross-paper rollups
   and color-coded highlights.
3. **The grant card surfaces Linked Papers** — every library paper tagged
   with this grant id is one click from the grant editor; clicking opens
   the paper reader with that grant's overlay pre-activated.

The model leans on the existing draft-overlay machinery from V3.103+:
each annotation already carries `cite_in_drafts: [draftId]`, and each
library paper carries `meta.library.linked_drafts: [draftId]`. We treat
grant draft ids as just another draft id in this generic system — no
new "scope" concept, just two new sources that contribute draft ids
(grantDrafts collection alongside the existing items.json grants).

## Slice A — Linkage core (was: V3.187)

### Files

- [rm/pages/grant-builder.html](../../rm/pages/grant-builder.html) — adds
  `repo_path` field to the editor toolbar, "Linked Papers" sidebar panel
  with "+ Link" button and `.paper-overlay.md` drop zone, plus the
  Firebase Storage SDK.
- [rm/js/grant-editor.js](../../rm/js/grant-editor.js) — wires the
  `repo_path` input (autosave), the Linked Papers panel
  (`renderLinkedPapers`, `pickPaperToLink`, `tagPaperWithGrant`,
  `unlinkPaperFromGrant`), and the overlay drop zone
  (`wireOverlayDropzone`, `uploadOverlayFile`,
  `renderOverlayFilesList`).
- [rm/js/paper-overlays.js](../../rm/js/paper-overlays.js):
  - `_loadAllDrafts()` now also reads the V3.179 `grantDrafts/{id}`
    collection alongside items.json `type:'grant'`, so grant writer
    drafts appear in the paper reader's "+ Link draft" picker.
  - `_refreshLinkedDrafts()` resolves grant titles from grantDrafts when
    the id isn't found in items.json.
  - `_loadActive()` honors a `?draft=<id>` (or `?grant=<id>`) URL param
    by activating only that draft for the session; the persisted
    per-paper active set is left intact for the next visit without the
    param. Lets the grant editor's "open paper" link land users in a
    paper reader scoped to the grant.

### Data model

No new fields. Reuses:
- `grantDrafts/{id}.repo_path: string` — already accepted by V3.179's
  schema; surfaced in the editor for the first time.
- `meta.library.linked_drafts: [id]` on library items — already
  supported by V3.103.

## Slice B — Overlay upload + annotation_type (was: V3.188)

### Files

- [rm/js/grant-editor.js](../../rm/js/grant-editor.js) (cont.) — overlay
  drop zone uploads `.paper-overlay.md` files to Storage at
  `grant-overlays/{grantId}/{sha256}.md` and registers metadata at
  `grantDrafts/{grantId}/overlays/{sha256}`. Doc id = content hash so
  re-drops are idempotent. Auto-tags the referenced paper with this grant
  id (calls `tagPaperWithGrant(paperId)`) so the paper appears in the
  Linked Papers panel even before the user opens the paper reader.
- [rm/js/paper-overlay-import.js](../../rm/js/paper-overlay-import.js):
  - Validate function now parses `type:` per highlight, validates against
    the closed enum, defaults to `'note'`.
  - Stamps `annotation_type` on each created annotation.
  - Recognizes `grant:` / `grant_id:` frontmatter as aliases for
    `draft_id:` (legacy `bucket_id:` still accepted).
  - Preview modal shows a small type chip per highlight row.
- [rm/js/library-paper.js](../../rm/js/library-paper.js) — auto-fetches
  uploaded overlay files when the URL carries `?import=<overlayId>&draft=<grantId>`.
  Reads the metadata from `grantDrafts/{grantId}/overlays/{overlayId}`,
  fetches the file from `downloadUrl`, wraps it as a synthetic File, and
  hands it to `PAPER_OVERLAY_IMPORT.handleDrop()` so the existing import
  modal materializes the highlights. Lets a collaborator without the
  sibling repo materialize highlights by clicking "open & import" in the
  grant card.
- [firestore.rules](../../firestore.rules) — new rule block
  `grantDrafts/{grantId}/overlays/{overlayId}` (lab read, member create
  where `uploadedBy == auth.uid`, lab update, creator-or-admin delete).
- [storage.rules](../../storage.rules) — new `grant-overlays/{grantId}/*`
  block (lab read, lab write, 1 MB cap). Markdown files only by
  convention; no content-type guard since markdown has no standard MIME.

### Annotation enum

Closed list of 7, chosen for a grant lit review:

| type | use |
|---|---|
| `evidence` | Supports a claim. Often paired with `evidence_stance: for`. |
| `method` | Technique you'd use or cite when describing methods. |
| `result` | Specific finding to cite. |
| `limitation` | Gap/problem the paper acknowledges (gold for Significance/Innovation). |
| `claim` | A claim the paper makes that you want to track. |
| `note` | Default — generic annotation. |
| `question` | Follow-up to investigate. |

### Schema delta

- New field on annotations: `annotation_type: string` (one of the 7
  values above; `'note'` default for legacy data that doesn't carry it).
- New subcollection: `grantDrafts/{grantId}/overlays/{overlayId}` with
  fields `{fileName, fileHash, fileSize, storagePath, downloadUrl,
  paperId, paperDoi, draftId, overlayTitle, uploadedBy, uploadedAt}`.

## Verification

1. Open a grant draft at `/rm/pages/grant-builder.html?grant=<id>`. Type
   a sibling repo path (e.g. `../GELS-R01`) into the Repo field;
   confirm autosave.
2. Click "+ Link" in the Linked Papers panel; pick a library paper;
   confirm it appears in the panel and the underlying
   `meta.library.linked_drafts` array now contains this grant id.
3. Author a `.paper-overlay.md` in a sibling repo using the
   `paper-overlay` skill (`grant: <id>`, several highlights with `type:`
   set). Drag it onto the grant editor's drop zone. Confirm:
   - The overlay file uploads to Firebase Storage at
     `grant-overlays/{grantId}/<sha256>.md`.
   - A doc appears at `grantDrafts/{grantId}/overlays/<sha256>`.
   - The Uploaded overlays list shows it with an "open & import" link.
   - The referenced paper is auto-tagged with this grant id (appears in
     the Linked Papers panel).
4. Click "open & import" → land in the paper reader with the import
   modal pre-populated. Confirm matched highlights show their type chip.
   Import. Confirm `annotation_type` is set on each new annotation in
   Firestore.
5. In the paper reader, verify the new type-filter pills (7 pills with
   counts). Toggle "limitation" off → red highlights disappear. Toggle
   back on → they return.
6. Open the same paper reader with `?id=<paper>&draft=<grantId>`.
   Confirm only that grant's overlay is active (overlays popover shows
   1/N drafts active). Refresh without the param → persisted set
   restored.
7. `firebase deploy --only firestore:rules` and
   `firebase deploy --only storage` — confirm both deploy cleanly.

## Out of scope / deferred

- **Cross-paper rollup in the grant editor** (e.g. "evidence highlights
  across all 14 linked papers") — V3.190+.
- **Annotation-type editing for non-overlay annotations** — the type
  filter renders all annotations (defaulting to 'note'); the
  annotation-panel doesn't yet expose a type picker for hand-created
  highlights. V3.190+.
- **Auto-PDF-stub when the overlay references an unknown paper_id** —
  today the import fails if the paper isn't in the library. Auto-stub
  would create a library item and queue a PDF fetch. V3.190+.
- **Letter-of-support uploads** still V3.183+.
- **Cloud Functions trigger on overlay upload** to auto-summarize the
  per-type annotation counts onto the grant card's badge — V3.190+.
