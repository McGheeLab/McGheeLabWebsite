# V3.62 — Page consolidation Tier 4: activity hub

## Goal

Final tier of the V3.57–V3.62 consolidation sweep. Five activity-
related pages collapse into one tab-aware shell at
[rm/pages/activity-overview.html](../../rm/pages/activity-overview.html)
selected by `?tab=<name>`. This is the largest single page-merge in
the sweep (the activity-overview renderer alone is 4309 LOC) and
closes the consolidation work. Reduce 5 pages → 1.

## Context

After V3.57–V3.61, RM was at 42 user-facing pages (down from 51).
Tier 4 was always the biggest single PR. Five pages all read the
same email/calendar/tracker data with different framings:

| Tab | Former page | Renderer LOC |
|---|---|---|
| Overview (default) | activity-overview.html | activity-overview.js (4309) |
| Tracker | activity-tracker.html | activity-tracker.js (2123) |
| Year Timeline | year-review.html | year-review.js (1507) |
| Email | email-review.html | email-review.js (2254) |
| Lab Stats | activity-summary.html | activity-summary.js (172) |

The combined renderer LOC is ~10K. Loading all five eagerly on every
page hit would be wasteful — instead the unified shell uses
`document.write` to inject only the active tab's renderer scripts.

## Approach

Same `?tab=<name>` shell pattern V3.58–V3.61 established, scaled to
five tabs. The biggest change versus prior tiers: each tab's inline
CSS was substantial enough to extract into its own `rm/css/<tab>.css`
file. The shell loads all four extracted CSS files eagerly (each
scoped to its prefix — `act-*` / `cx-*` / `jp-*` for overview, `yr-*`
for timeline, `ch-*` / `er-*` / `disp-*` for email, plus the existing
`activity-tracker.css`). Cross-tab CSS pollution is harmless because
of the prefixing.

### Per-tab DOM blocks

Each tab's content is wrapped in `<div class="act-tab tab-<name>">`.
CSS rules:

```css
html[data-act-tab="overview"]  .act-tab:not(.tab-overview)  { display: none; }
html[data-act-tab="tracker"]   .act-tab:not(.tab-tracker)   { display: none; }
html[data-act-tab="timeline"]  .act-tab:not(.tab-timeline)  { display: none; }
html[data-act-tab="email"]     .act-tab:not(.tab-email)     { display: none; }
html[data-act-tab="lab-stats"] .act-tab:not(.tab-lab-stats) { display: none; }
```

The early head script sets `document.documentElement.dataset.actTab`
from the `?tab=` query, so inactive blocks are hidden before first
paint.

### `#content` collision handling

Three of the renderers (year-review, email-review, activity-summary)
all query `#content`. Putting all three in the static HTML would
collide. Solution: the shell does NOT include a `#content` div in
any of those tabs' blocks. Instead, an inline body script appends a
single `#content` div to the active tab's block when one of the
three tabs is active. Only one renderer is active at a time, so no
DOM-element collision.

### Per-tab script loading

Each tab has its own dependency stack — the bundles aren't fully
identical:

- **Overview:** yr-shared, task-editor, explorer-detail, activity-overview.js
- **Tracker:** chart.js@4.4.0, rm-categories, GIS client, calendar-service, activity-tracker.js
- **Timeline:** yr-shared, chart.js@4.4.4, cv-schemas, cv-send, year-review.js
- **Email:** yr-shared, disp-shared, task-editor, chart.js@4.4.4, task-quick-builder, email-review.js
- **Lab Stats:** activity-summary.js (only)

Common scripts (firebase compat, firebridge, util.js, nav.js,
api-firestore-adapter, etc.) load eagerly. Per-tab scripts inject via
`document.write` so the renderer's `DOMContentLoaded` boot fires at
the natural time.

### Note on Chart.js version drift

The lab apps locked to chart.js@4.4.0 (activity-tracker) while
year-review and email-review use chart.js@4.4.4. The unified shell
loads whichever the active tab needs. Future cleanup could
standardize on 4.4.4 — non-blocking.

- **Firestore paths** — all unchanged.

## Trade-offs

- **All four extracted CSS files load on every tab.** Total ~750 LOC
  of CSS = ~30KB. Not free, but small. Each is properly scoped so
  there's no cross-tab visual interference.
- **The shell file is 250+ LOC** because it contains five DOM blocks.
  Acceptable — the CSS extraction kept it manageable.
- **Tab switch is still a full page reload** (same as prior tiers).
  Cached resource fetch is ~150ms.
- **The `#content` divs are added by JS at page load** for three of
  the tabs. Slightly less clean than static HTML but unambiguous and
  avoids the DOM-element collision problem.
- **Two chart.js versions in the source tree** (4.4.0 + 4.4.4). Each
  tab pulls only its own. Minor: the SW cache holds both.
