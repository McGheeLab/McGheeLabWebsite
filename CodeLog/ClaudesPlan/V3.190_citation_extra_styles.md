# V3.190 — Additional citation styles + diagnostic improvements

## Trigger

User report (2026-05-12, follow-up to V3.188) — two papers still misbehave:

1. `10.1007/s00018-025-06036-6` (Springer CMLS) — "still doesn't work at
   all". Journal style guide says `[N]` bracketed Vancouver numbers,
   which V3.188's `RE_NUMERIC` already covers. So either:
   - The PDF doesn't use standard ASCII brackets (some Springer typesets
     render bracketed cites as `〔N〕` or `［N］` or via a separate font
     mapping that the text layer extracts as different codepoints), OR
   - The refs parser fails for this paper and the inline scanner finds
     0 tokens (no `[N]` anywhere in body text), OR
   - The PDF text layer is empty / image-based.

2. `10.3389/fmolb.2022.998475` (Frontiers in Molecular Biosciences) —
   "about 1/2 of citations work". V3.188 catches 2-author + et-al cites
   inside the standard `(...)` group, but misses **3+ author cites
   without "et al."** like `(Smith, Jones, and Williams, 2021)` and
   author-with-particle cites like `(van der Berg, 2020)`.

We can't fix #1 blindly — we need the user to share what the console
diagnostic actually says. V3.190 makes that diagnostic strictly more
useful, and **always** logs (V3.188 only logged when ≥1 match found,
which is the wrong way around — pages where zero matches surface are
exactly the pages we need to diagnose).

## Changes

### 1. Always-on per-page diagnostic + debug text dump
`_scanPage` now `console.info`s a `[paper-citations] p.N matches: …`
summary even when the page produced zero matches (`(none)` is logged
in that case). Set `window.__PAPER_CITATIONS_DEBUG__ = true` before
navigating to additionally dump:
- The first ~400 chars of the page's joined text layer (lets us see
  what citation tokens actually look like in the PDF — bracket vs paren
  vs superscript, ASCII vs unicode, etc.).
- The page's `medianH` + `items.length` (lets us debug whether the
  geom-super heuristic has reasonable data to work with).

User instruction set for diagnosing a new failure:
```
1. Open the paper in the RM reader.
2. Open DevTools → Console.
3. Run `window.__PAPER_CITATIONS_DEBUG__ = true`.
4. Page through 2-3 body pages.
5. Share the `[paper-citations]` lines back.
```

### 2. Author-with-particle support
Surnames can now carry 0-2 lowercase particles before the capitalised
core: `van`, `von`, `der`, `den`, `de`, `del`, `della`, `le`, `la`,
`du`, `ten`, `ter`, `d'` (ASCII apostrophe) / `d’` (Unicode curly).
Catches `(van der Berg, 2020)`, `(de Vries, 2019)`, `(von Hippel,
2018)`, `(le Carré, 2020)`, `(della Rovere, 2021)`, etc.

Implementation: new `_PARTICLE_SRC` prefix prepended to `_SURNAME_SRC`.
The particle group is greedy on 0-2 repeats; backtracks to 0 when the
following text isn't a capitalised word. Risk of overreach in body
prose is bounded because particle-surnames only fire inside
`_scanAuthorYearGroup` / `_scanNarrative` — both gated by a year
following the author, so "from van Gogh's painting" can't accidentally
get flagged as a citation.

### 3. 3+ author cite support
Author group regex's second branch now reads
```
(?:\s*,\s*SURNAME)*\s*,?\s*(?:and|&)\s+SURNAME
```
Catches `(Smith, Jones, and Williams, 2021)`,
`(Murray, Lopez, Wang, and Chen, 2022)`, etc. Two-author cites
(`Smith and Jones, 2020`) still work via the 0-iteration path of the
new repeat.

### 4. (Deferred) Unusual bracket codepoints
I considered extending `RE_NUMERIC` to also match unicode bracket
variants (`〔〕`, `［］`, `⟨⟩`) but skipped — these are extremely rare
in Springer / Nature / Frontiers PDFs and adding them without seeing
an actual failing PDF could cause false positives. If the user's
console diagnostic on the CMLS paper shows weird bracket chars, we
add them in a follow-up.
