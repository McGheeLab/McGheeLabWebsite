# V3.857 — Scientia online: upload from the desktop, sync both ways

Alex (2026-10-23): *"i want gabe to be able to upload files from scientia into the online
version, and i want him to be able to sync it to his desktop version."*

This closes open decision 8 of [V3.832_scientia_integration_plan.md](V3.832_scientia_integration_plan.md)
("Gabe's own app syncing with the site") — wanted, and built now.

## What "online version" means here (assumption, stated)

The **online version** is Gabe's own build served unchanged at `mcgheelab.com/rm/scientia/`
(the V3.832 sandbox, wrapped by `rm/pages/scientia.html`). Alex's words pair "the online
version" with "his desktop version": the same app in two places. It is *not* a translation
of Scientia records into our canvas notebook (that bridge is lossy — the ink models differ —
and §4.9 of the V3.832 plan keeps it a separate, later project). Nothing in Gabe's app is
rewritten: his sync client already speaks a small HTTP protocol to "the computer that holds
the record"; we give it a second computer in the cloud.

## Goal

1. **Upload**: Gabe exports from desktop Scientia (Settings → *Export everything (JSON)*, or
   the notebook folder's `.scientia/record.json`) and drops the file on the online page. The
   online copy then shows that notebook, saved to his account — not to one browser.
2. **Sync**: his desktop app and the online copy converge on one record. A change on either
   side shows on the other within seconds; both can be offline and catch up; the same
   three-way field merge and ⚠ conflict decisions Gabe built apply.
3. Media (images, PDFs, recordings) travel with the record.

## How Gabe's sync works (read from `src/13zc-sync.js`, `serve.py`, `sisync.py`)

- `serve.py` on the desktop is the **hub**: it holds the record in memory and is its single
  writer. Every browser (the desktop's own included) is a **device** that `push`es changed
  records one by one (`{store, id, rec, del, prev, base}`) and long-polls `pull` for
  everyone else's ops (`seq`-numbered, tagged with the sender's `conn` so a device never
  receives its own). `hello` says whether the caller is paired, whether it is "the computer"
  (`local`), and the hub's `sid`/`seq`/record count. `state` is the whole record; a device
  whose `sid` no longer matches gets `reset` and reloads it. `snapshot` POST **replaces** the
  whole record (new `sid`) — only the computer may do it.
- `sisync.py` merges: a push whose `base` predates another device's change goes through
  `merge3(prev, mine, cur)` — fields only one side touched merge, `AUTO_MAX` timestamps take
  the max, scalar lists union, the rest becomes a **conflict** the person decides from ⚠.
- `journal`, `blobs` (browser-kept files) and `datasets` (folder handles) never sync.

## Design — Firestore is the second computer

```
 desktop Scientia  ←→  serve.py (hub A)  ←→  scientia-cloud.py (bridge)  ←→  scientiaHub (hub B, Cloud Function)  ←→  online Scientia (device)
      browser              Gabe's code         new, runs on the desktop         new, Gabe's protocol on Firestore         Gabe's build + cloud-sync.js shim
```

### 1. `functions/scientia-hub.js` — Gabe's hub protocol as a Cloud Function
One HTTPS function, `scientiaHub`, routes `/api/sync/hello|state|pull|push|conflicts|resolve`,
`/api/snapshot` (GET = state, POST = replace, `?keep=` = a kept copy to Storage), `/api/media`
(POST bytes → Storage, GET `/api/media/list` → name → download-URL map), `/api/rec` (recordings),
`/api/ping`, `/api/notebook`, `/api/cloud/key*` (desktop keys), and harmless stubs for the
desktop-only endpoints (`net`, `pair/*`, `devices*`, `hw/*`, `stt/*`, `slides*`, `ink/*`,
`vault`, `tailscale/serve`) so the untouched build never sees a 404 where it expects JSON.
`functions/scientia-hub-core.js` is the DOM-free port of `sisync.py` (`merge3`, `planPush`,
`pullResult`, `planResolve`, `planReplace`, `exportState`) shared by the function, the node
fixtures and the local dev hub.

**Where it lives — one hub per person, under the owner catch-all (no rules deploy):**
- `userData/{uid}/scientia/hub` — `{sid, seq, minSeq, records, savedAt, conflicts[], conflictsN, meta}`
- `…/hub/rows/{store}__{id}` — the current record per row (`rec`, or `deleted:true` as a
  tombstone that keeps the version `seq`/`dev` Gabe's "others changed it" test needs)
- `…/hub/ops/{seq}` — the ops log devices pull from (last 50 000 kept, `minSeq` moves)
- `…/hub/keys/{id}` — desktop sync keys (sha-256 hash, name, lastSeen); the key itself is
  shown once
- `…/hub/media/{name}` — `{path, url, bytes, mime}` for files in Storage
  `scientia/{uid}/images/*` and `scientia/{uid}/recordings/*` (download-token URLs, so an
  `<img>` needs no auth)
`match /userData/{userId}/{document=**}` already gives the owner read+write; the function
uses the Admin SDK. Auth = Firebase ID token (`Authorization: Bearer`) for the browser, or
`X-Scientia-Key: sck_<uid>_<secret>` for the desktop bridge; both require `users/{uid}.role
!= 'guest'`. Pushes run in Firestore transactions of ≤150 ops (read meta + the touched rows,
plan, write rows + ops + meta). `pull` never blocks (see the shim); the bridge polls.

### 2. `rm/scientia/cloud-sync.js` — the shim in the hosted build
One `<script src="cloud-sync.js">` inserted before Gabe's app script (the only change to
`rm/scientia/scientia.html`; `scripts/scientia_patch.py` re-applies it to his next build).
It loads the Firebase compat SDK, signs in from the site's persisted session, and overrides
`window.fetch` for the relative `api/…`, `images/…`, `recordings/…` URLs the build uses:
- `api/*` → the function, with the ID token. `hello` answers `local:false` so the build
  behaves as a **device** (Gabe's own rules: no whole-record replace from a device, blobs stay
  local, no SW).
- `api/sync/pull?wait=25` waits on a Firestore listener of the hub meta doc (`seq`,
  `conflictsN`) instead of holding a function open, then calls `pull` once — idle costs
  nothing.
- First sign-in with an **empty hub and notes already in this browser** (the sandbox era):
  the shim uploads what the browser holds as the hub's first record, so nobody loses the
  notes they made in the sandbox.
- `images/…` and `recordings/…` → the media map (`MEDIA.url` patched after load + a
  MutationObserver on `src`/`href`), so pictures and audio come from Storage.
- Signed out: `hello` says `auth:false` → Gabe's pairing screen, which the shim replaces
  with a "sign in on the lab site" card.

### 3. `rm/pages/scientia.html` — upload, download, desktop keys
The banner becomes a sync panel: live status (records · last change · conflicts) from the
hub meta doc; **⇪ Upload from desktop** (a `.json` export or `record.json`; `journal`/`blobs`/
`datasets` stripped client-side; POST `/api/snapshot`; the frame reloads); **⇩ Download
(JSON)**; **Desktop sync…** — make / name / revoke keys inline (no browser prompts), the
three steps, and the bridge script to download. "Open full screen" and the manual stay.

### 4. `rm/scientia/scientia-cloud.py` — the desktop bridge
A small Python script that runs next to `serve.py` (Mac or Windows, standard library only).
It is a *device of both hubs*: it keeps a shadow of every row on each side, pulls from one
hub and pushes to the other with `prev`/`base` filled from that side's shadow, relays the
hub's merged `echo` back, and tags everything with its own `conn` so nothing loops. Resets:
if one side's `sid` changed (a file uploaded online, another notebook folder chosen locally)
that side is the source and the other is replaced (the desktop hub keeps `before-replace`
copies in `.scientia/kept/`; the cloud keeps one in Storage). First run with records on both
sides needs `--prefer local|cloud`. Media: files referenced by `media` rows and recordings are
uploaded when missing in the cloud and downloaded into the notebook folder when missing
locally (≤30 MiB each through the function). Config: `cloud.json` next to Gabe's
`config.json`. Run: `python3 scientia-cloud.py --key sck_…` once, then `python3
scientia-cloud.py` (loops; `--once` for a single pass).

## Not in this version
A server-side journal (desktop "time travel" stays desktop-only); transcription in the cloud
(the desktop Whisper still transcribes; the cloud answers `rec/status` with none); mentor/admin
view of someone else's Scientia hub (the catch-all is owner-only — a later rules clause);
files over 30 MiB; the translation into our canvas notebook.
