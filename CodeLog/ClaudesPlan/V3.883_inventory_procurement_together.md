# V3.883 — Inventory and procurement, working together (journeys tested across both pages)

**Date:** 2026-10-23
**Request (Alex):** *"lets make sure that the inventory and procruement work together well. do multiple tests to ensure
that all the different user workflows will be easy and seemless."*

## Baseline (before any change)

Every existing suite on either side was green: procurement core 287, custom items 69, labels 20, use plans 29, and on
the emulator inventory rules 59, procurement rules 162, inventory E2E 96, procurement E2E 96. Each side was tested on
its own; no test followed a person from one page to the other.

## The seams, and what was wrong at each

| hand-off | what happened | fix |
|---|---|---|
| **Put away as a new item** (`newInventoryItem`) | no `is_consumable`, `condition` or `subcategory`. A box of tips put away from a request was not a consumable, so **every member's scan asked "per use or package?"** (`INV_USE.modeOf` → '') | consumable = `consumable` or `research_*`, as inventory's own **+ Add Item** does; `condition: 'active'`; `stock_status` `full` / `n/a` |
| **Location spelling** | put-away kept the text as typed; a restock to "Freezer A / drawer 2" added a second location beside "Freezer A/drawer 2" | `tidyLocation` (the custom-item form's rule) on the new item, the restock match and the ticket's own `location` |
| **Reorder existing** (`catalogue`) and the put-away restock search (`searchInventory`) | listed custom aliquots / materials / media, which nobody sells | skip `lab_made` |
| **"Low"** | procurement's `stockOf` used `qty_min` only; inventory also calls a batch low at 20 % left (`INV_QTY.severity`). The same item read "in stock" in Reorder existing and "low" in inventory | `stockOf` mirrors `INV_QTY.severity` (explicit `qty_min`, else ≤ 20 % of `qty_made`) |
| **Request reorder twice** | an item already on order could be requested again from the inventory panel, the scan toast or Reorder existing, and nothing on either page said so | `openRequestsFor(tickets, item)` (core): the reorder composer says *Already requested: Ordered · PO-77 · ETA … (by Sam)* with a link, and the inventory panel shows it beside **Request reorder** |
| **Where did this come from?** | an item put away from a request kept `procurementTicketId` / `last_procurement_ticket_id`, but the inventory panel never showed it, so the request (and its receipts) could not be reached from the item | the panel says *Bought through a request (Oct 21) — view it* and *Last restocked through a request — view it*, linking `procurement.html?ticket=` (which already opens the right tab) |

The inventory page now loads `procurement-core.js` (DOM-free) and the tickets route, so "open request" and "low" mean
the same thing on both pages, from one implementation.

## The journeys (one database, both real pages)

`scripts/tests/v3883-inventory-procurement-journeys.html`: the real `procurement.js` and the real `inventory.js`,
each in its own iframe (`scripts/tests/fixtures/journey-procurement.html`, `…/journey-inventory.html`), both reading
and writing ONE in-memory Firestore held by the harness, so what one page writes the other reads. Persona switch =
reload the frame as someone else (student, PI, purchaser, inventory manager, other member). Dates cross the frames as
ISO strings revived in the reading frame, so `instanceof Date` holds.

1. **A new thing, start to finish.** Student requests → PI approves → purchaser orders with a PO file → a member
   receives with a receipt → puts it away (location typed with spaces) → *Open in inventory*: it is in the default
   pills, a consumable, location tidied, *Bought through a request* links back; one scan takes a package without asking
   the mode; the PO and receipt are in Receipts, linked.
2. **Reorder from the inventory panel.** *Request reorder* → the composer is prefilled (name, vendor, cat #, price,
   project) and linked to the item → submit → the inventory panel shows it as on order → a second *Request reorder*
   lands on the composer with *Already requested*.
3. **Reorder existing.** The catalogue lists bought things and leaves custom items out; a tracked item at 10 % reads
   low in both places.
4. **Restock.** Untracked: quantity added to the same (tidied) location. Tracked, by a member: location and quantity
   recorded, count not raised, the warning says to ask an inventory manager. Tracked, by an inventory manager: count
   raised with an `add` ledger row.
5. **Receipts reach the item.** A receipt filed in Receipts for the request is one click from the inventory item
   (*view it* → the request card's *Receipts & documents*).
6. **Make something from what was bought.** The custom-item form's *Made from* finds the item just put away; an
   untracked box is noted unless *whole packages* is chosen, which takes one off its Qty column.

Then everything in the baseline again, plus the selftests.
