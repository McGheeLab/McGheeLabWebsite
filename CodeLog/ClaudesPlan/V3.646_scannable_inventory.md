# V3.646 — Scannable inventory: label queue, custom stock, boxes, usage

> Approved plan (verbatim source): `~/.claude/plans/we-have-a-working-reactive-hamster.md`

## Goal

Make the QR codes the lab already prints resolve to something. Today they resolve
to **nothing outside one Windows machine** — printed tube records append to
`data/tubes.ndjson` on the printer PC (`LabelPrinter/agent/server.py:355-375`) and
`grep -rln firebase web/` in that repo returns nothing.

RM becomes the surface where labels are composed and codes are minted; the printer
becomes a **queue consumer**; a scan — desktop webcam, USB barcode gun, or the
Ourlab app — resolves to a real record you can take material from.

```
compose a label anywhere → queues to the printer → print → scan on any surface
   → say how much you took → the count drops → the manager is told when it runs low
```

## Why now

RM's inventory cannot express what the lab holds. Quantity is **three
unreconciled numbers** with nothing summing or validating them:

1. `item.quantity` — a scalar, edited through a *text* input
   (`rm/js/inventory.js:311`), so `inlineSave`'s else-branch (`:171`) sometimes
   stores a **string**. One of 777 seed rows already is one. It has **no unit
   anywhere**.
2. `item.locations[] = [{name, quantity, notes}]` — **0 of 777 items populate
   it**, no invariant that the sum equals `quantity`.
3. `item.stock_status` — hand-set, and `low`/`out_of_stock` appear on **zero** of
   777 rows, so the Low/Out tab (`:34`), the amber dashboard card
   (`dashboard.js:299-303`) and the protocol stock chips
   (`protocol-inventory.js:227-252`) are all live code paths that have never
   rendered a non-empty result.

No consumption path, no audit trail, no threshold, no alerting.

## Measured constraints (verified by running the real code)

1. **A URL payload costs the 2-column QR.** An 8–11 char code is QR v1 = 63 + 14
   quiet = **77 dots**, leaving 159 of 236 at 2 columns — just above the label
   app's `QR_MIN_TEXT = 150` floor. Any full URL is 29+ chars → v2 → **89 dots** →
   147 left → **suppressed**. `LabelPrinter/tests/check_qr.mjs:40` already blesses
   the URL as "the future 31-char payload" but only asserts `version ≤ 2` — it
   never checks `QR_MIN_TEXT`, which is why this looked free.
2. **Do not widen the code body.** `LabelPrinter/web/core/layout.js:572-578`
   prints the human-readable code in a `blockW = qrPix` = 63-dot block at `h=12`
   with **no `fitHeight` and no clip warning**. Exhaustive over all 32⁴ bodies:
   **31% of today's codes already overflow it** (worst `MG-MMMMM` = 75 dots).
   Widening trades a probabilistic problem central minting *eliminates* for a
   deterministic legibility regression. Widening the block to `qrPix + QR_QUIET`
   (77) gives 0% overflow at every length — that's the fix.
3. **Central minting is what makes 4 random chars safe.** Local minting checks
   collisions only within the print batch; 32⁴ = 1,048,576 ⇒ ~38% chance of a
   duplicate across 1,000 codes. Reserving `labels/{CODE}` in a transaction makes
   keyspace a retry-*rate* question (~1% per mint at 10,000 codes).
4. **`normalize()` degrades a URL by `split('/').pop()`** — so the box URL must be
   **path-style at the site root** (`MCGHEELAB.COM/L/MG-A7K2X`); `?` and `#` are
   not in the QR alphanumeric charset anyway. It also folds `I/L/O/U` inside the
   prefix, so `labels/` doc ids must be `normalize(code)`, never the raw mint.
5. **iOS WKWebView has no `BarcodeDetector`** (WebKit never shipped Shape
   Detection), so a vendored decoder is mandatory. jsQR only.

## Approach

**The queue carries label *content*, never geometry.** LabelPrinter's invariant is
that `web/core/layout.js` is the only file permitted to compute a coordinate. A
queue job ships cells in the **exact shape `emptyCell()` already produces**
(`LabelPrinter/web/core/batch.js:19-40`), and the printer's own engine lays them
out — keeping every fitting rule, overflow warning and QR-suppression decision.

### Collections

| path | why here |
|---|---|
| `inventory/{id}` + `kind:'stock'` | The adapter's delete-diff is **scoped to the route's `where`** (`api-firestore-adapter.js:249-253`), so a new kind is untouched by existing routes. Stock batches genuinely are inventory. |
| `inventoryLocations/{locId}` | Boxes are a **dimension**, not a fact. No `unit_price`/`vendor`/`reorder`; they *nest* (`parentId`); and `kind:'box'` would pollute every kind-agnostic reduce (`dashboard.js:298`, `analytics.js:80`, `budget-model.js:62`). |
| `labels/{CODE}` | Doc id **is** `normalize(code)`. One `getDoc` resolves any scan. Indirection lets a label be re-bound without the code changing. |
| `labelQueue/{jobId}` | `cells[]` matches `emptyCell()` field-for-field ⇒ zero translation at import. |
| `inventoryUsage/{eventId}` | Top-level, **not** a subcollection: the queries that justify the feature are cross-item, and `firestore.indexes.json` has **zero** COLLECTION_GROUP indexes today. |
| `labInitials/{INITIALS}` | Uniqueness by create-only reservation. Canonical value on `users/{uid}.initials` — `firestore.rules:261-263` already allows self-write, so **no `users` rule change**. |

Six new quantity fields **alongside** `quantity`, never repairing it in place:
`qty_tracked` (absent/false ⇒ nothing changes — the opt-in), `qty_unit`,
`qty_made`, `qty_remaining`, `qty_min`, `qty_recounted_at`, plus a server-only
`low_alerted_at`. Verified no existing consumer reads any new name. **No bulk
migration.**

### The core rule

Any lab member may **DECREASE** `qty_remaining` (a consumption event); only a
manager may raise it or set an absolute value (a recount — the auditable act).
`.get(field, <resource's own value>)` is deliberate so a write that *omits* the
field compares EQUAL rather than erroring; `is number` guards are mandatory
because `'10' <= '5'` is TRUE lexicographically.

### Ledger self-checks itself

`before`/`after` on **every** row means row N's `before` must equal row N−1's
`after` — so a lost write or a rogue edit to `qty_remaining` is detectable by
scanning history, without trusting the counter. `allow update, delete: if false`;
a wrong row is corrected by an offsetting `recount`, never by editing history.

### Contents are a reverse lookup

Items carry `locations:[{locId, name, quantity, unit, notes}]` + a flat
`locIds:[...]` mirror, so "what's in box 4" is
`where('locIds','array-contains','box-4')` — equality only, **no composite
index**. A denormalized `contents[]` on the box would need a write on every
consumption event from a client that may not own the box.

Alex's example gets an honest home: the **box** has `capacity_slots: 10`, the
**item** has `locations:[{locId:'box-4', quantity:3, unit:'pack'}]`, and remaining
slots is **derived, never stored**.

Five indexes. **`inventory: kind ASC, updatedAt DESC` is a fix to current
production**: `api-firestore-adapter.js:440-441` runs that exact query as a
cheap-freshness probe on every inventory page load, and with no index it throws
into `catch → fall through` (`:401-403`) and refetches all 777 docs. Keyed on the
field not the value, so one index serves all three routes. Also — if it was ever
created from a console error link it isn't in the file, and the next
`firestore:indexes` deploy would offer to **delete** it.

## Open assumptions

1. **Aliquot labels default to the parent's QR.** Alex's stated model was no-QR;
   made a toggle instead of the default, because a no-QR aliquot is a tube you
   cannot identify — the problem this feature exists to solve.
2. `labels/{CODE}` read is `isLabMember()`, not `request.auth != null`.
3. `.htaccess` overrides work on GoDaddy (box URLs degrade to bare codes if not).
4. Recipes deferred — `recipeId: null` + `composition[]` reserved now so it is a
   later addition, not a migration.
5. Making a batch does **not** decrement its ingredients (a second ledger
   direction; would double the rules surface).
