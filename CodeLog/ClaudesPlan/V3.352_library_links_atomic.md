# V3.352 — Atomic linked_drafts helper + library linkage visibility

**Part of:** [FuturePlan 09 — Builder ↔ library ↔ reader bridge](../Feature%20requests/FuturePlan_12_builder_library_bridge.md) (Release 3 of 3 — final).

## Goal

Kill the lost-update bug in draft↔paper linking and make the linkage
visible from the library side.

## What shipped

- **New `rm/js/library-links.js`** — `LIBRARY_LINKS.toggleDraftLink(
  itemId, draftId, makeLink)`: single-doc `update()` with
  `FieldValue.arrayUnion/arrayRemove` on `meta.library.linked_drafts` +
  `updatedAt` serverTimestamp / `updated_at` date stamps (the V3.309
  `_saveOne` pattern, so other clients' cached items.json invalidates
  via the adapter's MAX-probe). Concurrency-safe by construction — no
  read-modify-write. The items update rule's V3.309 branch already
  permits lab members this nested-field write; **no rules change**.
- **Five writers refactored to it** (was: each did
  `api.load('items.json')` → mutate → `api.save` whole-array — a
  full-collection batch replace where two concurrent writers silently
  lost one update): `paper-equations.js _toggleLinkToDraft`,
  `paper-overlays.js linkDraft`/`unlinkDraft` **and** the link-picker's
  multi-select commit (now diffs desired-vs-current and applies atomic
  ops), `grant-editor.js tagPaperWithGrant`/`unlinkPaperFromGrant`.
  `grep -rn linked_drafts rm/js` shows mutations only in
  library-links.js.
- **Library page linkage badge** — each row shows
  `→ N draft(s)` (`.lib-links-badge`) when `meta.library.linked_drafts`
  is non-empty; tooltip lists draft titles resolved from
  `projects/papers.json` (grant links fall back to the raw id — future
  work). Loaded non-blocking at boot into `_draftTitleById`.
- Script tag added to the three consumer pages: `library-paper.html`,
  `grant-builder.html` (editorScripts), `paper-builder.html`
  (editorScripts).
