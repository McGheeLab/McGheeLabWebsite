# V3.816 — Procurement: "Reorder existing" and "New item" as two doors

**Date:** 2026-10-21 · **Builds on:** V3.813–V3.814 · **Backend:** none (no rules or function change; FTP-only, batched)

Alex: *"separate the +new request button to two type 1) reorder existing, 2) new item. reorder existing allows the user to
search through existing item database that is already approved. users should have a full featured set of tools to find
existing items. filtering, search, grouped by type etc. new item needs all the new input and price compare information
filled out."*

## What "existing item database that is already approved" is

Two sources, merged into one **catalogue** (DOM-free, in `procurement-core.js`):

1. **Inventory** — every `inventory` doc of kind `item`. These are things the lab owns or stocks; each carries its vendor,
   catalogue number, last price, locations, stock status, and (since V3.814) `reorder.recurring` / `reorder.alternatives`.
2. **Procurement tickets that reached approval** — `approved`, `ordered`, `received`, `placed`. A ticket linked to an
   inventory item (`inventoryItemId`) folds its history into that entry (times bought, last bought, last price). A ticket
   with no inventory link (a consumable that was never put away, or one still on order) becomes its own entry, deduped
   with others by vendor + name + catalogue number.

`catalogue(items, tickets, now)` returns entries `{ id, kind: 'inventory'|'ticket', invId | ticketId, name, vendor,
catalogueNumber, url, category, categoryLabel, lastPrice, quantity, qtyRemaining, stock, locations[], timesBought,
lastBought, recurring, project, account, alternatives }`. `stock` is derived: a tracked item's count against its
minimum, else the inventory `stock_status`.

## The picker — "Reorder existing"

A card in the composer slot with:

- **Search** across name, vendor, catalogue number, location, project and account (every word must match).
- **Filters:** Category (inventory categories, with counts), Vendor (with counts), Stock (any / low or out),
  Source (in inventory / bought before, not in inventory).
- **Group by:** Category (default) · Vendor · Location · None — section headers with counts.
- **Sort:** Name · Recently bought · Most often bought · Lowest stock first.
- Each row: name, vendor · cat #, last price, stock and where it is, bought N× · last bought, badges for *recurring*,
  *low* / *out*, *not in inventory*; one **Reorder** button.
- Results re-render on every keystroke without losing focus (only the result list is replaced), capped at 200 rows with
  a "narrow the search" note.

Picking an inventory entry runs the existing `prefillReorder()` (project from the account, comparison from
`reorder.alternatives`, `purchaseType: recurring`); picking a ticket-only entry runs the V3.814 "Request again" path on
its latest ticket. Either way the composer opens in **reorder mode**.

## The two composers

- **Reorder mode** (from the picker, `?reorder=`, or Request again): the title names the item, a banner says what it
  restocks, and the fields the person must still answer sit on top — quantity, unit cost (prefilled), project
  (prefilled), urgency, needed-by, one-time/recurring (prefilled), why. The vendor / catalogue / link row and the price
  comparison are prefilled and folded under **Item details & price comparison** (a `<details>`), opened automatically
  when a validation error points inside it.
- **New item** (`#pt-new`, `?new=1`): the full V3.814 form, everything open, price comparison and AI assist on show.

`?pick=1` opens the picker from a link. The empty states and hints now say "New item" or "Reorder existing".

## Decisions

- **Inventory ∪ approved tickets**, not inventory alone: a consumable bought twice and never put away is exactly the
  thing people reorder, and it would otherwise be invisible.
- **Tickets fold into their inventory item** so one glove box does not appear twice.
- **Compact reorder form keeps the same fields and wiring** (folded, not removed), so validation, the AI import and
  the edit path are one code path.
- **No backend change.** The catalogue is computed on the page from data it already loads.
