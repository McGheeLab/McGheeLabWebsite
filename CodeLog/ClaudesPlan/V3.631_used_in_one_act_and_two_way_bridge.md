# V3.631 — "Used in" becomes one act, and the ABOUT↔FOR bridge goes both ways

R3 of the library-categorization program (R1 = V3.629 silent-loss fixes,
R2 = V3.630 Topics rename + one Organize surface). Alex's decision for this
release, from the R2 question set: *"Yes — one act, both records, prompt for
the why note."*

## 1 · Linking a draft offers the other half of the same act

An `output` focus card and a paper/grant draft are frequently **the same
object recorded twice** — the card carries `source_draft_id` (it was created
from that draft) and/or `links.draft_refs[]` (the PI pointed it at one). So
these were two storages for one intent, with nothing on screen suggesting the
second existed:

```
items/{id}.meta.library.linked_drafts   ← 105 papers in prod
researchFoci/{fociId}/refs/{refId}      ← 0
```

And the refs doc is where the **note** lives —
[rm/js/roadmap-attach.js](../../rm/js/roadmap-attach.js) calls it *"the entire
reason this feature exists: why is this paper appropriate HERE."* The
105-paper axis has never had a reason field of any kind.

New [rm/js/draft-focus-bridge.js](../../rm/js/draft-focus-bridge.js)
(`window.DRAFT_FOCUS_BRIDGE.offerForDrafts({item, draftIds, onDone})`): after a
draft link lands, if a focus card represents that draft and this paper isn't
attached there yet, offer to write the ref — with the why note focused.

New `ROADMAP_DATA.cardsForDraft(draftId)`: one cached whole-collection get over
`researchFoci` (single digits of docs), matching `source_draft_id` first then
`links.draft_refs[]`. **Deliberately not filtered to `level:'output'`** — in
the real data the card pointing at the CAREER draft (`gels-energy-landscape`)
is a `concept`, so an output-only filter would find nothing, which is exactly
the silent-empty this program keeps turning up.

Rules of engagement, all load-bearing:

- **The link has already happened when the offer opens.** Nothing in it can
  undo the link, "Not now" is free, Escape dismisses. An offer, never a gate.
- **Wired to the two INTERACTIVE pickers only** —
  `library-associations.js` `openAddPicker` and `paper-overlays.js`
  `_openLinkPicker`, both after `close()` + the caller's re-render. Explicitly
  **not** wired to `PAPER_OVERLAYS.linkDraft`, because that's what V3.629's
  `_ensureDraftLinked` calls while the user is filing a highlight — a modal
  must not ambush that flow. Bulk paths (reference import, `.paperbundle`,
  overlay-md) link dozens of papers and never prompt.
- **Attaches to the roadmap ROOT target** (`{kind:'roadmap', id:null}`): a
  draft link says nothing about *which* experiment. Refining to an
  experiment/analysis stays `ROADMAP_ATTACH`'s job.
- Writes the same snapshot shape `ROADMAP_ATTACH` writes, so a ref created
  here is indistinguishable from one created there — and patches
  `item.meta.library.roadmaps` in memory so a second offer in the same session
  knows it's already done.

Verified by running the real module against a stubbed `ROADMAP_DATA` in
headless Chrome — 5 cases: no draft ids → 0 and no modal; a draft with no card
→ 0 and no modal (never nags); a draft with a card → modal shows the right card
+ level + "for <draft>" line, note autofocused, saves note/relevance/root
target/snapshot and patches the item; the same draft again → no second modal;
Escape → 0 writes.

## 2 · The bridge now points both ways

`researchFoci/{id}.links.theme_id` is the only structural connection between a
paper's ABOUT axis (topics) and its FOR axis (the research map). V3.630 fixed
the forward half (it printed a raw kebab slug and omitted the `&theme=` deep
link it already supported). This is the reverse: a topic had no idea which of
the lab's work rested on it.

The topic detail view gains a **"This topic underpins"** strip above Research
groups — chips deep-linking to `research.html?id=<fociId>` with the card's
level. One cached whole-collection get, filtered client-side, per this module's
existing convention (no composite index, ever).

The empty state is deliberate rather than hidden: 8 of 9 real focus cards have
no `theme_id`, so a topic reading *"Not yet linked from the research map"* is
the only place anyone would learn the relationship exists.

## 3 · One definition of "which grant statuses are a draft"

`GRANT_DRAFT_STATUSES` was copy-pasted into **four** files —
`paper-overlays.js` (Set), `library-associations.js` (object map, whose own
comment admitted it was *"a mirror of paper-overlays.js"*), `library-paper.js`
and `library-mobile-paper.js` (inline Sets inside their draft loaders). Four
places to edit means the pickers can disagree about what a draft *is*, and
"every picker shows a different list" is one of the things that made this
subsystem confusing.

Now one list in `library-links.js` (`GRANT_DRAFT_STATUSES` +
`isGrantDraftStatus(status)`), because that module is the single writer for the
association arrays **and** the only one of these loaded on all six pages that
need it — including `library-mobile-paper.html`, which doesn't load
`library-associations.js`. Each consumer keeps the literal list as a
load-order fallback so nothing can crash on a page that loads it late.

## 4 · ★ The Comments page was reading drafts from the wrong collection

Every other surface resolves paper drafts from `projects/papers.json` (the
builder's source of truth). The Comments page alone scanned `items.json` for
`type:'paper'` rows lacking `is_library_entry` — i.e. **legacy** items-collection
paper rows. There are none in the current data, so this silently degraded on
the page V3.622 made the home of the categorization workflow. Three separate
consumers were affected:

1. `_loadPapers` → `_drafts` empty → the per-card Drafts pill row and the
   evidence form's draft select both read "No drafts available."
2. `_renderPaperPicker` → derived its list from `_papersById` filtered by
   `_isDraft`; `_papersById` holds the annotations' *parent* papers, which are
   library entries by definition, so `_isDraft` returned false for every one
   and the filter dropdown always rendered its "No draft papers yet" disabled
   row.
3. `_loadEvClaims` → same derivation, so the claim→draft bridge queried
   nothing, `_claimToDraft` stayed empty, and **no highlight could ever count
   as "categorized by claim evidence"** — which is what the V3.622
   "📥 To categorize" queue keys on.

`_loadPapers` now reads `projects/papers.json` (skipping `published`, matching
`LIBRARY_ASSOC`'s active test) plus proposal-status grants from `items.json`,
sorted by title; `items.json` is still read for `_papersById`, which genuinely
needs the library items. `_isDraft` is deleted — it could not return true.

Measured against production: the Comments page draft picker goes from **0
drafts to 4** (`career-…` submitted, `microscope-enabled-bioprinting` drafting,
`mri-lymphatic-r01`, `prostate-gels-r01`).

## Deliberately not done
The 3/2/1 relevance vocabulary is still declared in three places
(`ROADMAP_DATA.RELEVANCE`, `library-themes.js`, `library-paper.js`), which the
plan listed as a consolidation. The labels are already byte-identical
(Core/Supporting/Tangential) so there is no drift to fix, and `library-themes.js`
runs on a tab where `roadmap-data.js` isn't loaded — sharing it would add a
cross-module dependency and a fallback to buy nothing. Left alone on purpose.
