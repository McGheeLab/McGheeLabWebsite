# V3.873 — Lab members add aliquots and things we make in the lab

**Date:** 2026-10-23
**Request (Alex):** *"in the inventory, i want users to be able to add alliquots and custom inventory that we make in
the lab. for example we make our own LLS in different sizes, shapes, and colors etc. users will name this accordingly,
we dont need to make anything custom for these, but users should describe custom items so we know about them, also
they should say where they live for example fridge/box/001"*

## What was true before

- `inventory.html` had one way in, **+ Add Item**, built for purchases (vendor, catalogue #, price, account). Nothing
  asked what a thing *is* or where it lives, and the detail panel never showed `description` at all.
- That button saved with `api.save(DATA_PATH, _data)`: a whole-collection save that re-`set`s all ~3,500 inventory
  docs to add one. Same shape as the "+ New paper" bug fixed in V3.729 (a non-admin's batch is one rules refusal away
  from failing whole), and slow for everyone.
- V3.646 designed `kind:'stock'` ("a lab-made batch… owned by its maker") in `firestore.rules`, but no route, page or
  picker ever reads it. A stock doc would be invisible to the inventory page, scan-to-use, procurement, Scientia's
  inventory search and the notebook/protocol pickers, which all read `kind:'item'`.

## The call

**A lab-made thing is an ordinary inventory item with a flag** — `kind:'item'`, `lab_made:true` — not a new kind. That
puts it in every surface that already reads items with no change to any of them: the list, search, QR labels,
scan-to-use, the notebook/protocol pickers, Scientia's materials search (the hub row carries `description`). Alex: *"we
dont need to make anything custom for these"*: no per-type fields for size, shape or colour. The name carries those.

**No backend change.** `allow create` on `inventory/{id}` already admits any lab member for a non-stock item, and that
includes the `qty_*` fields at creation. Later edits follow the existing rule (anyone may decrease; raising the count
is a manager's recount). Delete stays admin-only; a mis-entered item can be fixed inline by anyone.

## The form (**+ Aliquot or lab-made**, next to + Add Item)

| field | required | why |
|---|---|---|
| What is it? — *An aliquot of something we bought* / *Something we made in the lab* | yes | `subcategory` `aliquot` / `made_in_lab`, so the tab's subtabs split them for free |
| Name | yes | e.g. "LLS 100 µm, rhodamine, spheres". Hint: size, shape, colour, concentration |
| Description | yes | Alex: *"users should describe custom items so we know about them"* |
| Where it lives | yes | free text with suggestions from every location already used (item locations + `inventoryLocations` boxes); spaces around `/` collapse, so `fridge / box / 001` → `fridge/box/001` |
| How many · of what | no | with a count, the item is created tracked (`qty_tracked`, `qty_made = qty_remaining = n`, `qty_unit`), so a scan asks "how many are you taking?" and the V3.646 low-stock alert fires at 20% of the batch |
| Made on | no (defaults to today, local date) | stored as `date_acquired` |

Stamped automatically: `lab_made:true`, `lab_made_type`, `category:'lab_made'`, `made_by_uid`, `made_by_name`,
`is_consumable:true`, `locations:[{name, quantity, notes}]`, `locIds:[]`.

## Where it shows

- A **Made in Lab** tab (`filter: i.lab_made`) with *Aliquots* / *Made in lab* subtabs.
- In the row: an *Aliquot* / *Made in lab* chip by the name; the Vendor cell reads "made by <name>".
- In the detail panel: an editable **Description** (also shown for any purchased item that has one), "Made by … on …",
  and no *Request reorder* (nobody sells it).
- Search now also matches location names and the maker, so typing `fridge/box/001` lists what is in that box.

## Shared changes

- `_invCreateItem(vals)` writes **one** doc in a transaction that refuses an existing id (slug + `-2`, `-3`… on
  collision), then invalidates the route cache, adds the row locally and opens it (so *Make label* is one click away).
  **+ Add Item uses it too**, which retires that button's whole-collection save.
- `forms.js` (`openForm`, used across RM): optional `suggestions` (a `<datalist>`) and `hint` on a field, `placeholder`
  on a textarea, required now rejects whitespace-only input, and a failed save says so in a toast instead of a browser
  `alert()` (falls back to `alert` only where `TOAST` is not loaded).
