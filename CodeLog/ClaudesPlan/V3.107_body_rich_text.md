# V3.107 — Paper builder: body rich text (markdown tokens)

## Goal

Third of four wishlist items
([rm/wishlist.md](../../rm/wishlist.md) "paper builder"). Paragraph
bodies have always been plain text — the user can type but can't
emphasize anything. This adds the small subset of markdown that's
useful in a journal manuscript:

| Source | Renders as | LaTeX |
|---|---|---|
| `**bold**` | `<strong>bold</strong>` | `\textbf{bold}` |
| `*italic*` | `<em>italic</em>` | `\emph{italic}` |
| `~sub~` | `<sub>sub</sub>` | `\textsubscript{sub}` |
| `^sup^` | `<sup>sup</sup>` | `\textsuperscript{sup}` |
| `` `code` `` | `<code>code</code>` | `\texttt{code}` |

`**bold**` and `*italic*` already worked in
[paper-export-tex.js](../../rm/js/paper-export-tex.js)'s
`paragraphTextToTex` (lines 164-165) since Phase F1, but the on-screen
renderer (`renderParagraphHtml` at
[paper-editor.js](../../rm/js/paper-editor.js#L1845)) only handled
`$math$` and `[@cite]`. V3.107 closes the loop: the screen, the
keyboard shortcuts, the toolbar, and the LaTeX export all agree on the
same five tokens.

## Approach

### Wire format stays plain text
No schema migration. Y.Text is still plain text under the hood. The
new tokens are inline markdown the user types (or clicks a toolbar
button to insert) — the same plain-text bytes get character-merged
across coauthors as before. Reader-side annotation tools and the
existing `[@cite]` / `$math$` paths are completely untouched.

### Render-time scanner extension
Extend the existing scanner loop in `renderParagraphHtml`:

```
   plain char → escape
   $...$       → KaTeX inline (existing)
   \(...\)     → KaTeX inline (existing)
   [@key]      → cite chip (existing)
   `code`      → <code>code</code>          NEW
   **bold**    → <strong>bold</strong>      NEW (must precede *italic*)
   *italic*    → <em>italic</em>            NEW
   ~sub~       → <sub>sub</sub>             NEW
   ^sup^       → <sup>sup</sup>             NEW
```

Inside any of the new wrappers, content is itself parsed by a
`parseInline` helper so cite chips and inline math still work inside
formatted text (e.g. `**Smith [@smith2024] showed $x^2$**` →
`<strong>Smith <chip>Smith 2024</chip> showed <math>x²</math></strong>`).

### Body-only toolbar
Each paragraph body gets a thin formatting toolbar (B / I / X₂ / X² /
`<>`) above the contenteditable. Skeleton bullets, equation source,
and the figure label/alt inputs do **not** get the toolbar — those
are either argument scaffolding (skeleton) or non-prose fields.

The toolbar uses `mousedown.preventDefault` to keep the caret in the
contenteditable, then calls
`window.PaperEditor.wrapSelectionInTokens(lhs)` which:
- If a selection exists: replace it with `lhs + selection + rhs`.
- If no selection: insert `lhs + rhs` and move the caret back by
  `rhs.length` so the user can type inside.

Both paths use `document.execCommand('insertText', false, …)` so the
contenteditable's `input` event fires and the existing Y.Text binding
picks up the diff — no special path through the binding.

### Keyboard shortcuts
Bound on the body contenteditable's `keydown`:

- `Cmd/Ctrl+B` → wrap `**`
- `Cmd/Ctrl+I` → wrap `*`
- `Cmd/Ctrl+E` → wrap `` ` ``

Sub/sup don't get keyboard shortcuts (no clean conflict-free key); the
user clicks the toolbar buttons. This matches the typical browser
keybinds for those operations.

### LaTeX export
`paragraphTextToTex` already emits `\textbf{}` and `\emph{}`. Add
three more `.replace(...)` lines for `~sub~`, `^sup^`, `` `code` ``.

### View-mode coupling
The paragraph block already has a skeleton ↔ body toggle
(`applyMode('skeleton'|'body')`) plus a doc-level view filter. The
toolbar is part of the body view: it shows when the body is visible
and hides when the user switches to skeleton-only.

## Out of scope

- **Block-level markdown** (lists, headings, blockquotes inside body) —
  outline structure lives in the skeleton. Body stays prose.
- **Underscore italic** (`_italic_`) — too easy to collide with
  variable names like `foo_bar`. Asterisk is enough.
- **Strikethrough** (`~~strike~~`) — collides with single-tilde
  subscript. Not worth the regex contortions for an uncommon need.
- **Toolbar in skeleton bullets** — bullets are outline scaffolding;
  formatting them is noise. The skeleton's `bindYTextToContentEditable`
  already routes through `renderParagraphHtml` so the **new tokens
  still render** when typed manually inside a bullet — they just don't
  get a toolbar.

```bash
RM_WRITE_ALLOWLIST=mcgheealex@gmail.com python3 rm/server.py

```

1. Open a paragraph body. Type:
   `Some **bold**, *italic*, H~2~O, x^2^, and \`inline code\` with $\\alpha$ math and [@smith2024] citation.`
2. Blur. Verify all five token types render side-by-side with
   bold/italic emphasis, sub/superscripts in correct vertical position,
   monospace code, KaTeX α, and the citation chip.
3. Re-focus the body. Verify the source reverts to literal text (with
   `**`, `*`, `~`, `^`, `` ` `` characters visible).
4. Select "bold" word. Click **B** in the toolbar. Verify the source
   becomes `**bold**` with the selection still highlighted (or caret
   at end). Blur → renders as bold.
5. Click in an empty paragraph. Press `Cmd+I`. Source becomes `**`
   (two asterisks) with caret between them. Type "italic" → source is
   `*italic*`.
6. Press `Cmd+E` — source gets backticks for code.
7. Verify the toolbar does **not** appear above skeleton bullets or
   equation source.
8. Switch view to "All skeletons" — body wraps (and their toolbars)
   should hide.
9. Click "Export LaTeX". Verify a paragraph with all five tokens emits
   the correct LaTeX commands per the table above.
10. Verify Y.Text wire format is unchanged: open the paper in a second
    tab, confirm the source has literal `**bold**` / `*italic*` /
    `~sub~` / `^sup^` / `` `code` `` characters.
