# V3.985 — A PDF opened from a module opens (the module frame lets its new tabs out of the sandbox)

**Report (instructor, 2026-11-12, after V3.984 went live):** in Report 2, opening the paper or the questions PDF shows
"mcgheelab.com is blocked — This page has been blocked by Chrome — ERR_BLOCKED_BY_CLIENT".

**Cause.** The class page shows a module inside `#cb-module-iframe`, sandboxed `allow-scripts allow-same-origin
allow-popups allow-forms allow-downloads`. The module's PDF links open a new tab (`target="_blank"`), and a tab opened
from a sandboxed frame inherits the sandbox unless the frame also has `allow-popups-to-escape-sandbox`. Chrome does not
run its PDF viewer in a sandboxed page, so the new tab shows the blocked page. The teacher's preview frame
(`teacher-teach.js`) has the same sandbox without `allow-downloads`, and the same fault.

**Reproduced** (headless Chromium, the live module inside an iframe carrying each sandbox, the paper's link clicked on
Tab 1): with the live sandbox the new tab ends on `chrome-error://chromewebdata/`, a sandboxed document (origin
`null`); with `allow-popups-to-escape-sandbox` added it loads
`…/report-02-files/report2-A-paper.pdf`, origin `https://mcgheelab.com`.

**Change.**
1. `class-builder.js` — the module viewer's iframe sandbox gains `allow-popups-to-escape-sandbox`, with a comment
   beside the V3.682 one saying why.
2. `teacher-teach.js` — the preview frame's sandbox gains the same token.
3. `sw.js` — `CACHE_VERSION` 954 → 955, so open browsers fetch the new scripts.

**Why it is safe.** The frames hold our own same-origin module files with `allow-scripts allow-same-origin`, which
already lets a module lift its own sandbox (Chrome warns about exactly that). The token only stops a module's new
tabs (PDFs, DOI and PubMed links) from inheriting a sandbox they were never meant to have. Scientia's embed
(`scientia/src/13g-embed.js`) already carries it.

**Not changed.** The modules themselves: Report 2's links already open a new tab.
