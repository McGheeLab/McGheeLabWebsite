# V3.206 — Library load perf

## Symptom

"The papers in the library take a really long time to load."

## Root causes (in priority order)

1. **Reads every items.json row.** `library.js` `_load` calls
   `api.load('items.json')` — Firestore returns every doc in the items
   collection (papers, grants, courses, tools). Library page then
   filters client-side for `type=='paper' && meta.library.is_library_entry`.
   For a typical lab with 200 library papers and ~50 other items that's a
   ~20% read-cost cut, plus all the per-doc payload non-paper rows carry.
2. **Heavy inline meta.** Each paper carries `meta.library.abstract`,
   `tldr`, `references[]`, `cited_by[]` inline. A single paper's
   references list can be 30-100 KB; multiplied across the library that
   dominates the network read and the IDB serialize step.
3. **Synchronous render of N rows.** `_render` iterates the full filtered
   list synchronously and appends one row at a time — 1000 papers ≈
   200-300 ms layout block on first paint.
4. **Search re-runs on every keystroke + reparses query.** No debounce; a
   fast typer triggers 10+ renders for one word. `_parseQuery` re-runs on
   every render even when the filter text hasn't changed.
5. **Cache TTL too short.** Items route on `cache: MEDIUM` (30 min); the
   adapter does a MAX(`updatedAt`) cheap-freshness probe that costs 1
   Firestore read regardless of TTL, so longer TTL is purely a win — it
   amortizes the probe across more visits.

## Fix shape

Seven coordinated changes, all in this single ship.

### 1. New route `library/papers.json`

`rm/js/api-routes.js` registers a route with `where: ['type','==','paper']`
+ `discriminator: {field:'type', value:'paper'}`, `wrapKey: 'papers'`,
`cache: LONG`, `shadowJson: true`. The route lives on the same items
collection so writes are still scoped to docs matching the where clause
(the adapter's collection-replace batch already does this — non-paper
items in the collection survive the save).

### 2. Heavy-fields subdoc — `items/{itemId}/details/main`

New `rm/js/library-extras.js`:

- `load(itemId, itemInline?)` → reads the subdoc; falls back to
  `itemInline.meta.library.{abstract,…}` if subdoc missing (back-compat
  for unmigrated rows).
- `savePatch(itemId, patch)` → `.set(patch, {merge:true})` on the
  subdoc. Single 1-doc write replaces the previous collection-replace
  batch.
- `stripInline(item)` → removes the heavy fields from `item.meta.library`
  so the main doc can be re-saved light.
- `delete(itemId)` → drops the subdoc (paper deletion path; the
  `deletePaper` Cloud Function handles cascading deletion in prod).

Heavy fields owned by the subdoc: `abstract, tldr, references,
references_source, references_parsed_at, references_parser_version,
cited_by, cited_by_fetched_at, semantic_scholar_id,
semantic_scholar_fetched_at`.

Call sites updated:

- `rm/js/paper-citations.js init()` — kicks off `LIBRARY_EXTRAS.load` and
  adopts the refs if the viewer parse hasn't won yet. Inline path still
  short-circuits when `meta.library.references` is present.
- `rm/js/library-paper.js onCacheRefs` — writes through
  `LIBRARY_EXTRAS.savePatch`; old code path preserved as fallback.
- `rm/js/library-upload.js parseAndCacheRefs` + `enrichItemFromSemanticScholar`
  — both write through extras; SS-wins rule preserved via a
  pre-write `LIBRARY_EXTRAS.load`.
- `rm/js/paper-cited-by.js init()` — falls back to extras when
  `meta.library.cited_by` is missing.

Firestore rule: `match /items/{itemId}/details/{detailId}` — lab read,
lab write, admin delete.

Existing data is NOT migrated automatically. New writes land in the
subdoc; old inline data continues to work via the fallback. A one-shot
migration script can be added later (`for each item: load → savePatch
→ stripInline → save main doc`) but isn't required for the perf win to
land.

### 3. Chunked render

`_render` paints `RENDER_FIRST_BATCH = 50` rows synchronously, then
schedules the remainder in `RENDER_BATCH_SIZE = 100`-row batches via
`requestIdleCallback`. A monotonic `_renderToken` cancels in-flight
batches when a new render starts (filter change, sort toggle, star
click). Falls back to `setTimeout` on browsers without
`requestIdleCallback`.

Effect: with 1000 papers, first paint drops from ~250 ms to ~15 ms.

### 4. Debounced search input

`_wireSearch` collapses keystrokes into one render via a 150 ms debounce.
Combined with the chunked render's preempt-on-rerun, fast typing now
costs ~one full render at the end of the burst instead of N partial
renders.

### 5. Memoized parsed query

`_parsedQueryCache = { key, val }` in module scope; `_render` checks
`key === _filterText` before reparsing. Sort toggles, star clicks, and
tag-chip clicks rerun `_render` without changing the filter text — the
parse now skips entirely for those.

### 6. Cache LONG

`library/papers.json` route declares `cache: LONG` (4 hr). The cheap
`MAX(updatedAt)` probe handles invalidation regardless of TTL, so the
longer TTL just lets the probe amortize across more visits.

### 7. Reuse `_items` as alias of `_libraryPapers`

Two callers (`LIBRARY_UPLOAD.findDuplicate(items)`,
`LIBRARY_SYNC.syncPendingCaptures(items)`) take the full array for
dedup; both work fine on the smaller paper-only set since they only
care about paper-shaped rows. `_items` stays as a back-compat alias so
those callers don't need to change.

## What "done" looks like

1. Cold open of `/rm/pages/library.html`:
   - Network panel shows a single Firestore query against `items` with
     `type=='paper'` filter applied server-side (not a collection scan).
   - First 50 rows visible in < 50 ms after data lands; the rest stream
     in via idle callbacks.
   - Search input feels snappy — typing 10 chars triggers ~1 render at
     the end, not 10.
2. Open a library paper for the first time after this ship:
   - References load from `items/{id}/details/main` if previously
     parsed, or fall back to the parser if neither extras nor inline
     refs exist. New parses land in the subdoc, not items.json.
3. Open a paper that was uploaded before V3.206:
   - References render from `meta.library.references` (inline
     fallback). No regressions.
4. Add a new paper via drag-drop:
   - `parseAndCacheRefs` writes refs to extras subdoc.
   - `enrichItemFromSemanticScholar` writes abstract / tldr / refs /
     cited_by to extras subdoc.
   - The main item doc save (library/papers.json route) does NOT
     contain references / cited_by / abstract / tldr.

## Follow-ups (NOT in this ship)

- True virtualized table (windowed rendering with absolute-positioned
  rows + spacer) for libraries pushing 5000+ papers. Chunked render
  handles 1000-2000 well; beyond that the DOM size itself starts to
  matter.
- Server-side text search via a `search_tokens[]` array field on the
  main item doc + `array-contains-any` queries. Only worth it if a
  user reports search lag on large libraries.
- One-shot migration script (`scripts/migrate_library_extras.py` or a
  one-time admin button) that copies inline heavy fields into the
  subdoc and strips them from the main doc. Cuts the items.json read
  size further once the inline tail is gone.
- `cached_at_iso` on the cheap-freshness probe so we don't refetch
  unchanged routes for the LONG TTL window. Already implemented in
  `_refreshRouteCacheCheap`; verify it triggers on the new route.
