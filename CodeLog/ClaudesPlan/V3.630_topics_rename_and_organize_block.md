# V3.630 — "Topics", and one Organize surface instead of five

R2 of the library-categorization program (R1 = V3.629). Alex: *"there are
currently multiple ways to categorize a library journal paper — (1) three
types of groups in the library, (2) associations with a paper we are writing,
(3) lab themes. Each does something subtly different, so we need to figure out
how to make it all better."*

**No storage changes.** Every field, id, collection, URL and search token is
untouched; every picker is reused verbatim. This release is entirely about what
the user can see and name.

## What the investigation found

Read-only Firestore counts over the real lab data (173 `type:'paper'` items):

| Axis | Papers |
|---|---|
| `linked_drafts` (draft associations) | **105 (61%)** |
| `themes` (Lab Themes) | **52 (30%)** |
| `theme_relevance` | 2 |
| personal manual groups | **1 group** ("HUVECs", 5 papers), 1 user |
| smart groups · draft groups · `librarySharedGroups` · pins | **0 · 0 · 0 · 0** |
| `roadmaps` / `researchFoci/{id}/refs` | **0 / 0** |
| `tags` | **3** |

Three facts drove the design:

1. **The 61% is one draft.** Papers per draft: `career-…-granular-microgel-
   scaffolds` = 104, `microscope-enabled-bioprinting` = 1. There are only two
   drafts in existence. So "association with a paper we're writing" isn't being
   used per-manuscript — **the axis with the biggest number is the axis being
   used as a group.** 39 papers (23%) carry no categorization at all.
2. **The same concept exists in three collections.** "Microscope-Enabled
   Bioprinting" is at once a draft, a Lab Theme (`microscope-enabled-bioprinter`,
   28 papers) and a Research Focus (`mebp`). The single bridge that exists ties
   together exactly the three records holding all the data — focus
   `gels-energy-landscape` → the CAREER draft via `links.draft_refs` **and** →
   theme `granule-based-in-vitro-models` via `links.theme_id` — three records
   for one body of work holding 104 / 11 / 0 papers, with no join.
3. **★ The correct mental model was already in the code, in a comment, and
   nowhere in the UI** ([rm/js/library-paper.js](../../rm/js/library-paper.js), `_renderRoadmapEditor`):
   *"themes are what a paper is ABOUT, roadmaps are what it's FOR."*

So the fix isn't new taxonomy — it's saying out loud what the code already
believes.

## 1 · "Lab Themes" → **Topics**

The old name sat one box away from the reader's **"🧭 Lab focus"**. Two phrases
nobody can tell apart, backed by two collections with two permission models
(`labThemes`: any lab member creates; `researchFoci`: PI-only), expressing the
paper's two genuinely different questions. Renaming one of them is what makes
the distinction survivable.

User-facing wording only — **`?tab=themes`, `labThemes`, every theme id, and
the `theme:` search token all keep working**, so no link, bookmark or saved
smart group breaks. `topic:` is added as a search synonym that collapses onto
the same `fields.theme`. Files: `rm/pages/library.html` (tab label, title,
h1, "+ New topic", auth hint, intro, search placeholder), `rm/js/library-themes.js`
(30 display strings, verified one-by-one — each replacement asserted to match
exactly once rather than swept), `rm/js/library-paper.js`, `rm/js/library.js`
(`topic:` alias), `rm/js/research-links.js`.

The intro now states the contrast explicitly and links to the research map, and
**a Topics entry finally exists in the nav** — the tab has had none since
V3.367, reachable only from the library's in-page tab bar.

### The theme↔focus bridge, display half

`links.theme_id` is the only connection between the two axes and it was
half-built: [rm/js/research.js](../../rm/js/research.js) `sectionTheme` printed
the **raw kebab slug** and linked to the Topics tab *without* the `&theme=`
deep link that tab has supported since V3.367. Now resolves the topic's name
(one 6-doc `labThemes` get cached in `init()`, slug as fallback so it can never
render empty) and deep-links properly. Heading "Literature theme" → "Topic".
The reverse direction — a topic listing the focus cards pointing at it — is
V3.631.

## 2 · One Organize block in the reader

The sidebar stacked **five** widgets, each appended via its own
`getElementById(a) || getElementById(b) || …` insertion-order fallback chain:

```
_renderTagEditor      "Categories"            →   3 papers
_renderAssocEditor    "Used in paper drafts"  → 105 papers
_renderThemeEditor    "Lab themes"            →  52 papers
_renderRoadmapEditor  "🧭 Lab focus"          →   0 papers
_renderGroupsWidget   "📁 My groups"          →   1 group
```

The least-used axis owned the most generic name; two indistinguishable names sat
adjacent; nothing said who could see any of it. Now one bordered block, four
labeled rows, each with a **🌐 lab / 🔒 only you** badge and a `?` explaining
the axis in one sentence:

```
┌─ ORGANIZE ──────────────────┐
│ Topics  ?           🌐 lab  │  what it's ABOUT (durable)
│ Used in ?           🌐 lab  │  what it's FOR (ends when it ships)
│   🧭 Lab focus              │  …at experiment/analysis resolution
│ My shelf ?       🔒 only you│  a private pile
│ ▸ Tags        power search   │  collapsed — 3 of 173 papers
└─────────────────────────────┘
```

Implementation deliberately conservative: `_ensureOrganizeBlock()` +
`_orgHost(hostId, slotId)` + `_orgRowTitle(label, scope, hint)`. **Every widget
keeps its logic and its host id verbatim** — only the parent changes (a fixed
slot instead of the fallback chain) and the title comes from one helper so the
rows can't drift. `_orgHost` is idempotent, so widgets that rewrite their own
`innerHTML` on repaint (topics, shelf) work untouched. Visual order comes from
slot order, not call order; the one ordering that still matters is assoc before
roadmap, since both live in `#lp-org-usedin`.

Two details worth keeping:
- **Lab focus is a sub-row of "Used in", not its own heading.** A draft link
  says "feeds that manuscript"; a roadmap ref says "feeds that experiment
  inside it". Same question, different resolution. V3.631 merges them.
- **A lab-shared group is not private,** so "My shelf" flips its badge to 🌐
  when any shared group is present, and shared chips carry their own 🌐.

CSS in `rm/css/style.css` (`#lp-organize`). Rows own the divider *above* them
and the header owns none, so the first *rendered* row draws the header's
underline — which slot is first varies (an absent module renders nothing and
`.lp-org-slot:empty` hides it), so any `:first-child` rule would be wrong half
the time.

## 3 · One Organize popover on the library row

The row carried `★ ☆` + `+ draft` + `📌` + `📁` + `🗺` with nothing to
distinguish them — and 📌 pin vs ★ star are near-duplicates on different
scopes (pin: per-user, 0 users; star: lab-wide). `📌 📁 🗺` collapse into one
**Organize** button carrying a count of where the paper is filed, opening a
popover with the same four rows and the same badges.

Not a reimplementation: "Used in" renders inline because
`LIBRARY_ASSOC.renderPills` already does that; the rest hand off to the modals
that already exist (`ROADMAP_ATTACH.open`, `LIBRARY_GROUPS.openGroupPicker`,
`togglePin`, the Topics tab), closing the popover first so two layers never
fight. `★` stays in its own column — it's a lab-wide flag on the paper, not a
place you file it. `widgets_enabled` prefs still gate the rows, and the
`pin-toggle` / `add-to-group` handlers stay because the groups shelf renders its
own chips that use them. On the papers tab `library-themes.js` isn't loaded, so
the Topics row falls back to ids + a plain link.

CSS in `rm/css/library-associations.css` (`.lib-org-*`).
