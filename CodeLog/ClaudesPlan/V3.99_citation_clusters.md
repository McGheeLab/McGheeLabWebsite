# V3.99 — Citation panel: expand clusters + narrow flash to the marker

## Goal

Two related bugs in the "Citations on this page" panel
([rm/js/paper-citations.js](../../rm/js/paper-citations.js), shown in
[rm/pages/library-paper.html](../../rm/pages/library-paper.html)):

Reported:
> *"on the citations on page viewer, when there is a cluster of citations
> e.g. [1,5,9] the citations are not separated and we only see the 1st
> citation represented. Also the entire sentence connected to the
> citation is highlighted. we only want the number highlighted for the
> picker."*

1. **Cluster underrepresentation.** When the PDF text says `[1, 5, 9]`,
   the panel surfaces only ref `1`. Refs `5` and `9` are silently
   dropped — `_matchedRef` did `parseInt((match.inner.match(/\d+/) ||
   [''])[0], 10)` which only resolves the first digit-run, and
   `refKey = m[1]` ("1, 5, 9") meant the whole cluster collapsed into
   one row.
2. **Whole-sentence flash highlight.** Hovering a row flashed the
   bounding box of *every pdf.js text-item* the regex match overlapped.
   pdf.js groups glyphs into sentence- or run-sized text-items, so a
   citation marker buried inside one of those items made the entire
   sentence flash. The user wants only the marker (`[1,5,9]` — or
   ideally just the digit being hovered) highlighted.

## Approach

Both bugs share one fix path: compute the per-ref char-span of every
citation marker in the page text, then convert that to a rect by
slicing each overlapping pdf.js text-item by the character fraction
that actually overlaps. Two new helpers, `_scanPage` simplified:

### `_expandNumericInner(inner)` (new)

Given the captured inner of `RE_NUMERIC` (`"1, 5, 9"`, `"3, 5–7"`,
`"12"`), returns a list of `{ n, charStart, charEnd }` — one entry per
ref number, with the inner-string offsets the digits occupy. Range
tokens like `5–7` expand to one entry per ref but all three share the
range's char-span (no fake `6` glyph exists in the PDF — hovering
ref 6 highlights the literal `5–7`).

### `_rectForRange(ranges, rangeStart, rangeEnd)` (new)

Given a char-range in `fullText` (the joined per-page string built in
`_scanPage`), returns `{ x, y, w, h, items }` where `x`/`w` slice each
overlapping text-item by the **character fraction** that lies inside
the range. Approximation: assumes roughly even glyph distribution
within an item, which is good for body text and degrades for kerned
or justified runs — still vastly better than the whole-item rect.

### `_scanPage` rewrite

- For numeric matches, iterate `_expandNumericInner(m[1])` and emit one
  match per ref (`refKey = String(n)`, `inner = String(n)`,
  rect from `_rectForRange`).
- For author-year matches, emit one match per regex hit (no expansion)
  but use `_rectForRange(start, end)` so the rect is the marker, not
  the run.

### `_matchedRef` simplification

Now `match.inner` is always a single number for numeric kind, so the
`/\d+/` heuristic disappears.

## Behaviour change

| Page text contains | Panel rows before | Panel rows after |
|---|---|---|
| `[1]` | ref 1 (rect = whole containing run) | ref 1 (rect = `1`) |
| `[1, 5, 9]` | ref 1 only (rect = whole run) | ref 1, ref 5, ref 9 (each rect = its own digit) |
| `[5–7]` | ref 5 only | ref 5, ref 6, ref 7 (all rect = literal `5–7`) |
| `(Smith, 2020)` | "Smith 2020" (rect = whole run) | "Smith 2020" (rect = `(Smith, 2020)`) |

Same hover affordance, just much more precise. Same dedup via
`refKey` in `_renderPanel` — if `[1, 5, 9]` and `[5]` both appear,
they merge into a single row for ref 5 with two `hits` (existing
behavior).

## Files changed

- **`rm/js/paper-citations.js`** — added `_expandNumericInner` and
  `_rectForRange` helpers; rewrote the numeric branch of `_scanPage`
  to expand clusters/ranges; switched author-year and numeric branches
  to the narrowed rect; simplified `_matchedRef`'s numeric path.
- **`sw.js`** — `CACHE_VERSION` 73 → 74.

## Out of scope

- Per-glyph rects with sub-character precision (would require
  `pdf.js` `page.getTextContent({ includeMarkedContent: true })` and
  manual glyph-positioning math).
- Showing each row's individual token (`[5]` instead of the original
  `[1, 5, 9]`). The cluster token is informative — the narrowed
  flash visually disambiguates which digit each row belongs to.

## Verification

1. Hard reload the paper reader (evict SW cache `mcgheelab-shell-v73`).
2. Open a paper with cluster citations like `[1, 5, 9]` or numeric
   ranges like `[12–14]` on a visible page.
3. Citations panel should show **one row per unique ref**, not one
   per cluster.
4. Hovering each row flashes a small rect on **just that digit** (or
   on the literal range tokens for ranges), not the surrounding
   sentence.
5. Single-citation tokens (`[3]`) and author-year tokens
   (`(Smith, 2020)`) still match correctly and now also flash a tight
   rect rather than the whole text run.
6. Console: no new warnings; the existing
   `[paper-citations] parsed N reference(s)…` log line is unchanged.
