# V3.814 — Procurement: reassign the funding string at any stage (requester told), and a request form an AI can fill in

**Date:** 2026-10-19 · **Builds on:** V3.813 (Procurement v2) · **Backend:** rules + `onProcurementTicketWritten` redeployed (scratch-copy discipline, V3.806 users hunk still excluded)

Alex, after V3.813's project → funding-string change:

> I as admin need to be able to reassign the funding string, if I need to reassign it then the requestor should be
> notified that I made that change as a follow up.
>
> Also we need a way to make the repeat procurement easy, to make a procurement request you must fill out some type
> of form that asks if it's a one time purchase or possibly recurring, why it is needed, and a price comparison
> between a few sources. This can be downloaded as a prompt to AI to find and fill out and then an import results
> button to get the response from the AI tool. This way the user doesn't need a crazy amount of work for a simple item.

## 1. Reassign the funding string — `reassign` action

**Today:** an approver can change the project only through *Edit request*, and only while the ticket is
`requested` / `needs_info` / `approved`. Once it is ordered the funding string is frozen for everyone but a raw admin
write (which the UI never makes), and an approver's edit of a *requested* ticket told the approvers, not the requester.

**Now:** a dedicated **Change funding** action (`reassign`) on every non-terminal ticket
(`requested`, `needs_info`, `approved`, `ordered`, `received`, `placed`), role **approver** (admin, or cap
`procurement:approve` — the same role that assigns the funding string at approval time). Same-status: it never moves
the ticket. The inline form is the project picker from the composer plus an optional "why" note; saving requires a
*different* project (or an "Other" name) and writes:

| field | value |
|---|---|
| `projectId`, `project`, `fundingAccount`, `fundingLabel` | the new project |
| `fundingChangedBy/ByName/At`, `fundingChangedFrom` | who, when, the old `fundingLabel` |
| history | `reassign` entry — "Charged to *new* (was *old*) — note" |
| notes | kind `funding`, same text — so it sits in the ticket's thread |

The card gets a **Funding changed** row (by whom, when, from what). "Edit request" keeps working as before, so
nothing a student does changes.

**Rules.** The approver branch already allows `requested>requested`, `needs_info>needs_info`, `approved>approved`
with no key restriction. For `ordered`, `received` and `placed` a new clause lets an approver make a same-status write
that touches **only** `fundingKeys()` (= note keys + the eight fields above). A purchaser still cannot touch the
funding string; a member still cannot. `requesterKeys()` also gains the new request fields of §2.

**Notify (`plan()`).** A fresh `reassign` history entry → **requester**: "Funding changed: *item*" / "Now charged to
X (was Y) — note". When the ticket is `approved` or `ordered` the **purchasers** also hear ("Charge to a different
string"), because they are about to order, or have ordered and may need a cost transfer. The `reassign` check runs
*before* the notes check, since the action also appends a note (the old "a decision note re-sent" early return would
otherwise swallow it). Also fixed on the way: an **edit by someone other than the requester** on a `requested` /
`needs_info` ticket now tells the requester too ("Your request was changed"), not just the other approvers.

## 2. The request form: one-time or recurring, why, and a price comparison an AI fills in

New request fields (stored on the ticket, editable, in `EDITABLE` and `requesterKeys()`):

| field | values |
|---|---|
| `purchaseType` | `one_time` · `recurring` — **required** (the form asks; the default is unset) |
| `recurrence` | when recurring: `monthly` · `quarterly` · `semester` · `yearly` · `unsure` |
| `comparisons[]` | up to 6 rows `{vendor, catalogueNumber, url, unitPrice, packSize, leadTime, notes, chosen}` — optional |
| `repeatOf` | the ticket this one was copied from ("Request again") |

*Why* already exists (`reason`, required). The **price comparison** is optional (a $12 item should not need three
quotes) but the approver sees it on the card — "No price comparison" in muted text when absent — so the PI can ask.
Rows need a vendor; a price must be a plain number; a link must be http(s). **Use this one** on a row copies vendor,
catalogue #, link and unit price into the main fields and marks the row `chosen`.

**AI assist, no popups:**

- **Download AI prompt** builds a prompt from what is typed (item, vendor/cat#, quantity, why, category, today's
  date), asks for 2–4 sources from suppliers the university buys from, a recommendation, and whether a lab buys this
  once or repeatedly — and demands **only** a JSON block in a fixed schema. It downloads as
  `procurement-prompt-<item>.txt` and is copied to the clipboard. The user pastes it into whatever AI they use.
- **Import AI results** opens an inline paste box in the composer. `parseAiResults()` strips code fences and prose,
  tolerates `$12.50` prices, drops rows with no vendor, clamps `recommended` into range (default: the cheapest priced
  row), and returns `{error}` beside the box when nothing usable is there. `applyAiResults()` fills `comparisons`,
  takes the recommended row into the main fields when vendor or price is still empty, and takes the AI's
  one-time/recurring guess only when the user has not chosen. Then the composer re-renders and a toast says what came in.

**Repeat procurement:**

- **Request again** on any ordered / received / placed / denied / withdrawn ticket opens the composer prefilled from
  it (`prefillFromTicket`: item, vendor, cat #, link, qty, unit cost, category, project + funding string, purchase
  type, recurrence, comparisons, reason; needed-by and urgency reset) with `repeatOf` and the same `inventoryItemId`,
  so putting it away restocks the same inventory item.
- Items put into inventory from a procurement ticket now carry `reorder.recurring` and `reorder.alternatives` (the
  comparison rows), and **Request reorder** from inventory (`prefillFromInventory`) brings them back as the new
  ticket's comparisons and purchase type — the second time round the form is already full.

The Report CSV gains `purchase_type`, `recurrence`, `sources_compared`. Search also matches comparison vendors.

## Decisions

- **Approver, not admin-only, may reassign** — it is the same role that assigns the string at approval; admins are
  approvers. Alex can narrow it to admin by not granting the cap.
- **Reassign at every stage including placed** — the charge may need moving after the fact (cost transfer).
- **Comparison optional, purchase type required** — the form *asks* for all three things Alex listed, the AI path
  makes the comparison cheap, and the approver can see when it was skipped. Easy to flip to required later
  (one line in `validateRequest`).
- **Prompt asks for JSON only** — the import must be deterministic; prose answers fail with a clear inline message.
- **No network from the page** — the "AI" step is the user's own tool; nothing is sent anywhere by RM.
