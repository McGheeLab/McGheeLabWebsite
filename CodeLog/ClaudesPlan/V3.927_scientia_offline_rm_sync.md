# V3.927 — Offline Scientia: RM actions happen when the notebook syncs

## Goal

Gabe (26 Oct 2026): the desktop Scientia works offline and must not change the shared lab layer (`rm/scientia/lab-mode.js`,
`cloud-sync.js`). What he does there that belongs in the lab reaches RM when the notebook reaches the lab cloud — through
the desktop bridge (`scientia-cloud.py`) once the computer is online, or when the website syncs. Example: the ✓ on a
component is a My Week report, and it lands in RM's My Week when the offline notebook syncs to the cloud.

What syncs, and what it does in RM:

| What | On the desktop (offline) | When it reaches the lab cloud |
|---|---|---|
| Papers in the local library | added as today | a paper whose metadata is not in RM is added to the lab library (Gabe: "should port to RM") |
| Notes | as today | already synced; RM-project notes shared with the lab already list in RM (V3.880) |
| Tasks | a task component | **every** task becomes an RM task (Gabe), done reconciled both ways (V3.872 sync) |
| Lit reviews | a native tab in the app | already synced; the hub already lists reviews on their projects |
| My Week | the ✓ on a component | the tick becomes the My Week report for that day |
| Protocols | — | not now (Gabe: "don't touch protocols for now") |

Not synced to RM: materials and equipment scheduling. A material component that came from the lab inventory (a resource
note with `inventoryId`, made on the website) shows on the desktop as a fixed, read-only card that still connects, links
and pulls into other notes like any component.

## Approach

**The desktop never calls RM.** Everything meant for RM is ordinary notebook data; the hub — the one place that already
talks to RM for Scientia (`FirestoreHub.quietSyncs`: library mirror, task reconcile, reminders → My Week, activity,
projects, notes, shares) — gains jobs that act on that data, idempotently, and writes the outcome back into the record,
which syncs home. Nothing in `lab-mode.js` or `cloud-sync.js` changes.

- **Trigger.** `quietSyncs` runs throttled on hello; the bridge says hello on every start, and the website on every open.
  The new jobs also run after a push that carried rows they care about (`/api/sync/push`, debounced), so an offline
  notebook's work reaches RM within a minute of the bridge coming online.
- **Idempotent.** Every RM document the jobs write has an id derived from the notebook record (block id, block id + day,
  library row id), so a retried or doubled sync never writes twice.
- **State on the record.** Each synced item carries `rmSync: { state: 'pending' | 'done' | 'error', at, msg }`, written by the
  hub; the desktop shows a small "waiting for the lab" mark until it is `done`, and the reason when it is `error`.
