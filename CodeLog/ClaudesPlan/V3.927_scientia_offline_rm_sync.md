# V3.927 — Offline Scientia: RM actions happen when the notebook syncs

## Goal

Gabe (26 Oct 2026): the desktop Scientia works offline and must not change the shared lab layer (`rm/scientia/lab-mode.js`,
`cloud-sync.js`). What he does there that belongs in the lab reaches RM when the notebook reaches the lab cloud — through
the desktop bridge (`scientia-cloud.py`) once the computer is online, or when the website syncs. Example: the ✓ on a
component is a My Week report, and it lands in RM's My Week when the offline notebook syncs to the cloud.

What syncs, and what it does in RM:

| What | On the desktop (offline) | When it reaches the lab cloud |
|---|---|---|
| Papers in the local library | added as today | a paper whose metadata is not in RM is added to the lab library (Gabe: "should port to RM") |
| Notes | as today | already synced; RM-project notes shared with the lab already list in RM (V3.880) |
| Tasks | a task component | **every** task becomes an RM task (Gabe), done reconciled both ways (V3.872 sync) |
| Lit reviews | a native tab in the app | already synced; the hub already lists reviews on their projects |
| My Week | the ✓ on a component | the tick becomes the My Week report for that day |
| Protocols | — | not now (Gabe: "don't touch protocols for now") |

Not synced to RM: materials and equipment scheduling. A material component that came from the lab inventory (a resource
note with `inventoryId`, made on the website) shows on the desktop as a fixed, read-only card that still connects, links
and pulls into other notes like any component.

## Approach

**The desktop never calls RM.** Everything meant for RM is ordinary notebook data; the hub — the one place that already
talks to RM for Scientia (`FirestoreHub.quietSyncs`: library mirror, task reconcile, reminders → My Week, activity,
projects, notes, shares) — gains jobs that act on that data, idempotently, and writes the outcome back into the record,
which syncs home. Nothing in `lab-mode.js` or `cloud-sync.js` changes.

- **Trigger.** `quietSyncs` runs throttled on hello; the bridge says hello on every start, and the website on every open.
  The new jobs also run after a push that carried rows they care about (`/api/sync/push`, debounced), so an offline
  notebook's work reaches RM within a minute of the bridge coming online.
- **Idempotent.** Every RM document the jobs write has an id derived from the notebook record (block id, block id + day,
  library row id), so a retried or doubled sync never writes twice.
- **State on the record**, written back by the hub: a task gets `rmTaskId` (until then the app shows "waiting for the
  lab"); a ✓ entry loses `pending` and gains `sent` or `error` (the ✓ shows waiting / sent / not sent); a paper gets
  `rmSync: { state: 'done' | 'matched', rmId, at }`.

### Papers (hub: `syncUp`, core `planLibraryUp`)
- Candidates: library rows without `rm` / `rmId`, kind paper, not yet `rmSync` done or matched, with a title and a DOI
  or authors (the rest stay on the desktop).
- Match against RM's library entries by DOI, then by normalised title + year → `rmSync: {state: 'matched', rmId}`.
- Otherwise `items/{rowId}` is created (`create()`, never over an existing doc) with the fields RM's own
  `LIBRARY_METADATA.buildPaperItem` writes (`paperItemFromRow`, the inverse of `rmItemToLibraryRow`), `meta.library.source:
  'scientia'` and `source_ref.scientia {uid, rowId}`; the row gets `rmSync: {state: 'done'}`. The next library mirror finds
  the item under the same id and makes that same row `rm: true` — no second row, cites unchanged.
- On Gabe's notebook (26 Oct): 307 papers, 302 already RM's, 5 his own — 2 are in RM by DOI or title, 3 will be added.
- Note: a paper an admin later deletes in RM leaves the notebook too (the mirror's rule for `rm` rows).

### Tasks (hub: `syncUp`, core `planTaskPairing`)
- Every live task block with no `rmTaskId` and no pairing gets `createTask` with the `b` the web app's `taskFields`
  builds (text = first line, due, allDay, prio, the note's title and project), and the block gets `rmTaskId`. Done then
  flows both ways through the existing `syncTasks` / `planTaskSync` (V3.872).

### My Week (app: ✓ on a component; hub: `syncWeekSteps`, `syncTicks`)
Gabe chose the website's model: the ✓ reports the component onto a My Week step picked from the week.
- `syncWeekSteps` mirrors `userData/{uid}/dayPlans` in the picker's window (4 weeks before this week's Monday to this
  Sunday, LAB_TZ, not cancelled — `myweek-report.js` `loadSteps`) into a new read-only store `mwsteps` (app `DB_VERSION`
  10). Old builds skip ops for stores they do not know (`13zc-sync.js`), so they are unaffected.
- The app's ✓ (`23b-labsync.js`) offers those steps (needs-a-result first, newest first, a search over 6) and keeps the
  choice on the block: `myweek: [{stepId, title, date, at, pending: true}]`.
- `syncTicks` sends each pending entry as RM does (`pick` → `DAY_DISTRIBUTE.saveOutcome(step, payload, {closeAs:
  'done'})`): the outcome with the component's card in its links (the same component replaced, not doubled), the step
  closed (`closedStatusFor`), `confirmed_at`, the done work event (`ActivitySignals.recordWork` →
  `trackerEntries/{uid}/entries/auto-dayplan-{id}-{date}`, left alone when confirmed or dismissed), and the step's task
  and tracker copies (`cascadeUpdate`'s task and tracker adapters). Then the entry loses `pending` and gains `sent` (or
  `error`; a step that is gone or cancelled stops waiting). Not reproduced: the huddle, notebook, equipment and PMR copies.
- The website's own ✓ reports at once and never writes `pending`.

### Trigger and cost
`syncUp` (throttled to 1 min), `syncWeekSteps` (10 min) and `syncTicks` run in `quietSyncs` (hello: the bridge's start,
the website's open). After a push the hub runs only what the push carries: task blocks or library rows → `up` + `tasks`;
a block with a pending ✓ → `ticks` at once. `syncTicks` reads the blocks only then, or at most every 5 minutes on hello.

### Desktop app (Gabe's `scientia/src`)
- `15c-litreviews.js`: the Lit reviews tab (after Portfolio), the topic and projects in a review's head box, reviews out
  of quick notes — over the same `doc.review` the website uses. On the website the lab layer draws its own (the module
  checks `window.SIS_LAB`).
- `23b-labsync.js`: the ✓; "waiting for the lab" on a task without `rmTaskId`; a lab-inventory material (`inventoryId`)
  as a fixed card (no log box, no new batch) and a read-only sheet. Its wrappers make `TASK.body` and
  `WIDGETS.task.body` (and `MATS2.cardBody` and `WIDGETS.matcard.body`) one function, so the lab layer, which re-points a
  widget only while the two match, still wraps them on the website.
- `serve.py`: a ~5 MB app page could stop loading in Chrome / Edge — the stock `copyfile` ignores a short write on the
  unbuffered socket; every chunk now goes with `sendall`.

## Not in this version

Protocols; materials and equipment scheduling; `lab-mode.js` / `cloud-sync.js` (unchanged — the web build carries the two
new app modules, which stand aside there for the lab layer's own tab, ✓ and cards; the lab-mode harness still passes).
Library marks for papers not yet sent are left for later.
