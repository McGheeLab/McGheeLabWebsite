# V3.593 — Voice call security + correctness hardening

## Context

After V3.587 (TURN) I ran two independent adversarial Opus reviews over
the whole voice-call feature — one on WebRTC/signaling correctness, one on
rules/security/mobile — because this is live-network code handling
microphones, and the first real call had already surfaced one predicted
failure. They found a **silent microphone tap** plus a set of correctness
defects that would make calls unreliable in normal use. This release fixes
them.

Nothing here is speculative: each item is a concrete failure path the
reviews traced end to end.

## The security hole (worst finding)

Nothing tied `voiceCalls/{channelId}` to membership of
`chatChannels/{channelId}`. Two consequences, both exploitable from the
browser console by any non-guest lab member:

1. **Silent audio tap.** `handleSignal`'s `offer` branch lazily created a
   peer for any sender, and `createPeer` unconditionally attaches the
   local microphone — so writing one unsolicited `offer` doc made the
   victim's browser answer *with live mic audio*. No tile appeared (the
   panel renders from the participant roster, which a lazily-created ghost
   peer isn't in), no participant count changed, no trace at all. The
   roster snapshot tore the ghost down every ~5s, so an attacker just
   re-offered on a timer.
2. **Join any call.** `VOICE_CALL.open('<any dm channel id>')` wrote a
   participants doc and joined the mesh — including a PI↔student 1:1. The
   attacker's tile showed a client-controlled `name`, so it could read as
   a plausible muted participant.

Fixes, defence in depth (both halves needed):
- **Rules:** new `inCallChannel(channelId)` helper (one `get()` of the
  channel doc; DM `members[]` OR channel `subscriberUids[]` — the same
  split `functions/chat.js` uses for push) now gates call-doc
  create/update/delete, participants create/update, and signals create.
  Create also pins `startedBy == request.auth.uid` (see below).
- **Client:** an `offer` from a uid not in the fresh participant roster is
  never answered. Because a legitimate offer *can* beat the roster
  snapshot, it's buffered in `_pendingOffers` and replayed only if that
  uid genuinely appears (and dropped if they never do).

**Read-rule shape matters.** Firestore rejects a whole *list* query whose
rule needs a `get()` of another document, so the active-call watcher can't
use `inCallChannel`. Instead the call doc carries a denormalized
`memberUids` (written from chat's member list) and:
- `allow get: if isLabMember()` — reveals only that a call exists in a
  channel whose id you already know; never audio or signaling.
- `allow list: if isLabMember() && request.auth.uid in resource.data.memberUids`
  — and the client query is now
  `where('memberUids','array-contains',uid)`, so nobody subscribes to
  every call in the lab (which also leaked "who is talking to whom" in
  real time, since a DM call doc carries the partner's display name).

Also closed: **forged caller identity / push spam.** `startedBy` was
unvalidated, so anyone could create a call doc attributed to Alex and fan
an FCM push ("📞 Alex McGhee started a call") to a whole channel — with
create→delete→create looping it indefinitely. The create rule now pins
`startedBy` to the caller and requires `startedByName is string`.

**Kick / disruption:** participants `delete` was any-member, so a 1Hz
delete loop kept everyone renegotiating. Now self, admin, or a peer whose
`lastSeen` is >60s old — the age clause is what makes ghost cleanup
possible *without* allowing a live kick. Signals get the same treatment at
120s.

## Correctness fixes

| # | Defect | Failure it caused |
|---|---|---|
| 1 | `_joining` was set AFTER an `await` | A second Join click during the first one's await ran the whole join twice: mic stream, heartbeat, level timer and **both Firestore listeners duplicated and leaked permanently** — every signal then handled twice, forever. Now set before any await, cleared in `finally`, with a `_gen` generation token to abort a superseded attempt. |
| 2 | Signals/roster handled after `leave()` | `createPeer` inserted into `_peers` *before* throwing on the null stream, leaving a zombie entry. The roster loop skips uids already in `_peers`, so that person **never negotiated again in any later call — permanent one-way silence, no error**. Now listeners are channel-scoped, `createPeer` checks preconditions first, and `leave()` clears every map. |
| 3 | Retry budget stored on the peer entry, which `teardownPeer` deletes | The counter was destroyed on teardown, so the answerer never enforced it; and the exhausted branch left the dead pc in `_peers`, permanently blocking any rebuild. Budget now lives in `_peerRetries` (survives teardown), resets on a successful connect (a hiccup at minute 1 shouldn't doom minute 90), and an exhausted peer is torn down and recorded in `_failedPeers` so the roster loop won't rebuild-loop it. |
| 4 | Ghost call docs, no janitor | Every closed tab left an `active` doc with zero participants → permanent phantom ring banner + live 📞 for the whole channel, and the next *real* call hit `if (!exists \|\| !active)`, **skipped the write, and therefore fired no FCM push and showed the stale caller name**. `ensureCallDoc` now purges a doc with no fresh participants older than `GHOST_MS` and creates a clean one, so `onCreate` (and the push) fires properly. |
| 5 | `onSignals` re-entrancy | Snapshots deliver the FULL result set, so an in-flight `await` let the next snapshot re-process the same offer concurrently. Now `_handledSignals` (marked synchronously before any await) + `_sigChain` serialization. |
| 6 | `leave()` deleted all my signals | Raced a fast rejoin and deleted the NEW session's offers → that pair stuck at "connecting" forever with no retry path. Cleanup dropped entirely; the recipient deletes signals normally and `purgeCall` reaps debris. |
| 7 | Same uid in two tabs | Presence and signalling are uid-addressed, so two tabs fought over the participant doc and cross-wired each other's SDP/ICE — frequently killing audio to that person outright. Full fix is per-client addressing (deferred, see below); this release **refuses the second session** with a clear message, using a `sessionId` on the participant doc. |
| 8 | `dismissLocal(chId, 0)` | A stored `0` acted as a match-anything wildcard, silently muting that channel's ring for the rest of the session. Now never stores 0. |
| 9 | `escHTML(nonString)` | Rules don't type-check Firestore fields, so a numeric `startedByName` threw `.replace is not a function` out of the banner renderer and **aborted the whole `render()` pass**. `escHTML` now coerces. |
| 10 | Panel rebuilt on every heartbeat | ~1 full `innerHTML` rebuild/sec wiped the speaking-dot classes the 200ms level meter had just set (visible flicker). Now diffed via `panelSignature()`. |
| 11 | Misc | `CSS.escape` in the tile selector (a client-written `uid` field with a quote threw every 200ms); audio-graph + `srcObject` cleanup in `teardownPeer`; pc handlers nulled; `AudioContext.resume()`; `joinedAt` no longer re-stamped every heartbeat; `encodeURIComponent` on the push deep link; `testIce()` clears its timer and reports `onicecandidateerror` (701 = unreachable vs 401/403 = bad credentials — previously indistinguishable). |

Also: the active-call watcher now uses a **raw** `query.onSnapshot`, not
`firebridge.onSnapshot`, whose `permission-denied` path pops a page-level
"your access may have changed" banner — that would have fired for every
lab member on `chat.html` in the window before the rules deploy landed.

## ★ Deploy order is REVERSED from the usual

**FTP the client FIRST, then deploy rules.**

- New client + old rules → fine (old rules are permissive).
- Old client + new rules → **broken**: the old watcher queries
  `where('active','==',true)`, which the new `list` rule rejects outright
  (no `memberUids` constraint), so no ring banners at all.

```
# 1. FTP the repo (rm/ tree + sw.js)
# 2. firebase deploy --only firestore:rules
# 3. firebase deploy --only functions:onVoiceCallCreate   (encodeURIComponent only)
```
The security holes stay open in the window between 1 and 2, which is
acceptable only because exploiting them takes deliberate console work by
a signed-in lab member. Keep that window short.

Call docs created before this release lack `memberUids` and so are
invisible to the new watcher query; they can't be joined either, and
`purgeCall` clears them on the next call in that channel.

## Deferred (flagged, NOT in this release)

- **Per-client signalling (full multi-tab support).** Presence and signal
  addressing should key off a per-page client id, not the uid
  (`participants/{uid}_{clientId}`, signals carrying `toUid`/`fromUid` for
  the rules predicate). That's a schema + rules change; V3.593 blocks the
  broken case instead.
- **Server-side janitor.** Firestore does not cascade deletes, so
  `participants`/`signals` outlive a deleted call doc. `purgeCall` handles
  it opportunistically on the next join; a scheduled function doing a
  recursive delete would be the real fix.
- **Negotiation watchdog.** A lost `offer` (write failure) leaves a pc
  that never reaches `failed`, so nothing recovers and the tile spins
  forever. Needs a "no connection after ~10s → re-offer" timer.
- **Signalling write volume.** One Firestore doc per ICE candidate is the
  real ceiling on mesh size; batching candidates with `arrayUnion` would
  cut it substantially.
- **iOS app: background audio + earpiece routing.** `UIBackgroundModes`
  has no `audio` entry, so a call goes silent when the app backgrounds or
  the screen locks; and nothing sets the `AVAudioSession` category, so
  WKWebView WebRTC output commonly lands on the earpiece instead of the
  speaker. Both need native changes in OurlabMobile (and `audio` has App
  Review implications — it must genuinely be a live call, which this is).
  **Alex's call**, and the app is owned by a parallel session.

## Verification

1. `await VOICE_CALL.testIce()` on the campus network → expect
   `relay: true`. If false, read `errors`: 701 = TURN unreachable,
   401/403 = credentials rejected (then `voiceCallConfig/turn` is
   mandatory, not optional).
2. Real two-person call across networks → audio connects.
3. **Security regression test** (as a member NOT in a given DM, after the
   rules deploy): `VOICE_CALL.open('<that dm id>')` must fail, and
   hand-writing an `offer` signal doc must be rejected by rules AND
   ignored by the recipient's roster check.
4. Close a tab mid-call → next call in that channel rings normally with
   the correct caller name and fires a push.
5. Open chat in two tabs, join from both → second one refuses with "already
   in this call in another tab".
6. Rapid double-click Join, and Join-then-immediately-Leave-then-Join →
   exactly one mic stream, one heartbeat, one listener pair (check
   `navigator.mediaDevices` indicator / no duplicate console signals).
