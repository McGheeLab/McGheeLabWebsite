# V3.76 — Split-view navigation robustness

## Goal

Make workflow-split navigation seamless and rock-solid. The user
reported a confusing case (Lab Research workflow → split → click a
paper in the library iframe → "new workflow nav bar appears, then the
previous workflow nav goes away") and asked for broader robustness
fixes, not a one-off patch.

## Root cause

When a workflow-split iframe navigates within itself (e.g.
`library.html?embed=1` → `library-paper.html?id=X` via an `<a href>`
in [rm/js/library.js:252](../../rm/js/library.js#L252)), the new URL
drops the `?embed=1` query that V3.73's `nav.js` used to suppress
nested nav. The new document's `nav.js` then renders the regular
non-workflow top nav inside the iframe — the user sees an unexpected
second nav row, and the parent's strip looks "different" by contrast.
The `?embed=1` query is a fragile signal because it relies on every
in-page link to forward it.

A second related issue: parent's `state.left` / `state.right` (the
split URL params) doesn't update when the iframe navigates within
itself, so the strip's chip "open" markers go stale (Library chip
still highlighted as open in the left pane, even after the iframe is
showing library-paper).

## Three fixes that compose

### Fix 1 — `window.name` as a durable embed signal

The HTML spec says a frame's *browsing context name* (`window.name`)
persists across navigations within the same frame. So if we set the
iframe's `name` attribute at creation, every document loaded into that
iframe inherits it, regardless of URL.

- [rm/js/split-view.js](../../rm/js/split-view.js) — `paneHTML()`
  adds `name="rm-embed-<side>"` to the iframe element WHEN
  `_HAS_WORKFLOW`. Out-of-workflow split keeps `name=""` so iframes
  render their full nav.
- [rm/js/nav.js](../../rm/js/nav.js) — `renderNav()` checks
  `window.name.startsWith('rm-embed')` first; either it OR the
  existing `?embed=1` query triggers suppression. The two are
  belt-and-suspenders: name is durable across in-iframe navigations,
  query is the explicit initial-load signal.

### Fix 2 — Iframe URL sync to parent split state on `load`

When the iframe navigates within itself, parent has no idea unless we
listen.

- [rm/js/split-view.js](../../rm/js/split-view.js) — new
  `wireIframeLoad(side)` attaches a `load` listener to each iframe.
  On every load, reads `iframe.contentWindow.location.pathname +
  .search + .hash`, strips `?embed=1`, updates `state[side]` if
  changed, calls `writeState()` which dispatches the V3.75
  `rm:split:state-change` event. Strip refresh listener on
  `nav.js` re-renders chips with fresh `state.left` / `state.right`.

### Fix 3 — Strip `?embed=1` from saved state URLs

`?embed=1` is an iframe-rendering artifact; it has no business in
parent's URL bar, in `state.left` / `state.right`, or in the survivor
URL when user closes split.

- [rm/js/split-view.js](../../rm/js/split-view.js) — new
  `_stripEmbed(href)` helper. `writeState()` calls it on
  `state.left` / `state.right` before serializing to the URL.
  `wireIframeLoad()`'s sync also strips before assigning.

## Why the three together

Each fix targets a different boundary where state can drift:

- Fix 1 — parent ↔ iframe (in-frame navigations preserve embed)
- Fix 2 — iframe URL ↔ parent split state (synced on every load)
- Fix 3 — saved URLs (clean of internal artifacts)

Together: the strip is the single source of truth for navigation in
workflow split; iframes are pure content; state stays consistent
across user actions.

## Files modified

- [rm/js/split-view.js](../../rm/js/split-view.js) — `paneHTML`
  iframe name attr, new `wireIframeLoad`, new `_stripEmbed`,
  `writeState` normalizes URLs.
- [rm/js/nav.js](../../rm/js/nav.js) — `renderNav` checks
  `window.name` for embed signal alongside the existing `?embed=1`
  query check.
- [sw.js](../../sw.js) — `CACHE_VERSION` 50 → 51.

## Untouched (intentionally out of scope)

- **Out-of-workflow split** — iframes still get full nav inside (no
  `window.name` set). User can navigate within each pane via the
  iframe's own nav. No swap-via-strip UX. A future V3.77+ could add
  a parent-side page picker for this case.
- **`pageState` updates from inside iframe nav** — pageState lives on
  parent's sessionStorage; in-iframe navigations don't update it.
  Resume-where-you-left-off works at the boundary (when user
  closes split, parent navigates to the active iframe URL, strip
  renders, pageState updates) — just not while still in-split.
- **Cross-pane interactions** — each iframe is independent. Out of
  scope.

## Risks

- **`window.name` collisions**: third-party iframes (GIS, Microsoft
  OAuth) sometimes use it, but those are first-party RM pages we
  control. Safe.
- **`load` event firing on initial iframe load**: dispatches a no-op
  state-change. Cheap; the strip re-renders identically. Could guard
  but pragmatically not needed.
- **Cross-origin `contentWindow.location` access**: only an issue if
  iframe somehow navigates to a cross-origin URL (shouldn't happen
  for `/rm/*` internal pages). Wrapped in try/catch.
- **History pollution**: `writeState` uses `history.replaceState`, so
  iframe-load syncs don't add history entries. Browser back/forward
  remains coherent.
