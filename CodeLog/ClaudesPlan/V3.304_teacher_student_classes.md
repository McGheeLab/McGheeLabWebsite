# V3.304 — Teacher & Student External User Types (Class Modules for Outside Schools)

> **Version note:** CHANGELOG tops out at V3.300, but the uncommitted working tree already contains V3.302-labeled rules blocks (publish gates for stories/newsPosts/projectPackages). This feature takes **V3.304**; confirm at ship time nothing else claimed it.

## Context

The site will soon host many more outside guests — in particular teachers who want to use the lab's interactive class modules (`modules/`) with their own students. Today there is no external-educator concept: every new Google sign-in lands as `role:'guest'` with nothing to do, class materials are fully public but unorganized for outsiders, and Alex has no visibility into who is accumulating in the `users` collection. This version adds a full teacher/student lifecycle: teacher signs up → requests a class → admin approves and provisions the teacher's own class instance → teacher shares a join code → students enroll → both can write admin-moderated reviews → approved teachers get featured on the team page. Two new RM admin panels give Alex oversight of teachers and of unclassified guests.

**Decisions locked with the user:**
- Teacher/student experience lives on the **main site**; admin panels live in **RM**
- Materials = the `modules/` training modules; **soft gating** accepted (JS-checked enrollment; static HTML stays technically fetchable)
- Each approved teacher gets **their own class instance** (own `schedules` doc, own roster/code) — never mixed with Alex's BME classes or students
- Students join via **class code** (no email infrastructure)
- Teachers get a **simplified fixed panel**, never the full class-builder editor
- Teacher public profiles are **teacher-written, admin-approved**; reviews are **admin-moderated**, displayed on #/classes and beside featured teachers, with ALL review data visible in the admin panel
- One big version, not phased

## Role taxonomy

Teachers and students keep `role:'guest'` and get new **`category`** values `'teacher'` / `'student'` (added to `CATEGORIES` and `CATEGORY_DEFAULT_ROLE` in [user-system.js:22-41](user-system.js#L22-L41)). Because `role === 'guest'`, RM's `isLabMember()` gate and pending overlay keep them out of the lab dashboard with **zero RM changes**, and the team-page filter at [app.js:595](app.js#L595) (`role !== 'guest'`) keeps them off the lab team sections automatically. All class capabilities come from doc ownership (`schedules.ownerUid`) and `enrollments` membership — never from `role`.

**Guest-oversight taxonomy (derived, not stored)** — the Guests panel buckets every `users` doc by first match: lab member (`role !== 'guest'`) → collaborator (`category==='collaborator'`) → teacher → student → **guest (unclassified)**. No schema change; panel offers one-click recategorize.

## Data model (new Firestore collections)

| Collection | Doc id | Shape (key fields) |
|---|---|---|
| `classRequests/{autoId}` | auto | `teacherUid/Name/Email, school, gradeLevel, classSize, subjectArea, requestedFolders[], message, status: pending\|approved\|denied, scheduleId, decidedAt/By, denyReason` |
| teacher class = `schedules/{tc-…}` (reused) | `tc-<school-slug>-<4ch>` | existing schedule shape + `kind:'teacher-class'`, `teacherUid, school, grantedFolders[]` (admin-only, rules-pinned), `modules[]` built from manifest, `enrollmentOpen`, `tabs:[]` |
| `joinCodes/{CODE}` | **the code itself** (6 chars, A-Z/2-9 no ambiguous) | `scheduleId, teacherUid, active, createdAt` — codes can't live on the public-read schedules doc; get-by-exact-id only, list restricted to owner/admin |
| `enrollments/{scheduleId}_{studentUid}` | deterministic composite | `scheduleId, studentUid/Name/Email, teacherUid (denorm), joinCode, status: active\|removed` — one doc per (class, student); "am I enrolled" is a single get; students never need `list` |
| `reviews/{autoId}` | auto | `authorUid/Name, authorRole: teacher\|student, scheduleId, teacherUid, school, rating 1-5, text, status: pending\|approved\|rejected, featured, moderatedAt/By` |
| `teacherProfiles/{teacherUid}` | uid | `name, school, subjectArea, blurb, photo{thumb,medium,full}, status: draft\|pending\|approved\|hidden` — separate from `users` (owner-writable) so `approved` is admin-only; any owner edit forces status back to draft/pending → auto re-approval |

**No Cloud Functions needed.** Join-code validation is rules-expressible because the code is the `joinCodes` doc id: the enrollment-create rule `get()`s it and checks `active` + `scheduleId` match server-side.

## firestore.rules changes

1. **HARDEN `users/{userId}`** ([firestore.rules:148-150](firestore.rules#L148-L150)) — currently owner has full write, so **any signed-in user can set `role:'admin'`**. Must close before inviting the public: owner create must land `role:'guest'` (or carry a valid `inviteToken` matching an unused invitation's role); owner update may not change `role`; admin unrestricted. `category` stays owner-writable (self-identify as teacher/student). Client change: `Auth.register` (user-system.js:786-791) stamps `inviteToken` on the profile payload so invited registration still passes.
2. **Pin `schedules` teacher-class fields** (update clause ~L264-271): when `kind==='teacher-class'`, owner updates must preserve `grantedFolders`, `ownerUid`, `kind`. Docs without `kind` (Alex's classes) short-circuit — fully backward compatible.
3. **NEW `classRequests`**: create by self with `status:'pending'`; read/update/delete own-while-pending; admin everything.
4. **NEW `joinCodes`**: `get` any signed-in (the enroll path); `list` owner/admin only (codes stay secret); create requires caller owns the referenced schedule.
5. **NEW `enrollments`**: create is self-service, id must equal `scheduleId + '_' + auth.uid`, gated on `get(joinCodes/{joinCode}).active == true` and scheduleId/teacherUid match; read by student-self, class teacher, admin; teacher/admin update-delete; student self-update limited to `status/studentName/updatedAt` (self-leave).
6. **NEW `reviews`**: public read only when `status=='approved'`; author reads own; create requires `status:'pending'`, `featured:false`, and real participation (schedule owner OR `exists(enrollments/{scheduleId}_{uid})`); author edit only while pending; admin moderates.
7. **NEW `teacherProfiles`**: read if approved/admin/owner; owner writes forced to `status in ['draft','pending']`; only admin lands `approved`.

**Composite indexes** (firestore.indexes.json) — only two: `reviews(status ASC, createdAt DESC)` and `classRequests(status ASC, createdAt DESC)`. All dashboard queries deliberately single-equality + client sort.

**storage.rules** — verify `users/{uid}/**` owner-write covers a `teacher-photo` upload path (reuses existing `uploadImageSet` flow); add sibling allowance only if needed.

## Rollback

- Frontend: git revert the release commit, bump CACHE_VERSION **up** (never down), re-FTP. New collections become inert orphans — harmless; Alex's classes are never mutated.
- Rules: redeploy previous firestore.rules from git. Rolling back the users hardening reopens a hole that already existed (no regression); rolling back new blocks fails teacher/student writes closed — safe.
- Partial rollback (keep rules, revert UI) is safe: every new rule is default-deny.
