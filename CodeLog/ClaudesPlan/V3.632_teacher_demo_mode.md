# V3.632 — Teacher/Student Demo Mode (admin preview of every external-user state)

## Context

V3.304 shipped the external teacher/student platform: teachers request a
class, admin provisions a `schedules/{tc-…}` doc, students join with a
6-char code, both write moderated reviews, approved teachers appear on the
People page. Since then **nobody has actually seen most of those screens.**
Two structural reasons:

1. **Alex cannot reach them at all.** `renderDashboard`
   ([user-system.js:1406](../../user-system.js#L1406)) dispatches the
   teacher/student panels only inside `if (Auth.isGuest())`. Alex is
   `role:'admin'`, so setting `category:'teacher'` on his own profile does
   nothing — he gets the lab dashboard. The only way to see the teacher
   dashboard today is to create a second Google account, get it approved,
   and keep it as a guest.
2. **Most states are hard to manufacture.** "Request denied with a reason",
   "class with 14 students", "removed student hits the code gate",
   "profile pending approval", "join code disabled" each need a real
   multi-account round trip through the admin panel.

So the panels most likely to embarrass the lab in front of an outside
teacher are the least-tested code in the repo. This version adds an admin
demo mode that renders **the real dashboards and the real class page**
against in-memory fixtures, one click per state.

**Companion work (not code):** a rules stress test was run against the
Firestore emulator (62 checks, 10 deviations) — see
`CodeLog/ClaudesPlan/V3.632_teacher_rules_findings.md` for the findings and
proposed rule fixes. Demo mode deliberately does **not** claim to test
permissions; see "What this does not test" below.

## Goal

One admin surface, `#/demo`, that lists every teacher/student/guest state
as a persona. Picking one renders the **actual production render/wire
functions** — `renderTeacherDashboard`, `wireStudentDashboard`,
`wireTeacherClassPage`, the module-viewer gate, the public reviews strip,
the People-page teacher cards — against fake data, with writes intercepted
into a visible action log instead of hitting Firestore.

Non-goals: no fake Firebase Auth accounts, no demo documents written to
production Firestore, no changes to what a real teacher or student sees.

## Approach

### The seam

`teacher-classes.js` gets four one-line resolvers near the top:

```js
function demo() { const d = ML.TC_DEMO; return (d && d.active) ? d : null; }
function src()  { return demo()?.db || TC_DB; }          // data layer
function me()   { return demo()?.uid || ML.Auth?.currentUser?.uid; }
function myProfile() { return demo()?.profile || ML.Auth?.currentProfile || {}; }
```

Every call site outside the `TC_DB` literal switches `TC_DB.x()` → `src().x()`
and `Auth.currentUser.uid` → `me()`. With `teacher-demo.js` absent or
inactive these return the real data layer and the real uid, so production
behavior is byte-for-byte unchanged — the demo file is pure addition.

Two raw-Firestore writes inside `joinClassWithCode` are folded into
`TC_DB.createEnrollment()` and `TC_DB.setUserCategory()` so the demo db can
intercept them too (the module now has exactly one write surface).

### The demo data layer

`teacher-demo.js` builds a `world` object (users, classes, joinCodes,
enrollments, reviews, teacherProfiles, classRequests) and exposes `DEMO_DB`,
implementing the same ~20-method interface as `TC_DB`. Reads answer from the
world; **writes mutate the in-memory world and append to an action log** —
so clicking "Regenerate code" really does swap the displayed code, and the
log records `joinCodes/ABC123 → created` + `joinCodes/XY7K9Q → active:false`.
That makes demo mode a functional check of the button wiring, not just a
screenshot. The world resets on page reload (noted in the UI).

Demo classes' `modules[]` are expanded from the **real**
`modules/manifest.json`, so the module list and the iframe viewer load real
module HTML — the same expansion the admin approve modal does.

### Personas

| id | What it shows |
|---|---|
| `visitor-signedout` | class page → "Sign in to view this class" |
| `guest-new` | guest dashboard → teacher CTA + class-code card |
| `teacher-fresh` | request form (module-set checkboxes), no classes, empty public profile |
| `teacher-pending` | pending request chip + "being reviewed" + Withdraw |
| `teacher-denied` | denied chip + reason + a fresh request form |
| `teacher-live` | 1 class, active code, **0 students**, profile draft |
| `teacher-busy` | 2 classes, 14 students, one code disabled, profile approved, approved + pending reviews |
| `student-new` | join-a-class card, no classes |
| `student-enrolled` | 1 class + review form |
| `student-reviewed` | pending review with moderation chip + Edit |
| `student-removed` | class page → code gate; dashboard shows no classes |

### Hooks (5 small, all no-ops when demo is off)

| File | Hook |
|---|---|
| [user-system.js](../../user-system.js) | `renderDashboard` / `wireDashboard` dispatch on the demo persona before the `isGuest()` branch; `wireGuestProfileCard` routes its two writes through the demo log |
| [class-builder.js](../../class-builder.js) | `resolveSchedule` returns the demo schedule for `tc-demo-*` ids |
| [teacher-classes.js](../../teacher-classes.js) | the four resolvers; `wireTeacherClassPage` honors `demo.signedOut`; `tcCanViewModules` asks the persona |
| [app.js](../../app.js) | `#/demo` route (render + wire + AUTH_GATED); `TC_DEMO.mountBanner(view)` after every render |
| [rm/pages/admin-teachers.html](../../rm/pages/admin-teachers.html) | "🎭 Demo mode" link to `/#/demo` |

### The banner

Rather than a fixed overlay (which would fight the sticky site header), the
strip is prepended into the rendered view on every route change: persona
name, a switcher `<select>`, "↻ reset data", "✕ exit demo", and an
expandable action log. Precedent: the class-builder View-as toolbar
(V3.248), which does the same thing scoped to one page.

## What this does not test (stated in the UI, not just here)

Demo mode runs as **Alex, signed in as admin**. It proves layout, empty
states, copy, and button wiring. It cannot prove permissions: a real
teacher's reads may be denied where the admin's succeed. Permission
fidelity comes from the emulator suite and from a second real Google
account — both documented in the findings doc.

## Rollback

Delete the `<script>` tag (or the file). Every seam falls back to the real
data layer when `ML.TC_DEMO` is absent, so the platform keeps working with
zero other edits.
