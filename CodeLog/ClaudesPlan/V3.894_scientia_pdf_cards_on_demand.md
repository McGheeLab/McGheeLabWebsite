# V3.894 — Scientia: PDF cards draw on demand (a canvas with many PDFs stays smooth)

**Ask (Alex, 2026-10-24):** "when there are too many pdf's on the canvas it seems to slow down and the site glitches and
freaks out. is there a way to keep this from happening?" → option 1 of the four offered: fix the PDF card itself, on
the web now (our layer), and the same change to Gabe for his desktop.

## What was measured (the ERK review, 28 PDFs, 660 pages; local Scientia, Retina 2×)

- Opening the note: every PDF card loads its file and draws the first 2–3 pages of its own scroll area, on screen or
  not (`PDFW.body`'s IntersectionObserver is rooted on the card's stage, not the screen) → **57 pages drawn, 4 on
  screen, 383 MB of canvas**, 3.8 s of main-thread long tasks while it settles; `getPage` for all 660 pages to size
  the slots.
- **Any `changed()` rebuilds every box** (`DocView.update` → `fill` removes and recreates them all): one note created
  on another device and synced in → all 28 viewers thrown away, 57 pages redrawn, a 438 ms freeze, memory doubled until
  GC. Typing, dragging a card and zooming do not trigger it; every sync pull that applies anything does.
- On the web each PDF is fetched whole on every opening (Storage `cache-control: private, max-age=0`; pdf.js
  auto-fetches the rest of the file). Range requests work (206, `Content-Range` exposed to mcgheelab.com).

## Approach — `rm/scientia/lab-mode.js` §14 (web), then a PR for `scientia/src/13zk-docs.js` (desktop)

A PDF card (scroll or one-page view; the maximised view and the phone layout keep Gabe's drawing):

1. **Survives a rebuild.** `PDFW.body` returns the same viewer element when the block object, the pane and what it
   shows (`media`, `view`, page in one-page view, `pages`, `w`, `h`, read-only) are unchanged — `fill` moves it into
   the new box, canvases intact. A changed block (its record replaced by sync, resized, other view) gets a new viewer.
2. **Draws only on screen.** A shared viewport IntersectionObserver (400 px margin) activates a card; its page slots
   (built from the stored page count, sized from page 1's aspect) draw when in the card's own scroll window. Off screen
   for 4 s → pages released (canvas 0×0, text layer removed), the PDF document can be dropped (at most 6 kept).
3. **Sharp enough for the zoom, no sharper.** Resolution = zoom × devicePixelRatio (¼ steps, 0.5–3); a zoom change
   (wrapped `Paper.prototype.apply`, debounced) redraws visible pages only when off by > 1.25× / < 0.5×; redraws go
   to a new canvas swapped in when done (no flash). Below zoom 0.33 a card shows its title and page count instead.
4. **Fetches only what it draws.** `PDFW.load` adds `disableAutoFetch` + `disableStream` (range requests).
5. Quotes keep working: a page's first draw adds `QUOTE.textLayer` (what Gabe's `PDFW.page` wrapper does), so the
   highlights and text selection are there; slots exist before drawing, so "from …" can scroll to its page.

At most 2 pages render at once (a small queue, on-screen cards first). `SIS_LAB.pdf.stats()` reports cards / active /
drawn pages / canvas MB / loaded documents for tests.

## Key decisions

- **Our layer first, Gabe's code by PR.** `scientia/src` is Gabe's (scientia/CLAUDE.md); the web gets the fix today and
  his desktop gets it when he merges. §14 checks `PDFW.onDemand` so the two never stack.
- **Fix the card, not `fill`.** Rebuilding every box on each change is Gabe's design for all components; only the PDF
  card is expensive enough to need to survive it.
- **A title, not a thumbnail, when zoomed far out**: a thumbnail would still load and parse every PDF on screen.
