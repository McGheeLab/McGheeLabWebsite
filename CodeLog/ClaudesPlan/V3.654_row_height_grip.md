# V3.654 — The horizontal lines get a grip too

## The ask (Alex, 2026-08-20, on V3.653)

*"the horizontal lines are not getting the grip right now"*

Correct, and deliberate at the time — wrongly. V3.652 gave the `|||` only to
column lines, reasoning that row height in LaTeX is `\arraystretch`, a property
of the whole table (the style bar's "rows:" control), so a per-row drag would be
a handle for something with nowhere to be stored.

That reasoning was half right. `\arraystretch` genuinely cannot make *one* row
taller — but `\\[dim]` can. It is the row terminator with an extra vertical space
argument, and it is exactly what dragging a horizontal border should mean.

## The model

A new scalar attr, separate from `style_json` because it is per-row data rather
than a table-wide style — the same split as `cell_styles_json`:

```
row_heights_json   {"<r>": <extra points>}
```

Points, because that is what the `.tex` needs and the browser can divide.
Shared helpers in `paper-layout-rules.js` (`parseTableRowExtras`,
`shiftTableRowExtras`, `TABLE_ROW_EXTRA_MAX_PT`), so all four table surfaces read
one parse, as with every other table attr.

- `0` and negatives are **dropped** rather than stored as no-ops, so a row
  dragged back to its natural height leaves no residue and the attr disappears
  entirely when the last one goes.
- Clamped to **60 pt**. Past that the writer wants another row, not a taller one,
  and an unbounded drag could otherwise push a table off the page with no way
  back except editing JSON.
- Re-keyed by `_tblStructOp` alongside cells, merges, align, widths, cell styles
  and `rule_after` — in the same transact, or the extra height stays on the row
  index that used to be there.

## The grip

`i > 0` now earns a grip on **both** axes — every line that has a band before it
to resize. A column line sizes the column on its left; a row line adds height to
the row above. Opening edges (line 0) still get none: there is nothing before
them. The grip keeps its place between the `＋` and the `−`, and carries
`cursor: row-resize` on a horizontal line.

Drag maths mirrors the column drag: pixels → points at the CSS 96 dpi reference
(the same conversion the mm column widths already use), clamped, previewed live,
committed on mouse-up only if the pointer moved. A row entirely covered by a
rowspan has no `td[data-r]` of its own, so there is nothing to resize and the
drag bails rather than guessing.

## Rendering it

**Browser** (editor grid, doc-side preview, Document view): `padding-bottom` on
the row's cells, driven by a `--pe-row-extra` custom property so the drag can
preview without touching every cell. Padding *under* the row, because that is
what `\\[dim]` does in the PDF — space after the row, not a taller cell box.

**LaTeX**: `rowEnd(r)` composes the extra into the terminator the row already
ends in — ` \\[6pt]` instead of ` \\`. It has to be *composed*, not appended:
` \\ \\[6pt]` would be an empty extra row. Both the float and longtable paths
use it. No extras means the plain ` \\`, byte-identical to before; asserted.
