# V3.598 — My Day watch surface + notification tile

R5, the last release of the smart equipment schedule-change program
(R1 = V3.588 criticality, R2 = V3.594 adjacency + feed, R3 = V3.595
reminders, R4 = V3.597 watches; = **FuturePlan 08 Phase 3 complete**).

**FTP-only** — no rules, indexes, or functions change. Everything here
rides infrastructure the previous four releases already deployed.

## Goal

Close the loop where students actually plan their day. Two additions:

1. **Set a watch from the My Day composer.** When the availability strip
   says the slot you dragged is taken, offer "🔔 Notify me if 2 PM–4 PM
   frees up" right there — no trip to the Equipment page.
2. **🔔 tile on the RM home strip.** Unread notifications surface on the
   landing page, leading with the newest one's actual text.

## Problem

V3.597 put watches on the equipment calendar, which is the right place
for browsing a device's week — but it's not where students plan. My Day's
composer is: you pick the scope, drag a window, and the strip tells you
it's taken. That refusal was a dead end. The student either picked a
worse slot or made a mental note to check back later, which is exactly
the manual polling the watch feature exists to eliminate.

Separately, the V3.594 feed only existed inside My Day, so a student who
landed on the RM home page had no signal that anything was waiting.

## Approach

### The CTA appears exactly where the refusal does

`renderAvailStrip()` already computes `EQUIP_AVAIL.checkSlot()` and
renders its failure reason. The watch button is appended in that same
branch, so it shows up attached to the specific refusal it answers.

**Gated on `check.bookings`.** `checkSlot` returns that array *only* from
its clash branch — a slot refused for falling outside posted hours or
past the advance limit will never "free up", so offering to watch it
would be a lie. This is a slightly implicit signal, so the reason is
written down at the call site.

### Chips make existing watches visible where they're created

`renderWatchChips()` lists the user's active watches for the composer's
current device + date, each with a ✕. Without this a student could set
the same watch repeatedly and never see it, since the equipment page was
previously the only place they were visible.

### Shared wrappers, identical doc shape

`EQUIP_AVAIL.createWatch/deleteWatch/listWatches` write the *same* doc
shape as `EDB.createWatch` on the Equipment page. `firestore.rules`
whitelists the keys exactly, so any drift here fails the write — and
there is deliberately **no update wrapper**, mirroring
`allow update: if false`.

### Home tile leads with content, not a count

"3 unread" tells you nothing about whether you need to be off the scope in
ten minutes. The tile shows the newest notification's title instead, and
is always `urgent: true` (amber) — these are time-sensitive by
construction.

**Escaping matters here.** `home-feed.js`'s `boot()` injects `label` and
`detail` into `innerHTML` raw; each tile escapes its own content (see
`tileTasks` / `tileMeeting`). Notification titles carry other people's
display names, so `tileNotifications` calls `esc()` before returning.

## Files modified

- `rm/js/equipment-availability.js` — `createWatch` / `deleteWatch` /
  `listWatches` on `window.EQUIP_AVAIL`.
- `rm/js/my-day.js` — `state.compWatches`; `loadComposerWatches()`;
  `renderWatchChips()`; the 🔔 CTA inside `renderAvailStrip()`'s failure
  branch; `watch-slot` / `watch-drop` click routes.
- `rm/js/home-feed.js` — `tileNotifications()`, first in the tile list.
- `rm/css/my-day.css` — `.md-a-watch`, `.md-a-wchip*`.

## Data model changes

**None.** Reuses `equipmentWatches` (V3.597) and
`userData/{uid}/notifications` (V3.594).

## Out of scope

- Watches are still **single-device, single-date** — a "sometime this
  week" request has no representation in `dayPlans` or
  `equipmentWatches`, and adding one is a data-model change, not a UI
  one.
- The availability strip still shows a fixed **next-7-days-from-today**
  window rather than the viewed week (pre-existing, `my-day.js`).
- Watches are deliberately **not** `dayPlans` items — they're ephemeral
  signals, not scheduled work, so they get no `day-distribute` adapter.

## Release ritual

FTP only. `sw.js` CACHE_VERSION → 567.

No `firebase deploy` of any kind — but note this release is only
*useful* once V3.597's rules + indexes are live, since it writes
`equipmentWatches`.

## Rollback

Revert the four files + re-FTP + bump `sw.js`. Watches created from My Day
are indistinguishable from those created on the Equipment page, so nothing
needs cleaning up.

## Verification

1. My Day → composer → 🔔 Equipment ingredient → pick a device → drag a
   window that's **already booked** → the red refusal line is followed by
   "🔔 Notify me if … frees up".
2. Click it → toast confirms, and a `🔔 2 PM–4 PM ✕` chip appears under
   the strip.
3. Open Equipment → Calendar → same device/week → the watch renders as a
   hatched band (V3.597) — one watch, two surfaces.
4. Click ✕ on the chip → gone from both surfaces.
5. Drag a window **outside posted hours** → refusal shows, but **no**
   watch button (it could never free up).
6. Cancel the blocking booking from another account → push + the item
   appears in My Day's 🔔 section.
7. RM home page → 🔔 tile shows the newest notification's text; clicking
   it goes to My Day. Mark all read → the tile disappears on reload.
8. A notification whose title contains `<b>` or `&` renders as literal
   text on the home tile (escaping).

**109 plain-node fixtures** across three suites guard the notification
logic (`equipment-adjacency` 46, `equipment-reminders` 31,
`equipment-watches` 32). Run all three before any equipment functions
deploy.

**The design principle throughout:** most fixtures assert that nothing is
sent. A Soft booking exerts no pressure and receives no nudges; a day of
Soft bookings produces zero pushes. Students who mute a category are
worse off than students who never had it.

**Known limitations carried forward:** multi-day/overnight bookings are
excluded from adjacency and watch matching entirely; criticality is
notification-only (it does not affect displacement, approval routing, or
conflict resolution); server-side quiet hours remain unimplemented
(pre-existing).
