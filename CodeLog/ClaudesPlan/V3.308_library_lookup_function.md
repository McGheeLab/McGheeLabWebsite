# V3.308 — Production metadata lookup (Cloud Function) + client-side first-page extraction

> Source: `CodeLog/Feature requests/FuturePlan_01_library_paper_reader.md` Release 1
> (moved into production 2026-07-11).

## Goal

Add-by-DOI, PDF ingest metadata sniffing, and extension-capture enrichment all
work on **mcgheelab.com** (they currently only work on localhost), with a
smarter title-search fallback that asks before applying a fuzzy match.

## Problem

Every metadata path in the library rides `LIBRARY_METADATA.lookup()` →
`POST /api/library/lookup`, and PDF ingest rides `extractFirstPage()` →
`POST /api/library/extract-first-page`. Both endpoints exist only in the dev
`server.py` (sibling ResearchManagement repo). On the static prod deploy there
is no server, so:

- "Add paper by identifier" always fails.
- PDF drag-drop can't read the first page → no DOI sniff → every upload lands
  as `source:'manual'` with `title=filename`, empty authors.
- `library-sync.js` can't enrich sparse extension captures (arXiv/PubMed).

The existing title fallback at ingest (library.js `_ingestOne` step 3) is also
crude — "first line longer than 12 chars" — and **silent-applies** whatever
CrossRef returns, which can stamp a wrong paper's metadata without the user
noticing.

## Approach

### 1. New Cloud Function `libraryLookup` (functions/library-lookup.js)

- `onRequest` v2 function, CORS + Bearer-ID-token verification copied from the
  `deletePaper` pattern in [functions/library.js](../../functions/library.js)
  (same `ALLOWED_ORIGINS`, same 401/403 flow).
- Gate: authenticated AND `users/{uid}` exists AND `role != 'guest'`.
- Body `{doi | pmid | arxiv_id | title}` — exactly one used, same precedence
  as server.py (`doi` → `pmid` → `arxiv_id` → `title`). Optional
  `{refresh:true}` skips the cache read (future fullRefresh hook).
- Ports of `_csl_to_unified` / `_strip_jats` / `_lookup_crossref` /
  `_lookup_crossref_title` / `_lookup_pubmed` / `_lookup_arxiv` from server.py,
  1:1 so the JSON response stays byte-compatible with `buildPaperItem`
  consumers. Node 20 native `fetch`, zero new deps. CrossRef polite-pool
  `User-Agent` with a mailto.
- Not-found → `200 {"error": "..."}` (server.py convention — clients check
  `meta.error`); upstream fetch failure → `502 {"error": "Lookup failed: …"}`.
- **Cache:** Firestore `metadataCache/{sha1(kind:normalizedKey)}` docs
  `{kind, key, result, fetched_at}`; 30-day TTL; identifier lookups only
  (title queries are never cached); error results are never cached.
- Registered in [functions/index.js](../../functions/index.js).

### 2. firestore.rules — metadataCache deny-all

```
match /metadataCache/{cacheKey} {
  allow read, write: if false;   // Admin SDK only (libraryLookup function)
}
```

### 3. rm/js/library-metadata.js — transport branch + client-side extraction

- `lookup(params)`:
  - `RM_RUNTIME.isLocal` → try `/api/library/lookup` first (dev server keeps
    working offline); if that fetch *network-fails or 404s*, fall through to
    the Cloud Function (graceful when server.py isn't running).
  - deploy → Cloud Function directly
    (`https://us-central1-mcgheelab-f56cc.cloudfunctions.net/libraryLookup`,
    `Authorization: Bearer <idToken>`); throws "Sign in to look up metadata"
    when no Firebase user.
- `extractFirstPage(blob)` becomes **client-side-first** on BOTH runtimes:
  uses `PDF_VIEWER.extractTextItemsFromPdf` (already a module on library.html)
  limited to page 1, builds `{text, doi_guess, arxiv_guess, title_guess}`:
  - `doi_guess`/`arxiv_guess` via the existing `sniffIdsFromText`.
  - **`title_guess` (new):** the largest-font text run on page 1 — cluster
    items by height, take the tallest cluster ≥1.15× the page's median
    height, join its items in reading order (15–300 chars sanity window).
  - Server endpoint kept as fallback only when `PDF_VIEWER` is absent on a
    local runtime; on deploy without PDF_VIEWER it returns the empty shape.
- `PDF_VIEWER.extractTextItemsFromPdf(source, opts)` gains optional
  `opts.maxPages` (backward-compatible) so first-page extraction doesn't
  parse a whole 40-page PDF.

### 4. rm/js/library.js — better title guess + confirm-before-apply

In `_ingestOne` step 3, when there's no DOI/arXiv sniff:
- Title query priority: `firstPage.title_guess` → first text line > 12 chars
  (existing heuristic) → none.
- A title-search hit is **fuzzy** → show a native `confirm()` summarizing the
  match (title / authors / year / journal) before applying; declined or no
  hit → manual fallback, whose title now prefers `title_guess` over the
  filename.
- Same confirm added to the `_wireDoiAdd` free-text-title path (typed titles
  are also fuzzy matches; DOI/PMID/arXiv paths stay silent as today).

## Data model changes

New `metadataCache` collection (Admin-SDK-only, schema
`{kind, key, result, fetched_at}`). No index needed (doc-id point reads).
No changes to `items`.

## Out of scope (later releases of FuturePlan 01)

Metadata edit UI + fetch-diff (R2), DOI-driven fullRefresh + citation
localization + audit harness (R3), missing-PDF queue (R4). Semantic Scholar
*title* search (CrossRef title only here; SS enrichment still runs post-add
via the existing `enrichItemFromSemanticScholar`).

## Rollback

Client: git revert + re-FTP + CACHE bump (lookup falls back to failing like
today). Function: `firebase functions:delete libraryLookup` or redeploy
previous index.js. Rules block is additive deny-all — removing it is safe.

## Open questions

- None blocking. `library-sync.js` needs no change (it calls
  `LIBRARY_METADATA.lookup`, which now works on prod).

## Verification

- Local: `python3 rm/server.py` → add-by-DOI still uses the dev path.
- Prod (after functions+rules deploy and FTP): as a signed-in member,
  Add-by-DOI creates an item; adding the same DOI again is served from
  `metadataCache` (check function logs); drag-drop a PDF with a visible DOI →
  `source:'crossref'`; drag-drop an identifier-less PDF → confirm dialog with
  the CrossRef title match; decline → item titled with the PDF's own title
  guess, `source:'manual'`; signed-out lookup → clear sign-in error; guest
  account → 403.
