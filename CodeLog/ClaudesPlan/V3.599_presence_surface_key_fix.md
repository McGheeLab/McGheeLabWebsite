# V3.599 — Presence fix: surfaces must be keyed per webview, not per device

## The report

V3.596 shipped, everything deployed green, and the bug it was meant to fix
was still there. Alex: *"gabe had the chat open on his phone, when I sent
him a message he got the message, saw it, and got a notification banner."*

## Forensics

`onChatMessageCreate` at 20:25 logged `[Notify] Sent 2/2` with **no**
`Presence-suppressed` line — the gate ran and found nothing to suppress.
So the server was fine; the client was publishing the wrong thing.

The stored presence for both real phones read:

```
app  vis=False  age=204s  ['/rm/pages/chat.html']  ctx=[]
```

**First lesson: that snapshot was read ~20 min after the incident and
described the END state, not the state at message time.** Reasoning from it
produced a confident, wrong hypothesis (that WKWebView pins
`document.visibilityState` to `'hidden'` for an un-hidden child view).

So V3.599 added `dbg: {vs, tv}` to the presence payload — the raw inputs to
`isVisible()` — and re-ran it in the simulator. The data inverted the
hypothesis:

```
app  paths=['/rm/pages/tasks.html']  visible=False   vs='visible'  tv=False
```

`document.visibilityState` reports `'visible'` for a **hidden** background
webview (unreliable in the *opposite* direction), and — the real finding —
**My Day, the active tab, had no entry at all.**

## Root cause

V3.596 keyed `surfaces` by `deviceId`. Every webview in the Ourlab app
shares one `WKWebsiteDataStore` → one `localStorage` → **one deviceId**. All
five webviews (My Day / Focus / Chat / Tasks / misc) wrote to the same map
entry and clobbered each other. Idle-preloads land 3-5 s after launch and
each write `visible:false`, erasing the active tab's `visible:true`.

Two browser tabs in one browser hit the identical collision.

That is why a phone sitting on chat published `visible:false`, and why the
gate correctly (given its inputs) let the push through.

## Fix

1. **`surfaceId() = deviceId() + ':' + <sessionStorage id>`**
   (`rm/js/presence.js`). sessionStorage is per-tab on the web and
   per-webview in the app — exactly what "a surface" means. deviceId stays
   in the key so entries remain attributable per install.
2. **`pruneStaleSurfaces()`** — per-tab keys are unbounded over time, so
   sweep entries idle > 1 h once per page load (one read, at most one
   write). Purely housekeeping: the server already ignores stale entries.
3. **`isVisible()` now trusts `__OURLAB_TAB_VISIBLE` in the app** and only
   falls back to `document.visibilityState` on the web, where it is
   reliable. Not the root cause — on the app the old expression reduced to
   the same value — but the measurement proved `visibilityState` cannot be
   trusted in the shell, so relying on it was latent breakage.
4. **`dbg: {vs, tv}`** kept permanently. The V3.596 bug cost a chain of
   deduction because the doc recorded only the verdict.
5. **`tab-lifecycle.js` `selfCheck()` now corrects in both directions** —
   it dispatched `ourlab:tab-hidden` when this webview is not the active
   tab but never corrected a wrongly-hidden active tab. A no-op in
   practice (the seed evaluates true), kept as a safety net; all three
   resume paths are idempotent.
6. **`publishPresenceContext()` moved to the END of `render()`**
   (`rm/js/chat.js`) — `isWatchingFeed()` reads `_shellMode`, which
   `renderShell()` assigns partway through `render()`.

## Known gap

An app that is backgrounded (phone locked / home screen) keeps
`__OURLAB_TAB_VISIBLE === true`, so its surface stays "visible" until it
ages out of `FRESH_MS` — a ~90-150 s window in which a message to the
channel you were just reading is suppressed. iOS suspends the webview's
timers so the heartbeat stops and it self-heals. Closing it properly needs
the native shell to fire `ourlab:tab-hidden` on app background; deferred,
and worth doing since it would also stop chat holding Firestore listeners
open while backgrounded.
