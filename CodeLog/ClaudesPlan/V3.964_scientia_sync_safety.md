# V3.964 — Scientia: one copy per port, a sealed notebook refused, a device keeps its notes, the hub gets room

**Date:** 2026-11-09 · **Branch:** `scientia/sync-safety` · **Gabe's request:** "on my tablet, I have been adding many notes or
components to shared projects and they don't sync through to the website" and "when trying to set up my computer from
website to open locally, it said there was an error" (service.log attached).

## What was found on Gabe's computer

- **Four servers on port 8766 at once:** his standalone (Scientia-In-Situ, `python serve.py` in a cmd window since 12:06),
  two copies of the installed lab app (two `service.py` supervisors: the one from 19:14 and the one tonight's install
  started), and a fourth from the install. Windows lets a second socket bind over a listening one when
  `allow_reuse_address` is set (Python's `ThreadingHTTPServer` sets it), so every connection to `localhost:8766` landed on
  one of them at random: the browser, the tablet (over Tailscale) and the lab site's "Open on my computer" check each
  talked to a different app. `install.ps1` stopped only the process *listening* on the port, never the supervisor, which
  started the old copy again; and `service.py`'s `running()` ping got the standalone's 423, so it started a second one.
- **The notebook folder is sealed:** the standalone's lock (`access.py`, its own) had encrypted `record.json`, the images
  and the recordings (`SiSLock1`). The lab app's `load_json` returned `None`, so `sisync` ran with an **empty record**
  (`has_record = False`): to a device that looked like a wiped notebook (`hello.records == 0`), and the 3-second save
  would have written a plain-text record over the sealed one at the first push.
- **The hub ran out of memory:** after each restart the bridge realigned and asked `api/sync/state` for the whole
  record; `FirestoreHub.allRows()` did one `rows.get()` of every row (~25 MB of JSON, decoded all at once), and the
  function (512 MiB) died with `JavaScript heap out of memory` (log, 2026-11-10 03:17Z, repeatedly). The bridge got a
  torn answer, backed off, and sent the same thing again — so nothing from this computer reached the cloud since 11:52.

## What changed

| File | Change |
|---|---|
| `scientia/serve.py` | `Server.allow_reuse_address = False` and `SO_EXCLUSIVEADDRUSE` on Windows: one Scientia per port; a second one prints why and exits 3. `sealed()`: every `api/sync/*`, `api/snapshot` and `api/vault` answers **423** `{sealed: true}` with one sentence; `api/lab/status` says `state: 'sealed'`. |
| `scientia/sisync.py` | `load()` reads the first 8 bytes when the record will not parse: `SiSLock1` → `self.sealed = True`, nothing loaded, `sync.json` not written; `save_now()` never writes a sealed notebook. The standalone's own `load_json` unseals before this point, so there it is unaffected. |
| `scientia/service.py` | exit code 3 (the port is held by another program) → ten minutes between tries, not two seconds. |
| `scientia/install/install.ps1` | step 1 also stops every `python`/`pythonw` running `ScientiaInSitu\app\…` (the supervisor too), then waits 0.8 s. |
| `scientia/src/13zc-sync.js` | `reset()` sends the whole outbox batch after batch before loading (one push carries 400; a failed push keeps the device as it is). `fullLoad()` refuses an empty record over a device that holds notes: `SYNC.held` with the sentence, sync paused, the dot red with it. |
| `scientia/src/13zzj-polish.js` | the header dot is red for `state: 'sealed'`. |
| `functions/scientia-hub.js` | `memory: '1GiB'`; `allRows()` pages 400 rows at a time by document id; one log line per `state` / `push` with ms and rss. **Alex reviews; needs `firebase deploy --only functions:scientiaHub`.** |
