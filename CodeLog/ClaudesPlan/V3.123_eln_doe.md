# Plan — ELN safety + location surfacing (next: DOE)

## Context

Two follow-ups to the Lab Notebook (V3.110 → V3.118 already shipped) come
directly from grad-student bench reality:

1. **Hazard warnings on chemical chips.** A student picks a reagent and the
   chip renders without any indication that it's flammable / corrosive /
   acutely toxic. The data is already in inventory — `safety.signal_word`
   ("Danger" / "Warning"), `safety.ghs_pictograms[]` (GHS01–09),
   `safety.hazard_statements[]` (H-codes), `safety.precautionary_statements[]`,
   `safety.exposure_routes[]`, `safety.ppe_required[]`, `safety.nfpa_ratings`,
   `safety.first_aid` — and **65 of 158 chemicals are hazardous**, so this is
   a daily-bench surface, not a rare edge case. The pictogram→symbol→color
   mapping is already implemented at [rm/js/chemicals.js](rm/js/chemicals.js)
   `ghsPictograms()`; reuse it.

2. **Location info on every inventory chip.** Students need to *find* the
   item they're using. The schema is `locations: [{name, quantity, notes}]`
   on every inventory doc, but **0/935 items are populated today.** Surface
   the field anyway with a graceful "location not set" hint that points
   admins to [rm/pages/inventory.html](rm/pages/inventory.html) to populate.
   No bespoke admin tool needed in the notebook for this version — that page
   already has location editing.

DOE (LHS + Full Factorial + CCD with structured `state.doc.design`) is
**Phase 2**. **Phase 3** is the bigger vision: the lab notebook becomes a
single tool that runs the **full experimental loop** — plan the experiment,
walk to the bench and record actuals against the plan, end the run with a
summary, spawn the next iteration. The point is that the same notebook
entry IS both the experimental design document AND the recording sheet,
so a student never has to copy planned values onto a paper sheet to take
to the bench. See Phase 3 below for the design.

## Phase 3: Plan → Execute → Complete — the bench workflow

> *The workflow that makes students actually use the notebook.*

### Why this matters

Today's notebook is a great record-keeper but it doesn't help with the
**flow** of an experiment. A student writes their plan in Notion or on
paper, walks to the bench with that plan in hand, scribbles actual
numbers on a paper sheet, then transcribes those numbers later (often
days later, often badly). The McGhee Lab notebook should be the single
tool that runs the full loop — **the entry IS the plan AND the
recording sheet**. If the user has to copy planned values onto a paper
sheet to take to the bench, we've already lost.

The non-negotiable bench constraint: **at the bench, the student is
gloved, often time-pressed, and frequently on a phone**. Friction kills
adoption. Every interaction in run mode must be one-tap or one-checkbox.

### The lifecycle

A new top-level field on the entry doc:

```js
phase: 'plan' | 'running' | 'complete'
```

Default `'plan'` for new entries; legacy entries without `phase` are
inferred as `'complete'` (so existing notebooks don't suddenly look
unfinished). The `status` field stays for the existing `open` /
`closed` / `archived` enum — it's about archival lifecycle, not
experiment lifecycle. Phase is orthogonal.

### Plan mode (the default — same as today + one button)

Plan mode is what the notebook already does:
- WYSIWYG body, autosave, attachments
- Project + tags + status
- Materials chips with hazard + location (V3.121)
- Protocols chips (V3.116)
- DOE design panel (Phase 2)

**Difference from today**: a single primary `▶ Start run` button in the
entry footer. The footer also gains a `📝 Plan` pill in the meta row
showing the current phase.

Materials panel in plan mode: each row gains a small free-text **"Planned
qty"** input (e.g. `5 mL of 100 mM Tris`). Default empty; the writer
fills in if the experiment has a plan-level quantity. The DOE matrix is
fully editable. Protocols are linkable but no deviation log yet.

### Run mode (the flip — `▶ Start run` was clicked)

Click `▶ Start run` → entry's `phase` becomes `'running'`,
`run_started_at` is stamped, the UI rerenders into recording mode.

**Visual structure** in run mode (top → bottom):
1. **Plan summary** (read-only, collapsed by default, click to expand):
   shows the entry's body, materials, protocols, design as a frozen
   reference. The plan is what the user is *executing* — it should be
   easy to reread but impossible to mistakenly edit at the bench.
2. **▶ Recording** panel — the active surface. Sub-sections:
   - **Materials — actuals.** Each planned chip becomes a row with:
     - Name + planned qty (read-only display)
     - "Actual lot" input (auto-fills if the chip already has a default
       lot from inventory)
     - "Actual qty" input (defaults to planned qty; one click confirms)
     - **"✓ same as planned"** checkbox (default checked) — the
       primary affordance. The student only has to *uncheck* a row when
       something diverged. This is the bench-friendliness key.
     - When unchecked: actual lot + actual qty become required
   - **Protocols — deviations.** Each linked protocol gets a card:
     - "✓ followed as written" checkbox (default checked)
     - When unchecked: free-text deviation log + photo button
     - Each deviation entry stamps `at`, optional `step_ref`, optional
       photo
   - **DOE — observed.** When the entry has a design, each design row
     becomes its own collapsed card. Tap a row → expand into a focused
     panel for *just that run*: per-output value inputs, per-run notes,
     per-run photo. "Mark run complete ✓" stamps `started_at` + `ended_at`
     on the run. Run-by-run focus mirrors how a student actually moves
     through a 12-row design — one row at a time, 30 minutes apart.
   - **📌 Observations.** A free-form chronological log, the final
     bench-recording surface. One tap on a sticky **`+ Observation`**
     FAB → quick-add card with: optional metric name + value + unit
     (`OD600 = 0.42`), free-text note (`gel looked uneven near top`), an
     optional photo, and an automatic timestamp. This is where everything
     that doesn't fit into Materials / Protocols / DOE goes — and that's
     usually a *lot* of what happens at the bench.

**Mobile / bench affordances** (active in run mode only):
- Sticky `📷 Photo` FAB always visible — same upload pipeline as today,
  the photo lands in attachments + gets timestamped
- Sticky `+ Observation` FAB next to it
- Big tap targets on the "✓ same as planned" / "✓ followed as written"
  checkboxes (≥ 36 px)
- Optional voice memo per observation: tap-and-hold the obs text input
  → records up to 30 s via Web Speech API → transcribed in-place. No
  audio is uploaded; just the transcript.

Footer in run mode: `⏹ End run` button (primary). `📝 Back to plan`
escape hatch (admin-confirm; rare; resets `run_started_at`).

### Complete mode (post-`⏹ End run`)

Click `⏹ End run` → `phase` becomes `'complete'`, `run_ended_at` stamped,
a `📊 Summary` textarea appears in the entry footer for the post-run
debrief ("ran clean", "ran out of TEMED, swapped from lot A23-118 to
A24-202", "two outliers in row 7 — re-do?"). Everything else is
read-only by default.

The complete view also exposes a **plan-vs-actual diff**: a small table
where each material / protocol / design-output row shows planned and
actual side-by-side, color-coded green when they matched and amber when
they diverged. This is the post-experiment artifact a student wants to
share at PMR.

A `↻ Spawn next iteration` button creates a new entry pre-filled with
the current entry's planned design (carried over) + materials list +
protocols + a `derived_from: <thisEntryId>` link. The summary text gets
copied into the new entry's body as a "Last iteration's takeaways" block.
This is what makes the workflow self-perpetuating — finishing a run
makes starting the next run a one-click operation.

### Schema additions (entry doc)

```js
{
  ...existing fields...
  phase: 'plan' | 'running' | 'complete',     // default 'plan'
  run_started_at: ISO,                         // null until ▶
  run_ended_at: ISO,                           // null until ⏹
  summary: string,                             // post-run free text
  derived_from: entryId | null,                // for "↻ Spawn next iteration"
  observations: [{
    id, at, text,
    metric: string?, value: number?, unit: string?,
    attachment_paths: [string]?,
  }],
}
```

Per-chip extensions on `inventory_refs[i]`:
```js
{
  ...existing fields...
  planned_qty: string,         // "5 mL of 100 mM Tris" — free-text
  actual_qty: string,          // copies planned by default
  actual_lot: string,          // empty unless overridden / chip carries default
  same_as_planned: bool,       // defaults true; un-check on divergence
}
```

Per-protocol extensions on `protocol_refs[i]`:
```js
{
  ...existing fields...
  followed_as_written: bool,            // default true
  deviations: [{ at, text, step_ref?, attachment_path? }],
}
```

Per-DOE-run extensions on `state.doc.design.runs[i]`:
```js
{
  ...factor values from Phase 2...
  actuals: {
    started_at, ended_at,                // null until "Mark run complete"
    outputs: { measurement_name: value }, // free-form key/value
    notes: string,
    attachment_paths: [string],
  },
}
```

### Status pill on the rail

Each entry's row in the left rail gets a phase glyph alongside the
existing tag dots / 📎 / 🧪 / 📋 counts:

- `📝` plan
- `▶` running (color-pulsed amber so a half-finished run is visually
  obvious; the user can scan their backlog and see "I left a run open
  yesterday — go close it")
- `✅` complete

### Templates seed the plan skeleton

The Phase-2-plan-listed Templates feature pairs natively with Phase 3.
Each template prefills materials / observations / DOE / protocols
slots so a student can hit `+ New entry → Cell culture day` and walk to
the bench in 30 seconds.

Initial template set:
- **Cell culture day** — 3 media-change observation slots, 1 confluence-
  check observation slot, materials seeded with media + trypsin
- **Microscopy session** — sample list + imaging conditions table
  (objective / exposure / channel / Z) + per-sample observation slots
- **Bioprinting run** — print parameters (nozzle / pressure / speed /
  temp) + post-print QC observation slots
- **Reagent prep** — molarity calculator + planned aliquot count
- **DOE screening run** — pre-pops a Plackett-Burman or 2-level fractional
  design (or a custom one) + per-run observation slots

### Schema migration / back-compat

Existing entries (V3.110 → V3.121) have no `phase` field. On load:
- `phase || 'complete'` — assume legacy entries are post-experiment
  records (which they effectively are, since the run-flow didn't exist)
- All Phase 3 sub-fields default empty when not present

Saving an old entry doesn't touch its phase unless the user clicks
`▶ Start run` (which is only offered when `phase === 'plan'`). For an
existing legacy entry to participate in the workflow, the user clicks
a small `🔄 Convert to plan` admin/owner action that flips `phase` to
`'plan'`. Friction-by-design: we don't want to silently push legacy
entries into a workflow they weren't authored for.

### Why this is genuinely simple at the bench

- The pivot to recording mode is **one button**. No copy-paste, no new
  document.
- Recording mode defaults are **everything matched plan**. The bench
  user only interacts when something diverges — the common case is
  rapid checkmarks.
- Photo + observation are **one-tap FABs**, always visible, always
  fast. No nesting, no menus.
- Voice memo per observation means a student can record while gloved.
- Spawn-next-iteration means yesterday's experiment is the seed for
  today's experiment, not a context switch.

This is the workflow that distinguishes "I should keep a notebook"
from "the notebook is the easiest place to do this."

## Beyond Phase 3 — additional features (ranked, ship as needs surface)

These are remaining ideas from the user's "what else would a student
want?" brainstorm. Phase 3 absorbs lot/expiry tracking and templates
as required dependencies; the rest stay in the queue.

### Medium-value

1. **Inline calculators** — molarity / dilution / pH / unit conversion
   pickers. One-click insert with values stored as data-attrs so the user
   can edit later and the calculated result re-derives. Reuse mathjs
   (already lazy-loaded by protocols). Especially valuable inside Phase 3
   recording mode for "I weighed 0.241 g, what molarity does that give
   me?" mid-experiment.

2. **Timer / stopwatch widgets** — embed countdown timers in the body
   ("incubate 30 min"). Notify when done via Web Notifications API. Tiny
   per-widget state; persist `started_at` on the entry doc. Pairs
   naturally with Phase 3 — drop a timer into the recording panel for a
   30-min incubation between observations.

3. **CSV / data import → inline preview** — paste a CSV, get a sortable
   table with a small auto-chart for numeric columns. Reuses existing
   attachment Storage path; the table renders from the parsed CSV. In
   Phase 3 complete mode, CSV import becomes the primary path for plate-
   reader / flow-cytometry output.

4. **Sample lineage tree** — every entry can declare `derived_from: [entryId]` (Phase 3 already adds the field for "↻ Spawn next
   iteration"). A new "Lineage" panel visualises ancestor + descendant
   entries as a small graph. Critical for cell-culture work.

### Lower-value / speculative

5. **Equipment booking shortcut** — an entry can link a calendar booking
   from `/rm/pages/scheduler.html`; calendar shows the linked entry on
   click.

6. **Barcode / QR scan** — phone camera reads a label, auto-fills the
   inventory chip or sample id. Uses `BarcodeDetector` API where
   supported, fallback to a JS lib. High-value during Phase 3 recording
   mode for "I just picked up tube #7 — log it".

7. **Failed-experiment archive view** — filter by
   `phase === 'complete' && summary contains "fail"` (or status archived
   + tag failed). Useful for end-of-rotation retros.

8. **AI summarize last N entries on Project X** — Anthropic API call,
   streams a markdown summary into a new entry. Already authenticated
   per [CLAUDE.md](CLAUDE.md) (Anthropic API key path exists in
   cv-builder.js).

9. **Pre-registration / hypothesis lock** — designate an entry as a
   pre-reg: locks `body_html` after the user clicks "Lock hypothesis";
   subsequent edits go into a sibling "results" entry. Phase 3's
   `phase: 'running'` already provides a soft version of this (the
   plan section is read-only at the bench). True pre-reg locking would
   prevent even pre-run plan edits.
