# V3.316 — Protocol builder: rich tables, definition list, timeline (FuturePlan 03, Release 2)

## Goal

Second release of the FuturePlan 03 widget roadmap: three data-display
block kinds so protocols can carry arbitrary tables, an appendix-style
derivation list, and the gold standard's horizontal timeline track.

## New block kinds

| kind | body | attrs |
|---|---|---|
| `table` | optional caption | `{columns:[{key,label,align,mono}], rows:[{<key>:string}]}` |
| `kv` | — | `{items:[{term, def}]}` |
| `timeline` | optional title | `{marks:[{at, label, sub, included}]}` |

All attrs are **plain JSON arrays** on the attrs Y.Map (the V3.315
`dehydrateBlock` Array.isArray fix makes this safe). Coarse-grained
collaboration — an edit replaces the whole array — which matches the
docHeader chips precedent and avoids deep Y-type plumbing for what are
low-contention widgets.

## Decisions

- **Materials stays its own kind.** The plan sketch said "materials
  becomes a preset of the generic table"; in practice materials' value
  is its inventory row-linking (Y.Array rows, item_ref chips, the
  matcher) which is deeply Y-typed. Rewiring it through the generic
  table would risk the V3.121/V3.139 machinery for zero user-visible
  gain. So: `materials` keeps its renderer; `table` covers everything
  else. Revisit only if a real need appears.
- Cell text renders through `renderProse` in the doc view, so `[!var:]`
  chips / pills / `~sub~` work inside table cells, kv definitions, and
  timeline labels.
- `timeline.marks[].included` (boolean, default true) renders excluded
  marks dimmed with a strike — the gold standard uses this for
  condition points that exist on the axis but aren't run.

## Rollback

Client-only. Old clients coerce the new kinds to `step` on render
without touching stored Yjs state.
