# V3.597 — Notify-me watches ("tell me if it frees up")

R4 of the smart equipment schedule-change program (R1 = V3.588
criticality, R2 = V3.594 adjacency + feed, R3 = V3.595 reminders;
= FuturePlan 08 Phase 3).

> Planned as V3.596; a parallel session shipped presence-aware
> notifications under that number mid-build, so this is V3.597.

## Goal

A student needs the confocal Thursday afternoon. It's booked. Today the
only option is to keep reopening the calendar to see whether it opened
up. Instead: switch the calendar into **🔔 Notify me** mode, drag across
the busy stretch once, and get told if a usable gap appears.

## Problem

Cancellations are the highest-value information on a shared instrument
and they were invisible to everyone except the person cancelling. V3.594
tells your immediate neighbors; it can't tell someone who *wants* time
they never booked, because nothing recorded that intent.

## Approach

### Same gesture, two meanings

Drag-to-select on the week grid already exists (it opens the booking
modal). The **🔔 Notify me** toolbar toggle flips what a release means —
watch instead of book — so there's no second interaction to learn. The
pointerup handler short-circuits to `openWatchConfirm()` before the
booking modal when `_watchMode` is on, and an amber banner keeps the mode
obvious while it's active.

### The matcher only fires on genuinely usable time

`functions/helpers/equipment-watches.js` is pure (no Firestore, no FCM).
The interesting property is **not** "does it notify on a cancel" — it's
"does it stay quiet when the freed time is still unusable". A watch that
cries wolf gets muted, which is the same failure mode the whole program
is built to avoid. So a watch fires only when:

1. The change actually **released** time inside the window. For a
   cancel/displacement that's the booking's whole interval; for a **move**
   it's only the part of the old interval the new one no longer covers
   (a booking nudged by 15 minutes releases 15 minutes, not two hours).
2. After re-deriving availability from the **after-state**, the released
   region contains a contiguous free gap of **≥ 30 minutes**. Two
   students splitting a blocked afternoon means the first cancel produces
   nothing useful; only the one that opens real time notifies.
3. The watch isn't throttled (`lastNotifiedAt`, 15 min).

`freeGaps(window, busy)` is the primitive — interval subtraction, tested
directly. This is the **one** sanctioned server-side copy of overlap
math; the client already has three (`checkAvailability`,
`checkConflicts`, `EQUIP_AVAIL.checkSlot`). Don't add a fourth.

### Lifecycle

- **Persists** across openings — a student who misses one gap should hear
  about the next. `lastNotifiedAt` throttles instead of consuming.
- **Fulfilled** when the owner books anything overlapping their own
  window (`fulfilledWatches` on the create trigger) — they got what they
  wanted, so stop.
- **Swept** when the date passes, by the V3.595 15-minute job.
- **Deleted** by hand from the 🔔✕ pill on the band.

### Both engines share one read

`runBookingChange()` loads the day's bookings **once** and hands the same
array to adjacency and watches. They ask different questions of the same
docs; querying twice would be waste. Both are individually try/caught so
neither can take down the status notifications that already went out.

### Grid rendering

Watch bands are grid children at `z-index: 2` — above cells and booking
blocks (1), below sticky headers (3) — with the amber hatch pattern
cloned from the existing `--closed` treatment. `pointer-events: none` on
the band so drag-to-book still works straight through it; only the 🔔✕
pill accepts clicks.

`_watchRange` guards the render → load → render cycle: watches load for
the visible week and repaint once, and only if the user is still on that
week.

### "Already free" guard

If the dragged window is currently bookable, the confirm dialog says so
and offers **Book it now** as the primary action, with "Watch anyway"
demoted. Watching time you could just take is the most obvious way to
waste an afternoon.

A watch also **requires a device filter** — it names one instrument.
"Notify me if any scope frees up" is a different feature.

## Data model

`equipmentWatches/{watchId}`:
```
{ uid, userName, equipmentId, equipmentName,
  date 'YYYY-MM-DD', startTime 'HH:MM', endTime 'HH:MM',
  status 'active'|'fulfilled', createdAt,
  lastNotifiedAt?, fulfilledAt?   // server-only
}
```

**Rules — two deliberate choices:**

- **Read is own-only** (plus admin), unlike `equipmentBookings` which is
  lab-readable because the calendar is shared. A watch reveals *intent* —
  who wants which instrument when — and there's no reason for the lab to
  see each other's.
- **`allow update: if false`.** `lastNotifiedAt` and
  `status: 'fulfilled'` are Admin-SDK-only. If a client could write
  `lastNotifiedAt`, a student could clear their own throttle and turn a
  watch into a notification loop. Changing a window = delete + create,
  which is what the UI does.

Create is whitelisted by key with format checks on date/times and
`startTime < endTime`.

**Indexes:** `(uid, date)` for the client's visible-week query;
`(equipmentId, date, status)` for the server matcher. The expiry sweep's
single-field range query uses automatic indexes.

## Out of scope

- Setting a watch from My Day → next release.
- Multi-day / overnight watches — a watch is one date (inherits the
  V3.594 limitation).
- Device-agnostic watches ("any confocal").
- Auto-booking a freed slot. Deliberate: it would race other watchers and
  silently commit someone to instrument time.

## Release ritual

Order matters — **rules and indexes must land before the client**, or
`createWatch` / `listMyWatches` 403 and the index-backed query fails:

1. `node functions/test/equipment-watches.test.js` (32),
   `equipment-adjacency` (46), `equipment-reminders` (31) — all green.
2. `firebase deploy --only firestore:rules,firestore:indexes`
3. **Wait for the two `equipmentWatches` indexes to finish building**
   (Firebase console → Firestore → Indexes).
4. `firebase deploy --only functions`
5. FTP.
6. `sw.js` CACHE_VERSION → 566.

## Rollback

FTP the previous client + redeploy the previous functions revision. The
`equipmentWatches` collection and its rules can stay (inert — nothing
reads or writes them). Existing watch docs are harmless; delete the
collection by hand if you want it gone.

## Verification

1. **Tests green** before deploying.
2. **Set a watch:** Equipment → Calendar → pick ONE device in the filter
   → 🔔 Notify me → drag across a busy afternoon → confirm → a hatched
   amber band appears with a 🔔✕ pill. Reload; it's still there.
3. **No device filter** → dragging in watch mode tells you to pick one
   instead of silently creating a device-less watch.
4. **Already-free guard:** drag over empty time → dialog says it's free
   and offers "Book it now" as the primary action.
5. **The core case:** from another account, cancel the booking that
   blocks the watched window → the watcher gets a push naming the freed
   span, and it appears in My Day's 🔔 section.
6. **Still-blocked silence:** with two bookings covering the window,
   cancel only one so under 30 minutes opens → **no** notification. This
   is the assertion that matters most.
7. **Throttle:** cancel/move two bookings in the same window within
   15 minutes → one notification, not two.
8. **Fulfillment:** book inside your own watch window → the watch flips
   to `fulfilled` and its band disappears.
9. **Delete:** 🔔✕ removes the band immediately and the doc from
   Firestore.
10. **Drag-through:** with watch mode OFF, dragging across a watch band
    still opens the booking modal (pointer-events).
11. **Privacy:** signed in as another non-admin, the other user's watch
    band is not visible.
12. **Expiry:** a watch dated yesterday is gone after the next 15-minute
    tick (`gcloud functions logs read equipmentBookingReminders` shows
    `swept N expired watch(es)`).
