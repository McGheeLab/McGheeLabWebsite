# V3.595 — Equipment reminders + weekly manager digest

R3 of the smart equipment schedule-change program (R1 = V3.588
criticality, R2 = V3.594 adjacency + feed; = FuturePlan 08 Phase 3).
**Functions-only** — no client files change.

## Goal

Two scheduled jobs:

1. **Booking reminders** — a "today" push in the morning and a T-30
   push before the slot starts. The T-30 one **names the next booking
   when there is a real handoff**, which is the notification that
   actually prevents somebody running over.
2. **Weekly manager digest** — Monday morning, per equipment manager:
   pending approvals + how booked their machines are this week.

## Problem

V3.594 tells you at *booking* time that somebody is queued behind you.
That is days early. Nothing brought it back on the day, and there were
no scheduled equipment notifications at all — RM's only `onSchedule`
functions were scrapers and the yjs compactor. Managers also had no way
to learn about pending approvals other than opening the page.

## Approach

### Time handling — the part worth reading before editing

Booking `date` / `startTime` / `endTime` are **local wall-clock strings**
(`'YYYY-MM-DD'`, `'HH:MM'`), not Timestamps. So the job never parses
them into `Date` objects. Instead it computes "now" in Phoenix once, as a
`{dateStr, minutes}` pair (via `Intl.DateTimeFormat`, the same technique
as `functions/ics-scraper.js:163`), and every decision is string equality
or integer comparison.

**This is only simple because Arizona has no DST.** A test asserts
Phoenix really is UTC-7 right now — if that ever fails, the assumption
is broken and this file needs real timezone handling. Do not copy the
pattern to a DST zone.

### Idempotence

A 15-minute cadence sees each booking many times. `reminded.morning` /
`reminded.tminus` flags on the booking doc (Admin SDK, so no client rule
carve-out) make each reminder fire exactly once.

The T-30 window is 30 minutes against a 15-minute cadence, so **every
booking gets two chances** to be caught — a skipped or slow tick doesn't
lose the reminder. A test walks a full day of ticks and asserts exactly
two land in the window.

The `tminus` flag is stamped even when the push is *skipped* for a
freshly-created booking, so a booking made 5 minutes before it starts
doesn't get pinged and doesn't get re-examined every tick.

### Reminder content

- **Morning-of** (≥ 07:30, only for slots that haven't started):
  `Today: AX-R Confocal` / `10 AM–12 PM — notes`.
- **T-30**: `AX-R Confocal in 25 min`, plus — when the adjacency engine
  finds a genuine non-Soft handoff owned by someone else —
  *"Bob is booked right after you — please be off by 12 PM."*
  This reuses `ADJ.findNeighbors` on bookings **already loaded** for the
  day, so it costs no extra query.
- Both go to the owner **and** the co-operator.

### Digest stays quiet when there's nothing to say

A manager with no pending approvals and no bookings this week gets
**nothing**. A weekly "0 pending, 0 booked" push is exactly the noise
that makes people mute a category. When it does fire it names the
busiest device, which is the useful detail when scanning fast.

The digest is push-only — no in-app feed item. It's a convenience
summary, not something you catch up on item by item.

### Feed retention rides along

`sweepFeed()` deletes notification-feed items older than 14 days,
piggybacking on the 15-minute job so the feed needs no separate
scheduled function. It's wrapped in try/catch: if the collection-group
query ever needs an index it doesn't have, reminders must still run.

## Files modified / added

**Added**
- `functions/equipment-reminders.js` — `equipmentBookingReminders`
  (`every 15 minutes`) and `equipmentWeeklyDigest` (`30 7 * * 1`), both
  `timeZone: 'America/Phoenix'`. Plus `phoenixNow`, `shiftDateStr`,
  `bookingAudience`, `sweepFeed`, exported under `_internal` for tests.
- `functions/test/equipment-reminders.test.js` — 31 fixtures, plain
  node: Phoenix offset, date rollovers (month, year, leap day), the
  T-30 window against the tick cadence, the morning threshold, audience
  dedupe, and the handoff-line rule.

**Modified**
- `functions/index.js` — require + export both new functions.

## Data model changes

| Path | What | Rules |
|---|---|---|
| `equipmentBookings.reminded.{morning,tminus}` | idempotence flags | server-only (Admin SDK); absent from client whitelists |

**No new collections, no rules change, no new indexes.** Both queries use
the existing `(status, date)` composite index. The feed sweep uses a
collection-group query on a single field, served by Firestore's automatic
single-field indexes.

## Out of scope

- Notify-me watch windows → next release.
- Digest utilization is **booked hours**, not booked/available ratio —
  the posted-schedule math isn't worth the extra reads for a summary push.
- No no-show detection / check-in tracking (FuturePlan 08 Phase 4).
- Multi-day bookings still excluded from the handoff line (inherits the
  V3.594 limitation).

## Release ritual

1. `node functions/test/equipment-adjacency.test.js` (46) and
   `node functions/test/equipment-reminders.test.js` (31) — both green.
2. `firebase deploy --only functions:equipmentBookingReminders,functions:equipmentWeeklyDigest`

No FTP. No `sw.js` bump (no client files changed). No rules or index
deploy.

**First-deploy note:** the 15-minute job starts firing immediately, and
every confirmed booking for *today* that hasn't started yet will get a
morning-of push on the first run after 07:30. Deploying mid-morning is
therefore slightly noisy on day one; deploying in the evening avoids it
entirely.

## Rollback

```
firebase functions:delete equipmentBookingReminders equipmentWeeklyDigest
```

`reminded.*` flags left on bookings are inert. Nothing else to clean up.

## Verification

1. **Tests green** before deploying.
2. **T-30:** create a confirmed booking starting ~35 minutes out. Within
   two ticks a push arrives reading "… in N min"; check the booking doc
   now has `reminded.tminus: true`, and confirm no second push on later
   ticks.
3. **Handoff line:** with two accounts, book B right after A as "Needed
   on time", then wait for A's T-30 → the body should name B and give
   A's end time. Re-run with B as Soft → the body should have no handoff
   sentence.
4. **Morning-of:** leave a booking for later today; after the first tick
   past 07:30 a "Today:" push arrives once, `reminded.morning: true`.
5. **No self-spam:** create a booking starting in 10 minutes → **no**
   T-30 push (freshly-made guard), but `reminded.tminus` is still
   stamped.
6. **Digest:** invoke `equipmentWeeklyDigest` from
   `firebase functions:shell` — a manager with pending approvals gets one
   push naming counts and the busiest device; a manager with an empty
   week gets nothing.
7. **Feed items:** reminders appear in My Day's 🔔 section with the ⏰
   icon (V3.594 surface).
8. **Logs:** `gcloud functions logs read equipmentBookingReminders` shows
   one `[EquipRemind]` summary line per tick with the booking count.
