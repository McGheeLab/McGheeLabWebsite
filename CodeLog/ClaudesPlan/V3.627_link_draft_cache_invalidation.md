# V3.627 — "Linking a paper to a draft does nothing" (route-cache invalidation)

Alex, 2026-08-12, testing the V3.619-622 program: *"I try to link a paper
to drafts, I select a paper we have in the drafts and it doesnt allow me…
it doesnt say anything, it just doesnt work."* Both link pickers (toolbar
overlays pill AND left-sidebar association pills), modal closes, nothing
changes, no error.

## Diagnosis (server-side forensics first)

The write was NOT the problem. Firestore showed the test landing
correctly minutes after the report:

```
items/kim-2026-aspiration-assistedbi
  meta.library.linked_drafts = ["microscope-enabled-bioprinting"]
  updated_at = 2026-08-13         ← the test write
papers/microscope-enabled-bioprinting  exists, status "drafting", title OK
```

So `LIBRARY_LINKS.toggleDraftLink` persisted, and the draft id resolved to
a real active paper draft. The break was display-only.

**Root cause:** every writer in `rm/js/library-links.js` updates
`items/{id}` through the Firestore SDK **outside `api.save`**, and the
module never invalidated the adapter's stale-while-revalidate route cache.
So `items.json` (cache: MEDIUM, 30 min) kept serving the PRE-WRITE array,
and every consumer that refreshes through `api.load` re-derived from it and
painted the link back off:

- `paper-overlays.js _fetchLinkedDrafts` — `items.find(...)` returns the
  cached row, `ids` = old array → `_linkedDrafts` rebuilt without the new
  link. The picker had already set the authoritative array on `_paperItem`
  and this threw it away.
- `library-associations.js loadDraftInfo` (sidebar pills) — same source.
- `library-paper.js`'s `PAPER_OVERLAYS.onChange` handler — reloads
  `items.json` and re-renders the pills from it.

That's why BOTH pickers failed identically and silently.

**Why the cache's staleness probe didn't save us:** the MEDIUM route probe
is `collection('items').orderBy('updatedAt','desc').limit(1)` compared
against the cache's `savedAt`. `_toggleArrayField` does bump
`updatedAt: serverTimestamp()`, but a *query* can only see it once the
value has materialized in the `updatedAt` index — a probe fired
immediately after the write ack can still read the previous top doc and
conclude "nothing changed", handing back the stale list. The symptom
would then clear itself ~30 min later or on the next unrelated item
write, which is why 105 items do carry links that display fine.

## Fix

`api.invalidate(path)` already exists for exactly this case (V3.485:
*"callers that write a doc OUTSIDE api.save must bust the
stale-while-revalidate cache themselves"*). `library-upload.js`,
`library-fetch-pdfs.js` and `library-mobile.js` all call it after their
direct writes — **`library-links.js` was the one that never did.**

Added `_bustItemCaches()` (awaited, so a caller that refreshes right after
us can't race the clear; invalidates `items.json` + `library/papers.json`;
warns and continues if the adapter is absent) and called it after the
`ref.update()` in all three writers:

- `_toggleArrayField` — backs `toggleDraftLink`, `setCitedInDraft`,
  `toggleRoadmap`
- `toggleTheme`
- `setThemeRelevance`

So the same latent staleness in Lab Themes membership, theme relevance
weights, roadmap/Lab-focus attachment and the builder's cited-sync is
fixed by the same change.

Verified statically end-to-end: `items.json` declares `cache: MEDIUM` →
`_routeCache` returns a handle → `LOCAL_CACHE.scope(...).clear()` exists
and deletes the IndexedDB entry (same key `api.load` reads), so the next
load goes to the network.
