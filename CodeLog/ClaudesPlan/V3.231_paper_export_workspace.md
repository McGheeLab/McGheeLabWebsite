## Context

Today the paper writer's "Export LaTeX" button opens a `prompt()`-driven dialog in [rm/js/paper-editor.js](../../rm/js/paper-editor.js) (`openExportDialog`) that asks the user to pick `preview` vs `in_place`, then [rm/js/paper-export-tex.js](../../rm/js/paper-export-tex.js) (`runExport`) walks the Yjs CRDT and POSTs `.tex` + `.bib` files to a local Python dev-server route (`/api/paper/export-tex`). There is no PDF compile step, no way to pick a journal template at click-time, no surface for the user to load a journal's `.cls` / `.bst`, and no way to tweak figure / table / equation presentation without editing the template JSON on disk.

The change replaces that dialog with a dedicated **Paper Export Workspace** page that lets the writer choose a journal template, toggle a curated set of LaTeX add-ons, override per-block style attrs (figure placement / width, table booktabs vs. grid, equation numbering), compile to PDF via a Tectonic-backed Cloud Run service, and preview the PDF inline using the existing pdf.js viewer.

This is **Phase 1**. Phase 2 (journal `.cls`/`.bst` upload library, in-service figure fetch, scheduled TTL cleanup, latexdiff, IMRAD guidelines panel) is scoped separately to keep this shippable and isolate failure modes if the Tectonic container misbehaves in production.

## Approach

**New page**: `rm/pages/paper-export.html?paper={id}` — left column is the config form, right column is the pdf.js preview. The Export button in the editor topbar navigates here instead of opening the dialog.

**Engine**: Tectonic in a Cloud Run service (no Cloud Function callable hop — Cloud Run verifies the Firebase ID token directly). Chosen over full TeX Live because (a) ~50 MB binary vs ~2 GB image, (b) reproducible CTAN auto-fetch with `Tectonic.toml`, (c) faster cold start. Real risks (shell-escape for `minted`, proprietary fonts in Nature/Springer) are flagged via per-template `requires_shell_escape` and a "supported packages" list rather than dual containers.

**Compile cadence**: button-triggered only. No KaTeX-approximation preview — maintaining two rendering paths drifts and erodes trust.

**Persistence**: shared top-level `paperExports/{paperId}` Firestore doc gated by `isLabContributor()` write / `isLabMember()` read. Compile history lives in `paperExports/{paperId}/compiles/{compileId}` subcollection. Reads/writes via direct `firebridge.db()` refs (the adapter's routes table only handles exact paths, not `{paperId}` wildcards; same precedent as `papers/{paperId}/yjs_*` and PMR cross-user reads).

**.zip export survives**: the new page includes a "Download bundle (.zip)" button (JSZip in-browser) that produces the same `.tex`/`.bib`/`figs/` files the legacy `runExport` writes today.

**Add-on registry** (curated, 8 entries for Phase 1, lives in `paper-export-tex.js`):
- `lineno`, `setspace-double`, `microtype`, `cleveref`, `hyperref-colors`, `anonymize`, `placeins`, `twocolumn`
- Each entry: `{id, label, preamble, requires_shell_escape, incompatible_with: {templates, addons}, notes}`. Hard conflicts encoded; long-tail compile-and-warn.

**Style overrides** (per-paper, applied at tex-build time over the template defaults):
- Figure: `placement` (H / htbp / t / b), `default_width`.
- Table: `use_booktabs` (bool), `placement`.
- Equation: `display` env (equation / align).

Per-block `attrs` in the Yjs doc remain authoritative for what the user typed; overrides only fill template defaults.

## Deploy outcome (2026-05-16)

The plan called for browser → public Cloud Run. What actually shipped is browser → public Firebase Function → private Cloud Run. The pivot happened during deploy after multiple hours fighting the Cloud Run public-ingress layer. Recording it here so future-Claude doesn't try the original architecture again.

### What we tried that didn't work
Public access to `paper-compile-*.run.app` returned **Google's Frontend Load Balancer 404** ("Error 404 (Not Found)!!1" with Google logo + `referrer-policy: no-referrer`) for every external request. Container logs showed only the very first authenticated `gcloud run services proxy` request reaching the container; every subsequent public curl never logged at all — traffic dropped at the GFE before reaching the service. We confirmed none of these were the cause:
- Missing `allUsers/run.invoker` IAM binding (added; Console UI changes kept silently stripping it)
- Authentication toggle set to "Require authentication" instead of "Allow public access" (toggled; no effect)
- Ingress restricted to `internal` (was already `all` by default)
- Multiple `--allow-unauthenticated` redeploys
- IPv6 wildcard bind (added explicit `app.listen(PORT, '0.0.0.0', ...)`)
- Network-side: tested from UofA + home wifi, same 404
- Both URL formats: project-number (`paper-compile-665438582202.us-central1.run.app`) and hash-based (`paper-compile-6zcsqhynhq-uc.a.run.app`)
- TCP startup probe (was succeeding; container reported `listening on :8080` cleanly)
- Container response time on a successful authenticated request through `gcloud run services proxy` — Express returned an Express 404 (not GFE 404), proving the container was reachable when traffic actually arrived

Most plausible root cause: an inherited GCP org-level policy on this project that strips `allUsers` from individual Cloud Run services. The visible symptom matches the "default URLs disabled" Cloud Run feature or an `iam.allowedPolicyMemberDomains` org constraint, but neither showed in `gcloud beta run services describe` annotations and the user couldn't see project-org policies in the Console.

### What we shipped
- **Cloud Run `paper-compile`** stays — same Tectonic container, same Express server, same Firestore-write + Storage-upload behavior. Now **private** (`--no-allow-unauthenticated`). `verifyToken` middleware was changed to trust `X-User-Uid` + `X-User-Role` headers set by the proxy instead of verifying Firebase ID tokens directly; Cloud Run IAM (only the Functions runtime SA has `run.invoker`) is the actual security boundary.
- **`functions/paper-compile-proxy.js`** (new) — the `paperCompile` Firebase Function (v2, public). Verifies the user's Firebase ID token, checks `users/{uid}.role != 'guest'`, mints a GCP identity token via the metadata server (audience = Cloud Run URL), forwards the request to Cloud Run with the token + verified user headers, streams the response back. Public access works because Firebase's deploy path doesn't hit the same org policy that's stripping `allUsers` from Cloud Run services.
- **`rm/js/paper-export.js`** — `PAPER_COMPILE_URL` points at the Firebase Function URL (`https://us-central1-mcgheelab-f56cc.cloudfunctions.net/paperCompile`) instead of the Cloud Run service URL.

### Cloud config — current state
- Cloud Run `paper-compile`, region us-central1, private. Env: `FIREBASE_STORAGE_BUCKET=mcgheelab-f56cc.firebasestorage.app` (NOT `*.appspot.com` — this project's bucket uses the post-Oct-2024 naming).
- IAM on `paper-compile` Cloud Run: `roles/run.invoker` bound to `serviceAccount:mcgheelab-f56cc@appspot.gserviceaccount.com` only.
- Compute SA (`665438582202-compute@developer.gserviceaccount.com`) has `roles/datastore.user` + `roles/storage.objectAdmin` at project level + `roles/iam.serviceAccountTokenCreator` on itself.
- Firebase Function `paperCompile`, region us-central1, public, v2, CORS enabled.

### Service worker caching trap (also burned time)
After all the cloud-side work was done, the browser kept hitting the old Cloud Run URL. Spent ~30 min on "the function isn't working" before realizing it was actually `mcgheelab-shell-v206` SW cache holding a stale `paper-export.js`. DevTools Application → Service Workers → Unregister + Application → Clear site data **was not enough** — a fresh SW would reinstall and re-cache the stale JS from the browser's HTTP cache. The reliable fix: console-delete the specific cache entry:
```js
caches.open('mcgheelab-shell-v206').then(c => c.delete('/rm/js/paper-export.js'));
```
followed by hard-reload with DevTools Network tab → "Disable cache" enabled.

**Verification pattern** for future cloud-config changes that depend on paired client-side JS:
```bash
curl -s https://mcgheelab.com/rm/js/paper-export.js | grep -A1 PAPER_COMPILE_URL
```
Confirms what production is actually serving before chasing server-side bugs.
