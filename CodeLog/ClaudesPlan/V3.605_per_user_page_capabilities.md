# V3.605 — Per-user, per-page elevated capabilities (Permissions page)

## Goal

Give admins a way to grant individual users **named elevated powers on
specific pages** from the Permissions page — starting with the paper
reader. Before this, the admin matrix could only grant *pages*
(`userPermissions/{uid}.allowedPageIds`); the actions inside a page were
gated by role or by the `labConfig/guestEditors` / `extensionMembers`
email allowlists. Three groups were stuck:

1. **Guest-role users** (class students, new arrivals) — blocked from the
   whole of RM by the pending-access overlay; no way to let them read +
   annotate library papers without promoting them to full lab member.
2. **Lab members not on the email allowlists** — saw "+ New group…" in the
   reader, then got a raw `alert()` when the `labConfig/annotation_groups`
   write was rejected (`isLabContributor()`); same wall for extension
   capture (`isExtensionMember()`).
3. **Collaborators** — page grants existed, but nothing could lift them
   into write-level actions.

## Design

**Named capabilities, flat strings, one doc.** Grants are
`'<pageSlug>:<capId>'` strings in a new `caps: string[]` array on the
existing `userPermissions/{uid}` doc (admin-write, owner-read — no new
rules surface for the grant store itself). The pageSlug is the HTML
filename slug (`library-paper` ↔ `/rm/pages/library-paper.html`), NOT a
PAGE_REGISTRY id — reader pages aren't nav items, so caps carry their own
page identity.

**Registry-driven UI.** `rm/js/capability-registry.js` (new, dependency-
free, loaded only by admin-permissions.html) declares each page's
capabilities with labels + lab-facing descriptions. First entry:

| cap | grants |
|---|---|
| `library-paper:view` (base) | open the reader + read library-entry items/details |
| `library-paper:annotate` | create highlights + notes |
| `library-paper:groups` | create annotation groups ("+ New group…") |
| `library-paper:capture` | extension capture (pending_captures, paper_index) |

Every non-base cap `requires` the view cap (admin UI auto-checks it).
Adding a future page = one registry entry + `hasCap()` ORs in rules.

**Rules are OR-only.** New helper `hasCap(cap)` (exists + `cap in
userPermissions/{uid}.caps`), placed LAST in each OR chain so members
short-circuit without the extra get(). Insertions:

- annotations create: `isLabMember() || hasCap('library-paper:annotate')`
- `labConfig/annotation_groups` write: `isLabContributor() || hasCap('library-paper:groups')`
- `pending_captures` + `paper_index`: `isExtensionMember() || hasCap('library-paper:capture')`
- `items` read: `+ hasCap('library-paper:view') && is_library_entry == true`
  — scoped so grant drafts (same collection) stay invisible to cap-guests
- `items/{id}/details` read+write: same view-cap + parent `is_library_entry` gate

Explicitly deferred: a claims cap (`drafts/{id}/claims` create stays
member-only); the email allowlists stay live (rules OR them — retire later).

**Client.**

- `firebase-bridge.js`: `loadAccessGrant()` surfaces `caps`; new
  `hasCapability(cap)` / `hasAnyCapabilityFor(slug)` /
  `hasExplicitPageGrant(pageId)` exports; the guest pending-overlay's 3s
  timer now awaits the grant and skips rendering when the current page is
  explicitly granted (overlay is UI-only; rules remain the gate);
  `canAccessPage()` passes on any page cap and cuts guests off from the
  implicit default-workflow baseline (explicit grants only).
- `admin-permissions.js`: per-user drill-in gains a **Capabilities**
  section (generic loop over the registry: card per page, checkbox +
  description per cap, `requires`/base auto-check logic, companion-page
  "also grant library" nudge). `saveAll()` now merges page + cap edits
  into ONE write per uid carrying `allowedPageIds` + `allowedCollections`
  + `caps`, and deletes the doc only when pages AND caps are both empty —
  fixing the pre-existing quirk where clearing the last page checkbox
  deleted the whole doc (which would have destroyed caps). Derived-actions
  lists cap grants and softens the guest line when grants exist.
- `library-paper.js`: `_computeAccess()` at boot → `_canAnnotate` (member
  OR annotate cap; when false the create toolbar never opens and a
  read-only banner renders in the panel) and `_allowNewGroup` (admin OR
  allowlist email OR groups cap — the allowlist preflight also fixes the
  old alert wall for plain members). `_loadLibraryItems()` gives cap-
  guests a rules-provable `where('meta.library.is_library_entry','==',
  true)` query in place of the api adapter's whole-collection items.json.
- `annotation-panel.js`: new `allowNewGroup` init option — "+ New group…"
  is omitted (and the handler guarded) when false.
- `nav.js`: the `lab-member` gate also passes when the item's href slug
  has an explicit page grant or any capability.

## Deploy

1. `firebase deploy --only firestore:rules` — safe ahead of the client
   (pure OR additions; zero behavior change until caps are granted).
2. FTP (batched per V3.604).

Reverse order would strand granted guests on PERMISSION_DENIED.

## Key decisions

- **Scoped items read** over a blanket `hasCap` read: grant-draft metadata
  lives in the same `items` collection and must stay hidden from
  cap-granted guests; cost is the small client query fallback.
- **Caps are independent of role** — no auto-revoke on demotion; the
  Derived-actions panel makes the combined effect visible.
- **Overlay bypass is per-page** — a granted guest still sees the pending
  overlay everywhere except granted pages.
