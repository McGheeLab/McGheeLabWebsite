# V3.119 — Protocols Builder: authorship, versioning, forking

## Goal

Land Phase 5a of the Protocols Builder roadmap (master plan:
`~/.claude/plans/we-want-to-make-idempotent-pixel.md`). The user-locked
add-on requirements:

> "Ensure the user who is making the protocol is listed as the author.
>  We should also include version numbers and we keep all versions as
>  version control. Other users can fork the protocol as well. If a fork
>  becomes much different the user can migrate a fork to a full new
>  protocol, otherwise it stays attached to the og protocol as a fork
>  specialty version."

This adds three intertwined capabilities to the V3.113 + V3.117
Protocols Builder:

1. **Authorship** — every protocol carries an immutable `author_uid` +
   cached `author_name` set at creation. Editor + list cards show
   "Created by Alex McGhee".
2. **Version control** — git-style "Save Version" creates an immutable
   snapshot at `protocols/{id}/versions/{vN}`. Yjs continues to handle
   live collab; a snapshot is a manual checkpoint with optional label
   and message. Old versions are read-only viewable; never deleted.
3. **Forking** — any lab member can fork any protocol they can read.
   A fork is a fresh `protocols/{forkId}` doc whose `forked_from`
   field points back at the parent and the chosen source version. Fork
   owner can later "Migrate to standalone" to clear the lineage if the
   fork has diverged enough.

### Schema additions

```js
protocols/{id} = {
  // … existing V3.113 fields …
  author_uid: 'abc123',         // NEW — immutable, set at creation/fork
  author_name: 'Alex McGhee',   // NEW — cached at creation; not auto-refreshed
  current_version: 3,           // bumped on every saveVersion (was reserved)
  fork_count: 0,                // NEW — incremented when someone forks this
  forked_from: null | {         // NEW — null on originals
    protocol_id: 'agarose-lls-sieves',
    protocol_title: 'Agarose LLS — Sieves', // cached at fork time
    version: 5,
    forked_at: '2026-05-09T…',
    forked_by_uid: 'abc123',
    migrated_to_standalone_at: null, // populated on migrate
  },
}

protocols/{id}/versions/{vN} = {  // NEW subcollection
  version: 3,                       // matches the Nv- prefix in the doc id
  tree: { meta:{}, sections:[…] },  // full deep-copy of the tree at snapshot
  meta_snapshot: { title, summary, status, tags, category }, // for restore preview
  snapshot_at: '2026-05-09T…',
  snapshot_by_uid: 'abc123',
  snapshot_by_name: 'Alex McGhee',
  parent_version: 2,                // null for v1
  label: 'After supplier change',   // optional
  message: 'Switched from Sigma to Invitrogen agarose…', // optional
}
```

### Versioning semantics

- **Save Version** — modal asks for optional label + message. Atomically:
    1. `current_version` increments on the parent doc.
    2. New doc at `versions/v<current_version>` with tree dehydrated from
       Y.Doc + meta snapshot.
    3. Toast: "Saved as version <N>".
- **Versions dropdown** — lists all versions newest first. Click → opens
  `?protocol=X&version=N`. The editor renders the snapshot in read-only
  mode (Y.Doc not connected; tree rendered from the version doc's JSON).
- **No "Restore" in V1** — user who wants to diverge from an older
  version should **fork** at that version (see below). Phase 5b can add
  in-place restore if requested.

### Forking semantics

- **Fork** button on the editor opens a modal:
    - "New protocol slug" (auto-suggested as `<src-slug>-fork`)
    - "Fork from version" (defaults to `current_version`)
    - "Title" (defaults to `<src-title> (fork)`)
- On submit:
    1. Read source version (or live tree if forking from current).
    2. Create new `protocols/{forkId}` with `ownerUid` and `author_uid`
       set to the forking user, `forked_from` populated, tree deep-copied,
       `current_version: 1`.
    3. Increment source's `fork_count` (transactional).
    4. Navigate the user to the new fork.
- **Forks render lineage** in the editor topbar: a small chip
  "Fork of [Agarose LLS Sieves v3] by Alex McGhee" with a link to the
  parent. List cards show the same chip below the title.
- **Migrate to standalone** — fork owner clicks the button. Modal
  confirms ("This fork's connection to the parent will be cleared.
  Past version snapshots remain. Continue?"). On confirm,
  `forked_from.migrated_to_standalone_at` is stamped (we don't NULL the
  field — keeping the lineage record for analytics; the UI just hides
  the badge once migration is stamped, treating the protocol as
  standalone).

### Read-only historical-version rendering

When `?version=N` is in the URL:
- The editor still loads `protocols/{id}` for metadata (so it can show
  the title + author byline), but ALSO loads `protocols/{id}/versions/{vN}`
  for the tree. The render pipeline gets the snapshot tree, not the live
  Y.Doc.
- Yjs `connect()` is **skipped**. Block renderers are passed a
  fake-Y-shaped read-only tree (sections rendered from JSON; bodies
  rendered as plain text — formula chips still work because the symbol
  table builder operates on the same dehydrated shape).
- The save-state and edit affordances are all disabled. A read-only
  banner replaces the topbar's edit controls.
- "Switch to latest" link returns to `?protocol=X` (no `&version=`).

### Firestore rules

```firebase
match /protocols/{protocolId}/versions/{vId} {
  allow read: if (request.auth != null && isLabMember())
              || (get(/databases/$(database)/documents/protocols/$(protocolId)).data.status == 'published');
  allow create: if request.auth != null
                && isLabMember()
                && request.resource.data.snapshot_by_uid == request.auth.uid
                && (request.auth.uid == get(/databases/$(database)/documents/protocols/$(protocolId)).data.ownerUid
                    || isAdmin());
  allow update: if false;     // versions are immutable once written
  allow delete: if isAdmin();
}
```

The `protocols/{id}` rule already permits owner/admin updates; the
`current_version` and `fork_count` increments piggyback on that. The
`forked_from` field is set at create time only — we'd ideally add a
rule that prevents downstream mutation, but for V1 that's deferred.

### Reads on the parent doc when forking

`forkProtocol` runs a Firestore transaction:
- read source `protocols/{srcId}` (for `current_version`, title)
- read `protocols/{srcId}/versions/{vN}` (for the tree)
- write new `protocols/{forkId}` doc
- update source `fork_count` += 1

The transaction guards against concurrent forks racing on `fork_count`.

## Acceptance test

1. Open Agarose LLS Sieves protocol. Editor topbar shows "Created by
   Alex McGhee" plus a "Save version" + "Fork" button.
2. Click "Save version", label "v1.0 — initial port", confirm. Toast
   "Saved as version 1". Versions dropdown shows it.
3. Edit a step. Click "Save version" again, label "v1.1 — typo fix".
   Versions dropdown now shows v1, v2.
4. Click "v1" in the dropdown → URL becomes `?protocol=…&version=1`,
   page renders read-only with the original step text.
5. From a second user account: open the protocol, click Fork, accept
   defaults, hit Create. A new protocol opens at the fork's slug.
   Topbar shows "Fork of Agarose LLS Sieves v2 by Alex McGhee".
6. Make substantial edits in the fork. Click "Migrate to standalone",
   confirm. The fork-of chip disappears; the protocol behaves as a
   standalone going forward.

## Out of scope

- **In-place restore** — viewing-only V1. Phase 5b can add a "Restore
  this version" button that snapshots current state then replaces tree.
- **Version diff view** — no side-by-side. Future phase.
- **Auto-detected divergence** — migrate is a manual judgment call.
- **Cross-fork comparisons** — no "compare with parent" UI yet.
- **Public publish flow** — published-status read rule exists since
  V3.113 but is not exercised here. Future phase.
- **Author display name refresh** — `author_name` is cached at creation
  for fast list rendering. If a user changes their display name, old
  protocols keep the old name. Acceptable for V1; a future phase can
  add a "refresh author names" admin action.
