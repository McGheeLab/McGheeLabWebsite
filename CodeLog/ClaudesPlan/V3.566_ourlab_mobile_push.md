# V3.566 — Ourlab mobile m-v0.2: native push notifications

> Second mobile milestone (FuturePlan 05 WS-D m-v0.2 + WS-C payload fix).
> Native FCM push on iOS/Android via `@capacitor-firebase/messaging`,
> reusing the existing `users/{uid}/pushTokens` registry and `notify.js`
> — NOT a forked `devices` collection. Two repos: web seams here, plugin
> + capabilities in `~/Documents/GitHub/OurlabMobile` (m-v0.2).

## Goal

A push sent by any existing Cloud Function (chat mention, DM, task
event, huddle, scheduler, …) arrives as a real notification on the phone
and, when tapped, deep-links into the target rm/ page. All 8 functions
already call `notify.sendToUsers`; the only backend change is making the
payload display-capable for native clients.

## The core fix (WS-C) — `functions/helpers/notify.js`

Today `buildMessage` is **data-only** (correct for web: the service
worker displays via `onBackgroundMessage`; a `notification` field would
double-fire). But a data-only push **does not display on a backgrounded
iOS app** — it arrives silently. Fix: branch on an explicit `native`
flag stamped on the token doc.

- Web token → unchanged data-only payload (SW-displayed).
- Native token (`native: true`) → add a top-level `notification` block +
  `apns` (sound) + `android` (high priority, sound) config; keep `data`
  for tap deep-linking.

Branch on `native`, NOT the platform string: a web PWA on an iPhone
stores `platform:'ios'` but is still a web token. `sendToUsers` now reads
`data.native` into each token entry and passes it to `buildMessage`.

## Web seams — this repo (V3.566)

| File | Change |
|---|---|
| `functions/helpers/notify.js` | Platform-aware `buildMessage(token, notif, {native})`; `sendToUsers` threads `native` from each pushTokens doc. Web path byte-compatible with before. |
| `rm/js/mobile-push.js` | **NEW.** Capacitor-only (no-op in browsers + on rm/ web, which never loads it). Requests notification permission, gets the FCM token via `FirebaseMessaging.getToken()`, writes `users/{uid}/pushTokens/{token}` with `native:true, client:'capacitor', platform, deviceId, lastSeen`. Listeners: `notificationActionPerformed` → deep-link (`data.url`, accepts `chat.html?..`/absolute/full-URL), `notificationReceived` → foreground toast, `tokenReceived` → re-write. sessionStorage-throttled (once/session, re-write on rotation). |
| `sw.js` | CACHE_VERSION bump. |

No firestore.rules change — `users/{uid}/pushTokens` is already owner
read/write, and `native` is just a new field. Web `push-notifications.js`
(McgheePush) needs no guard: it is loaded only by the marketing SPA,
never by rm/ pages, so there is no double registration inside the app.

- App launch → permission granted → `getToken()` returns a token →
  `[ourlab-push] token registered for <uid> (ios)` logged; token doc
  written with `native:true`. (Apple-silicon Simulator supports APNs.)
- `xcrun simctl push app.ourlab.mobile push.apns` (aps.alert + `url`) →
  foreground toast "💬 New message — Alex mentioned you in #general"
  fired by `notificationReceived`. Confirms delivery → plugin → JS.

## Out of scope / still required for REAL-DEVICE background push

- **APNs Auth Key (.p8)** created in the Apple Developer portal and
  uploaded to Firebase console → Cloud Messaging → Apple app config.
  Without it, FCM cannot reach APNs, so a real backgrounded iPhone gets
  nothing (Simulator via simctl bypasses this). **Manual, Alex-only.**
- Per-channel device prefs UI in settings; device list / stale-token
  pruning (`lastSeen`).
- The daily digest / meeting-reminder functions (FuturePlan 05 WS-C
  remainder) — separate release.
- Suppressing the web SW token path — only needed if rm/ ever adopts web
  push; today it doesn't.

## Release ritual

Deploy order: **`firebase deploy --only functions`** (notify.js is shared
by 8 functions) → FTP the web tree (mobile-push.js + sw bump; inert on
web). Mobile: `npm run build` + Xcode run; TestFlight later at m-v1.0.

## Rollback
