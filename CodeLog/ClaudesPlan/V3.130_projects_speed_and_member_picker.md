# V3.130 — Speed up Add Item / Add Member + roster-picker for Personnel

## Why

User report: adding a project on `/rm/pages/projects.html` "takes a really
long time", and adding people to a project does too. Also: the people
picker should be a list of lab members, not free text.

Two distinct slowness causes — both stem from the adapter's
collection-save semantics:

1. **`+ Add Item` calls `api.save('items.json', data)`.** That route is
   `scope: 'lab', collection: 'items', shadowJson: true`. Per
   [rm/js/api-firestore-adapter.js:201-285](../../rm/js/api-firestore-adapter.js#L201-L285),
   collection-scope save does a **full collection replace** —
   `batch.set(items/{id}, ..., {merge:true})` for *every* item, plus
   delete for any server doc not in the payload, chunked at 400 ops per
   commit. With a real lab `items.json` (currently ~hundreds of papers
   plus tens of grants/courses/tools), every save rewrites the whole
   collection. The shadow JSON write is fire-and-forget but the
   Firestore batch is still on the critical path.

2. **`addProjectMember` calls `api.save('projects/<type>.json', data)`.**
   Same shape — `scope: 'lab', collection: 'projects', where: ['type', '==', X]`.
   Adding a member to one paper rewrites every other paper doc
   (the `where` filter narrows the deletion sweep but the upsert still
   touches every row in the payload).

The third issue is unrelated to slowness: `window.addPersonnel`
([rm/js/projects.js:1289-1303](../../rm/js/projects.js#L1289-L1303))
opens a free-text input for the person name. The newer
`addProjectMember` (V3.126) already uses a dropdown, but legacy
`addPersonnel` does not.

## Fix

### Surgical writes (mirrors V3.96 pattern in task-quick-builder.js)

Add two helpers near the top of [rm/js/projects.js](../../rm/js/projects.js):

```js
async function saveItemSurgical(item) {
  // Write one items/{id} doc directly via firebridge.db, ~150-300ms.
  // Falls back to full api.save on any Firestore failure.
}

async function saveProjectDocSurgical(canon, row) {
  // Write one projects/{row.id} doc directly. Same pattern.
  // Includes the type discriminator so listing queries still resolve it.
}
```

Both helpers `set(..., {merge: true})` so partial fields stay safe; both
stamp `updatedAt: serverTimestamp()`. Both also fire-and-forget the JSON
shadow write via `api.save` so the local mirror stays in sync without
blocking.

### Refactor

- `openAddForm(type)` — replace `data.items.push(newItem); await api.save(ITEMS_PATH, data)` with `await saveItemSurgical(newItem); _allItems.push(newItem)`. Same render path.
- `editItemById(id)` — replace the read-modify-write with `await saveItemSurgical(updated); patch _allItems in place`.
- `deleteItemById(id)` — switch to direct doc delete + targeted update of any items whose `related_ids` referenced the deleted id (typically 0-3 such items, so a per-doc loop is fine).
- `addProjectMember(itemId)` — replace `api.save(canon.sourcePath, data)` with `saveProjectDocSurgical(canon, row)`. Patch `canon.member_uids` in place (already done).
- `removeProjectMember(itemId, uid)` — same.
- `unlinkBucketFromItem`, `pinItemToDashboardUI` — these call `api.save(ITEMS_PATH, ...)` indirectly via `LINKS.removeLink`/`LINKS.pinItemToDashboard`. Out of scope for V3.130; refactor of [rm/js/links.js](../../rm/js/links.js) is a separate pass.

### Personnel picker

Convert `addPersonnel(itemId)` to a dropdown:
- Options: every roster entry (both `_firebaseUid: true` users and
  `_legacy: true` slug entries), labeled with name + role + email.
- Adds a literal `__free__` option that drops back to the prompt-style
  free-text path (one-off external collaborators).
- Keeps the `personnel[]` field as a string ID array (no schema change).

This sits ALONGSIDE `addProjectMember` — they're different concepts:
Personnel is human attribution (shown on cards, includes external
collaborators), Members is access control (gates Firestore reads, must
be a real Firebase UID).

## Out of scope

- Migrating items.json off the unified-collection model into per-type
  collections (would side-step the full-collection-rewrite issue at the
  cost of a much bigger refactor).
- Moving `members` access control to a different storage shape.
- Caching the picker open-state across modal close/reopen.
