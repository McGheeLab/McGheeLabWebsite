# V3.637 — Closing the rest of the teacher-platform findings (issues 4–7)

Finishes the list opened by [V3.632_teacher_rules_findings.md](V3.632_teacher_rules_findings.md).
V3.635 closed issues 1–3 (the ones that let someone grant themselves a class,
hijack a join code, or undo a Remove). This closes the remaining four.

**Suite after this version: 84 checks, 84 as intended, 0 deviations.**

## Issue 4 — "Enrollment closed" now actually closes enrollment

The teacher's toggle was enforced only by `joinClassWithCode`, so a student
holding the code could still enroll into a closed class. The enrollment-create
rule now also requires
`get(schedules/$(scheduleId)).data.get('enrollmentOpen', true) == true`, and so
does the student re-join clause — re-joining costs what joining costs,
including a class that is still open.

Default is `true`, so classes predating the flag are unaffected. A side effect
worth knowing: enrolling into a **deleted** class now fails at this `get()`
too, which is correct — its join codes may still be marked active.

## Issue 5 — `users` is no longer a public directory

`allow read: if true` on `users/{userId}` meant any visitor could list every
user document: names, emails, roles, bios. Production numbers at the time of
writing: **45 user docs, 31 of them guests** — i.e. the majority of that
collection is now outside teachers and their students, some of them minors,
because that is exactly what V3.304 invited in.

```
allow read:  if resource.data.get('role', 'guest') != 'guest'
             || isOwner(userId)
             || isLabMember()
             || isAdmin();
```

Three things had to line up for this to be safe:

1. **The public team page's query must match the rule.** A `list` is denied
   outright if any doc it would return fails, so `DB.getAllUsers()` (an
   unconstrained list) could no longer be the public source. New
   `DB.getPublicProfiles()` = `where('role', '!=', 'guest')`, used only by
   app.js's team page; the signed-in callers (`setupTeamPicker`, the admin
   user table) keep `getAllUsers()` and pass via `isLabMember()`/`isAdmin()`.
2. **`!=` must not silently drop anyone.** Verified against production: 0 docs
   are missing `role`, and the narrowed query returns **exactly** the same 14
   profiles the old client-side `u.role !== 'guest'` filter produced, with 0
   dropped. The rendered page was checked too — all five category sections,
   16 cards, no console errors.
3. **First sign-in must still work.** Profile bootstrap reads
   `users/{uid}` *before* it exists. On a missing doc the first clause errors
   on a null `resource`, but an errored operand does not poison an `||` whose
   other side is true — `isOwner` carries it. Both the read and the create are
   now asserted in the suite so nobody re-breaks sign-up.

**Residual, deliberately out of scope:** lab-member documents stay publicly
readable, because the public team page renders them straight out of this
collection. Narrowing that means mirroring the public fields into
`teamProfiles` (which today is the legacy *claimed-profile* collection, not a
public mirror) and backfilling — its own version. What this version removes is
the part V3.304 created: 31 guest profiles, growing with every teacher and
student who signs up.

## Issue 6 — a deleted class no longer blocks its participants' reviews

Review-create dereferenced `get(schedules/…)` before checking enrollment, so
after "Delete class" the `get()` returned null, the expression errored, and the
rule denied — the review you most want ("the class is over, how was it?") was
the one that couldn't be written. Enrollment is now checked **first**, and the
schedule read is guarded by `exists()`.

**Known limit, now asserted as intended:** the *owning teacher* still can't
review a class after it's deleted — with the schedule doc gone there is no
server-side evidence of ownership left, and accepting a self-asserted
`teacherUid` would open the moderation queue to spam. If you want that,
soft-delete the class (`deletedAt` instead of `delete`) — it preserves the
ownership evidence and matches the existing posture of keeping enrollments for
audit. Not done here because it touches the admin panel, the class page, and
both dashboards' class lists for one edge case.

## Issue 7 — the module catalog reaches the phone app, and its absence is loud

`rm/js/admin-teachers.js` fetches `/modules/manifest.json` by absolute
site-root path. `OurlabMobile/scripts/sync-rm.mjs` copies the `rm/` tree plus a
hand-listed `['scheduler.js']`, so that URL 404'd inside the app; the failure
was caught into an empty catalog, and an empty catalog renders an approve modal
with **zero** module checkboxes that then refuses to submit — a dead end with
no explanation.

Two changes, because either alone leaves a hole:

- `sync-rm.mjs` now also copies `modules/manifest.json` (nested path, so it
  `mkdirSync`s the parent). Ships with the next TestFlight build.
- `admin-teachers.js` records `manifestFailed` instead of swallowing it, shows
  a standing error in the toolbar, and **blocks** Approve and Edit-granted-
  modules with a specific message — approving without a catalog would silently
  provision a class with no modules at all. It names the workaround (approve
  from a browser) so an older app build is a detour, not a mystery.

## Deploy — order matters, and it is the reverse of V3.635's

**FTP first, then `firebase deploy --only firestore:rules`.**

Issue 5 is why. New rules + old client = the public team page's unconstrained
`getAllUsers()` list is denied, so **every signed-out visitor sees a broken
team page** until the FTP lands. The other direction is harmless: old rules +
new client just means the narrowed query runs against a permissive rule.
V3.635's changes are safe in this order too (its client-side additions —
passing `joinCode` on re-activation, stamping `removedBy` — are inert under the
old rules).

The mobile half (`sync-rm.mjs`) rides the next `release_push.py` build.
