# V3.152 — Insert at cursor, name-slug eqi tokens, reference inserts work

## Three coupled bugs

User report (post-V3.143):

> I click on an inline reference and the location of mu cursor is lost,
> it moves to the begenning of the paragraph that i am on. It should
> insert whatever i want where my cursor is. the inline equation needs
> a name reference instead of a unique ID. the reference insert
> selects, but the insert does not work.

Three bugs:

1. **Cursor jumps to position 0.** V3.143's char-offset persistence
   model was correct, but `_insertAtSavedCaret` had a remaining
   off-by-one-DOM-swap timing bug.
2. **Inline equation tokens use opaque IDs.** Authors see
   `[!eqi:eq-abc123]` in source, can't tell what equation it points to
   without round-tripping through the panel.
3. **Reference inserts (`+ Eq` / `+ Fig` / `+ Table`) don't actually
   insert.** Same root cause as #1.

## Bug 1 — order of operations in `_insertAtSavedCaret`

The contenteditable lives in **two states**:
- **Source state** (when focused): `el.textContent` = raw source like
  `hello $\\alpha$ world`.
- **Rendered state** (when blurred): `el.innerHTML` = chip spans + KaTeX
  + citation markup, generated by `applyRendered(el, source,
  renderFn)`.

Two handlers swap state:
- `el.addEventListener('focus', () => el.textContent = yText.toString())`
  ([rm/js/paper-editor.js:3003-3009](rm/js/paper-editor.js#L3003-L3009))
- `el.addEventListener('blur',  () => applyRendered(el, ...))`
  ([rm/js/paper-editor.js:3018-3023](rm/js/paper-editor.js#L3018-L3023))

V3.143 saved `(savedEl, savedCaret)` (char-offset) and rebuilt the
Range fresh in `_insertAtSavedCaret`. The order of operations was:

```js
var freshRange = _rangeFromCharOffset(el, savedCaret);  // walks RENDERED DOM
el.focus();                                             // ← swap to SOURCE
sel.addRange(freshRange);                               // ← stale: range nodes are detached
```

That's the bug. The Range was correct *for the rendered DOM at that
instant*, but `el.focus()` immediately swapped the DOM to source via
`el.textContent = yText.toString()`. Setting `textContent` removes all
existing children — including the nodes `freshRange.startContainer`
referenced. By the time `sel.addRange` ran, the Range was again
pointing at detached nodes. Result: the selection collapsed to position
0 (the start of the contenteditable), and `execCommand('insertText',
...)` inserted at position 0 — exactly what the user reported.

**Fix:** focus FIRST so the source-text DOM is in place and stable,
THEN build the Range:

```js
el.focus();
var freshRange = _rangeFromCharOffset(el, savedCaret);  // walks SOURCE DOM
sel.addRange(freshRange);                               // ← live: nodes still attached
```

Source-text DOM is just text nodes (no chip spans), so `_rangeFromCharOffset`
walks them cleanly and the Range references nodes that aren't going
away.

## Bug 2 — `[!eqi:<id>]` → `[!eqi:<name-slug>]`

V3.109 used the equation library entry's auto-generated id
(`eq-abc123`). Authors couldn't read their own source.

V3.152 emits a slug derived from the entry's name field:

```js
function _eqiSlugFromEntry(e) {
  var n = (e.name || '').trim();
  if (!n) return e.id;
  var slug = n.toLowerCase()
    .replace(/[^a-z0-9_-]+/g, '-')
    .replace(/^-+|-+$/g, '')
    .slice(0, 60);
  return slug || e.id;
}
```

Hookes Law → `hookes-law`. Fine-Structure Constant → `fine-structure-constant`.
Unnamed entries fall back to id. 60-char cap keeps tokens readable
even for verbose names.

Three resolvers gain two-pass lookup (id first, then slugified-name):

- [rm/js/paper-editor.js](rm/js/paper-editor.js) `getInlineEquationById(idOrName)`
  — used by `renderInlineEqLibraryChip` for the in-page chip render.
- [rm/js/paper-export-tex.js](rm/js/paper-export-tex.js)
  `paragraphTextToTex`'s `[!eqi:...]` regex callback — used at LaTeX
  export.

Both share the same slug rule (a private `_slugifyEqName` /
`_eqiSlugFromEntry` helper in each module). Old `[!eqi:eq-abc123]`
tokens still resolve via the id-first pass.

## Bug 3 — reference inserts don't work

The `+ Eq` / `+ Fig` / `+ Table` toolbar buttons all call into
`_openRefPicker` / `_openFigRefPicker` / `_openTabRefPicker`, which all
land in `_openPicker`'s `pickIdx` → `_insertAtSavedCaret(entry.insert)`.
Same code path as `+ Inline Eq` / `+ Cite`. Same Bug 1. The fix to
`_insertAtSavedCaret` covers all five toolbar buttons + the right-click
context-menu insertion path.

## Verification

1. Open a paper, click into a paragraph, type "hello world", place
   caret between "hello" and "world".
2. Click `+ Inline Eq` → picker opens. Pick an entry named "Hookes
   Law". The token `[!eqi:hookes-law]` inserts BETWEEN hello and world
   (not at the start). On blur, renders as the rendered KaTeX chip.
3. View the source via right-click → Copy paragraph (or unfocus +
   refocus): the source contains the readable slug, not `eq-abc123`.
4. Click `+ Eq` (reference picker) → pick a numbered equation → token
   `[!eqr:<label>]` inserts at the caret. Reference chip renders on
   blur.
5. Same verification for `+ Fig`, `+ Table`, `+ Cite`.
6. Pre-V3.152 papers with existing `[!eqi:eq-abc123]` tokens continue
   to render correctly (id-first lookup).
7. Export to LaTeX → both `[!eqi:hookes-law]` and any pre-existing
   `[!eqi:eq-abc123]` tokens resolve to `\(<latex>\)`.
8. Hard-reload to evict SW cache `mcgheelab-shell-v127`.

## Out of scope (deferred)

- **Slug collision detection.** If two inline-equation entries share
  the same slug, the first-match-in-document-order wins. The picker
  doesn't currently warn; authors who rename will eventually notice.
- **Migration of legacy `[!eqi:eq-abc123]` tokens to slug form.**
  Coexistence is fine (both render correctly); not worth a sweep.
- **Same name-slug treatment for figures/tables/main equations.** Those
  already use user-set labels (`fig:cellgrowth`, `tab:cellcounts`,
  `eq:hookes`). Inline equations were the only token kind using opaque
  ids.
