# V3.607 — Release push covers the phone app too

## The gap V3.604 left

V3.604 batched the release *notification*, but "push" still meant one thing:
FTP. Ourlab mobile is **not** a remote-URL wrapper —
`OurlabMobile/scripts/sync-rm.mjs` rsyncs the whole `rm/` tree into the
Capacitor `webDir` at build time (deliberately: the lab needs ~2h offline in
the basement BSL-2). So an FTP-only push updates browser users and **silently
leaves every phone user on old code**, while the announcement they just
received claims the changes are live. The app half was also hand-authored
each time: hand-bump `CURRENT_PROJECT_VERSION`, hand-write the `m-vX.Y.Z`
changelog entry, hand-run five CLI steps.

## Goal

One command ships both halves from the ledger, and the announcement names the
build that carries them.

## `scripts/release_push.py`

Input: `CodeLog/Updates/PENDING_RELEASE.md` pending entries. Everything else
is derived.

1. **Preflight** — parse pending entries (handles wrapped multi-line entries),
   read the web version from CHANGELOG head, enforce the 5-entry floor
   (`--force` = Alex said "push"), verify the mobile repo + ExportOptions.
2. **Bundle diff BEFORE syncing** — `diff -rq <app public/rm> <repo rm>` is
   the real "what is this build actually carrying" list, since the rm/ tree
   holds several sessions' uncommitted work. Drops `pages/*.html`, which
   differ by construction (sync-rm injects script tags into all ~85).
3. **Version + build** — `CURRENT_PROJECT_VERSION` + 1 in **both** Debug and
   Release blocks (ASC rejects duplicate build numbers); next `m-vX.Y.Z`.
4. **Generate the mobile changelog entry** from the ledger — the same
   sentences lab members receive, so app users and browser users are told the
   same thing about the same code.
5. `npm run build` (sync-rm → cap sync).
6. **Device-verification gate** — honors the standing rule that app changes
   are never shipped unrun (`--verified` skips, `--dry-run` implies).
7. **Archive → export → upload** to TestFlight.
8. **Print the announcement block** ready to paste, including the app build.
9. **Roll the ledger** into Shipped, stamped `V3.x · app m-vY (build N)`.

### Key decisions

- **Patch vs minor is decided by committed history, not dirtiness.** First
  attempt bumped minor whenever any native-ish path was dirty — which fired on
  17 branding/asset files that have been uncommitted since m-v0.3 and *already
  shipped in earlier builds*, and on `cap sync`'s generated
  `android/app/src/main/res/**`. Now: `decisive` = hand-authored native files
  committed since the `.last-release.json` baseline → minor; `advisory` =
  merely-dirty files, printed but not acted on; `--minor`/`--patch` override.
  `project.pbxproj` is excluded from the signal entirely — *this script* edits
  it, so counting it would make every release a minor bump forever.
- **`CodeLog/Updates/.last-release.json`** in the mobile repo is the baseline
  (version, build, web version, git sha, date). Written only after a
  successful upload, so a failed run doesn't move the goalposts. Absent on the
  first run → patch + a printed note that detection sharpens next time.
- **Upload is in scope, FTP is not.** Cyberduck is GUI-only, and pressing 📣
  Send stays a human act (it buzzes the whole lab). The script prints both as
  remaining steps.
- **Run from a real terminal** — codesign fails with
  `errSecInternalComponent` under a sandbox.

## Announcement carries the app build

`releaseAnnounce` accepts `appVersion` + `appBuild`; the release doc stores
them; the What's New page renders "📱 In the phone app from **build N** —
update from TestFlight if you don't see it." Without this, a phone user reads
a release note describing code their app doesn't have yet.
