# V3.805 — Profile bootstrap is create-only (the PI demoted himself to guest)

## Incident

2026-10-13, ~19:57 UTC. Alex signed in to RM as `mcgheealex@gmail.com` and got the
"pending lab access — email mcgheealex@gmail.com" overlay. Firestore showed
`users/uAicelwQ5gNQdH1Qc8wqZcJDRZQ2` with `role: guest, category: guest`, written at
19:56:59Z by a **merge** (bio, papers, CV untouched). Six fields changed, compared against
the 1-hour version-retention read (`?readTime=2026-10-13T19:56:00Z`):

| field | before | after |
|---|---|---|
| role | admin | guest |
| category | pi | guest |
| name | Alexander McGhee | Alex McGhee (Google displayName) |
| photo | Storage `users/<uid>/photo/{thumb,medium,full}.webp` | Google avatar (lh3) |
| createdAt | 2026-03-20T23:36:27Z | 2026-10-13T19:56:59.755Z |
| updatedAt | 2026-07-13T17:11:05.100Z | 2026-10-13T19:56:59.755Z |

There were **zero** other admins, so no one could promote him back in-app. No rules
deploy since 2026-10-01, so it wasn't a rules regression.

## Root cause

`rm/js/profile-bootstrap.js` wrote `set({email,name,role:'guest',category:'guest',
createdAt,updatedAt,photo}, {merge:true})` whenever `firebridge.onAuth` delivered a
null profile. Null doesn't only mean "no doc": `_loadProfile()` leaves it null when
every read attempt **fails** (offline, network blip, `unavailable`), and the live
`users/{uid}` snapshot can report `exists:false` from cache. Either way, an existing profile
got the bootstrap merged over it.

Rules (`users` update) freeze `role` for non-admin owners, so a member's misfire is
denied. `isAdmin()` lets an admin rewrite their own doc, including their own role, so the
only account that could be hit was the PI's.

`user-system.js` `_ensureGuestDoc()` had the same shape: `getUser().catch(() => null)`
treated a failed read as "no doc", and that one also writes `bio: ''`.

## Fix

Both writers now create the doc in a transaction: `t.get(ref)`, then `t.set` only if
`!snap.exists`. A transaction reads from the server, never the cache, and fails
instead of queueing offline, so the guest doc is written only when the server confirms
it doesn't exist. No rules change, so this is FTP-only.

Regression test: `scripts/tests/profile-bootstrap-rules.test.mjs` (emulator, real rules)
reproduces the incident with the old write and proves the transaction leaves admin and
member docs untouched while still creating first-sign-in guest docs.

## Data repair (manual, Alex-approved)

Restore the six fields above with a field-masked REST PATCH (`updateMask` on exactly
those six, `currentDocument.updateTime` precondition). The photo's medium/full download
URLs can be rebuilt from the Storage objects' `firebaseStorageDownloadTokens` if the
1-hour version window has passed.

## Follow-up (not done — needs a rules deploy, Alex's call)

Rules defense in depth: deny an admin changing **their own** `role`
(`request.auth.uid == userId && role changes`). That would make self-lockout impossible
from any future client bug. Demoting yourself would then take another admin or the
console. Also consider a second admin account so one bad write can't lock the lab out.
