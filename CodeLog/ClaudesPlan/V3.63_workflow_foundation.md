# V3.63 — Workflow-driven UX redesign · PR 1: foundation

## Goal

First of three PRs (V3.63 / V3.64 / V3.65) implementing the workflow-
driven UX redesign. This release ships the data model + admin tooling
without changing any non-admin user's experience. Subsequent PRs add
the workflow chooser dashboard (V3.64) and per-user custom workflows
(V3.65).

## Why

After V3.62 the RM nav is still a "feature catalog" — six dropdown
groups, every signed-in user sees every page their role allows.
Different users (PI, postdoc, undergrad, collaborator) want different
things. Workflows bundle pages around a task (paper writing,
purchasing, meetings) so each user sees only what they need, with the
admin controlling per-user page access.

## What ships

### Page registry — `rm/js/page-registry.js` (new, ~155 LOC)

Walks `nav.js`'s `NAV_ITEMS` at startup and produces `window.PAGE_REGISTRY`:

```
PAGE_REGISTRY = {
  list,                  // array of { id, label, href, group, gate }
  byId,                  // Map<id, entry>
  byHref,                // Map<href, entry>
  pageIdFromHref(href),  // helper
  DEFAULT_WORKFLOWS,     // array of 5 seeded workflows
  defaultPageIdSet,      // Set<id> = union of all default-workflow pageIds
}
```

Page ids are derived deterministically from `path + ?tab=`:

| URL | id |
|---|---|
| `/rm/index.html` | `dashboard` |
| `/rm/pages/library.html` | `library` |
| `/rm/pages/library.html?tab=comments` | `library__tab__comments` |
| `/rm/pages/activity-overview.html?tab=tracker` | `activity-overview__tab__tracker` |

Adding a page to `NAV_ITEMS` automatically makes it pickable in the
admin matrix and the workflow builder — no per-feature code on the
workflow side.

### Five default workflows (seeded constants)

```
Lab Research               🔬 — Activity Tracker, Library, Projects, Tasks
                                + future Lab Notebook, Protocols
Paper Writing              📝 — Paper builder, Library, Library Comments,
                                Tasks, PMR, Chat + future Lab Notebook
Certification & Training   🎓 — Compliance, Chemicals, Career, Tasks
Task Scheduling            📊 — Tasks, Activity Overview (Tracker / Year /
                                Email tabs), Scheduler, Sharing, PMR
Meetings                   🗣️ — Meetings, Huddle, Chat, Tasks, Calendar
```

Stored in `labConfig/defaultWorkflows` after the admin clicks the
"Seed defaults" button in the new admin page. Until then, the seeded
constants are the working defaults.

### Firestore data model

| Path | Scope | Write | Read | Purpose |
|---|---|---|---|---|
| `labConfig/defaultWorkflows` | lab | admin | all auth | `{ workflows: [{ id, label, description, icon, pageIds: [] }, ...], updatedAt }` |
| `userPermissions/{uid}` | top-level keyed by uid | admin | owner+admin | `{ allowedPageIds: [...], updatedAt }` — missing/empty doc means implicit baseline access |
| `userData/{uid}/customWorkflows/{workflowId}` | per-user | owner | owner | per-user saved workflows (PR 3 / V3.65 starts writing here) |

**Why `userPermissions/{uid}` is a top-level collection** (not a
field on `users/{uid}`): the existing `users/{userId}` write rule
allows the owner to write any field of their own profile, which would
let a user grant themselves any page. Top-level collection has its
own admin-write rule.

### `firestore.rules` change

Added one new rule block:

```firestore
match /userPermissions/{userId} {
  allow read:  if isOwner(userId) || isAdmin();
  allow write: if isAdmin();
}
```

Existing rules cover the other two paths:
- `labConfig/{docId}` (line 464) — `read: auth, write: admin` covers the new `defaultWorkflows` doc.
- `userData/{userId}/{document=**}` (line 735) — `owner read+write` covers `customWorkflows/*`.

### `firebridge.canAccessPage(pageId)` + `loadAccessGrant()`

New helpers in [rm/js/firebase-bridge.js](../../rm/js/firebase-bridge.js).

- `canAccessPage(pageId)` — synchronous gate. Admin always passes.
  Otherwise checks the user's `userPermissions/{uid}.allowedPageIds`
  (or, if no grant doc, the implicit baseline =
  `PAGE_REGISTRY.defaultPageIdSet`).
- `loadAccessGrant()` — lazily fetches the grant doc once per page.
  Returns a promise; subsequent calls return the cached result.
  Pages call this once during boot before relying on
  `canAccessPage`.

### Admin matrix page — `rm/pages/admin-permissions.html` + `rm/js/admin-permissions.js`

Admin-gated via `firebridge.gateAdmin('manage workflow permissions')`.
Two tabs (selected by `?tab=`):

- **Users × Pages**: rows = non-admin users from `users/*`,
  columns = every PAGE_REGISTRY page grouped by section. Checkbox
  edits write to `userPermissions/{uid}.allowedPageIds` on Save.
  Setting an empty list deletes the doc (user falls back to
  implicit baseline). Pending edits highlighted amber until saved.
- **Default Workflows × Pages**: rows = the 5 default workflows
  (from Firestore or seeded constants), columns = every page.
  Single Save writes the whole `{ workflows: [...] }` doc.
- First-run "Seed defaults" button writes the seeded constants to
  Firestore when `labConfig/defaultWorkflows` doesn't exist.
- Filter input box at top filters visible rows in either tab.

CSS reuses [rm/pages/admin-migrate.html](../../rm/pages/admin-migrate.html)'s `.mig-table` styling, extended with sticky-row + sticky-column rules for matrix scrolling.

### `rm/js/api-routes.js` changes

Two new routes registered:

```js
api.registerRoute('workflows/defaults.json', {
  scope: 'lab', collection: 'labConfig', doc: 'defaultWorkflows',
  cache: LONG,
});
api.registerRoute('workflows/custom.json', {
  scope: 'user', subcollection: 'customWorkflows', wrapKey: 'workflows',
  cache: SHORT,
});
```

`userPermissions/{uid}` is intentionally **not** registered as an
`api.*` route — it's a small per-doc read accessed only by
`admin-permissions.js` (write) and `loadAccessGrant()` (read). Direct
`firebridge.db()` calls keep things simple.

### `rm/js/nav.js` change

Added a Settings → "Permissions" admin-gated entry pointing at
`/rm/pages/admin-permissions.html`. Visible only when
`firebridge.isAdmin()`.

### `sw.js`

`CACHE_VERSION` 37 → 38.
