# V3.392 — Citation family never loaded: the `window.firebridge` guard bug

## Goal

Make inline `[@key]` citation chips render in the target journal's family
(IEEE `[1]`, ACS/Nature superscript, Science `(1)`, author-year preprints
`(Smith 2024)`) instead of the legacy "Author Year" short label. This was
the dominant open thread across V3.388–V3.391 and the reason the Document
view still showed the wrong citation style.

## Root cause (definitively isolated)

`PaperCiteStyle.init()` (`rm/js/paper-cite-style.js`) is the only thing
that sets `_family` (from the template's `citation.render_family`).
`getFamily()` returns `_family`; `renderCitationChip`
(`paper-editor.js:5204`) reads it and, when it is null, falls to
`hit.shortLabel` = `firstAuthor + ' ' + year` → **"Araiza Canizales 2026"**.

`init` began with:

```js
if (!paperId || !window.firebridge) { return Promise.resolve(); }
```

But `firebridge` is declared `const firebridge = (function(){…})()` in
`firebase-bridge.js:4` — a **lexical global**, reachable by bare name but
**never** assigned to `window` (a repo-wide grep for `window.firebridge =`
is empty). So `window.firebridge` is permanently `undefined`,
`!window.firebridge` is permanently `true`, and **init bailed on every
call** — returning `Promise.resolve()` before setting `_family` or logging
anything.

### Why it was so hard to see

- `getNumber(key)` kept working (returned correct first-appearance
  numbers) because it recomputes from the Yjs tree and never touches
  firebridge. The steady-state symptom was therefore the confusing
  `family: null | num: 1`.
- `fetchTemplate('acs'/'ieee')` worked in isolation because it lives on
  `PaperExportTex`, not firebridge.
- init's internal fetch already used **bare** `firebridge.db()` (which
  works), so only the *guard* was wrong — the rest of init was correct and
  never ran.
- The decisive diagnostic (run in the direct editor tab) printed
  `firebridge? false` for `!!window.firebridge` while the same snippet's
  bare `firebridge.db().collection('paperExports').doc(pid).get()`
  returned `exists = true, templateId = ieee`. That contradiction —
  bare works, `window.` is false — is the whole bug in one line.

## Fix

`rm/js/paper-cite-style.js` — guard now tests the bare binding, matching
the `firebridge.db()` call init makes two lines later:

```js
if (!paperId || typeof firebridge === 'undefined' || !firebridge) {
  return Promise.resolve();
}
```

`typeof` keeps it safe against an impossible load-order where the const
isn't defined yet. Nothing else in init changed — the wait-for-
PaperExportTex poll, the `paperExports.templateId → meta.template_id →
'mebp-journal'` fallback chain, and the `paper-equations-changed` repaint
dispatch were all already correct; they just never executed.

## Verification

After FTP + reload of the paper builder (mebp-paper is currently on the
`ieee` template): inline chips should render as `[1]`, `[2]` … in first-
appearance order, wrapped in brackets, instead of "Araiza Canizales 2026".
Switching the template in the Document view toolbar should flip the family
live (superscript for ACS/Nature, `(1)` for Science).

## Follow-ups (NOT done here)

1. **Systemic `window.firebridge` sweep.** The same mistake appears as
   read-checks in ~11 other modules. Most are graceful
   `(window.firebridge && …) || null` fallbacks that merely degrade, but
   a few silently take the wrong branch and are real bugs:
   - `library-paper.js:1671` — `if (!window.PAPER_OVERLAY_IMPORT ||
     !window.firebridge) return;` → overlay import always returns early.
   - `profile.js:16` — `if (window.firebridge)` branch never runs.
   - `tasks-inbox.js:1174` — `!window.firebridge || !window.firebridge
     .isAdmin()` → always takes the non-admin path.
   - `library-paper.js:613` — `isMember` computed from `window.firebridge`
     → always falsy.
   Each needs per-case verification (some have redundant bare-`firebridge`
   paths elsewhere), so this is a dedicated pass, not a blind
   search-replace.
2. **`paper-export-tex.js` control bytes** (lines ~619, 657) — scrub the
   stray non-text bytes so tooling stops treating the file as binary.
