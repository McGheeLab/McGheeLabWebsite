# V3.97 — Delete paper from library (cascade)

## Goal

Let admins (and the original uploader) remove a paper from the library
with a single click. The action must clean up everything tied to the
paper — not just the row — because a "library item" is several pieces
of state spread across Firestore + Cloud Storage + every user's task
tree.

Reported on the wishlist after V3.96:
> *"we also need a way to delete papers from the library."*

## Scope of cleanup

Deleting one paper requires removing all of:

| What | Where |
|---|---|
| Item doc | Firestore `items/{itemId}` |
| PDF blob | Cloud Storage `papers/{itemId}/<hash>.pdf` |
| Annotations | Firestore `papers/{itemId}/annotations/*` |
| Yjs collab state | `papers/{itemId}/yjs_snapshot/*`, `yjs_updates/*`, `presence/*` |
| Snapshots | `papers/{itemId}/snapshots/*` |
| Block comments | `papers/{itemId}/comments/*` |
| Task evidence refs | Every `evidence.item_ids[]` array nested under every project / sub-bucket / subtask / subtask-children inside every user's `userData/{uid}/tasks/*` |

**Why a Cloud Function instead of client-side Firestore + Storage
calls?** Three reasons:

1. **`storage.rules` has no `delete` rule** for `papers/{paperId}/{=**}`
   — client `.delete()` would fail. Doing the cascade server-side via
   the Admin SDK bypasses both Storage and Firestore rules, so we don't
   have to relax client guarantees just to enable deletion.
2. **Cross-user task scrubbing.** `firestore.rules` pin every
   `userData/{uid}/tasks/*` write to the owning uid; only the Admin
   SDK can scrub another user's tasks for evidence refs to the
   deleted paper.
3. **Atomicity.** One request, one log line, fewer moving parts.
   Partial failures are also easier to detect.

**Why scan all tasks instead of using a Firestore index?**
`evidence.item_ids` lives at multiple nested levels inside every tasks
doc (`projects[].evidence`, `projects[].buckets[].evidence`,
`projects[].buckets[].subtasks[].evidence`, and recursively in
`subtasks[].children[]`). Firestore does not index inside arrays of
objects, so an `array-contains` query is impossible — we walk the
tree. Per-user task collections are tiny (typically <50 docs/user); a
full collection-group read on delete is acceptable for an action that
fires at most a few times per day.

## Approach

### Server side — `functions/library.js` (new)

HTTPS endpoint `deletePaper`. CORS allowlist + bearer-token auth match
the existing pattern in [`functions/scrape-now.js`](../../functions/scrape-now.js).

Steps inside the function (Admin SDK):

1. **Auth**: parse `Authorization: Bearer <idToken>`, verify via
   `getAuth().verifyIdToken`, extract uid + email.
2. **Authorize**: read `users/{uid}.role`. Allow if `role === 'admin'`
   OR caller email matches `items/{itemId}.meta.library.pdf.uploaded_by`
   (case-insensitive). Reject 403 otherwise.
3. **Idempotency**: if `items/{itemId}` is missing, still try to
   `recursiveDelete(papers/{itemId})` to mop up orphans, then return
   `{ ok: true, alreadyMissing: true }`.
4. **Storage**: delete `meta.library.pdf.storage_path` blob via
   `getStorage().bucket().file(path).delete({ ignoreNotFound: true })`.
   Failure is logged but not fatal — finish the rest of the cascade.
5. **Subcollections**: `db.recursiveDelete(db.collection('papers').doc(itemId))`
   handles `annotations`, `yjs_snapshot`, `yjs_updates`, `presence`,
   `snapshots`, `comments`, and the doc itself in one batched call.
6. **Cross-user task scrub**: `db.collectionGroup('tasks').get()`,
   walk each doc's project / bucket / subtask / children tree, prune
   `itemId` from every `evidence.item_ids` array found, write back
   only docs that changed.
7. **Item doc**: `items/{itemId}.delete()` last — partial upstream
   failures don't leave a row pointing at half-deleted state.
8. **Return** `{ ok, itemId, blobDeleted, tasksScanned, tasksUpdated }`.

Wired into [`functions/index.js`](../../functions/index.js) alongside
the other module re-exports.

### Client side — `rm/js/library.js`

- **`_canDelete(it)`** — visibility gate: `_isAdminAny()` (already
  defined in this file at ~line 715) OR caller email matches
  `it.meta.library.pdf.uploaded_by`. Pure UI gate; the trust boundary
  is the server.
- **`_renderRow(it)`**: append a `🗑` button with
  `data-act="delete-paper"` after the existing `Send` button, only
  when `_canDelete(it)`.
- **`_onTableClick`**: new `delete-paper` branch — native `confirm()`,
  `firebase.auth().currentUser.getIdToken()`, POST to
  `https://us-central1-mcgheelab-f56cc.cloudfunctions.net/deletePaper`
  with `{ itemId }`. On success, prune from `_items` /
  `_libraryPapers` and `_render()`. Toast + `_setBusy('Deleting…')`
  pattern matches the neighbouring `open-pdf-tab` and `assign-paper`
  branches.

`storage.rules` and `firestore.rules` are untouched — the Cloud
Function bypasses both.

## Out of scope (deferred)

- **Soft-delete / undo / trash bin.** Hard delete only — if undo
  becomes desired, revisit with a `deleted_at` flag and a trash view.
- **Background cleanup of orphan task evidence refs.** The cascade
  scrubs at delete time, but pre-existing orphan refs (papers
  deleted via the Firebase console before this version, or by old
  manual edits) remain. A separate one-shot admin tool can sweep them
  later if needed.
- **Tightening `firestore.rules` items deletes.** Currently
  `items/{itemId}` allows `write: if isLabMember()`, so any lab
  member could in theory delete from the SDK. The Cloud Function is
  the authoritative path — UI gates the button to admin/uploader, and
  the server re-checks. Tightening rules to admin-or-uploader-only is
  a separate change that requires an `isOwner()` predicate.

## Verification

1. **Deploy the function**:
   ```
   firebase deploy --only functions:deletePaper
   ```
2. **Local dev server** for the UI:
   ```
   RM_WRITE_ALLOWLIST=mcgheealex@gmail.com python3 rm/server.py
   ```
   Open http://localhost:8000/rm/pages/library.html (hard reload to
   evict SW `mcgheelab-shell-v71`).
3. **Happy path** — admin deletes a paper that has a PDF, an
   annotation, and at least one task with `evidence.item_ids`
   referencing the paper:
   - Click 🗑, confirm.
   - Row disappears from the list.
   - Firebase console confirms `items/{id}` and all
     `papers/{id}/*` subcollections are gone.
   - Cloud Storage browser confirms `papers/{id}/...pdf` is gone.
   - Tasks page refresh: the affected subtask no longer shows the
     paper as evidence.
4. **Permission check** — non-admin non-uploader: button is hidden.
   Even if they POST manually with their bearer token, the function
   returns 403 with `permission-denied`.
5. **Idempotency** — POST `deletePaper` twice for the same id; the
   second call returns `{ ok: true, alreadyMissing: true }`.
6. **Partial-state cleanup** — manually delete only the
   `items/{id}` doc in the Firebase console (simulating a prior
   failed delete), then call `deletePaper` again: the function still
   succeeds and runs `recursiveDelete(papers/{id})` to mop up the
   orphans.
