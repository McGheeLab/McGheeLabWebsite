# V3.719 — Aims group under their grant; outputs name the grants they serve

## Goal

Alex: *"in the aims & outputs section, I want the aims to be grouped in a grant.
the outputs should get associations with one or more grants."*

## Why the two halves are shaped differently

An **aim** belongs to exactly one grant in practice — it is that grant's
commitment. So aims *group*: a heading per grant, its aims beneath. A flat rail
of every aim in the lab answers nobody's question, because no one reads aims
except in the context of the grant that has to deliver them.

An **output** can serve several grants at once — one paper can discharge
commitments in two awards. So outputs do *not* group; each card carries its own
grant chips instead. Grouping them would have meant either duplicating a card
under each grant or picking a false primary.

## Implementation

`groupedByGrant(list, cardFn, emptyLabel)` in `research.js` buckets cards by the
grant they resolve to through `RD.grantIdsForCard`, in the grants' own hub order.
It is generic over the card renderer, so outputs could be grouped the same way
later with no new code. Grants with no cards are skipped; unattached cards
collect under "No grant yet" **last and still visible**, never dropped.

`grantChipsFor(f)` renders an output's grants from the same resolver — so an
output linked only to an *aim* shows that aim's grant without a redundant direct
link. Indirect (concept-level) hits are excluded: nobody chose them, and showing
them would imply an association that does not exist. With no grant, an admin sees
an amber "no grant yet" chip; a student sees nothing, because it is the PI's gap
to close.

Aim cards drop their own grant pill — the heading above them already says it.
`deliveryCard` now takes its foot content from the caller rather than always
calling `parentPillsFor`.

The *capability* Alex asked for on outputs already existed: `crossOptions` builds
the links modal's pools from `PARENTS.output`, which includes `grant`, as
checkboxes — so one or more has always been possible. What was missing was seeing
the result on the map.

## Verified

Against live data: the delivery band shows one aim group, "⚡ GELS CAREER
Submitted · 3", holding all three aims; the single output shows the amber
"no grant yet" chip because it genuinely has no links at all. Zero console
errors, zero nested anchors. 43 graph assertions + 17 picker assertions green,
including multi-grant resolution and direct-plus-via-aim dedup.

## Note carried over from V3.718

The References card still appears under Concepts in Alex's browser. That is not a
data problem — the doc is `level:'reference'` linked only to the grant — but the
pre-V3.718 coercion of unknown levels to `'concept'`, running in whatever build
his browser has. The fix is in the code; it cannot take effect until that code is
the code being served. **There is no data-side workaround**: under the old build,
*every* level it does not recognize becomes a concept.
