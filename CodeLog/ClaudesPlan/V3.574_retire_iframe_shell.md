# V3.574 — Retire the persistent iframe shell (back to fast multi-page app)

## Goal

Make the Ourlab phone app functional again. After V3.573 introduced a
persistent iframe shell for reload-free tab switching, the user reported
"nothing is showing up anymore." A full on-device debug confirmed the
shell is fundamentally unworkable in Capacitor's WKWebView, so this
version retires it and returns the app to a normal multi-page navigation
model — the proven, working architecture.

## Problem

The V3.573 shell (`app-shell.html` hosting each tab as a kept-alive
same-origin iframe) hit an intractable WKWebView limitation:

1. **Auth doesn't cross frames.** The native Google sign-in resolves in
   the shell's top frame, but that session never propagated into the tab
   iframes. IndexedDB auth persistence is not shared across same-origin
   frames in this WKWebView. A simulator screenshot proved it: the shell
   top bar rendered the signed-in avatar ("AM") while the *same* My Day
   page inside the iframe was completely blank — no data.
2. **Sharing the instance breaks writes.** The attempted fix — pointing
   the iframe at the parent's Firebase instance (`window.firebase =
   window.parent.firebase`) — made reads work but broke **every write**:
   `DocumentReference.set() ... Data must be an object, but it was: a
   custom Object object`. Firestore rejects objects constructed by a
   different frame's `Object` constructor (cross-frame `instanceof` fails).
3. **`browserLocalPersistence` didn't rescue it.** Forcing localStorage
   persistence (which *is* shared cross-frame) so each iframe runs its own
   authenticated instance was theoretically sound, but the on-device
   result was still an authenticated-blank iframe.

There is no viable cross-frame path. Reads OR writes always break.

## Approach

Retire the shell. Each tab becomes a normal top-level page navigation
again — exactly how the RM web app works, and how the app worked before
V3.573. At top level there is one frame, so Firebase auth persists and
Firestore reads + writes both work with zero cross-frame issues.

The reload cost that motivated the shell is already mitigated: V3.572
vendored Firebase locally, painted the app background at parse time, and
removed the splash flash, so per-page loads are fast.

### File-by-file

- **`OurlabMobile/scripts/sync-rm.mjs` (step 3)** — entry `index.html`
  redirect changed from `/rm/pages/app-shell.html` back to
  `/rm/pages/my-day.html`. One line + comment rewrite explaining why.
- **`rm/js/firebase-bridge.js`** — remove the shell-era persistence
  forcing: drop the explicit `setPersistence(browserLocalPersistence)`
  block and the one-shot `updateCurrentUser` IndexedDB→localStorage
  re-persist. Keep the `ourlab-authed` localStorage paint hint (used by
  `mobile-shell.js`'s `ensureAuthGate` to skip the loading splash for a
  returning user on navigation). Also drop the now-unused
  `_persistMigrated` flag.

### Left in place (inert)

- `rm/pages/app-shell.html` + `rm/js/app-shell.js` — orphaned, nothing
  navigates to them. Kept in case a future WKWebView gains cross-frame
  auth; otherwise dead code.
- Shell-parent detection in `mobile-shell.js`, `chat.js`, `tasks.html`,
  `surface-guide.js` — dormant for top-level pages (`window.parent ===
  window` ⇒ checks never fire). Harmless; left to avoid churn.

## Data model changes

None. No Firestore paths, rules, indexes, or scope changes.

## Out of scope

- Deleting the orphaned shell files (optional future cleanup).
- Any new no-reload navigation scheme. If reload speed becomes a concern
  again, the answer is per-page load optimization, NOT an iframe shell.

## Release ritual

- `sw.js` CACHE_VERSION 547 → 548.
- CHANGELOG + ARCHITECTURE + this plan doc.
- **Deploy:** OurlabMobile rebuild (sync + `cap sync ios` + Xcode) — the
  app-side entry change. Web side is **FTP-only** (`rm/js/firebase-bridge.js`
  + `sw.js`), no Firestore rules / indexes / functions deploy.

## Rollback

Fully reversible: git-revert the two edits and re-run the OurlabMobile
build. No data migrations, no rules changes. (Reverting would restore the
broken shell, so there's no reason to.)

## Open questions

- None blocking. The fix is verified for the core regression (My Day
  loads live data top-level). Chat tap-to-open and Add-Task writes are the
  same top-level page class as My Day and as the working web app, so they
  follow structurally; final confirmation is a user tap on the simulator.

## Verification

1. Cold-launch the app → lands on My Day, **loads live data** (focus
   section, plan, week strip), avatar shows a connected auth ring. ✅
   (verified on simulator).
2. Tap **Chat** → conversation list loads; tapping a person/channel opens
   the thread (no longer suppressed by embed mode).
3. Tap **Tasks → + Add Task** → the fold-up sheet saves a task (write
   succeeds — no cross-frame Object error).
4. Tab switches reload but are fast (local Firebase, no splash flash).
