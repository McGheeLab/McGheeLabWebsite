# V3.724 — A card created from a parent is actually attached to it

## The report

Alex: *"when i am within a grants/grant and i add a new aim via the + New aim
button, that aim does not automatically get attributed to the grant we are
editing. It does get placed in the aims section as unattributed. Look for other
things that can be added to any of these surfaces and dont get attributed
automatically to the parent."*

## The bug was not in the button

`research.js`'s handler was correct:

```js
var ck = RD.LINK_KEY[detail.level];      // 'grant_ids' for a grant
var cs = {}; if (ck) cs[ck] = [detail.id];
RESEARCH_COMPOSER.openCreate(level, afterMutation, { links: cs });
```

`openCreate` merges the seed into the form model, and its own export comment has
promised since V3.554 that this *"auto-links back"*. But the composer's `save()`
builds `payload` from **form fields only** — title, abbr, icon, colour,
one-liner, template answers, description — and never carries `f.links`. So the
seed prefilled the form and was dropped on the floor; `RD.create` wrote
`links: {}`.

Nothing threw. The card *was* created, which is why it looked like it worked.
The defect had been latent since the seed parameter was introduced, and only
became visible when V3.719 started grouping aims under their grant and the
orphans piled up under "No grant yet".

It affected **every** "＋ New &lt;child&gt;" button on every level: a grant's aims
and outputs, a concept's grants and outputs, a specialty's concepts.

## Fixes

1. `payload.links = seededLinksFor(level)` — the seeded parent links, filtered
   through `PARENTS[level]`.
2. **The filter matters** because the seed is computed before the form opens and
   the level tabs let you change your mind afterwards; without it, switching to
   'concept' would have written `grant_ids` that no renderer reads.
3. The level tabs now offer only levels that can genuinely hang off the seeded
   parent. From the hub (no seed) every level is still offered.
4. A card created from a parent inherits its `member_uids` / `member_roles`, so a
   new aim starts with the grant's people rather than empty.

## The audit Alex asked for

| Surface | Verdict |
|---|---|
| `openCreate` with a seed (every ＋ New child button) | **BROKEN — fixed here** |
| `openGrantIdea` (new grant from a concept) | passes `links` straight to `RD.create` — fine |
| `openOutputLinker` → `ensureCard` + `setParentLink` | fine (key from `LINK_KEY` since V3.717) |
| V3.717 grant migration | passes `links` — fine |
| Roadmap experiments / analyses | stored on the card doc — attributed by construction |
| Roadmap reference papers | `researchFoci/{id}/refs` subcollection — attributed |
| Media, overview blocks | on the card — attributed |
| `＋ Paper` (`openPaper`) | links the draft into the card's `draft_refs` — fine |
| Hub "⤵ Add existing paper" | deliberately unparented — there IS no parent at hub level; V3.719's amber "no grant yet" chip is what surfaces the result |

## Guard

`scripts/tests/v3724-selftest.html` (16 assertions, in `run-all.sh`'s browser
layer) drives the real composer for all five parent → child pairs and asserts
what `create()` was called with, plus the level-tab invariant and the
no-seed hub case.

**Why a browser test and not a node one:** every other layer was already correct.
The data layer, the `LINK_KEY` table and the handler all pass their own tests;
the contract was even documented. The only thing that catches this is clicking
the button and reading the write. Verified honestly — the suite reports
`links: {}` against the pre-fix behaviour and `{grant_ids:['gels-career']}`
after, so it fails for the right reason rather than passing vacuously.

**The lesson:** a "prefill the form from a seed" parameter is two obligations —
show it, and save it. This one did the first and was written as though it did
both, and the doc comment made it read as tested.
