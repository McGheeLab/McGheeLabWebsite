# V3.929 — Scientia on this computer is the lab's, and in step within seconds

## Goal

Gabe (27 Oct 2026), after installing V3.928: (1) syncing works but slowly unless the app is refreshed; (2) the pills and
the rest of the lab's features (the website's Scientia) are not in the installed app; (3) retire the old way of running
it. The shared lab layer must not change.

## (1) Why it was slow, and the fix

The app's own window long-polls its server, so a change that reaches this computer shows at once; the delay was before
that. The bridge opened a new HTTPS connection for every request (urllib), and on Gabe's network about one new connection
in eight hung until its timeout (measured: 4 / 30 failed, each ~6–21 s; the bridge waits up to 30 s), so the sync stalled
again and again. One kept-open connection: 0 / 30 failed, 0.10 s median (0 / 40 against the lab cloud with the key,
0.17 s). `labsync.HubConn` is that connection (short connect timeout, one retry on a fresh one); `keep_alive()` routes
the bridge's cloud requests through it without editing the bridge (the vendored copy stays byte-for-byte the lab's).
`serve.py` uses the same connection for pairing and the RM calls.

## (2) The lab layer on this computer, unchanged

`lab-mode.js` returns unless `window.SIS_TARGET === 'web'`. The desktop build now loads it as it is, inline, after the
app, with `window.SIS_TARGET = 'web'` and `window.SIS_DESKTOP = true` set before the app (between `<!--sis-desktop-->`
markers, which the canvas export strips). What it expects from the website, the app's server provides:
- `api/rm/*` → the lab hub as this computer's key (`rm_proxy`, the kept-open connection); without a key, an "offline"
  answer instead of an error.
- `api/rec/part`, `api/rec/parts`, `api/rec/compose` (the one recorder) → parts in `recordings/.parts/<rid>/`, joined into
  `recordings/<name>.<ext>` in the notebook folder (named as the app's own recorder names them); the bridge carries the
  file to the cloud like any recording.
- `/rm/js/recorder-core.js`, `speech-to-text.js`, `stt-device-worker.js` → bundled copies (`scientia/vendor/rm/`,
  refreshed by `scientia_build.py`); any other `/rm/…` address → 302 to the site (RM's pages open there).
- The host-page bridge (`rm-read`, `rm-report`) falls back as it does outside the Lab Notebook.
What the computer keeps (`23d-desktoplab.js`, run by the build right after the lab layer): the Activity and Data tabs and
views (folder handles need the computer); the ✓ is the app's own (`23b`, offline, reported by the hub on sync) and the
lab's `.lab-mw` is hidden there.

## (3) The old way, retired

On Gabe's computer: the old app folder (`~/Scientia In Situ/app`, the private Scientia-In-Situ repo) is an archive — its
`launch.bat` and `scientia-cloud.py` are renamed `*.retired` with a note; the installed app (V3.928) starts with Windows
and runs the sync itself.
