# V3.433 — Calculator inputs obey their (driven) bounds

## Context

Alex, in demo 2: "on the document viewer I am able to write in a value
greater than the max set by our constant." The cap→max param binding
set the number input's HTML `max`, but `type=number` doesn't block
typing past it — `renderCalculator`'s input handler stored
`parseFloat(inp.value)` unclamped, so the math ran on over-cap values.

Policy (Alex's choice): the rail always holds — if the driven cap later
drops BELOW an already-saved value, the saved value snaps down.

## Change (`rm/js/protocol-widgets.js`, renderCalculator only)

- `effBounds()` extracted from `applyBounds()` (driven min/max via
  `drivenNum`, fallback static `v.min`/`v.max`) + `clampBounds(n)`.
- **Keystrokes**: the STORED override is clamped on every `input`
  event — the symbol table never sees an over-cap number. The field
  text is left alone mid-typing ("15" may transit "1").
- **Commit** (`change`/blur): the field text itself snaps to the
  clamped value (+ value label).
- **Mount**: a saved override from an earlier session outside the
  current bounds is clamped before the field seeds (`needsReseed`
  rebuilds the table before outputs paint, existing mechanism).
- **Cap moves**: the per-control refresher re-clamps a saved override
  that the moved bound now excludes, then folds it into the table via
  the existing `reseedPending` next-tick recompute (same pattern as
  driven defaults).
- Sliders are inherently bounded; the added clamps are no-ops there.

## Verification

- No DOM harness — browser probe (sw 406): lesson-2 doc, dose max
  driven by upper_cap=100 → type 999, field snaps to 100 on commit and
  outputs never flash an over-cap value; drop upper_cap to 50 → saved
  dose 90 snaps to 50 live, math re-runs; raise the cap back → the
  clamped value stays (no un-snap; it's the stored override now).
- `node --check` passes; full scratchpad suite unaffected (752 ok).
