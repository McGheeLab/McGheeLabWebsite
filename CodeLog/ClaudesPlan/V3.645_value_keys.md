# V3.645 — Value keys & inventory refs in the paper builder

## Context

Numbers and named materials get retyped across a manuscript and drift.
"Needle-to-target error is 0.5 µm" appears in the abstract, results, and
discussion; when the analysis is rerun and the number becomes 0.6 µm, three
places have to be found by hand and one gets missed. Same for materials: a
24-well plate's catalog number is typed once in Methods and once in a table,
differently.

Alex wants to write with a **key** where the value goes, define the value once,
and have the draft resolve it exactly:

```
Needle-to-target error is [!val:N2TError] and the minimum reliable dispense
is [!val:MRD] per channel. We utilized a 24 well plate [@item:24WP] to hold
fibroblast culture media made of FBS [@item:FBS_CC].
```

with `[!val:N2TError] = 0.5 µm`, `[!val:MRD] = 10 µL`, and the `[@item:]` keys
resolving out of the **lab inventory** — the same relationship `[@key]` already
has with the lab library. Clicking any key folds out **every sentence it appears
in**, so the writer sees what work that number is doing before changing it. In
the final draft each key resolves to exactly what is written to the right of the
equals sign.

Decisions made with Alex:

- **Two namespaces, one rule.** `[@…]` = a reference to a **shared lab record**
  (`[@smith2024]` → library, `[@item:24WP]` → inventory). `[!…]` = a reference
  to something **inside this paper** (`[!fig:]`, `[!sec:]`, `[!eqr:]`, and now
  `[!val:]`). Values are paper-local, so they take `[!val:]`; inventory is
  lab-global, so it takes `[@item:]`.
- **Prefixed, never bare.** `[@item:24WP]`, not `[@24WP]` — an item key and a
  citation key must never be able to shadow each other.
- **A value is text, with an optional number+unit split** — catalog strings are
  plain text; measured quantities carry a real number and unit so rounding is
  controlled in one place.
- **A searchable picker is required** for choosing inventory items.

## Approach

The builder already has everything this needs. Body text is plain source in a
`Y.Text`; chips are a *projection* re-derived on every render, and each chip
carries `data-src="<exact source token>"` so `serializeChipDom`
([paper-editor.js:6612](rm/js/paper-editor.js#L6612)) round-trips it losslessly.

**`equation_library` is the precedent to copy.** It is already a per-paper table
of user-named entries, inserted via a picker, referenced as `[!eqi:<slug>]`,
resolved by `getInlineEquationById`
([paper-editor.js:7118](rm/js/paper-editor.js#L7118)), and serialized into the
`.paperbundle`. `[!val:]` is structurally identical minus KaTeX.

### One table, two entry kinds

`[!val:]` and `[@item:]` are the same feature with different value *sources*, so
they share one per-paper table, one usage index, and one export pass:

```js
// newValueEntry() — rm/js/paper-schemas.js, beside newEquationLibraryEntry:418
{
  id,                    // 'val-xxxx'
  key,        // 'N2TError' | '24WP'  — the token slug, unique per paper
  kind,       // 'text' | 'number' | 'inventory'
  note,       // 'n=32, SD 0.08' — shown in the table + chip tooltip, never printed

  // kind:'text'
  value,      // printed verbatim

  // kind:'number'
  num,        // 0.5
  unit,       // 'µm'
  sigfigs,    // optional; rounds at render+export time only

  // kind:'inventory'
  inv_id,          // inventory doc id
  inv_kind,        // 'item' | 'chemical'
  snapshot: { name, vendor, catalogue_number },
  format,          // '({vendor} {catalogue_number})'
  refreshed_at,
}
```

Splitting `text` from `number` avoids a mode where a typed string and a numeric
field silently disagree. `kind:'number'` prints `num` (rounded per `sigfigs`) +
`unit`; `kind:'text'` prints `value` verbatim.

### Teaching six places that `[@item:` is not a citation

This is the real cost of the `[@…]` namespace and the part most likely to ship
broken. Today `[@…]` is matched by a wide-open `/\[@([^\]]+)\]/g`
([paper-export-tex.js:830](rm/js/paper-export-tex.js#L830)) and the key
validator already permits colons — so `[@item:24WP]` currently parses as a
citation with key `item:24WP` and would compile to `\cite{item:24WP}`, an
undefined citation in the bibliography.

Every one of these needs an `[@item:` branch **before** its citation branch, or
an explicit exclusion:

| Where | What breaks if missed |
|---|---|
| `renderParagraphHtml` [:6031](rm/js/paper-editor.js#L6031) | item renders as an unknown-citation chip |
| `renderChipsOnlyHtml` [:6507](rm/js/paper-editor.js#L6507) | chip reverts to raw text on focus |
| `paragraphTextToTex` [:830](rm/js/paper-export-tex.js#L830) | `\cite{item:24WP}` → undefined citation in the PDF |
| `getCitedKeysInPaper` [:7341](rm/js/paper-editor.js#L7341) | item keys pollute the References page's "cited" list |
| `collectCitationKeys` [:1336](rm/js/paper-export-tex.js#L1336) | item keys enter `refs.bib` as phantom entries |
| `paper-cite-style.js` [:64](rm/js/paper-cite-style.js#L64) | items consume citation numbers, shifting every `[1]` |

A single shared predicate (`isItemToken(inner)`) used at all six sites keeps
them from drifting, since they are otherwise hand-synced.

### `[@item:]` stores a snapshot, and this is load-bearing

Three independent reasons, all hard constraints:

1. **Size.** `inventory` is **3,481 docs ≈ 1+ MB on the wire**
   ([api-routes.js:157](rm/js/api-routes.js#L157)). The builder must never pull
   that to paint a chip.
2. **Archival correctness.** A submitted manuscript must not silently change
   because someone edits an inventory row two years later — and inventory ids
   are *not* stable under rename (the id encodes vendor + name + acquisition
   date) and have no uniqueness check on insert, unlike library citation keys.
3. **Permissions.** `match /inventory/{itemId}` allows read only if
   `isLabMember()` ([firestore.rules:1783](firestore.rules#L1783)) — there is no
   public read path. A shared or published paper that resolved live would 403
   for any non-lab reader. Rendering from the snapshot never touches the
   collection.

So the picker copies `{name, vendor, catalogue_number}` onto the paper at pick
time and the chip renders from that copy. A per-entry **↻ Refresh from
inventory** button, plus an "N items differ from inventory" banner on the Values
page, re-pulls deliberately.

Fields are `name`, `vendor`, `catalogue_number`
([inventory.js:66-67](rm/js/inventory.js#L66)) — exactly Alex's `(Nest M774JC)`
→ `({vendor} {catalogue_number})`. There is **no `unit` field** on inventory, so
`kind:'number'` units stay user-typed.

### The picker — reuse `PROTOCOL_INVENTORY`, do not write a fourth

[protocol-inventory.js](rm/js/protocol-inventory.js) is the only one of three
existing inventory pickers factored as a reusable module, and it already is what
Alex asked for:

- `ensureList()` (:66) — memoized, in-flight-deduped, merges **both**
  `inventory/items.json` and `inventory/chemicals.json`. Alex's example spans
  them (a plate is an `item`, FBS is a `chemical`), so the merge is required.
- `findMatches(text)` (:137) — the search: catalog# verbatim +15, CAS +15, name
  substring +10, vendor +8, formula +3, category +2, tie-broken by stock.
- `openPicker({onPick, anchorEl})` (:409) — anchored, viewport-clamped popover
  with a search input ("name, vendor, catalog #, CAS, category…"),
  `role="listbox"`, and ↑/↓/Enter/Esc navigation.
- `formatLabel(entry)` (:217) → `"Name (Vendor, cat. X, CAS Y)"`.

Its own header (:18-21) names the copies in `paper-editor.js` and
`lab-notebook.js` as tech debt; this feature must not add a fourth.

**One unified insert flow**, so defining and inserting are not separate chores.
`Insert value` in prose opens a picker listing the paper's already-defined keys
first, with a **Search inventory…** section beneath that queries `findMatches`
live. Picking a defined key inserts its token; picking an inventory hit prompts
for a short key, creates the `kind:'inventory'` entry with its snapshot, and
inserts `[@item:<key>]` — one action, not three.

Insertion itself reuses `_insertAtSavedCaret`
([paper-equations.js](rm/js/paper-equations.js) ~:5110), which already detects a
bracket token, builds chip DOM via `renderChipsOnlyHtml`, and dispatches a
synthetic `InputEvent` so the Y.Text diff path picks it up — the user never sees
raw `[…]` flash. Caret survives the picker's focus steal via the existing
`rememberFocus` / `lastFocusedCaret` pair.

### Relationship to the existing `[!inv:]` token

Protocols already have `[!inv:<id>]`
([protocol-inventory.js:256](rm/js/protocol-inventory.js#L256)) — a direct
reference to a global inventory id, resolved live. `[@item:KEY]` is deliberately
different: a **paper-local key** pointing at an inventory item, carrying its own
snapshot and print format. The two coexist over the same module, and no
`inv_key` backfill across the 935 existing inventory records is needed — the
paper-local key *is* the short name.

Note `paper-editor.js:3020-3290` is inventory-picker copy #2, whose
`insertInventoryItem` (:3244) writes a *frozen prose sentence* plus
`attrs.item_ref`. That is 80% of this feature minus the live link. Leave it in
place this release; retiring it is a separate cleanup.

### Storage — the Y.Doc, no Firebase deploy

`value_library` becomes a fourth root Y.Array beside `equation_library` in the
idempotent bootstrap at
[paper-editor.js:248-273](rm/js/paper-editor.js#L248). It lives in
`papers/{id}/yjs_updates`, already covered by existing rules — so this ships
**FTP-only, no `firebase deploy`**. It also gets collaborative editing and undo
for free, which `paperExports/{paperId}` (a set-merge blob) would not.

### Rendering

Chips show the **resolved value**, not the key — that is the point. Both follow
`renderInlineEqLibraryChip`
([paper-editor.js:6326](rm/js/paper-editor.js#L6326)): emit
`contenteditable="false"`, stamp `data-src` with the exact source token, and
render an unknown-key variant when the key is undefined.

- `.pe-val-chip` — resolved text, faint underline marking it dynamic; `title`
  shows `key — note`.
- `.pe-item-chip` — the formatted inventory string; `title` shows the item name.
- `.pe-val-chip-unknown` / `.pe-item-chip-unknown` — dashed `[?N2TError]`, so a
  typo'd key is visible rather than silently blank.

In the **Document view** the chip styling drops so the page reads as final
prose — a post-mount class toggle following `_resolveSecRefs`
([paper-doc-view.js:1434](rm/js/paper-doc-view.js#L1434)). No re-tokenizing:
doc view already calls the editor's renderer.

### The fold-out usage panel

`getCitedKeysInPaper` ([paper-editor.js:7341](rm/js/paper-editor.js#L7341))
already walks every prose surface (paragraph/figure/subheading/list `body`,
`skeleton_items[].text`, table `attrs.caption`) but discards positions. Add
`getKeyUsages()` — the same walk, keeping `{key, sectionId, blockId, offset}`.

For each hit, extract the enclosing sentence from the **source** text and render
it through `renderParagraphHtml` so the snippet shows resolved chips. Sentence
bounds come from `.`/`?`/`!` + whitespace, falling back to the whole paragraph
when none is found. Extracting from source (not rendered text) means a value
like "0.5 µm" cannot create a false sentence break.

Two entry points, both existing patterns:

- **Click a chip in prose** → the capture-phase `mousedown` handler at
  [paper-editor.js:6729](rm/js/paper-editor.js#L6729) (capture is required — it
  must beat the contenteditable focus that destroys the chip attrs).
- **A row on the Values page** → expands in place, `Set<key>` expander state
  mirroring `expandedClaimEvidence`
  ([paper-editor.js:4746](rm/js/paper-editor.js#L4746)).

Each usage row shows its section label and jumps via the existing
`.pe-block[data-block-id]` + `scrollIntoView` path. A usage count on every row
makes an unused key ("0 uses") obvious.

### Final resolution — export

- **LaTeX** — two passes in `paragraphTextToTex`
  ([paper-export-tex.js:697](rm/js/paper-export-tex.js#L697)), with the other
  token passes and **before** the markdown passes, each wrapped in `protect()`
  so an injected value containing `~` or `^` cannot be eaten by the sub/sup
  regexes. Values run through the existing `escapeTex`
  ([:1436](rm/js/paper-export-tex.js#L1436)). The `[@item:]` pass must precede
  the citation pass at :830.
- **`paper.md`** — `buildMarkdown`
  ([paper-export-bundle.js:208](rm/js/paper-export-bundle.js#L208)) currently
  dumps raw source. Expand both tokens: the `.md` is a *rendering* for humans.
- **`paper.json`** — keeps raw tokens plus the serialized `value_library`, so
  the bundle round-trips losslessly. This split is the existing contract.

## Traps

1. **The six citation sites.** Miss any one and item keys leak into the
   bibliography — the failure surfaces in the compiled PDF, not the editor.
2. **Both renderers, always.** A branch in `renderParagraphHtml` but not
   `renderChipsOnlyHtml` gives a chip that works blurred and turns into raw
   `[@item:x]` the moment you click into the paragraph.
3. **`data-src` must be the exact source token.** `serializeChipDom` needs no
   change *because* of this; get it wrong and typing near a chip silently
   corrupts the paragraph.
4. **The repaint guard**
   ([paper-editor.js:6828](rm/js/paper-editor.js#L6828)) short-circuits on
   paragraphs with no known token prefix. Without adding `[!val:` and `[@item:`,
   editing a value will not repaint chips already on screen — it looks exactly
   like the edit didn't save.
5. **Never bulk-load inventory outside the picker** — 1+ MB, and it puts a
   lab-member-only read on the paper-open path, 403-ing non-lab viewers of a
   shared paper.
6. **Key uniqueness** is enforced in the editor UI only (Yjs has no constraint);
   on collision, last-write-wins and the table must flag the duplicate.
7. `paper-export-tex.js` contains a byte that makes GNU grep treat it as binary
   — use `grep -a` or get silent zero hits.

## As built — where the implementation departed from the plan

Five changes, each because building it surfaced something the plan didn't know.

1. **`formatValueEntry` is the single resolver** (`paper-schemas.js`). The plan
   named six places that must agree about *citations*; the same reasoning
   applies to *resolution*. The editor chips, the Document view, the `.tex`
   export and `paper.md` all print through this one function, so the editor and
   the compiled PDF cannot disagree about what the paper says.

2. **`walkProseTexts` extracted** (`paper-editor.js`). `getKeyUsages` needs the
   same traversal `getCitedKeysInPaper` already had. Rather than a second
   hand-synced walk — the exact failure mode this release is guarding against —
   the existing one was lifted out and both now call it. A key used in a table
   caption therefore cannot be visible to the bibliography but invisible to the
   usage panel.

3. **Document view is pure CSS, not a post-mount JS pass.** The plan proposed
   mirroring `_resolveSecRefs`. Unnecessary: `.pdv-scale .pe-val-chip { … }`
   neutralizes the chip styling with nothing to keep in sync, because doc view
   already renders through the editor's renderer. An *unresolved* key
   deliberately keeps its warning colour there.

4. **`rm/css/inventory-picker.css` (new).** The picker's styles lived in
   `protocol-editor.css`, which the builder page does not load — so reusing
   `PROTOCOL_INVENTORY` would have loaded the picker's JS and none of its CSS
   and opened an invisible popover. The `.proto-inv*` rules moved verbatim into
   a shared file now linked by both `protocols.html` and `paper-builder.html`.

5. **An unknown key exports as `[?KEY]`, not a `%` comment.** The first
   implementation copied the `[!eqi:]` precedent of emitting
   `% [missing …]`. `%` runs to end of line in LaTeX, so mid-paragraph that
   silently deletes the rest of the sentence from the PDF. Caught by the export
   test; `[?KEY]` matches the editor chip and shows up in the proof.

**Also fixed in passing:** `paper-writing-guide.js`'s `no-citations` check tested
`body.indexOf('[@') === -1`, so a Methods paragraph whose only bracket token was
a reagent would read as "cited" and the check would stop firing on it.

**Noted, not changed:** `[!eqi:]` still exports `% [missing inline equation: …]`
and has the same end-of-line hazard. Left alone — it is a different feature and
changing its output is Alex's call.
