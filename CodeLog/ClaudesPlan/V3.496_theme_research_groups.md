## Goal

On a Lab Theme's detail page, show students **which research groups (PIs)
dominate this theme** — e.g. *Burdick* under "Granule-based in-vitro models" —
so a newcomer immediately sees the field's key labs and can read by group. PIs
are derived from the **last author** of the theme's tagged papers, ranked by a
**relevance-weighted** paper count, curated per-theme (canonical name,
institution, name-variant merges, note, star), and used to **filter the existing
Papers list**. A second new section recommends the **top related themes** to
explore next.

## Problem

The theme detail view today ([rm/js/library-themes.js](../../rm/js/library-themes.js))
lists a theme's papers as one flat, vote-sorted list. Nothing surfaces the
*people behind the field*: a student can't see that five of the papers are
Burdick-lab work and that Burdick is the granular-hydrogel pioneer they should
follow. There's also no "where do I go next" — themes are siblings with no
declared relationships. And library authors are stored as bare
`{family, given}` (from `functions/library-lookup.js`), so there's no robust way
to tell two same-initial PIs apart or to show an institution.

## Approach

Four coordinated slices, all shipping in one version (user decision: one
combined V3.496). Everything is lab-member gated (matches the rest of Themes);
all reads are whole-collection/subcollection gets or snapshots with **client-side
sort** — **no new composite indexes** (keep the V3.367 invariant).

### 1. Author enrichment: ORCID + affiliation (data pipeline)

- **`functions/library-lookup.js`** — in the CrossRef branch (currently
  `authors.push({ family: a.family || '', given: a.given || '' })` at ~line 98),
  also capture:
  - `orcid`: `(a.ORCID || '').replace(/^https?:\/\/orcid\.org\//i, '')` (CSL puts
    it as a URL; store the bare `0000-…` id),
  - `affiliation`: `(a.affiliation && a.affiliation[0] && a.affiliation[0].name) || ''`,
  - `sequence`: `a.sequence || ''` (CrossRef `'first'|'additional'` — informational).
  PubMed/arXiv branches (~152, ~205) have no ORCID; leave them `{family, given}`
  (those papers fall back to family+initial keying — acceptable).
- **`rm/js/library-metadata.js`** — `buildPaperItem` already stores
  `authors: meta.authors || []` verbatim, so the new fields pass through with
  **no client change** for fresh imports.
- **Backfill existing papers** — ride the existing bulk sweep in
  **`rm/js/library-recheck.js`** (`LIBRARY_RECHECK.open`): after each per-paper
  `libraryLookup`, **fill-only** merge `orcid`/`affiliation` onto the stored
  authors matched by `family`+`given` (never replace a name; only fill a blank
  `orcid`/`affiliation`). Same fill-only merge added to
  **`rm/js/library-refresh.js`** `fullRefresh` so the per-paper ↻ button also
  enriches. This makes the backfill a user-run sweep, not an automatic migration.

### 2. Derived research groups + curation

- **Derive** (in `library-themes.js`): for each paper tagged in the theme, the PI
  is the **last** author (`authors[authors.length-1]`). Group key preference:
  1. `orcid` when present (globally unique — auto-merges name variants, splits
     same-initial PIs for free),
  2. else `slug(family) + '-' + firstInitial(given)` (`burdick-j`),
  3. papers with no authors → an `__unattributed` bucket, always ranked last and
     never counted in the default top-5.
  Then **remap** every raw key through the curation merge-map (see below) so
  merged variants collapse to one canonical group.
- **Curation** stored per-theme at **`labThemes/{themeId}/groups/{groupKey}`**
  (concurrency-safe one-doc-per-group, matching the notes precedent), fields:
  `{ key, canonical_name, institution, note_html, starred, merged_keys: [rawKey…],
  created_by, creator_name, created_at, last_editor, modified_at }`.
  - `canonical_name` + `institution` → the chip/header label ("Jason Burdick ·
    UPenn"); `institution` pre-fills from the most-common captured `affiliation`
    when blank.
  - `merged_keys` → other raw keys folded into this group (fixes a wrongly-split
    PI, or peels one same-initial PI onto a new key = the "split" case).
  - `note_html` → per-lab rich text (sanitized with the existing `_sanitizeHtml`),
    complements the theme-wide Synthesis notes.
  - `starred` → ⭐ pins the group above the score order.
  - Any lab member creates/updates; delete = creator-or-admin.
- **Ranking** — `score(group) = Σ relevance` over the group's last-authored
  papers **in this theme**, relevance ∈ {Core 3, Supporting 2, Tangential 1}
  (see slice 3). ⭐-starred groups sort first, then by score desc, then by paper
  count, then by name. Each chip shows the label, in-theme score, and — as a
  secondary figure — the PI's **whole-library** last-author count (from the
  already-loaded `_papers` pool, deduped by the same key/ORCID). **Top 5 chips by
  default**, `＋ Show more` → 10 → all.

### 3. Per-paper relevance weight

- Stored as a **parallel map** on the item:
  `items/{id}.meta.library.theme_relevance: { [themeId]: 1|2|3 }`. Membership
  stays the boolean `meta.library.themes[]` array (untouched — `toggleTheme`,
  the `theme:` search token, and reader chips keep working). **Unset ⇒ weight 2
  (Supporting)** so pre-existing memberships preserve today's counts (uniform
  scale — relative order unchanged) and read neutrally until curated.
- **`rm/js/library-links.js`** — new
  `setThemeRelevance(itemId, themeId, weight)` writing the map entry (and
  clearing it when a paper is untagged, alongside the existing `toggleTheme`
  removal). Exported on `window.LIBRARY_LINKS`.
- Relevance is assignable **at add time and after**:
  - the themes-tab **Add-papers picker** (`_openAddPapersPicker`) gains a
    Core/Supporting/Tangential selector per checked row (defaults Supporting);
  - the **reader** theme chips (`library-paper.js` `_renderThemeEditor`) gain the
    same 3-way selector so relevance is set "at the time of adding" from the
    reader too;
  - each row in the theme's Papers list gets a small relevance pill to re-rate
    later.

### 4. Chip → Papers-list filter + Related themes

- **Filter**: clicking a group chip sets a `_groupFilter` key; `_renderPaperList`
  filters `_themePapers` to papers whose remapped last-author key === filter
  (👍 voting + "Start here" preserved within the filtered set). Active chip
  highlighted; an `× clear` resets. One list — no duplicate paper UI.
- **Related themes** ("Explore next"): stored at
  **`labThemes/{themeId}/related/{otherThemeId}`** `{ rank, added_by, added_at }`
  (directional: "from this theme, explore these"; concurrency-safe subcollection,
  same rules block as groups). Rendered as a ranked strip of cards linking to
  `library.html?tab=themes&theme=<id>`, **top 5 → show more**.
  - **Manual** add / remove / reorder (▲▼, the PMR `section_order` pattern).
  - **Suggest** helper: a "✨ Suggest" button ranks candidate themes by
    **papers shared** between this theme and every other theme (computed from the
    already-loaded `_papers` — each paper's `themes[]`), plus a bonus for cached
    cross-citation overlap (`meta.library.cited_by`, where present). Suggestions
    are one-click-to-add proposals only — **never auto-committed** (citation data
    is only partially cached, so it can't be authoritative).

## Data model changes

| Path | Shape | Scope / rules |
|---|---|---|
| `items/{id}.meta.library.authors[]` | now also `orcid`, `affiliation`, `sequence` (fill-only; existing `{family,given}` preserved) | rides existing items rule — no rules change |
| `items/{id}.meta.library.theme_relevance` | `{ [themeId]: 1\|2\|3 }` (unset ⇒ 2) | rides existing items rule — no rules change |
| `labThemes/{themeId}/groups/{groupKey}` | `{key, canonical_name, institution, note_html, starred, merged_keys[], created_by, creator_name, created_at, last_editor, modified_at}` | member read/create/update, creator-or-admin delete |
| `labThemes/{themeId}/related/{otherThemeId}` | `{rank, added_by, added_at}` | member read/create/update, creator-or-admin delete |

**Indexes: none.** All group/related/relevance reads are whole-collection or
subcollection gets/snapshots sorted client-side (V3.367 invariant preserved).

## Out of scope (V3.496)

- **Library-wide author-identity / ORCID researcher profiles** — curation stays
  **per-theme**; the same PI recurring in another theme is re-curated there.
  (Global alias map is the front end of a bigger disambiguation project.)
- **Citation-count ("field influence") ranking** — we rank by weighted paper
  count, not summed citations.
- **Auto cross-cited clustering as the source of truth** — we only *suggest*
  related themes; manual rank is authoritative.
- **Co-senior (two last authors) attribution** — v1 credits the single last
  author only.
- **PubMed/arXiv ORCID capture** — CrossRef only this version.

## Rollback

- **Code:** git revert the working-tree changes + re-FTP; drop sw.js back.
- **Rules:** additive and harmless to leave deployed (they only grant access to
  new subcollections nothing else reads). Reverting is optional.
- **Function:** the enriched `libraryLookup` only adds author fields; safe to
  leave. Revert + redeploy if truly needed.
- **Data:** all writes are additive — `theme_relevance` map, `groups`/`related`
  docs, and fill-only author fields. Untagging clears the relevance entry.
  No destructive migration, no role flips.

## Open questions (flag during implementation)

1. **Same-initial PIs with no ORCID** (two "J. Wang") still collide on the
   family+initial fallback until someone runs recheck (to get ORCIDs) or peels
   them apart via `merged_keys` (the split case) — confirm the split UI is
   intuitive.
2. **Relevance default = Supporting (2)** for pre-existing memberships — verify
   that uniform default reads right once some papers are marked Core/Tangential.
3. **"All count" ranking** (Tangential = 1, not 0) is deliberate: enough
   tangential papers *is* a relevance signal (user call). A jammed-packing-sim
   paper's PI still gains +1 — intended.
4. **Whole-library secondary count** dedup should use ORCID when present, else
   family+initial — confirm it doesn't double-count a PI whose papers split
   across keyed/un-keyed variants.
5. **Suggest weighting** (shared-papers vs cross-citation bonus) — tune the
   ratio after seeing real theme overlaps.
