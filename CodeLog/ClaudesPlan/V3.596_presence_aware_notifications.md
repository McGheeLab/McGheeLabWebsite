# V3.596 — Presence-aware notification suppression

## Goal

Notifications currently fire on every surface — desktop browser, Ourlab
iOS app, PWA badge — regardless of whether the user is already looking at
the page the notification is about. Alex's report:

> if I am active and looking at the chat page either on the app or from the
> desktop, I don't want a notification about a new message. However, I still
> do want a notification about other things that I am not actively looking
> at — for example if I'm on chat and there is an equipment notification, I
> would still want the equipment notification.

Suppress a push when the user is demonstrably looking at the surface it
points at, and *only* then.

## Decisions (confirmed with Alex before implementing)

1. **Slack-style, cross-device.** Active on *any* surface → no push to *any*
   device. This is the only design that can silence a **backgrounded** iOS
   app, which cannot suppress locally without a Notification Service
   Extension. So the gate lives server-side.
2. **Per-channel grain for chat.** Sitting in `#general` still notifies you
   about `#random`.
3. **Generic across all surfaces**, keyed on the notification's existing
   target `url`. Equipment / tasks / scheduler / huddle inherit it, and so
   does every future notification type.
4. **Voice calls always ring** — an explicit `urgent` bypass.

## Design principle: FAIL OPEN

Missing, stale, malformed, or unparseable presence always means *send*.
Every predicate in `functions/helpers/presence.js` is written so the only
path to `true` is a positive match on fresh data. A bug in this feature must
never cost someone a notification they needed. 21 of the 35 fixtures in
`functions/test/presence.test.js` exist to pin exactly this.

## Approach

### Why here

Every push in the codebase funnels through
`sendToUsers(db, messaging, userIds, notif, appKey)` in
`functions/helpers/notify.js` — chat, voice-call, huddle (×6), equipment
(×3), tasks, task-market (×3), scheduler. **One filter covers all of them.**

And every notif already carries a target `url`
(`/rm/pages/chat.html?channel=<id>`, `/rm/pages/equipment.html`, …), so the
surface key needs no new taxonomy and no payload change.

### Why the desktop symptom happens

RM pages never load `push-notifications.js` (marketing-SPA only — see the
header comment in `rm/js/mobile-push.js`), so no RM page has a foreground
`onMessage` handler. The FCM SDK therefore treats **every** push as
background and `firebase-messaging-sw.js`'s `onBackgroundMessage` displays
it unconditionally, even with the chat tab focused. Suppressing server-side
means that SW never receives the push at all.

### Data model — `userPresence/{uid}`

```js
{ surfaces: { "<deviceId>": {
    paths:        ["/rm/pages/chat.html"],  // array so shells can publish panes
    contextIds:   ["chan-abc"] | ["*"],     // "*" = any context on this path
    visible:      true,
    lastActiveAt: <serverTimestamp>,
    client:       "web" | "app",
} } }
```

Keyed by **device**, not tab, so the map stays bounded by the user's real
devices and a desktop never clobbers a phone. Written with
`set({surfaces:{[id]:…}}, {merge:true})` — a deep map merge.

`lastActiveAt` is a **server** timestamp deliberately: a client whose clock
runs fast would otherwise look permanently fresh and permanently silence
its own notifications. (`isViewing` also rejects future timestamps outright.)

### Match rule

Suppress iff some surface has `visible === true`, a `lastActiveAt` within
`FRESH_MS` (150 s), a matching path, and either the `"*"` wildcard or the
notif's context id — and `notif.urgent !== true`.

Context id is parsed from the url query: first present of `channel`
(chat), `item` (huddle), `id`. A context-less notif matches any surface on
its path, which is exactly right for equipment/tasks/scheduler.

### Idle handling

Client-side, not a second server timestamp. The heartbeat only writes while
visible **and** non-idle (no `pointerdown`/`keydown`/`wheel`/`touchstart`
for 5 min), so a laptop left open on chat over lunch goes stale on its own
and notifications resume. Keeps the server rule to one freshness check.

### Why not widen `chatPresence`

`chatPresence/{uid}` already exists with a visible-gated heartbeat — but its
2-minute beat and 5-minute "online" window are far too coarse to gate a
push, chat's presence dots depend on those timings, and every RM page
would have to write into a collection that chat subscribes to wholesale.
New doc, new cadence.

## Files

**Server**
- `functions/helpers/presence.js` **(new)** — `filterByPresence`,
  `surfaceKeyFromUrl`, `isViewing`, `loadPresence` (chunked `getAll`, 100 at
  a time, matching `voice-call.js`), `normalizePath`.
- `functions/helpers/notify.js` — presence filter between the existing
  per-app pref filter and the token gather; logs a suppressed count.
  **Only `sendToUsers` is gated.** `recordFeedItems` (V3.594) still runs for
  the full recipient list, so a suppressed notification still lands in the
  My Day 🔔 feed — the catch-up surface keeps working.
- `functions/voice-call.js` — `urgent: true`.
- `functions/test/presence.test.js` **(new)** — 35 fixtures, plain node.

**Client**
- `rm/js/presence.js` **(new)** — the heartbeat. Self-installing IIFE.
- `rm/js/nav.js` — auto-injects it, same pattern and reasoning as the
  existing `injectPageTimeTracker`. **Zero HTML files change** (would
  otherwise have been 72).
- `rm/js/chat.js` — extracted the existing corner-alert `feedVisible`
  predicate into `isWatchingFeed()` and reused it for
  `publishPresenceContext()`, so there is exactly ONE definition of "am I
  watching this feed". Published from `render()` (dedupes internally, so it
  covers every state change that re-renders), from the scroll handler
  (`_autoScroll` flips without a render), and cleared in
  `pauseChat()`/`destroy()`, re-claimed in `resumeChat()`.

**Rules**
- `firestore.rules` — `userPresence/{uid}`: `read: isLabMember()`,
  `write: own uid`. Modelled on the adjacent `chatPresence` block.

**Version** — `sw.js` CACHE_VERSION 564 → 565.

## Deploy order

1. `firebase deploy --only firestore:rules` — **first**, or clients can't
   write presence.
2. FTP the tree (`rm/js/presence.js`, `nav.js`, `chat.js`, `sw.js`).
3. `firebase deploy --only functions` — all of them share `notify.js`.
   Safe last: no presence docs → gate fails open → today's behaviour.

**App-build dependency:** the Ourlab app bundles `rm/`, so the phone won't
*publish* its own presence until the next OurlabMobile sync + TestFlight
build. Until then the phone never suppresses on its own account — but
desktop presence *does* silence the phone, which is the main win and lands
on FTP. `presence.js` is injected by `nav.js`, so it needs no addition to
the sync-step injection list.

## Flagged, not addressed here

Pre-existing, found during exploration, independent of this change:

- `firebase-messaging-sw.js` `notificationclick` hardcodes
  `mcgheelab.github.io`, so on `mcgheelab.com` clicks always open a new tab
  instead of focusing the existing one.
- Web quiet hours are dead code — the SW reads them from IndexedDB
  `mcgheelab-prefs`; `rm/js/settings.js` only writes Firestore.
- No `tasks` row in the settings Notifications tab, though senders use
  `appKey:'tasks'` — that toggle can never be turned off.
- `meetings` and `activityTracker` toggles have no senders.
- No user-facing toggle for this suppression (default-on, no opt-out).
