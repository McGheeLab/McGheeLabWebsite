# V3.808 — Teachers post a classroom visit with no account

**Date:** 2026-10-19
**Alex:** "I need to be able to have teachers add engagement opportunities as a guest, so they
do not need to sign in. I believe there is a hurdle right now for teachers to spark an
engagement opportunity based on the fact that they would need to make a sign in."

## The hurdle

Today a teacher who wants a scientist to visit must sign in with Google, hold
`category:'teacher'` (an approved class), then walk steps 1–5 of the Engagement tab (listing →
lab approval) before step 6 lets them post an opportunity. Many teachers use district
Microsoft accounts, and the ask itself is small, so most never start.

## Goal

A teacher posts a visit in one form, with no account and no sign-in, and can still do
everything that follows: see sign-ups, accept one, send the confirmation email, cancel, close
a panel, withdraw. The signed-in path (`#/engage` steps 1–7) stays as it is.

## Design

### Identity = a private link

- Posting returns a random **manage token** (24 random bytes, base64url, 32 characters). The
  teacher's private page is `mcgheelab.com/#/invite-a-scientist/{token}`. The token rides in
  the URL **fragment**, so it never reaches a server log or a Referer header.
- The success screen shows the link with **Copy** and **Email it to myself** (a mailto to the
  teacher's own address). The browser also remembers posts made from it (localStorage, a
  convenience only). The admin row shows the link too, so the lab can resend it.

### Server: one HTTP function, `engageGuest`

`functions/engage-guest.js`. A POST with an `action`; every guest read and write goes through
it, using the Admin SDK. The rules on `engageRequests` / `engageOpportunities` stay uid-based
and unchanged for everyone else.

| action | what it does |
|---|---|
| `submit` | validates, rate-limits, writes `engageGuestPosts/{id}` (`pending`), pushes admins, returns the token |
| `get` | the post, its live opportunity, its sign-ups (presenter email only once accepted), reviews |
| `update` | edit, only while `pending` |
| `decide` | accept (date ∈ presenter's ticks ∩ opportunity dates, = `bookedDate` for a panel; students 1–500; copies the private address; books the opportunity; auto-declines the rest when full) or decline |
| `emailed` | stamps `emailedAt` on an accepted visit |
| `cancel` | un-books (reopens if dates remain), as step 7 does |
| `enough` | a panel with ≥1 accepted: decline the waiting ones, `booked` |
| `withdraw` | closes the opportunity, declines waiting sign-ups (accepted visits stay) |

Accept is a Firestore **transaction** over the request + opportunity. The auto-decline notes
are the panel's own wording. `recountOpportunity` (engage-notify.js) keeps the public counts.

Validation mirrors the form: required name/email/school/city/subject/grade/size/title, enums
for activity/format/school type, 1–12 dates, each today…+400 days in Arizona, HH:MM times with
end > start, no duplicates, presenters 1–6, an address when "at the school" is ticked, length
caps on everything.

Abuse limits: a hidden honeypot field, **5 posts per IP per hour**
(`engageGuestRate/{sha256(ip)}`, no client access), and at most **200 posts waiting for
review**. Nothing a guest writes is public until an admin publishes it.

### The lab reviews, then publishes

`rm/js/admin-teachers.js ?tab=engage` gains **Visit posts without an account**: the teacher
link to share, then one row per post (teacher, class, kinds, dates with past ones struck, the
private address, the note to the lab, posted/published/last-opened dates, the private link).
Actions: **Publish**, **Decline…** (an inline note, no prompt), **Email the teacher** (a mailto
worded for where the post stands: received / live / N sign-ups / declined), **Copy their
link**, **Open their page**.

**Publish** is one admin batch:

- `engageProfiles/guest_{id}` (approved listing, `guest: true`),
- `engageProfiles/guest_{id}/private/contact` (the address, so the existing admin Confirm
  path also works),
- a new `engageOpportunities` doc with `teacherUid: 'guest_{id}'`, `status: 'open'`,
- the post → `published` with `opportunityId`.

From there the presenter page and the request rules treat it like any other teacher's
opportunity, unchanged.

### Telling the teacher

The site cannot email (no mail server; the Gmail OAuth scope is read-only), and a guest has no
push token. So:

- `engage-notify.js` never notifies a `guest_…` uid. Without this, `notifyUsers` would create a
  `userData/guest_…/notifications` feed for nobody.
- On a guest sign-up it pushes **admins** instead ("…posted without an account, so email them
  from the admin Engagement tab").
- The admin row's button becomes **Tell the teacher (N sign-ups)**.

The private page says plainly that the McGhee Lab will email when someone signs up.

### The teacher's pages (`engage-guest.js`, route `#/invite-a-scientist`)

- **Form** (not AUTH_GATED): five short numbered cards.
  1. You and your school.
  2. Your class.
  3. The visit (title, kinds with hints, where, topic, one presenter or several together,
     date rows with from/to times; a new row copies the last row's times).
  4. Where visitors go (shown only when "at the school" is ticked; marked private).
  5. A note to the lab.

  Every error appears beside its field at once. An unsent draft survives a reload.
- **Private page**: status card (waiting for review / live / booked / dates passed / declined
  with the lab's note / withdrawn), the keep-this-link box, and sign-ups:
  - *waiting for your answer*: Accept… with date radios + students + note, or Decline…;
  - *coming up*: the confirmation email draft with Copy / Open in your email app / Yes, I sent
    it, plus Cancel this visit;
  - *past*: with the presenter's review;
  - *declined or cancelled*: collapsed.

  Then the post's details, and Edit (while pending), That's enough presenters, and Withdraw.
- **Same email.** The confirmation email is the signed-in panel's, moved out of its closure
  into `ML.EngageKit.buildVisitEmail(c)`. A before/after capture of every draft the demo
  teachers render (to, subject, body, mailto) is byte-identical.

### Entry points

- `#/teachers` shows a **"Just want a scientist to visit your class?"** card to everyone but a
  set-up teacher.
- The admin tab has the shareable link.

## Rules (`firestore.rules`)

- `engageGuestPosts/{id}`: read and write by `isAdmin()` only. It holds the teacher's email,
  phone, address and the token.
- `engageGuestRate/{key}`: `false`. It is server-only.
- `engageOpportunities` create gains `|| isAdmin()`, placed **last** so a teacher's own create
  never depends on the `users/` read. Publishing is the admin creating for `guest_{id}`, which
  is nobody's uid.

## Verification

- **Emulator.** `functions/test/engage-guest.test.js` runs `handle()` with the real Admin SDK
  against the Firestore emulator. It covers:
  - validation, honeypot and rate limit;
  - token lookup, and editing while pending;
  - an admin publish, written exactly as the admin tab writes it;
  - accept (location copied, booked, the other sign-up auto-declined), plus a date the
    presenter didn't tick;
  - emailed, cancel (reopens), a stranger's request id;
  - a panel and "enough", and withdraw before and after publish.

  Result: 50/50.
- **Rules `:test`** (local source). Allowed: admin creates for a guest, a teacher still
  creates their own. Denied: presenter or teacher creating for a guest, unapproved teacher,
  `pendingCount`, anonymous. Guest posts are admin-only, and the rate counter is no one's. The
  published guest listing and opportunity behave like any other (presenter list/sign-up
  allowed, private contact denied). Result: 24/24, calibrated by flipping two expectations
  (2 failures).
- **Teacher email refactor**: byte-identical before/after capture.
- **Headless.** The form and private page run against a stubbed function (`page.route`). The
  admin tab and `#/teachers` card are checked too.
- **After deploy**: GET health probe; an invalid token returns 404; an invalid submit returns
  400 and writes nothing.
- **Live loop (Alex).** Post as a teacher with no sign-in → publish in the admin tab → sign up
  as a presenter → accept on the private page → send the email.
