# V3.577 — Fix push registration never running on-device

## Goal

TestFlight push produced no banner on the phone. Make push actually
register on real devices.

## Problem

A layer-by-layer probe (device → FCM → APNs → function → Firestore)
established:

- The APNs auth key is valid — signing a provider JWT with the `.p8` and
  hitting `api.push.apple.com` directly returned `BadDeviceToken` for team
  `K346A9LM62` (auth accepted; only the dummy device token was bogus).
- FCM→APNs delivery works — a direct FCM send to the simulator's sandbox
  token succeeded once the key was in the matching (Development) slot.
- **The phone never registered a push token.** It didn't appear under iOS
  Settings → Notifications, which means it never *requested* notification
  permission.

Root cause in `rm/js/mobile-push.js`:

```js
function boot() {
  if (!window.firebridge || !firebridge.whenAuthResolved) {
    return setTimeout(boot, 300);   // firebase-bridge not up yet
  }
  firebridge.whenAuthResolved().then(register)...
}
```

`firebridge` is declared as a top-level lexical `const`, so it is a bare
global binding — it is **not** a property of `window`. `window.firebridge`
is therefore always `undefined`, `!window.firebridge` is always `true`, and
`boot()` reschedules itself forever, never reaching `register()`. Push
never armed on any real device. (The single simulator token in Firestore
was a stale leftover from an earlier moment, masking the bug.)

This is the same `window.firebridge` dead-check class that was swept out of
the rest of the codebase in V3.392 / V3.460 / V3.461, accidentally
reintroduced when `mobile-push.js` was written in V3.566 (m-v0.2).

## Approach

One-line guard fix, matching every other rm/ script:

```js
if (typeof firebridge === 'undefined' || !firebridge.whenAuthResolved) {
  return setTimeout(boot, 300);
}
```

Now `boot()` proceeds once firebase-bridge has run →
`firebridge.whenAuthResolved().then(register)` → `ensurePermission()`
(iOS permission prompt) → `getToken()` → writes
`users/{uid}/pushTokens/{token}` with `native:true`.

Bump `OurlabMobile` `CURRENT_PROJECT_VERSION` 1 → 2 — TestFlight rejects a
re-used build number — and ship a new TestFlight build so the phone gets
the fix.

## Data model / rules

None.

## Out of scope

- Any change to the (correct) APNs key or Firebase config. Note the key
  should sit in **both** the Development and Production APNs slots so
  sandbox (sim/dev builds) and production (TestFlight/App Store) tokens both
  deliver — the user has done this.

## Verification

1. New TestFlight build (build 2) installed on the phone.
2. Launch → iOS shows "Ourlab Would Like to Send You Notifications" → Allow.
3. App now appears under Settings → Notifications; a fresh `ios native=true`
   token with a recent `lastSeen` and a real device id appears in
   `users/{uid}/pushTokens`.
4. Direct FCM probe to that token → `SENT ok` + a banner lands on the
   locked/backgrounded phone.
