# V3.989 — A new, uploaded or posted protocol shows on the Protocols list at once; posting errors say what failed

## Report

Alex, 2026-11-13: "I uploaded a html protocol, but I don't see it on the Protocols page, and I can't upload it to the
public facing webpage."

## What was checked

- **The rules are live.** Anonymously, the live database lets a visitor list `publicProtocols` (empty: nothing posted
  yet) and refuses the V3.113 public read of `protocols` with `status == 'published'` — the V3.986 rules are deployed.
  Whether the deploy included V3.987's `protocols/{id}/html/{pieceId}` rule cannot be seen from outside: both versions
  refuse an anonymous read there. (Reading the live ruleset with the admin `gcloud` sign-in was refused by the session's
  safety check, so it was not read.)
- **The list (reproduced, fixed).** `protocols.js` loads `protocols/list.json`, a MEDIUM (30 min) route cache in
  IndexedDB, refreshed in the background only after it expires. A protocol created or uploaded inside that window — by
  anyone — is missing from the list until the cache expires, and then appears one visit later. The route's comment says
  LIVE_SYNC keeps it current; protocols.js never attached it (and LIVE_SYNC skips its first snapshot anyway).
- First suspected, then **disproved by test:** the adapter's cheap freshness probe orders by `updatedAt` while protocols
  keep `updated_at`. It does not matter: the probe never runs, because `LOCAL_CACHE.scope().get()` returns
  `{data, age, stale}` — no `savedAt` — so `_refreshRouteCacheCheap` returns false and every stale refresh is a full
  refetch. The adapter edit was reverted. (Consequence for read costs only: the "cheap" path is dead code everywhere.
  Not changed here.)

## Then: "The lab roster did not load" (Alex pasted the dialog)

The upload had worked (the dialog showed the file, 139 KB). The contributors list was empty because all three roster
readers kept only members with a `uid` field, and a member's record has none — it is keyed by its document id, and
neither sign-up path (`profile-bootstrap.js`, `user-system.js`) writes `uid`. Other RM pages read `u.uid || u.id`
(`sharing.js`, `task-market.js`). Fixed the same way in `protocol-publish.js` (the dialog, so every caller is covered),
`protocol-html-view.js` and `protocol-editor.js` (which also fixes the admin author picker). The V3.987 harness gave its
roster `uid` fields and so could not see this; it now returns `{id, …}` like the adapter.

## Then: "on the protocol page, what we listed still says draft even though it's published"

Alex posted the HTML protocol to the website; the RM Protocols list card still said `draft`. The public site shows no
status, and the HTML view sets its status menu to Published after a post, so it is the list card. Same cause as the
missing upload: the 30-minute list cache, and V3.987's `publish()` updated `status` without `updated_at`, so even the
re-check below could not see the change. Already fixed by this version's `updated_at` stamp; verified separately
(below). Every other status write (editor metadata save, HTML view status menu, taking down) stamps `updated_at`.

## Changes

- `protocols.js` `revalidate()`: after drawing the cached list, one query — the protocol with the newest `updated_at` —
  and a reload of the list if it is newer than anything shown or not shown at all. A quiet visit costs one read.
  Deleting a protocol `api.invalidate`s the list so it does not come back from the cache.
- `protocol-publish.js`: posting and taking down also write `updated_at` (posting: the copy's own timestamp, so it does
  not read as "edited since"), so the list's status chip follows. A failed post now ends with the step and the
  database's words, e.g. `[writing the public copy: permission-denied — Missing or insufficient permissions.]`.
- `protocol-html-view.js`: posting waits for the file to load (it could have posted an empty file if pressed first).
- `protocols.js`: an `.html` file chosen in **Import protocol** opens **Upload HTML** with the file already in it.
- `sw.js` 959.

## Verified

- `scripts/tests/v3989-protocol-list-harness.html` (the real list page, util / local-cache / adapter / routes, an
  in-memory Firestore that survives reloads): with the V3.987 `protocols.js` the uploaded protocol is missing on the
  next two visits and appears only after the cache expires — reproduced; with V3.989 it is there on the next visit; a
  quiet visit is 1 read; an edit made elsewhere shows; a deleted protocol stays gone. 10 / 10. Import → Upload HTML: 3 / 3.
- V3.987 HTML protocol suite 48 / 48; V3.986 posting suite 47 / 47 (the refused post's message checked).
- Posted while the list was cached (same harness, driven with the exact fields each version's `publish()`
  writes): V3.987 list + post → the card says `draft` (reproduced); V3.989 → `published`, and `draft` again after
  taking it down. 6 / 6. A protocol posted by V3.987 before this ships keeps its old chip until the cache expires
  (≤ 30 min, then one visit) — signing out and in also clears the cache.
- Known edge: a protocol whose `updated_at` is older than the newest one shown (none are made that way — every create
  stamps now) is only picked up when the cache expires.
