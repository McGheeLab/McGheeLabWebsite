## Context

[rm/js/meetings.js](rm/js/meetings.js) is a V3.41 lift-and-shift of a
standalone app. It predates `APP_SHEET`, `TOAST`, `TASK_ASSIGN`, the
capability system, the Heroicons pass, and the no-browser-popups house rule.
It shows a schedule and holds agenda/action items — but there is no agenda
template, no minutes, no slide-submission pipeline, no chore board, no topic
suggestions, no way for a student to switch slots, no coordinator role that
actually works, and no bridge to My Week.

Three things in it are **broken today**, verified server-side:

| Broken | Evidence |
|---|---|
| **Slide upload always fails** | `meetings.js:516` uploads to Storage `meetings/{date}/…`; [storage.rules](storage.rules) has no `meetings/` block and no catch-all → default deny. |
| **`isMeetingAdmin()` is decoration** | [firestore.rules:1662-1668](firestore.rules#L1662) — `allow create/update: if request.auth != null`. Any signed-in user, **including a `role:'guest'`**, can rewrite every meeting doc. Meanwhile `meetingConfig` is `isAdmin()`-only, so a meeting admin can't save a setting. `renderSettings()` (`:1616`) / `wireSettings()` (`:1728`) also gate on `isAdmin()`. |
| **"Live" sync serves 30-min-old data** | `api.subscribe` doesn't write through the route cache ([adapter:566-620](rm/js/api-firestore-adapter.js#L566)); LIVE_SYNC's refresh → `api.load` returns the IndexedDB entry while fresh ([:332-344](rm/js/api-firestore-adapter.js#L332)). Route TTL is `MEDIUM` = 30 min. |

Plus `confirm()` at `:1024` and `:1291`, three hand-rolled overlays, a dead

sets (`a.completed`, `m.title`) that links to `'#'`.

**Outcome:** one page that runs the whole loop — rotation → slide submissions

## Phase 1 — Data model + rules (deploy before any client code)

### 1a. `meetings/{id}`

Two structural changes. **Presenters become a map keyed by uid** — that is
what makes "a student edits only their own slot" enforceable in one doc read.
And `updates` carries the submission pipeline.

```js
{
  date, time, duration, location, status: 'upcoming'|'completed'|'cancelled',
  kind: 'standard' | 'flash' | 'break',            // NEW

  // NEW — map, not array. Rules diff it by key.
  presenters: { '<uid>': { slot, name, title, abstract,
                           link: null | DriveRef, updatedAt } },

  // NEW — the round-robin slide pipeline
  updates: {
    submissions: { '<uid>': { link: DriveRef, note, submittedAt } },
    deck: null | DriveRef, deckBy, deckByName, deckAt,   // presenter's concat
    review: { status: null|'pending'|'approved'|'changes',
              by, byName, at, comment },                 // PI, day before
  },

  agendaItems: [{ id, text, minutes, type, order, done, topicId?, addedBy }],
  //                       ^^^^^^^ NEW — drives the run-meeting timer

  minutes: { text, items: { '<agendaItemId>': { notes, done, doneAt, doneBy } },
             startedAt, startedBy, updatedAt, updatedBy },   // NEW
  actionItems: [{ …, taskId, pushedAt }],                    // 2 fields NEW
  feedback: [...], notes: '',
  reminded: { presenter, submitCall, deckCall, reviewCall, dayBefore },  // NEW, function-owned
  createdBy, createdAt, updatedAt
}

DriveRef = { url, fileId, name, mimeType, thumbnailLink, iconLink,
             ownerEmail, ownerOk: true|false|null, verifiedAt }
```

Legacy `presenters[]` (array), `presenterId`, `presentationTitle/Notes/Links`
stay **read-only** for old docs. `getPresenters(mtg)` (`meetings.js:202`)
becomes the single normalizer: map → array sorted by `slot`, falling back to
the legacy shapes. A one-shot admin **"Migrate presenters"** button converts
old docs in place.

### 1e. Rules — [firestore.rules](firestore.rules), replacing lines 1661-1673

```
    // Meeting coordinator = site admin OR listed in meetingConfig/settings.
    // The exists() guard is load-bearing: get() on a missing doc RAISES, and
    // a raising branch denies the whole || chain. Placed LAST in every OR so
    // admins short-circuit without the extra read.
    function isMeetingCoordinator() {
      return isAdmin() || (
        request.auth != null &&
        exists(/databases/$(database)/documents/meetingConfig/settings) &&
        request.auth.uid in
          get(/databases/$(database)/documents/meetingConfig/settings)
            .data.get('coordinatorUids', [])
      );
    }

    match /meetings/{meetingId} {
      allow read:   if isLabMember();
      allow create: if isMeetingCoordinator();
      allow delete: if isMeetingCoordinator();
      // Members write the collaborative fields; inside `presenters` and
      // `updates.submissions` they may touch ONLY their own key.
      allow update: if isMeetingCoordinator() || (
        isLabMember() &&
        request.resource.data.diff(resource.data).affectedKeys()
          .hasOnly(['presenters','updates','minutes','actionItems','feedback','updatedAt']) &&
        (!request.resource.data.diff(resource.data).affectedKeys().hasAny(['presenters'])
         || request.resource.data.get('presenters', {})
              .diff(resource.data.get('presenters', {}))
              .affectedKeys().hasOnly([request.auth.uid]))
      );
    }

    match /meetingConfig/{docId} {
      allow read:  if isLabMember();
      // Coordinator manages the schedule; only an admin appoints coordinators.
      allow write: if isAdmin() || (
        isMeetingCoordinator() && resource != null &&
        !request.resource.data.diff(resource.data).affectedKeys()
           .hasAny(['coordinatorUids','primaryCoordinatorUid','reviewerUids'])
      );
    }

    match /meetingTopics/{topicId} {
      allow read:   if isLabMember();
      allow create: if isLabMember()
                    && request.resource.data.suggestedBy == request.auth.uid;
      allow update: if isMeetingCoordinator()
                    || resource.data.suggestedBy == request.auth.uid
                    || (isLabMember() && request.resource.data.diff(resource.data)
                          .affectedKeys().hasOnly(['votes','updatedAt']));
      allow delete: if isMeetingCoordinator()
                    || resource.data.suggestedBy == request.auth.uid;
    }

    match /meetingSwaps/{swapId} {
      allow read:   if isLabMember();
      allow create: if isLabMember()
                    && request.resource.data.fromUid == request.auth.uid
                    && request.resource.data.status == 'pending';
      allow update: if isMeetingCoordinator()
                    || (resource.data.toUid == request.auth.uid
                        && request.resource.data.status in ['accepted','declined'])
                    || (resource.data.fromUid == request.auth.uid
                        && request.resource.data.status == 'cancelled');
      allow delete: if isMeetingCoordinator();
    }

    match /labChores/{weekId} {
      allow read:   if isLabMember();
      allow write:  if isMeetingCoordinator();
      // A member may only tick their OWN chore done.
      allow update: if isLabMember()
                    && request.resource.data.diff(resource.data).affectedKeys()
                         .hasOnly(['assignments','updatedAt'])
                    && request.resource.data.assignments
                         .diff(resource.data.assignments).affectedKeys().size() == 1;
      // (the per-chore owner check is enforced client-side + verified in tests;
      //  rules cannot read the changed key's value — see "Accepted gaps")
    }
```

Model: `isInvMgr()` ([firestore.rules:111](firestore.rules#L111)) and
`isChatAdmin()` ([:1856](firestore.rules#L1856)) — note the existing
`isChatAdmin()` has **no `exists()` guard** and survives only because its
config doc happens to exist. Don't copy that half.

**Accepted gaps (state them, don't paper over them):**
- `minutes` / `actionItems` / `feedback` are whole-field member-writable, so
  any lab member can delete another's action item. That *is* "collaborative
  minutes" — Alex's call. The UI stamps `doneBy` / `addedByName` so it's visible.
- `updates.submissions` is inside the `updates` field, so a member could in
  principle overwrite another's submission. Narrowing it needs the same
  `.diff().affectedKeys()` trick one level deeper than rules allow on a nested
  map path. Enforced client-side; the rules test asserts the presenter/coordinator
  path works and the audit stamp (`submittedAt`, `deckBy`) makes tampering visible.
  Revisit only if it actually happens.
- `labChores` per-chore ownership: rules can bound the write to a *single*
  changed key but can't check whose it is. Client-enforced.

### Live sync — replace LIVE_SYNC with direct `api.subscribe`

Drop `LIVE_SYNC.attach`; subscribe each route and hydrate a state slice:

```js
api.subscribe('meetings/list.json',   d => { state.meetings = sortByDate(d.meetings||[]); scheduleRender(); });
api.subscribe('meetings/config.json', d => { state.config   = d || {};                    scheduleRender(); });
api.subscribe('meetings/topics.json', d => { state.topics   = d.topics || [];             scheduleRender(); });
api.subscribe('meetings/swaps.json',  d => { state.swaps    = d.swaps  || [];             scheduleRender(); });
api.subscribe('meetings/chores.json', d => { state.chores   = d.chores || [];             scheduleRender(); });
```

`api.subscribe` returns the same shape `api.load` does for these routes —
wrapped under `wrapKey` for collections, unwrapped for the single config doc
([adapter:585-619](rm/js/api-firestore-adapter.js#L585)). This is the fix for
the 30-minute staleness. Every direct write still calls `api.invalidate(path)`
so a **later page load** doesn't serve a stale cache (house rule: any
Firestore write outside `api.save` must invalidate).

`scheduleRender()` = 120 ms debounce, and it must **skip any subtree
containing `document.activeElement`** — snapshot-clobbering a half-typed
minutes note is the classic failure here.

## Phase 3 — Action items + chores → top of My Week

The `dayPlans` write rule is **owner-only on purpose**
([firestore.rules:3059-3072](firestore.rules#L3059), V3.624: *"a mentor
responds via barrier-acceptance … never by editing the plan"*). So the meeting
never writes into anyone's day. It writes a **task**; My Week surfaces it; the
student plans it themselves. Zero rules changes, zero new functions.

**3a. Write the task** — after the meeting/chore doc update, when the assignee
isn't the author, call [`TASK_ASSIGN.writeTaskFor`](rm/js/task-assign.js#L95)
directly:

```js
const task = await TASK_ASSIGN.writeTaskFor(assigneeUid, {
  text, due_date: deadline || 'TBD', bucket: 'assigned',
  createdByUid: _user.uid, createdByName: myName(),
  assignedToUid: assigneeUid, assignedToName: memberName(assigneeUid),
  source: 'meeting',
  source_ref: { kind: 'meeting-action', meetingId, actionItemId, meetingDate },
  //  chores:  { kind: 'lab-chore', weekId, choreId, label }
});
// stamp task.id back onto the actionItems[] entry / chore assignment
```

Rules already allow it: `create if isLabMember() && createdByUid == auth.uid
&& exists(users/{assignee})`
([firestore.rules:3141-3161](firestore.rules#L3141)). **Never**
`TASK_ASSIGN.open()` — for a non-admin sender it writes only an `open`
`taskMarket` post and no task doc, the V3.639 stranded-handoff bug
([task-assign.js:209-234](rm/js/task-assign.js#L209)). Free bonus:
`functions/tasks.js onTaskAssigned` already pushes on this write.

**3b. [rm/js/my-week.js](rm/js/my-week.js) — the card strip.**

- `loadAssigned()`: read **directly**, not via `api.load('tasks/assigned.json')`
  — that route is `cache: MEDIUM` (30 min) and a cross-user write can't
  invalidate the *recipient's* cache, so a fresh assignment would be invisible
  for half an hour. Mirror `loadNotifications()` (`:255`):
  `db().collection('userData').doc(uid).collection('tasks').where('bucket','==','assigned').get()`,
  client-filter `!done && !planned_item_id`. Single equality → no index.
- **Wire it into both `init()` (`:2234`) and `refresh()` (`:2182`).** `init()`
  currently omits `loadNotifications()`, which is why the 🔔 feed is empty on
  first paint — don't inherit that bug.
- `renderAssignedInbox()` modelled on `renderFocusPanel()`
  ([:724-775](rm/js/my-week.js#L724)), inserted in `render()`
  ([:447-482](rm/js/my-week.js#L447)) right after `nudge` so it is top-of-page
  in **all three** horizons. Card = text · source chip (`🗣 Lab meeting · Sep 11`
  or `🧹 Chore · week of Sep 7`, else `from <createdByName>`) · due date ·
  seven day-chips (Mon–Sun of the visible week, past days disabled) · ✓ Done ·
  ✕ Dismiss.
- Day chip → `DD.importAndDistribute`
  ([day-distribute.js:870-902](rm/js/day-distribute.js#L870)):

```js
const item = await DD.importAndDistribute({
  source: 'tasks', type: 'task',
  nativeDocPath: 'userData/' + uid + '/tasks/' + t.id,
  draft: { title: t.text, notes: t.notes, date: chipDate,
           details: { assignedTaskId: t.id, ...t.source_ref } },
}, ['tracker']);
await taskRef(t.id).update({ planned_item_id: item.id });   // owner write; card clears
```

  Verified chain: `importAndDistribute` pre-marks the origin surface with
  `record('task', {…, meta:{native:true}})`, and `record()` defaults
  `status: 'created'`, so `confirmDone` → `cascadeUpdate` → the `task`
  adapter's `update` ([:583-588](rm/js/day-distribute.js#L583)) patches
  `done:true` onto `userData/{uid()}/tasks/{taskId}` — `uid()` is the assignee,
  i.e. the owner. Rules allow it, and `distribute()` skips the origin surface
  so no duplicate task is created.
- `maybeCompleteMeetingWork(item)` beside `maybeCompleteFocusTask`
  ([:1829](rm/js/my-week.js#L1829)), called from the `i-done` / `c-did` branch
  ([:1758](rm/js/my-week.js#L1758)): flip the meeting's `actionItems[]` entry
  or the `labChores` assignment to done. Both permitted by Phase 1e.
- One CSS block in [rm/css/my-week.css](rm/css/my-week.css) reusing the
  `.md-focus-card` / `.md-ft` idiom.
