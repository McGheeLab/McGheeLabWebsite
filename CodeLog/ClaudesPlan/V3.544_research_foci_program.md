# Research Foci program — RM research redesign + public publish (V3.544–V3.551)

> At implementation time: copy this into `CodeLog/ClaudesPlan/V3.544_research_foci_program.md` (per repo ritual) and **re-verify the version head** in CHANGELOG/sw.js first — parallel sessions advance them (sw.js currently 517, head V3.543).

## Context

The RM "Research" surface is fragmented and hard to use. Three disjoint systems each model "research" differently, and none attach to students, grants, trainings, or daily work:

- **Lab Themes** (`rm/js/library-themes.js`, `labThemes`) — literature tool buried as a Library tab; attaches only to library papers.
- **projects.html pin-grid** (`rm/js/projects.js`) — what nav calls "Research": a flat mixed-type item hub.
- **projectPackages / stories** — public-site content, unrelated to RM workflows.

Alex wants **research focal points**: a three-level card model giving a high-level overview of the lab, attachable to students/papers/grants/trainings, flowing into My Day, weekly focus, notebook, and PMR — plus a designed per-focus **overview publishable to the public site**.

## Locked decisions (Alex, 2026-07-25)

1. **Three-level card model** (kept flexible): **Specialty** cards = lab-unique capabilities (MEBP, In-Situ ELISA, GELS, CELS, STEM, TFM); **Concept** cards = broad ideas combining specialties (e.g. Tissue engineering); **Output** cards = grant/paper/patent efforts combining the others.
2. **PI/admin-only authoring**; students read and get attached.
3. **Integration inherits via weekly focus** — focusAreas link to a research focus; My Day/notebook/PMR inherit through that link (no extra student tagging).
4. **New `rm/pages/research.html` replaces projects.html as nav "Research" landing**; pin-grid demoted to a child link. Lab Themes stay in the Library; concept cards link to a theme.
5. **Output cards authored + linked** — pills to real paper/grant drafts; patents supported without drafts; status auto-derives from linked drafts.
5b. **The research page is an action hub** (Alex, plan review): from a focus the PI can (a) **create a paper** and assign students to it (spawns a real paper-builder draft), (b) **create a grant idea** with submission specifics — agency/mechanism, where to submit, target deadline, scope — promotable to a real grant draft, and (c) **see a progress overview** of how students are advancing on that research thrust.
6. **Guided template authoring** — per-level structured prompts compile into a description Alex edits as rich text; cards carry **images, videos, and uploaded single-file `.html` interactive embeds** (sandboxed iframe).
7. **Public publish pipeline** — each focus can carry a designed **overview** (text / images / video / **YouTube autoplay** / **HTML embed** blocks) that Alex publishes to the public site; the public **`#/projects`** page (projectPackages stack, `renderProjects()` app.js:1256) is rebuilt to render published overviews. `#/research` (stories feed) stays.

## Data model

### `researchFoci/{fociId}` — new collection, single collection discriminated by `level`

Slug ids (`mebp`, `tissue-engineering`, `prostate-gels-r01`). One collection, not three: cross-level links are the point; whole-collection get + client sort renders the hub in one read. **No composite indexes needed.**

```js
{ id, level: 'specialty'|'concept'|'output',
  title, abbr, icon, color, one_liner,
  template_fields: { template_version: 1, answers: {...per-level keys} },
  description_html: '<sanitized rich text — internal detail body>',
  media: [ { id, kind: 'image'|'video'|'html', order, caption,
             // image: storage_dir + variants {thumb,medium,full} (webp set)
             // video: storage_path (.mp4/.webm) + poster_path
             // html:  storage_path (.html) + poster_path + title + aspect ('16/9') + height_px
           } ],
  links: {
    specialty_ids: [], concept_ids: [], output_ids: [],   // cross-level
    theme_id: null,                                        // labThemes link
    draft_refs: [ {id, title, kind:'paper'|'grant'} ],     // papers.json id space; status DERIVED via LIBRARY_ASSOC, never stored
    patents:    [ {id, title, number, status} ],           // authored inline, no draft
    training_slugs: []                                     // static training-<slug> pages
  },
  grant_meta: {   // output cards with kind grant-idea (V3.549): the specifics BEFORE a draft exists
    agency: '', mechanism: '',        // e.g. NSF / CAREER — mechanism maps to grant_subtype at promotion
    submit_to: '', submission_url: '',
    target_deadline: 'YYYY-MM-DD'|'TBD',
    scope_html: '',                   // sanitized rich text: scope, aims sketch, budget ballpark
    promoted_draft_id: null           // set when promoted to a real grant draft
  },
  member_uids: [], member_roles: { uid: 'lead'|'contributor' },
  status, status_source: 'manual'|'derived',   // output cards can derive from max-progress linked draft
  order,
  overview_blocks: [   // V3.552 — the DESIGNED public-facing overview (draft; lab-only until published)
    { id, kind: 'text',    html }                          // sanitized rich text
  , { id, kind: 'image',   media_id, caption }             // refs media[]
  , { id, kind: 'video',   media_id }
  , { id, kind: 'youtube', video_id, autoplay: true }      // iframe ?autoplay=1&mute=1&playsinline=1&loop=1&playlist=<id>
  , { id, kind: 'html',    media_id }                      // sandboxed iframe embed
  ],
  published: false, published_at: null,   // snapshot-publish state (see publicFoci)
  created_by, created_at, updated_by, updated_at, schema_version: 1 }
```

### `publicFoci/{fociId}` — snapshot-publish target (V3.553)

"Publish" **copies a snapshot** — `{id, level, title, abbr, icon, color, one_liner, overview_blocks, media (referenced subset), order, published_at}` — into `publicFoci`. Lab-internal edits never leak until re-publish (stories-style explicit publish, but PI-only so no review flow). Unpublish = delete the publicFoci doc + flip `published:false`.

### Storage rules

```
// V3.546 — Research Foci media (images, videos, single-file HTML sims).
// Public read from day one (published overviews serve visitors; token URLs
// are unguessable for drafts). The REAL write gate is the admin-only
// researchFoci Firestore doc — unreferenced media is unreachable in the
// UI (vizViews/paperExports precedent).
// Path: researchFoci/{fociId}/{mediaId}/{file}
match /researchFoci/{fociId}/{allPaths=**} {
  allow read:  if true;
  allow write: if request.auth != null
               && request.resource.size < 50 * 1024 * 1024
               && (request.resource.contentType.matches('image/.*')
                   || request.resource.contentType == 'video/mp4'
                   || request.resource.contentType == 'video/webm'
                   || request.resource.contentType == 'text/html');
}
```

Decision (was open question): **Firestore-authority approach** — storage write stays `auth != null`; admin-only authority lives on the Firestore doc write, matching vizViews precedent. Read is `if true` from day one so V3.553 needs no storage redeploy.

## Guided authoring composer (V3.545)

Step 1: level, title, slug (auto), icon, color, one_liner.
Step 2: per-level template prompts —
- **Specialty**: what is it (para a new student understands) / what makes it uniquely ours / what it enables.
- **Concept**: vision / why it matters / which specialties combine (pre-seeds `specialty_ids`) / open questions.
- **Output**: goal (artifact + claim) / approach / 3–5 milestones / target venue-agency.

Step 3: pure-JS `compileDescription(level, answers)` stitches an `<h3>`-sectioned HTML draft → dropped into a `contentEditable` surface (lift PMR barrier pattern `pmr.js:3447`; sanitizer from `library-themes.js:118`; paste-image via the research-media uploader). `description_html` stores the sanitized result; `template_fields.answers` keeps raw answers for re-compile.

## HTML-embed rendering (V3.547)

Click-to-activate poster → inject `<iframe src="<downloadURL>" sandbox="allow-scripts allow-pointer-lock allow-fullscreen" loading="lazy" referrerpolicy="no-referrer">`; **no `allow-same-origin`** — sim runs JS but can't touch Firebase auth/parent origin (plus it's cross-origin from `firebasestorage.googleapis.com` anyway). Sizing via `aspect-ratio`/`height_px`; ⛶ fullscreen. Storage serves inline (don't set `contentDisposition`); resolve URL at render from `storage_path` (`PAPER_FIGURES.downloadUrl` pattern). **v1 constraint: self-contained single-file HTML only** (no multi-file bundles) — upload validator warns.

## Create-from-focus actions (V3.549) — `rm/js/research-create.js` (new)

- **＋ New paper from this focus**: dialog (title, slug auto, template, student picker) → appends a `projects/papers.json` row using the exact `createPaper()` shape (`paper-builder.js:263` — `lead_author_uid`, `coauthor_uids[]` = assigned students, `paper_type:'journal'`), links it into `links.draft_refs`, attaches the students to the focus (`member_uids`), and offers "Open in builder". **Flagged implementation detail:** PMR/focus pickers query `papers/{id}.authorUids` (content doc) — verify how the builder lazily initializes `papers/{id}` and seed `authorUids` at creation without clobbering the editor's first save.
- **＋ New grant idea**: creates an output card (`status:'planning'`) with `grant_meta` (agency, mechanism, where to submit, target deadline, scope/aims rich text). Renders as a distinct "💡 grant idea" card on the outputs rail with deadline chip. **Promote to grant draft** button → papers.json row with `paper_type:'grant'`, `grant_subtype` from mechanism, stamps `grant_meta.promoted_draft_id` + `draft_refs`, hands off to the grant builder (existing "+ New grant" seam, V3.463-471).

## Student alignment + per-thrust progress overview (V3.551)

- Aligned students from `member_uids` (world-readable `users` for name/photo); drafts resolved live via `LIBRARY_ASSOC`; training chips.
- **Progress overview** (admin/mentor section on focus detail — the PI's "how is this thrust going" view): per assigned member, direct reads of their `focusAreas` where `focus_ref.id == fociId` — recent weekly outcomes (✅ success / ◐ partial / ✖ failure per week), focus-task completion %, and report summaries with notebook-entry deep links; plus the card's linked drafts with live status pills. Concept-level cards aggregate across their child outputs' members. **Visibility respects existing rules** (owner ∥ mentor ∥ admin): the PI (admin) sees everything; mentors see their mentees; other members see roster + links only — **no focusAreas rules loosening, no notebook-privacy bypass** (titles only, viewer-authorized).
