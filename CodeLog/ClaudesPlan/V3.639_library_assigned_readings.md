# V3.639 — Assigned & suggested readings on the library page

> Alex: *"my mentee has shared papers with me to read, and these readings do
> not show up. currently we route the readings to the task page. I want the
> assigned or suggested readings at the top of the library page, and users can
> mark as done. these assigned or suggested papers should have the user that
> assigned it tagged to it. these sections and all sections on the library page
> can be collapsed."*

## Goal

Give shared readings a real home — the top of the library page — with the
assigner named on every row, a one-click "mark as done", and collapsible
sections throughout the page.

## Root cause: the readings were never delivered

This is not a rendering bug. **The task doc was never written.**

Sending a paper (three call sites — `library.js:1303`, `library-paper.js:932`,
`pmr.js:4293`) funnels into `TASK_ASSIGN.open({paperRef})`. Since V3.317,
`task-assign.js:197-229` branches on whether the **sender** is an admin:

| Sender | `taskMarket` post | Task doc in recipient's queue |
|---|---|---|
| Admin | born `status:'accepted'` | **written immediately** |
| Non-admin | `status:'open'` | **never written** |

A mentee is non-admin, so their readings became `open` handoff posts awaiting
an accept/decline that only happens on `rm/pages/task-market.html` — a page
the recipient never visits. The mentee saw a success toast ("Handoff posted —
… will accept or decline on the Task Market"), so from their side it looked
delivered. The readings are not lost; they are sitting in `taskMarket`.

**This gate is JS policy, not security.** `firestore.rules:2073-2075` already
permits any lab member to write into another member's queue:

```
allow create: if isLabMember()
              && request.resource.data.createdByUid == request.auth.uid
              && exists(/databases/$(database)/documents/users/$(userId));
```

So the fix needs **no rules change**.

### Second failure mode

Even a successfully-delivered reading had a poor home:
`tasks-dashboard-buckets.js:218-295` (`renderAssignedByOthers`) has no
`paper_ref` branch at all — an assigned paper renders as a bare text row
("Read: &lt;title&gt;") with no link to the reader. Only PMR and the Market's
Assignments view are paper-aware. This is the part Alex's "we route the
readings to the task page" is reacting to.

## Approach

Three parts. All three are needed: (1) alone leaves the existing backlog
invisible, (2) alone leaves every future send stuck.

### 1. Delivery fix — paper sends bypass the marketplace

In `task-assign.js` `_submit`, when `paperRef` is present, write the task
directly into the recipient's queue for **all** senders and skip the
`taskMarket` post entirely.

Rationale: a shared reading is a *suggestion*, not a work handoff that needs
an accept/decline negotiation. The Assigned/Suggested toggle already encodes
the social weight, which is what the market gate was standing in for. The
marketplace keeps serving real task handoffs (`offer` / `request` / non-paper
`handoff`).

Note a non-admin **cannot** create a post with `status:'accepted'`
(`firestore.rules:2136-2139`), so "post + materialize" is not available to
them — skipping the post is the only consistent option, and it is the right
one anyway.

### 2. Backlog recovery — read the stuck posts

The new section unions two sources:

- **A. Materialized readings** — `userData/{me}/tasks` where
  `bucket=='assigned'` and `paper_ref.paperId` exists.
- **B. Stranded sends (pre-V3.639)** — `taskMarket` where
  `targetUid=='{me}'` and `status=='open'` and
  `task_payload.paper_ref.paperId` exists.

Both are equality-only queries, so **no composite index is required**
(Firestore serves multi-equality via zigzag merge on single-field indexes).
`taskMarket` read is already `isLabMember()`.

Source B is transitional but kept indefinitely — old posts persist, and the
read is cheap. Rows from B are visually identical; the user should not have to
care which pipeline delivered them.

### 3. Mark as done

| Source | Action |
|---|---|
| A (task doc) | `update({done:true, status:'completed', done_at})` — owner update, allowed by `firestore.rules:2085` |
| B (open post) | claim `open→accepted` stamping `claimedByUid=me` + `marketTaskId`, then `TASK_ASSIGN.writeTaskFor(me, {...task_payload, done:true})` |

The B path satisfies `marketContentUnchanged()`
(`firestore.rules:2126-2132`) — it touches only status/claim/marketTaskId,
never `title`/`description`/`task_payload`/`targetUid`/`source_ref`. Using
`update()` preserves `createdByUid` and `kind`, which the rule also pins.

Materializing on done (rather than on load) keeps reads side-effect free — no
surprise writes just from opening the library.

### 4. Collapsible sections

Reuse the existing shelf pattern from `library-groups.js:189-197` + 261-265 +
672-685 (`.lg-section` / `.lg-sec-head` / `.lg-caret` / `.lg-sec-body` /
`.lg-collapsed`, persisted in `localStorage`). Same CSS classes from
`library-groups.css:13-68`, so the new sections look native.

A new `library-collapse.js` applies that treatment to the page's top-level
blocks by wrapping them in a header + body at runtime (no HTML restructuring
of the blocks themselves):

| Section id | Block | Default |
|---|---|---|
| `readings` | new readings block | open |
| `dropzone` | `#library-dropzone` | open |
| `shelf` | `#lib-groups-shelf` | open |
| `papers` | the `lib-table` | open |

The extension card (`library.html:184`) is already a native `<details>` and is
left alone. Collapse state persists per-device under
`rm_lib_sections_collapsed`, mirroring the shelf's `rm_lib_shelf_collapsed`.

## Placement

Directly below the page header / auth hint and **above** the extension card,
inside `.lib-papers-block`. That is "the top of the library page" in the
meaningful sense — above the h1 would orphan the title.

The whole block hides itself when the user has zero readings, so members who
are never sent papers get no new clutter.

## Row anatomy

Title (links to `library-paper.html?id=`) · authors · **assigner chip
("from Ana Ruiz")** · kind chip (red `assigned` / blue `suggested`, matching
PMR's convention at `pmr.js:2166-2260`) · the sender's note · relative date ·
`✓ Mark as done`.

Sections: **📥 Assigned to me**, **💡 Suggested for me**, **✓ Done** (collapsed
by default). Done readings are kept rather than deleted — the mentor/mentee
loop benefits from "what have I already read".

## Deliberately out of scope (flagged for Alex)

1. **`pmr.js:4293` sends a paper-*draft* id** as `paper_ref.paperId`, but all
   renderers link it to `library-paper.html?id=` (library-item id space). Those
   rows link to nothing. Pre-existing; separate fix.
2. **Push notifications never say "paper"** — `functions/task-market.js`
   builds from `title`/`createdByName`, so recipients get "Task from …". With
   sends no longer creating posts, paper sends now produce *no* push at all;
   a `readingAssigned` notification is the natural follow-up.
3. **Readings still also appear on the tasks dashboard** as bare text rows.
   Left in place (removing them risks PMR/market regressions and is
   reversible); whether to hide or relabel them there is Alex's call.
4. `rm/js/sharing.js` is dead code; `training-rm-essentials.js:39` links the
   retired `/rm/pages/sharing.html`.
