# V3.629 — Three silent-loss paths in the library↔draft link

First release of the library-categorization program (see
`/Users/alexmcghee/.claude/plans/on-the-desktop-version-cuddly-ember.md`).
Found while investigating Alex's *"there are multiple ways to categorize a
library journal paper… make it less confusing"* — these three are independent
data-loss bugs, not confusion, so they ship first and alone. **No UI changes.**

The root of all three: the two levels of draft linkage drifted apart.

- `items/{id}.meta.library.linked_drafts` — *this paper feeds draft X*
- `papers/{id}/annotations/{annId}.cite_in_drafts` — *this highlight is
  evidence for draft X*

Nothing kept them consistent, and three separate consumers assume they are.

## 1 · The reader toolbar picker silently unlinked drafts it never showed

`_openLinkPicker`'s Save built `desired` from only the checkboxes it rendered,
then unlinked everything in `current` not in `desired`. So "the picker never
offered this draft" was indistinguishable from "the user unticked it" — and
pressing Save while changing **nothing** deleted links.

`_loadAllDrafts()` omits several classes of legitimately-linked draft:

- `items.json` grants that moved to `awarded` / `active` / `completed`
  (status-filtered at `paper-overlays.js:191`)
- drafts that have since been deleted
- for **non-lab-members**, every `grantDrafts` id — that whole block is
  `isLabMember()`-gated

`library-associations.js:351` has had the `listed.has(id)` guard since V3.365
with the comment *"ONLY over the active drafts listed in this picker"*; this
picker never got it. Now mirrored: unlisted ids are left untouched, because a
link is only removable from a surface that can show it.

Verified as pure logic (the awarded-grant scenario, Save with no changes):

```
OLD (bug):      ["UNLINK awarded-grant-r01"]
V3.629 (fixed): []
genuine untick: ["UNLINK mebp-draft"]     ← still works
genuine link:   ["LINK mebp-draft"]       ← still works
```

## 2 + 3 · Filing a highlight now links its paper

The panel's draft dropdown offers **every active draft in the lab**, not just
the linked ones (`_draftShortlist` floats linked ones to the top but keeps the
rest — has done since V3.475). So filing a highlight into an unlinked draft was
one click away, and two things then failed silently:

**(2) The evidence never reached the builder.** `paper-evidence-inbox.js`
`_fanOutItemIds` fans out over papers where `linked_drafts ∋ draftId`. A
highlight filed on an unlinked paper is invisible in the Evidence Inbox
**forever** — the exact failure V3.619 set out to fix, reachable by a different
route.

**(3) V3.628's guarantee had a hole** (my own regression). `activateDraft`
requires the draft to be in `_linkedDrafts`, so for an unlinked draft it
no-ops — and with a lens engaged the just-filed highlight still vanished off
the page. The normal path was fixed in V3.628; this edge was not.

One cure for both: **filing a highlight to a draft links the paper to that
draft.** That's also what the user meant — filing evidence out of a paper into
a draft *is* saying the paper feeds that draft.

- `library-paper.js` — new `_ensureDraftLinked(draftId)`: no-op when already
  linked, else `PAPER_OVERLAYS.linkDraft()` (atomic `arrayUnion` via
  `LIBRARY_LINKS` + `api.invalidate` + `_refreshLinkedDrafts`). Called from
  `onCiteToggle`'s add branch and from `onCreate` for each popover-filed draft,
  **before** `activateDraft` — which is the whole point, since `activateDraft`
  reads the refreshed `_linkedDrafts`. Sequential in the create loop: each
  `linkDraft()` re-reads and re-renders the linked set.
- `library-mobile-paper.js` — same helper written against `LIBRARY_LINKS`
  directly (`PAPER_OVERLAYS` is desktop-only). This finally gives
  `library-links.js` a consumer on that page; it has been loaded since V3.613
  with none. Mobile's create path always writes `cite_in_drafts: []`, so only
  the cite-toggle path needs it.
- Both are **best-effort** — a failed link warns to console and never costs the
  user the highlight they just made.

## Stale copy corrected (it now actively misleads)

- `paper-overlays.js` link-modal summary claimed linking *"unlocks it in the
  per-annotation 'Tag as evidence' picker"* — untrue since V3.475, and the
  evidence flow moved to the Comments page in V3.622. Replaced with what
  linking actually buys: the draft's highlight lens in the reader, the
  "File to:" chips on new highlights, the draft's Evidence Inbox, and the
  default scope of the builder's Cmd+K citation search (`paper-editor.js:5028`
  — the single biggest payoff, and the only one users never hear about).
- `annotation-panel.js:231-233` claimed `_getDrafts()` *"returns ONLY drafts
  linked to this paper"* — false since V3.475, and the false belief is what
  made bugs 2 and 3 invisible. Comment corrected, and the empty state
  "no drafts linked yet" → "no drafts in the lab yet" (it only ever appears
  when the lab has zero drafts).

  `annotations/{id}.cite_in_drafts` and `items/{id}.meta.library.linked_drafts`

  unlinked draft → still visible.
