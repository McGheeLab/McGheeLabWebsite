## Context

V3.208 added the `hidden` flag; V3.209 added the `collaborator`
category + `canAccessPage()` denying the implicit default-workflow
baseline for collaborators. **Both are UI gates only.** A collaborator
who runs a Firestore query from devtools can still read any
`isLabMember()`-gated collection.

This ship is the foundation for hard data-layer enforcement: it lands
the infrastructure (rules helpers, denormalized
`userPermissions/{uid}.allowedCollections` field, page→collection map,
migration script, admin matrix UI) **without gating any rule yet**.
V3.213 + V3.214 will tighten actual rule clauses incrementally on top
of this base.

The plan also lives at
`~/.claude/plans/think-about-all-the-quiet-badger.md` — that's the
master copy with full risk register; this file is the project-local
mirror per the V3 CHANGELOG / plan convention.

## Why phased, not one-shot

- firestore.rules deploys atomically to a single production project
  (`mcgheelab-f56cc`); no staging, no emulator config, no rules unit
  tests.
- Existing `userPermissions/{uid}` docs only carry `allowedPageIds` —
  the moment tightened rules ship without a migration, every existing
  collaborator gets `permission-denied`.
- `isLabContributor()` already burns 2 `get()` reads; the 10-read
  Firestore rules budget is real. Helpers must be cheap.

## V3.212 deliverables

1. **Rules helpers (no rule clauses use them yet)** —
   `isCollaborator()` reads `users/{uid}.category` (deduped with the
   `users/{uid}` get already done by `isLabMember()`); `collabMay(coll)`
   reads `userPermissions/{uid}.allowedCollections` (1 net new `get()`
   per evaluation).
2. **Page→collection mapping** in new
   [`rm/js/page-collections.js`](../../rm/js/page-collections.js)
   exposing `window.PAGE_COLLECTIONS` + `PAGE_COLLECTIONS.collectionsFor(pageIds)`.
3. **`firebase-bridge.js` loadAccessGrant** also reads
   `allowedCollections`.
4. **`admin-permissions.js`** writes both `allowedPageIds` and
   `allowedCollections` on every save; gains a "Recompute all
   collaborator grants" admin button.
5. **One-shot migration script** at
   [`scripts/migrate_user_permissions_add_collections.js`](../../scripts/migrate_user_permissions_add_collections.js).
   Default dry-run; `--commit` flag actually writes.
6. **Bookkeeping**: `sw.js` 181 → 182, CHANGELOG + ARCHITECTURE.

## Risks + mitigations

See `~/.claude/plans/think-about-all-the-quiet-badger.md` for the full
19-entry risk register. The biggest:

- **R4 (existing collaborators lose access):** addressed by mandatory
  migration script before rules deploy; V3.212 ships helpers but
  gates nothing.
- **R3 (mapping incomplete):** admin UI shows resolved collections list
  under each pageId so admin sees what they're granting.
- **R10 (mapping changes later):** "Recompute all" admin button walks
  every userPermissions doc and re-derives `allowedCollections`.

## Deploy order

```bash
# 1. Dry-run migration (no writes)
node scripts/migrate_user_permissions_add_collections.js

# 2. Inspect output; confirm allowedCollections values make sense

# 3. Commit migration
node scripts/migrate_user_permissions_add_collections.js --commit

# 4. Deploy rules (just the new helpers — no clause uses them yet)
firebase deploy --only firestore:rules

# 5. FTP repo (sw.js, page-collections.js, admin-permissions.js,
#    firebase-bridge.js, plus the updated nav-bearing HTML pages)
```

## Rollback

`firebase firestore:rules:rollback` reverts rules. The migration script
writes only the new `allowedCollections` field (merge-set), so existing
data is untouched — leave the new field even if rolled back; old client
code ignores it.

## Done when

- Helpers deployed; no rule clauses use them yet.
- Every existing `userPermissions/{uid}` doc has `allowedCollections`
  populated (migration ran in commit mode).
- Admin matrix saves both fields together; "Recompute all" button
  successfully walks every userPermissions doc.
- `loadAccessGrant` exposes `allowedCollections` for inspection.
- Smoke test on a real account: regular lab member access unchanged;
  admin matrix shows resolved collections; collaborator with library
  grant has `{papers? no, items: yes}` in their userPermissions doc.

V3.213 will start applying `collabMay('<coll>')` to actual rule
