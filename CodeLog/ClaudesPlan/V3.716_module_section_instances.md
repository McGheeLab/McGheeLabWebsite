# V3.716 — Learning Modules sections become independent instances

## The report

Alex: *"in the classes, I make new tabs or sections for various learning modules,
but the learning modules i put in inherit from a common one and just replicates.
I need each section that I put into any class to have its own instance of
whatever type of section I add."*

## Goal

Each "Learning Modules" section in a class owns its own list of lessons. Add,
delete, reorder, publish and homework-link act on that section alone, and each
placement has its own URL.

## Root cause

Two defects, one visible and one latent behind it.

**1. The section body ignored its own section.** `renderSectionBody` passes the
`section` object to every component — `text`, `richtext`, `files`, `speakers`,
`whiteboard`, all the BME295C ones — except this line:

```js
case 'modules':
  return renderModulesBody(editing);   // ← `section` never passed
```

`renderModulesBody` then read the single class-wide `_classData.modules`. One
array, N sections, N identical renders; `+ Add Module` in any of them pushed onto
the same array. The bug was a missing argument — nothing throws, nothing logs,
and it reads as correct in review. It is only visible to someone using the thing.

**2. The route was keyed on the bare filename.**
`#/classes/{classId}/modules/{htmlFile}`, resolved by
`modules.findIndex(m => m.htmlFile === moduleFile)` — first match wins.
`modules/manifest.json` holds **seven** files named `overview.html`
(`cell_culture`, `equipment`, `foundations`, `heat_transfer`, `optics`,
`solid_mechanics`, `surface_functionalization`). So even with the sections
separated, two placements of the same basename were one page, and the *first*
row's `folder` was used to build the iframe src — the second lesson silently
served the first lesson's content.

This second defect was already live in the **teacher program**, independently of
sections: `buildModules(grantedFolders)` in `rm/js/admin-teachers.js` walks every
granted folder, so a teacher granted `optics` **and** `equipment` gets two
`overview.html` rows, and `teacher-classes.js`'s module list linked by filename.
The second module was unreachable.

## Approach

Add one field, `sectionId`, to each entry of `schedules/{id}.modules[]`. The array
stays flat and class-wide — no schema move, no rules change, no index change — and
is **partitioned** by `sectionId`. Every read filters; every write stamps.

Three invariants drove the design:

**Nothing may be silently lost.** A normalizer, `ensureModulePlacements()`, runs on
load and on every canvas refresh: an entry with no `sectionId` (everything authored
before V3.716) or one pointing at a section that has since been deleted is adopted
by the **first** Learning Modules section. Deleting a section therefore re-homes its
lessons instead of orphaning them. The normalizer deliberately does **not** call
`markDirty()` — it mutates in memory and rides along on the next real save, which
is the entire migration. There is no migration script and no admin button.

**Teacher-classes must be untouched.** They are created with `tabs: []`
(`rm/js/admin-teachers.js`) and rendered straight off `schedule.modules` by
`teacher-classes.js`. The normalizer bails when a class has no modules section at
all, so no `sectionId` is ever stamped on one and their navigation stays class-wide.

**Old links must keep working.** The route now carries a placement id, but
`wireModuleViewer` resolves **id first, filename second**. Pre-V3.716 bookmarks,
`hw466ModuleHref`'s direct opens, and anything else passing a filename all still
land — on the first match, i.e. exactly today's behaviour.

## Decisions

**Student state stays keyed on the lesson, not the placement.** Considered and
rejected: keying the notes whiteboard (`schedules/{classId}/notesBoards/{key}_{uid}`)
and homework progress (`hwProgress/{assignment}_{uid}`) by placement id. Two
arguments against. First, it is wrong on the merits — a student's notes on a lesson
belong to the lesson; if a teacher files the same lesson under two sections, the
student should not find their notes gone. Second, every existing board and
`hwProgress` doc is keyed by filename or by a hard-coded assignment slug, so
re-keying would make them all invisible without a backfill sweep. Confirmed with
Alex before implementing. `&mod=` is still passed into the iframe, because the
module's own header needs it for prev/next, but nothing keys storage on it.

**Also fixed `teacher-classes.js`, against the original plan.** The plan said leave
that link alone as "churn with no benefit". That was wrong: the two-granted-folders
collision above is a live break, and the fix is `m.htmlFile` → `m.id || m.htmlFile`
on one line, resolved by machinery this version already adds.

**Scope held to Learning Modules.** `whiteboard` sections (one class-wide board set),
legacy same-key `files` sections (`storagePath = reg.path`, so two "Lecture Notes"
sections share their uploads), and `speakers` all still share class-wide. Each is a
real instance of the same class of defect and each needs its own migration story;
Alex chose to fix Learning Modules only. Recorded here so the others are not
mistaken for oversights.

## Files modified

| File | Change |
|---|---|
| `class-builder.js` | `modulesSections()`, `ensureModulePlacements()`, `modulesForSection()`; `case 'modules'` passes `section`; `renderModulesBody(editing, section)` filters; add-buttons carry `data-section-id`; `openAddModuleModal(kind, sectionId)` stamps it and orders within the section; `.cb-mod-move` swaps within the section; public href by `mod.id`; `wireModuleViewer` resolves id-first with section-scoped prev/next and appends `&mod=` |
| `modules/shared/module-header.js` | `getModuleRef()` reads `?mod=`; id-first resolve; section-scoped prev/next and lesson count; `moduleLink(mod, classId)` now takes the module so sibling links carry the placement id |
| `teacher-classes.js` | module list links by `m.id \|\| m.htmlFile` |
| `scripts/tests/module-placements.test.mjs` | NEW — 54 assertions, layer 1 |
| `scripts/tests/run-all.sh` | registers the new fixture in layer 1 |

No `firebase deploy`: `sectionId` is a new field inside an existing array on
`schedules/{id}`, which `firestore.rules:425` already permits, and the schedule doc
carries no `hasOnly` whitelist.

## Verification

`scripts/tests/module-placements.test.mjs` — 54 assertions, and it **extracts the
functions under test out of `class-builder.js` at run time** rather than
reimplementing them, so it cannot drift into testing a copy. Covers: migration of a
pre-V3.716 class; a later-added section starting empty; non-modules sections never
being placement homes; orphan adoption on section delete; teacher-class
`tabs: []` byte-identity; the two-sections-render-different-HTML regression guard;
per-section numbering, publish filtering and reorder-arrow disabling; id-first
routing with the right folder for two `overview.html` placements; the filename
fallback; the un-resaved-doc adoption path; the teacher-class two-folder collision;
and unpublished direct opens.

Layer 1 whole: 244 assertions green.
