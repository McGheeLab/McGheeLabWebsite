# V3.819 — "+ Item" in the Chrome extension: scrape a vendor page, add it to a purchase request

**Date:** 2026-10-21 · **Builds on:** V3.813–V3.816 · **Backend:** none (per-user `userData` subcollection, already
owner-only in the rules) · **Extension:** `ResearchManagement/extension/` (McGhee Lab Capture, MV3) · FTP-only for RM

Alex: *"I want to add a +item via the chrome extension. this should scrape the page we are on for items to buy. then the
user can add that item to the procurement request. only when the procurement is approved does the item get added to the
database."*

## The flow

1. **On any vendor page** the extension's content script scrapes the items for sale (`scrape-items.js`): JSON-LD
   `Product` / `ItemList` / `Offer`, schema.org microdata, Open Graph `product:*`, vendor-specific selectors (Fisher /
   Thermo, Sigma / MilliporeSigma, VWR, Amazon, McMaster-Carr, Cole-Parmer, Digi-Key, Grainger, BuyWays / Jaggaer), the
   page title as a last resort, and the current text selection as "use what I highlighted". The toolbar badge shows
   **+** when items are found and no paper was.
2. **In the popup** a section *Items to buy on this tab* lists them: name, vendor · catalogue #, price, with **+ Add**.
   Every field is editable (scrapers are never perfect), plus quantity and an optional note. **Add to request** writes
   the item to the person's own queue, `userData/{uid}/procurementCaptures/{id}`, and offers **Finish the request in
   RM**, which opens `procurement.html?capture=<id>`.
3. **On the Procurement page** the New-item composer opens prefilled from the capture (item, vendor, catalogue #,
   link, unit cost, quantity, the note as the first line of "why", and the capture as the first price-comparison row,
   marked as the chosen source). The person completes what only they know — project, one-time or recurring, why — and
   submits. The ticket is `requested`, as every ticket is. A strip above the composer, *Captured in your browser (N)*,
   lists any captures not yet used, each with **Add to request** and **Discard**, so a closed tab loses nothing.
4. **Only approval puts it in the database.** Submitting marks the capture `used` (with the ticket id) and nothing else.
   The item appears in the *Reorder existing* catalogue only when the ticket reaches `approved` (V3.816's
   `catalogue()` rule), and in Inventory only when it is put away. A denied or withdrawn request leaves no trace in
   either.

## Data

`userData/{uid}/procurementCaptures/{id}`:

| field | from |
|---|---|
| `name`, `vendor`, `catalogueNumber`, `url`, `price` (number or null), `priceText`, `currency`, `packSize`, `description`, `image` | the scrape, as edited in the popup |
| `quantity`, `note` | the popup |
| `sourceUrl`, `sourceHost`, `source` (`jsonld` · `microdata` · `og` · `vendor` · `title` · `selection` · `manual`) | the page |
| `status` (`captured` → `used`), `ticketId`, `capturedAtIso`, `capturedByUid`, `extensionVersion` | the extension / the page |

Rules: `match /userData/{userId}/{document=**}` is already owner read/write; the extension signs in with the same Google
account as the site, so the uid matches. No `isExtensionMember()` allowlist applies to purchasing — any lab member who
can open Procurement can capture. The ticket's create path is unchanged (`source: 'extension'`, `captureId` added).

## Decisions

- **Queue, not a direct ticket from the popup.** The request form is where project, purchase type, why and the price
  comparison are enforced and where the approver reads them; a ticket written from a 340-px popup would skip all of it.
  The popup collects what is cheap at capture time and hands over in one click.
- **Per-user queue under `userData`** — private, no rules change, no new collection, the same pattern as paper captures
  (`pending_captures`) without the allowlist.
- **Many items per page** — a cart or results page yields several; each becomes its own request (the purchaser batches
  them on one PO).
- **Dev server zips `extension/` on every download** (`/api/extension/download.zip`), so editing the folder is the
  release; the production Library link points at that dev route and does not work from the static host — pre-existing,
  noted for Alex.
