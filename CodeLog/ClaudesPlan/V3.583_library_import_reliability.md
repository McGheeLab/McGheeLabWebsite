# V3.583 — Library import reliability: stop lying about failures

## Where this came from

Gabriel reported that importing a PDF into the library logged the DOI
metadata but "the actual pdf is not getting stored." His console showed a
Storage 404, a `408 (Offline)`, `pending_captures` permission denials, a
CORS block on Semantic Scholar, and a service-worker `TypeError`.

Forensics (Cloud Functions logs + Storage object metadata + Firestore
`createTime`) say his imports **worked**:

| Time (UTC, 2026-07-29) | Event |
|---|---|
| 17:37:18 | `librarylookup` — import #1 |
| 17:39:34 | `deletePaper marks-2025-cellsamfoundation by gabrieldeclercq@arizona.edu (admin=false, uploader=true) — blob=true` |
| 17:39:55 | `librarylookup` — import #2 (the pasted console) |
| 17:57:13 | `deletePaper` again, `uploader=true, blob=true` |
| 17:57:57 | `librarylookup` — third try, metadata-only ("+ Add by DOI") |
| 17:58:28 | `fetchpaperpdf` — ↻ auto-fetch, Unpaywall, success |

`uploader=true` is derived from `meta.library.pdf.uploaded_by`
([functions/library.js:170](../../functions/library.js)), and that stanza
only exists when `uploadPdf()` resolved — so both imports had a real PDF
in Storage. **He deleted two working imports** because the page told him
they hadn't worked, then fell back to add-by-DOI + auto-fetch.

The bug is therefore not in the upload path. It's that several layers
answer a failure with something that looks like success, so the user (and
the next reader of the console) can't tell what actually broke.

## The four defects

1. **`sw.js` fabricates responses.** `networkFirst` / `cacheFirst`
   returned `new Response('', {status: 408, statusText: 'Offline'})` when
   the network failed with nothing cached. For a `<script>` under `/rm/`
   that reads as "this file isn't here": the page keeps loading and the
   module's global is simply absent. His `408` was on the workflow shell.
2. **Absent `RM_RUNTIME` is read as "localhost".**
   `window.RM_RUNTIME && window.RM_RUNTIME.isDeploy` is falsy both on
   localhost and when `runtime-mode.js` never ran — opposite meanings.
   With it absent, [rm/js/library-paper.js](../../rm/js/library-paper.js)
   points pdf.js at `/api/library/pdf-proxy`, which exists only under
   `server.py`. Metadata panel renders, PDF never does. That is exactly
   the reported symptom, and 1 → 2 is a complete causal chain.
3. **A guaranteed-denied query on every page load.**
   `pending_captures` is gated on `isExtensionMember()`; both
   `labConfig/extensionMembers.emails` and `guestEditors.emails` are
   **empty arrays**, so for every non-admin the read is denied by
   construction — once on load and again on every window refocus (4× in
   his paste). Scariest line on screen, unrelated to his task.
4. **Semantic Scholar can't be called from a browser.** No
   `Access-Control-Allow-Origin` for `mcgheelab.com`, so import-time
   enrichment (references / cited-by / abstract / tldr) has *never* run
   on the deploy — it logged "SS fetch failed" and moved on. The SW made
   it worse: the rejected cross-origin fetch fell into
   `staleWhileRevalidate`'s `.catch(() => cached)`, resolved `undefined`,
   and `respondWith(undefined)` threw `Failed to convert value to
   'Response'`.

Plus one hazard found while tracing, not part of his report:
`_saveItems()` rewrites all ~158 `type=='paper'` docs per import and
deletes any doc absent from the caller's in-memory list, so a stale tab
can delete a row someone else just added. V3.485 already moved the
paper-import flow to a direct single-doc `set` for exactly this reason.

## Changes

**[sw.js](../../sw.js)** (CACHE_VERSION 556 → 557)
- Cross-origin requests are handled only for `gstatic.com` / `jsdelivr.net`
  (the two CDNs we deliberately cache); everything else passes straight
  through. Replaces the per-host Firebase/Google opt-outs with a rule that
  can't miss a host, and takes the SW out of the path of third-party APIs.
- `fetchOnceRetried()` — one retry before giving up (GETs have no body, so
  re-issuing the Request is safe).
- No strategy fabricates a response any more: with nothing cached, the
  real network error propagates. `staleWhileRevalidate` can no longer
  resolve `undefined`, and swallows the background rejection when the
  cached copy already answered.

**[rm/js/library-paper.js](../../rm/js/library-paper.js)**,
**[rm/js/api-firestore-adapter.js](../../rm/js/api-firestore-adapter.js)**
- `_isDeployRuntime()`: use `RM_RUNTIME` when present, else fall back to
  the same hostname test `runtime-mode.js` uses. Absent global no longer
  means "local".

**[rm/js/library-sync.js](../../rm/js/library-sync.js)**,
**[rm/js/library.js](../../rm/js/library.js)**
- `_isCaptureMember()` (memoized per page): admin, or the user's email in
  `labConfig/extensionMembers` — a doc every signed-in user may read.
  Non-members get `{notMember: true}` and no query is issued.
- `_runCaptureSync` sets `_captureSyncUnavailable` on that, so refocus
  stops re-asking; an explicit "Sync captures" click gets one plain-English
  toast instead of a console error.

**NEW [functions/semantic-scholar.js](../../functions/semantic-scholar.js)**
- `semanticScholarLookup` HTTP function, modelled on `libraryLookup`:
  bearer ID token + `users/{uid}.role != 'guest'`, POST
  `{id, kind:'paper'|'citations', limit, refresh}`, returns the raw
  Semantic Scholar JSON so the client normalizers are untouched. The URL
  and field list are server-owned and the id is validated against
  `DOI:/ARXIV:/PMID:/PMCID:/CorpusId:/MAG:/ACL:` or a 40-hex paperId, so
  this can't become an open fetch proxy. One 429 retry; 7-day
  `metadataCache` (shorter than `libraryLookup`'s 30 days — citation
  lists grow, published metadata doesn't); 404 → "not indexed yet"
  rather than a 502.
- [rm/js/paper-semantic-scholar.js](../../rm/js/paper-semantic-scholar.js)
  now POSTs to it. `window.PAPER_SS` API unchanged
  (`lookupId` / `fetchPaperEnrichment` / `fetchCitations` / normalizers),
  so `library-upload.js` and `paper-cited-by.js` need no edits.

**[rm/js/library.js](../../rm/js/library.js)** — single-doc writes
- New-PDF import, attach-to-existing, add-by-DOI, and the star toggle all
  use `_saveOne()` instead of `_saveItems()`. `_saveItems` keeps one
  caller (the capture-sync merge, genuinely multi-row) and now carries a
  comment saying why nothing else should use it.

## Key decisions

- **Propagate errors instead of synthesizing them.** A fake 408 is worse
  than a failed request: the browser can't retry it, the console can't
  explain it, and the app runs half-initialized. Both layers of the chain
  are fixed, not just the symptom — the SW stops lying *and* the consumer
  stops guessing.
- **Don't populate the allowlists in code.** Adding students to
  `extensionMembers` also grants annotation-group writes and capture
  rights; that's a permissions decision for Alex via Settings, not a side
  effect of a bug fix. The code change makes a non-member's page quiet
  either way.
- **Server owns the Semantic Scholar URL.** Accepting a client `fields`
  string or URL would be the easy port and an SSRF-shaped mistake.

## Deploy

1. `firebase deploy --only functions:semanticScholarLookup`
2. FTP the tree (`sw.js` 557 forces the SW/asset refresh).

No `firestore.rules`, `storage.rules`, or index changes. `metadataCache`
is already Admin-SDK-only.
