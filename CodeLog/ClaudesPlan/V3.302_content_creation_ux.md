# V3.302 — Content-Creation UX Overhaul (Stories / News / Student Dashboard)

## Goal

Make creating stories and news posts safe, forgiving, and rewarding for
students, and give RM's home page a student-centric "what needs my
attention" glance. Driven by a full UX review (2026-07-11) of the
content-creation flows in `user-system.js` and the RM dashboard.

## Findings driving this version

1. **Publish bypass (security):** `Auth.canPublish()` is client-only —
   `firestore.rules` never validated `status`, so any signed-in
   contributor could write `status:'published'` directly.
2. **Hard project dependency:** stories require a published
   `projectPackages` doc, but only admins can create projects → a student
   with no matching project cannot write a story at all.
3. **Draft loss:** no autosave, no unload guard; media for a brand-new
   story uploaded to a throwaway `draft_${Date.now()}` / `temp_…` Storage
   path that never matched the final doc id (orphaned files).
4. **Opaque rejection:** admin "Reject" silently flipped status →
   `draft` with no reason and no author notification.
5. **Preview ≠ published render**; plain-text-only sections; ~90%
   copy-paste duplication between story and news editors.
6. **RM home has no data:** landing page is a workflow picker; no "tasks
   due / mentions / meeting / my story status" glance. Task autosave
   failures were silent (`console.error` only); `prompt()` used for real
   data entry.

## Approach

### Phase 1 — trust & unblock
- `firestore.rules`: new `canPublishContent()` helper (role admin/editor
  via users/{uid}); `stories` / `newsPosts` / `projectPackages`
  create+update now require `status in ['draft','pending',
  'changes-requested']` unless publisher.
- Story editor: "✏️ Propose a new project…" option in the project select
  reveals a text field → saves `proposedProjectTitle` (no `projectId`).
  Editors/admins publishing directly auto-create the minimal project.
  Admin pending queue shows the proposed title and creates + links the
  project on approve.
- Both editors: doc id assigned up-front (`DB.newDocId(coll)`) so media
  uploads land at the real Storage path; 30s debounced autosave (drafts /
  changes-requested only — never mutates pending/published status);
  `beforeunload` dirty guard.
- Admin queue: "Reject" → "Request changes" with a required reason
  textarea; sets `status:'changes-requested'` + `reviewNote` +
  `reviewedAt`. Author sees the note as a banner on the dashboard list
  item and inside the editor.

### Phase 2 — feedback loop & authoring polish
- Shared editor internals in `user-system.js` (single
  `sectionBlockHTML`, `setupSectionEditor` media/section engine with
  V3.301 3D-viz support, `setupTeamPicker`, `createEditorAutosave`)
  consumed by the story, news, AND project editors. (Done in a second
  pass after the concurrent V3.301 session finished, to avoid stomping
  its in-flight edits to the same functions.)
- Dashboard status strip (`#dash-status-strip`): pending ⏳ /
  changes-requested ✏️ / recently-published 🎉 banners for the signed-in
  user's stories+news; 🎉 dismissible via `statusSeenAt` stamp.
- True preview: `app.js` exposes `McgheeLab.buildStoryFeedCard` /
  `buildNewsFeedCard`; editors preview with the exact public card
  (actions bar hidden via CSS).
- Markdown-lite: `renderRichText()` (escape → `[text](url)` / `**bold**`
  / `*italic*` / newline→`<br>`) exported as `McgheeLab.renderRichText`;
  used by `buildStoryHTML` in app.js (public render + preview). Hint
  text under section textareas.

### Phase 3 — RM "My Lab Today" strip
- New `rm/js/home-feed.js` on `rm/index.html`: tiles for tasks due soon
  (personal buckets + assigned), unread chat mentions (`chatReadState`),
  next meeting, and my story/news review status (root-site collections,
  same Firebase project). Each tile fails/hides independently.
- `tasks-buckets.js`: `saveDoc` failure now raises `TOAST.error` with
  retry; success shows a subtle one-time "Saved ✓" indicator.
- `prompt()` replaced by a shared `RM_DIALOG.prompt()` modal
  (`rm/js/rm-dialog.js`) in tasks-buckets (rename builder, new
  sub-bucket, child subtask, new builder), library DOI add, and
  workflow-chooser rename.

## Key decisions

- `changes-requested` is a first-class status (distinct from `draft`) so
  the author can see *why* and the admin queue stays clean.
- Autosave never touches a doc whose status is `pending` or `published`
  (saving would silently unpublish); it only persists `draft` /
  `changes-requested` content.
- Markdown-lite over a toolbar editor: no new editing surface, sanitized
  at render time, works retroactively on existing plain text.
- Propose-a-project keeps every story project-linked (admin converts on
  approval) per Alex's choice, rather than making projects optional.
