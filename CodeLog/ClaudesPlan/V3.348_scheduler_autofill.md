# V3.348 — Scheduler guest picker: "Auto-fill from my availability"

## Goal

When a lab member responds to a scheduler invite (the guest availability
picker — freeform paint grid or sessions slot list), one click fills in
every slot they're actually free for, derived from their My Availability
data (painted weekly schedule + week overrides + custom events + connected
calendar busy times). The fill is **additive and reviewable**: it never
un-checks anything, the member can override / paint more, and nothing is
saved until they hit Save Availability.

## Problem

Guests re-derive their own availability by hand, squinting between their
calendar and the paint grid — exactly the data RM already has. Alex asked
(2026-07-12): "on the calendar for the scheduler i want a button that says
auto fill based on my availability which derives from your calendar. you
can always override and fill in more."

## Approach

Three layers, keeping the engine data-free:

1. **Engine (`/scheduler.js`, shared public+RM) — pure compute + UI.**
   - `resolveFreeIntervals(dates, data)` — pure. Input: raw docs
     `{ templateBlocks, overrides, customEvents, calendarBusy }`; output
     `{ 'YYYY-MM-DD': [[startMin,endMin], …] }`. Replays the same
     template→override resolution ScheduleService uses (add / remove /
     replace per date), unions `type:'available'` blocks, subtracts
     unavailable + custom events + calendar busy. Standalone because
     ScheduleService's override subscription is week-scoped — a scheduler
     spanning multiple weeks needs all override dates at once.
   - `computeFreeSlotIds(schedule, expanded, freeByDate)` — pure. Maps free
     intervals onto pickable ids: sessions → `allSlots` whose
     `[slot.start, slot.end)` is fully covered on `day.date`; freeform →
     cells (`${date}-${HHMM}`) whose granule is covered.
   - Guest view: when the host supplies `config.getAvailabilityData`,
     render **⚡ Auto-fill from my availability** next to Save. Click →
     fetch docs → compute ids → additively check/paint them → status text
     "Marked N slot(s) — adjust as needed, then Save." `wireFreeformDrag`
     now returns an `{ addBlocks(ids) }` handle so the fill goes through
     the same selection set the paint uses.
   - Both functions exported on `McgheeLab.Scheduler`.

2. **Public host (`user-system.js` `wireSchedulePage`)** — the live
   surface. `fetchMyAvailabilityData(dates)`: one
   `huddleScheduleTemplates/{uid}` get + `huddleScheduleOverrides where
   ownerUid==uid` + `scheduleCustomEvents where ownerUid==uid`
   (client-filter overrides by date) via the compat SDK when
   `Auth.currentUser` exists (rules already allow any-auth read on all
   three collections). No CalendarService on the public page →
   `calendarBusy: []`; the member's painted schedule is still the source
   of truth. Signed-out external guests see no button. Because Firebase
   auth restores asynchronously after first paint, a one-shot
   `Auth.onChange` re-render adds the button once the user appears.

3. **RM editor is deliberately NOT wired.** The editor's guest preview is
   read-only by design (`wireGuestForm` only runs for the guest's own
   view — `isOwn` is false in admin preview), so passing
   `getAvailabilityData` there would render a button that does nothing.
   `calendarBusy` stays an engine-level input so a future RM surface (or
   a public-page CalendarService) can supply real calendar events without
   another engine change.

## Data model changes

None. Reads existing collections under existing any-auth read rules.

## Out of scope

Calendar-provider fetch on the public page (needs OAuth tokens /
CalendarService init there); auto-save after fill (user reviews first);
auto-fill in the sessions **builder** (admin setup) — this is guest-side.
