# V3.625 — "My projects" health header + mentor barrier-accept

**Release 3 of 4** in the My Day outcomes → PMR health program. Program
plan (decisions incl. the scoring inputs Alex picked):
[V3.623_myday_outcomes_pmr_health_program.md](V3.623_myday_outcomes_pmr_health_program.md).

## Goal

At the top of the PMR the student sees their projects and a derived
health per project — traffic light + trend + one-line why — computed
from the outcome ledger. Barriers escalate week over week until a mentor
explicitly accepts the reason, which pushes health back toward neutral.

## Changes

### NEW [rm/js/project-health.js](../../rm/js/project-health.js) (`window.PROJECT_HEALTH`)
Pure compute, no DOM; all tunables in `PROJECT_HEALTH.CONFIG`.
- `listProjectsForStudent(uid, focusAreas)` — non-archived researchFoci
  OUTPUT cards with `member_uids ∋ uid` or roadmap experiment/analysis
  `owner_uids ∋ uid` (→ `owned: true`), ∪ any card referenced by the
  windowed focusAreas' `focus_ref` (`owned: false` unless also attached).
  Silence only ever counts against `owned` projects.
- `compute({projects, items, focusAreas, reviews, weekIdFor})` over an
  8-week window (`windowMondays`):
  - unaccepted-barrier chain: −1 × chain length per week (escalating);
    acceptance (healthReviews doc naming the barrier's `item_id`)
    neutralizes the item and a fully-accepted week breaks the chain
  - all-no-result weeks: −0.5 × streak
  - past week containing outcome-less items: −0.5, capped −2
  - silence on owned projects: −1/week after 1 quiet week, capped −3
    (the unfinished current week neither counts nor breaks the run
    unless already active)
  - ≥1 result in a week: +1, capped +2
  - health = Σ last 4 weeks → `healthy ≥ −1 > attention ≥ −3 > stuck`;
    trend = last 2 weeks vs the 2 prior; `why` = dominant factor with
    the live chain read off the window TAIL (accepted barriers stop
    claiming "unaccepted")
- Attribution: `item.details.focusId → focusAreas.focus_ref.id`;
  unattributed items never touch health.

### [rm/js/pmr.js](../../rm/js/pmr.js)
- Section `project_health` ("My projects") FIRST in
  `DEFAULT_SECTION_ORDER`; renderer `renderProjectHealthBlock` — status
  dot / title link to `research.html?id=` / trend arrow / why /
  8-week icon strip / 🚧 open count; expandable barrier history;
  student-editable description line stored `doc.project_health[]
  {foci_id, description}` (additive `emptyDoc`/`hydrateDoc` backfill,
  normal `scheduleSave`).
- Loader `loadProjectHealth` (cached per uid+day): window dayPlans +
  ALL healthReviews + ranged focusAreas in parallel, then
  `PROJECT_HEALTH.compute`.
- `✔ Accept reason` on barrier rows for reviewers only
  (`canAcceptBarriers()` = `isReadOnlyView()` ∧ (admin ∨ this student's
  mentor)) → note prompt → `userData/{uid}/healthReviews/{hr-…}` via
  `healthReviewsCollRef`; health repaints immediately; accepted rows
  show `✔ accepted by <name> — <note>`.
- **project_overview replaced**: out of `DEFAULT_SECTION_ORDER`, into
  new `LEGACY_SECTIONS` (still renders for docs that pinned it in
  `section_order`; label "Project overview (legacy)"). Data untouched.

### [rm/pages/pmr.html](../../rm/pages/pmr.html)
`.pmr-ph-*` styles; loads `research-data.js` + `project-health.js`
before `pmr.js`.

### firestore.rules (deployed with V3.624's — BEFORE FTP)
`userData/{userId}/healthReviews/{reviewId}`: read owner ∥ mentor ∥
admin; create mentor ∥ admin with `reviewer_uid == request.auth.uid`
pinned; update/delete author-mentor ∥ admin. Students cannot accept
their own barriers.

## Deliberately NOT done
- Health anywhere but the PMR (no My Day badge, no push on drops).
- No stored aggregate — derived at render like every RM rollup.
- Weight tuning: CONFIG constants are first-guess; expect a tweak
  release after 2–3 weeks of real data.

## Rollback

inert; `doc.project_health` is additive and ignored by old clients.

## Verification
1. Student with a 2–3 week unaccepted barrier chain on one project:
   header shows amber/red, why says "barrier N weeks unaccepted: …",
   strip shows 🚧 cells.
2. Mentor accepts with a note → ✔ line renders, health recomputes
   toward neutral on the spot; student sees the note on their own PMR.
3. Description line saves (owner) and is read-only for reviewers.
4. New PMR docs show no Project overview block; an old doc that pinned
   it still renders it with the "(legacy)" label.
