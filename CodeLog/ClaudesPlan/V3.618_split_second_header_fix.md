# V3.618 — Fix: second header inside split-view panes

## Symptom (Alex's report, 2026-08-12)

- In a workflow, splitting sometimes shows a second header inside each
  split pane — but not always.
- Entering a workflow from the chooser (→ workflow-shell) and then
  splitting always works (single header).
- Out-of-workflow split, then re-opening in a workflow, also works.

## Root cause

Two different signals decided header rendering, and they can disagree:

- The **parent's workflow strip** renders from `sessionStorage`
  (`mcgheelab.activeWorkflow`), which survives reloads and undecorated
  navigations.
- The **panes' header suppression** (`?embed=1` + `name="rm-embed-*"`)
  keyed off `?workflow=` being present in the split-view **URL** at load
  time (`_HAS_WORKFLOW`, V3.75).

`writeState()` in `rm/js/split-view.js` rewrites the URL on the very
first tick with only `left/right/active/ratio` — the `?workflow=` param
is dropped. So the decorated strip link works on first entry, but any
**reload, back/forward return, bookmark, or duplicated tab** re-enters
split-view with a workflow-less URL: `_HAS_WORKFLOW` is false, panes get
no embed suppression, and — because same-origin iframes share the tab's
sessionStorage — each pane's nav.js adopts the active workflow and
renders its **own strip** inside the iframe. Parent strip + pane strips
= the "second header", intermittently.

A second latent bug from the same URL-rewrite: on a fresh-tab entry with
a decorated URL, `writeState()` strips `?workflow=` **before** nav.js's
DOMContentLoaded `_wfAdoptFromUrl` runs, so the workflow never reached
sessionStorage — parent would render the slim top-nav while panes were
embedded headerless.

## Fix (rm/js/split-view.js only)

`_HAS_WORKFLOW` now:

1. **Self-adopts** `?workflow=<id>` into sessionStorage at IIFE time
   (mirroring `_wfAdoptFromUrl`'s fresh-state shape, preserving an
   existing same-id state) — fixing the fresh-tab latent bug.
2. Otherwise reads **sessionStorage** — the same source nav.js's strip
   uses — so panes and parent can never disagree again, including after
   reload/back-forward.

## Not changed (by design)

Out-of-workflow split still shows the slim parent nav + each pane's full
RM nav (V3.75 decision: without a strip, the pane's own nav is the only
way to navigate that pane). Making out-of-workflow split headerless
would need parent-side swap/close controls that don't depend on a
workflow — noted as a possible follow-up, not part of this fix.
