# V3.58 — Page consolidation Tier 2: tasks subpages → tabs

## Goal

Tier 2 of the V3.57–V3.62 consolidation sweep. The Task hub previously
shipped as four separate pages (`tasks.html`, `tasks-add.html`,
`tasks-inbox.html`, `tasks-archive.html`) each with its own near-
identical shell HTML and a manual cross-link tab bar at the top.
Collapse them to a single tab-aware shell at
[rm/pages/tasks.html](../../rm/pages/tasks.html) selected via
`?tab=<dashboard|add|inbox|archive>`. Reduce 4 pages → 1 page.

## Architecture

**Single shell, lazy per-tab script load.** The four renderer JS files
(`tasks-dashboard-buckets.js`, `tasks-inbox-buckets.js`,
`tasks-archive-buckets.js`, `tasks-buckets.js`) are unchanged — each
still looks for its own container element (`#dash-content` for
dashboard/add, `#content` for inbox/archive) and boots on
`DOMContentLoaded`.

The new shell:

1. Reads `?tab=<name>` early in `<head>` and exposes it on
   `window.__TASKS_TAB` (validates against the four known names;
   default `dashboard`).
2. Renders the four-link tab bar pointing at
   `tasks.html?tab=<name>`; active class on the current tab.
3. After the shared scripts (`util.js`, firebase, firebridge,
   `local-cache.js`, etc.) load, an inline body script:
   - Populates `#task-page-header` with the tab-specific header HTML
     (Task Dashboard with "+ Add Task" + "Send to Teammate" buttons,
     or "Add Task" with a "← Dashboard" back link, or just a plain
     `<h1>` for inbox / archive).
   - Populates `#task-tab-mount` with the renderer's expected
     container div (`#dash-content` or `#content`).
   - Calls `document.write('<script src="<TAB_SCRIPT>">')` to
     synchronously inject the per-tab renderer. **Why document.write:**
     it's the simplest way to inject a parser-blocking `<script>` with
     a dynamic src so the renderer's existing `DOMContentLoaded` boot
     fires at the natural time. `document.createElement('script')` +
     `appendChild` defaults to async, which races
     `DOMContentLoaded` and would silently miss the boot listener.

The four renderer scripts stay untouched. Each one's `boot()` finds
its container by ID, fetches data, attaches LIVE_SYNC, renders. The
inactive tab's renderer is never loaded → no wasted fetches, no
container-not-found errors.

## Untouched (intentionally)

- **`rm/js/activity-subnav.js`** — its `ACTIVITY_EXTRA_PATHS` (lines
  24-28) and `TASK_PATHS` (lines 47-52) still list the legacy
  `/tasks-add.html` / `/tasks-inbox.html` / `/tasks-archive.html`
  paths. With the redirects in place those URLs immediately bounce
  to `tasks.html?tab=...`. The subnav's "Task" pill highlights via
  the existing `currentPath === '/rm/pages/tasks.html'` match —
  works correctly. Keeping the legacy paths listed harmlessly avoids
  a churn-y edit unrelated to this PR's goal.
- **`rm/pages/lab-tasks.html`** — its own internal tab bar still links
  to the legacy URLs, which redirect cleanly. Tier 2 explicitly
  leaves lab-tasks alone (admin-only cross-user assignment, distinct
  domain).
- **Renderer scripts themselves** — V3.58 is shell-only. The bucket
  workspace renderers (`tasks-buckets.js`, `tasks-dashboard-buckets.js`,
  etc.) keep their existing structure and DOMContentLoaded boot.
  Future restructuring (e.g. converting to an SPA-style tab swap that
  doesn't need a page reload between tabs) is out of scope.

## Trade-offs

- **Each tab switch is still a full page reload.** The shell + shared
  scripts + per-tab renderer all re-run. With the SW + IndexedDB cache
  in place, this is fast (~150ms cached), but slower than a
  client-side tab swap. Acceptable for now — the simpler V3.58 design
  preserves all four renderers as-is. Future V3.6x could refactor to a
  true SPA tab swap if the reload cost becomes annoying.
- **`document.write` is "old-school"** but works correctly here
  because it's called inline before `DOMContentLoaded` and the script
  load is the entire point. No CSP issues; no third-party blocking.
- **The "Add Task" tab loads `tasks-buckets.js`** (the workspace) which
  is heavier than the rest because it does lab-roster loading,
  project switching, etc. Acceptable — the user has been on this
  pattern since V3.40.

## Verification

Local dev:

```bash
cd /Users/alexmcghee/Documents/GitHub/McGheeLabWebsite
RM_WRITE_ALLOWLIST=mcgheealex@gmail.com python3 rm/server.py
# open http://localhost:8000/rm/pages/tasks.html
```

Smoke flow:

1. Sign in as lab member. Open `tasks.html` with no params → loads
   `tasks-dashboard-buckets.js`, renders the Task Dashboard with pin
   grid. Tab bar shows Dashboard active.
2. Click "Add Task" tab → URL goes to `tasks.html?tab=add`, page
   reloads, `tasks-buckets.js` loads, the adder workspace renders.
3. Click "Task List" → `tasks.html?tab=inbox`, `tasks-inbox-buckets.js`
   loads, the inbox flat-list renders.
4. Click "Completed" → `tasks.html?tab=archive`, completed list
   renders.
5. Hit `tasks-add.html` directly → meta refresh redirects to
   `tasks.html?tab=add`.
6. Same for `tasks-inbox.html` / `tasks-archive.html`.
7. From Dashboard, click row-level "Open in adder" link on a subtask
   → goes to `tasks.html?tab=add#<subtask-id>`. Hash + query work
   together.
8. From Activity Overview tile "Task Inbox" → goes to
   `tasks.html?tab=inbox`.
9. From PMR row "→ tasks" → goes to `tasks.html?tab=add`.
10. DevTools → Application → Cache Storage shows
    `mcgheelab-shell-v33`.
