## 1. What Scientia is, in one paragraph

A single-file, local-first lab notebook (IndexedDB mirrored in memory + an append-only
journal, one Python server for the notebook folder, media, recordings, device sync). Every
note is an **infinite sheet of graph paper**; everything on it is a **box (component)**: text,
a widget, ink. Boxes carry a full date-time stamp, can be **wired** to each other with typed
relations, grouped in **regions**, marked up with **structures** (claim, evidence, barrier…)
and **terms** that then find themselves across every note and open a **lens** showing
everything that uses them. `+ Insert` is a self-registering widget registry (well plate,
image panel, calculator, equation, protocol, run, PDF, HTML, slides, recording, task,
reminder, live view, material, note card, pull-in). Around the notes: projects → themes →
aims, experiment stages (Planning → Run → Analysis → Reflection), timers, a day note with
capture, tasks and reminders, a library with a PDF reader, data-by-reference, materials,
weekly review, activity, search/palette, split panes, pen/touch/handwriting, sync.

Design rules worth adopting as-is: every write goes through one model (`M.*`); the derived
index is never stored; records are replaced, not mutated; features wrap earlier functions;
widgets register themselves; the build refuses to ship on a syntax error.

## 3. The fork: two ways to "integrate it into the site"

### Path A — host Gabe's app on Firestore
Replace `03-db.js` persistence with `userData/{uid}/scientia/{store}/{id}` (per-record
last-write-wins), media and recordings with Storage, strip the server-only parts (folder,
sync, pairing, Windows ink, PowerPoint, Whisper), add RM-aware widgets (Protocol, Inventory,
Library) inside Gabe's registry, add a read-only mentor mode, nav entry, mobile bundle.

- **Gets** all ~128 features in weeks, Gabe's UX intact.
- **Costs** a second lab system: its own library, tasks, reminders, timers, materials,
  review — none of which talk to PMR, My Week, the library or inventory unless each is
  bridged. Single-writer assumptions (journal, in-memory mirror of the whole record) fight
  multi-device Firestore. Our ink recorder/replay, lens and From-paper do not apply inside
  Gabe's paper. **Whoever forks it owns the divergence** from Gabe's daily builds.
- Rough effort: 3–5 weeks to a usable Firestore build, plus the bridges.

### Path B — the Scientia pattern on the whiteboard engine (**chosen by Alex, 2026-10-22**)
The notebook entry IS a board. Widgets are items on the sheet, from a self-registering
`+ Insert` registry, with Scientia's box chrome (kind, title, stamp, collapse, ⋯, resize).
Lift Gabe's self-contained widgets (well plate, image panel, calculator, equations,
auto-replace, pickers) behind a thin adapter; rebuild the canvas-level ideas (regions, wires,
terms, structures) on our data so PMR, library, tasks, inventory and the recorder all see one
model.

- **Gets** one data model; mentors read it (rules deployed in V3.830); our ink + recorder +
  replay + From-paper; the Ourlab bundle; the figure board on the same engine.
- **Costs** rebuilding features Gabe already has; the sheet stays page-based (not an infinite
  2-D plane) — see §6.1 for why that is acceptable.
- Rough effort: Phases 1–2 ≈ 2–3 weeks, Phase 3 ≈ 2 weeks, Phase 4 open-ended.

## 4. Path B architecture

### 4.1 Canvas = the whiteboard engine
`whiteboard.js` already gives: continuous sheet, outline ink, eraser, undo, lens zoom, view
dock, items layer with ⤧ Arrange (drag / resize / two-tap remove), recording + replay, text
and image items, the `notebookBoards` family routed by `boardsCol(ownerUid, 'notebookBoards')`.
New in the engine (small, generic):

- **`type:'widget'` items** — `{ type:'widget', kind, x, y, w, pageId, z, collapsed, title,
  data:{…}, stampAt, createdBy }`. `renderItems()` renders a host-supplied body via
  `opts.items.renderWidget(item, bodyEl, api)`; the chrome (kind chip, title, stamp, ▾ collapse,
  ⋯, resize grip) is the engine's so every host gets the same box. Bodies are `pointer-events:
  auto` always; ink goes around them; Arrange lifts the whole card for moving. On touch, a pen
  down on a widget header starts a drag only in Arrange, so a resting palm never moves a box.
- **Snap + no-overlap** on Arrange drop (14 px grid in sheet units; push-down like Gabe's
  `autoLayout`), and **Tidy layout** in the toolbar.
- **`+ Insert`** button in the toolbar and on long-press / right-click of the sheet: Gabe's
  `optionPicker` UX (search, grouped rows, icon, label, sub-line). The registry is host-side.
- **Regions** (Phase 2): `S.regions` on the board doc — a named, coloured rectangle in sheet
  units with member item ids and member stroke ids; drawn with a ⬚ Region tool (drag) or from
  a lasso of strokes. This is also the unit that becomes a panel.
- **Lasso** (Phase 2): select strokes by polygon; move / delete / *Make panel* / *Group as ink*.
- **Export** draws widgets as a titled box with their text (`drawTextItem` precedent).

### 4.2 The shared host module — `rm/js/canvas-widgets.js`
`window.CANVAS_WIDGETS` = registry + picker + chrome helpers used by both hosts:

```
CANVAS_WIDGETS.register({ kind, group, icon, label, sub, w, when, create(ctx, at), body(item, el, api), menu(item), summary(item), text(item) })
CANVAS_WIDGETS.insertMenu(handle, anchorOrPoint)     // the picker; calls create → handle.addWidget()
CANVAS_WIDGETS.mount(handle, { kinds:[…], onChange })  // wires renderWidget + save + collapse
```

### 4.6 Drawn regions → panels (figure board)
1. Draw with the pen as today. Select the drawing with **Lasso** (polygon over strokes) or
   **⬚ Region** (drag a rectangle). The selection becomes a region (name, colour) — still ink.
2. **Make panel**: the engine rasterises the member strokes with `paintStroke` into an
   offscreen canvas at 4× the page width (same renderer as export, so it looks like the
   board), crops to the region, uploads `paper-boards/{paperId}/{bid}/panels/{id}.png` (+ a
   medium webp), and creates a `panel` widget at the region's place with the next letter and
   an empty caption. The source strokes are hidden (`hiddenBy: panelId`), not deleted, so
   **Reopen ink** restores them and the ink timeline for the recorder stays intact.
3. **Clean up** on the panel: re-render with background removed, strokes thinned to a uniform
   width and colour, optional auto-crop to content; also *Replace with image* (upload / From
   paper / from the paper's own figure blocks) and *Promote to a manuscript figure* (writes a
   figure block through `PAPER_FIGURES.uploadImage` — the deferred V3.609 promotion).
4. **Collapse** folds the panel to its letter + caption line; several collapsed panels line up
   as a strip, which is how a figure's panel plan reads at a glance.
5. Notebook boards get the same tool later (a sketch → a figure widget cell).

### 4.8 Handwriting → text: the local ink helper
Alex wants an ink recognizer on the local machine, Mac or Windows. Gabe's model is the right
one: the browser posts the strokes to a tiny local server. We ship an **Ourlab ink helper**,
one small program per platform. Mac uses Apple's Vision text recognition
(`VNRecognizeTextRequest`) on a rasterised image of the strokes; Windows reuses Gabe's
`winink.py` (WinRT InkRecognizer: cursive, offline, nothing to install beyond Python). Both
answer `POST http://127.0.0.1:8767/ink/read` with CORS and
`Access-Control-Allow-Private-Network: true`, which Chrome and Edge accept from an https page
(Safari does not, so the iPad gets the fallback). The site probes the helper on load and shows
✍ *Convert to text* on a lasso only when a recognizer is reachable; the fallback is an
`inkRead` Cloud Function on Google Cloud Vision handwriting OCR, cost-gated per person per
day. The ink is kept (`hiddenBy` the new note widget), like Gabe's *Show the handwriting*.
The same helper carries **transcription** (faster-whisper, Gabe's `sttread.py`) for people who
prefer local over the cloud function.

### 4.9 A local version that syncs with the site
The capability stays; the mechanism is Firestore rather than a hub computer. The Ourlab app
(iPad / phone) already bundles `rm/` and runs Firestore with offline persistence, so a notebook
opened once keeps working offline and syncs when back online; on Mac and Windows the site
installs as a PWA (manifest and `sw.js` exist) with the same persistence flag (V3.578–581
local-first layer). Gaps to close in Phase 3: a Storage **upload queue** for images, panels
and recording chunks made offline (IndexedDB-backed, retried on reconnect, the widget shows
*waiting to upload*); conflicts = last write wins per item plus the recorder timeline; the ink

that is a separate translation bridge (Scientia `documents`/`blocks` ↔ RM entries and board
items; the ink models differ) and is not in Phases 1–3.

## 5. Lit review mode (the terms idea, as Alex refined it)

What Alex wants: a widget in the notebook that searches papers for a term; the papers it finds
become paper links in the notebook (a lit review); highlighted content from those papers can be
pulled into the notebook; sections of the review distil into key points; the review can be
added to a paper's figure board, where only the key points show as a bullet list, and every
paper in it is then automatically associated with the paper being written. This fixes
"students read papers but never link them to the paper they are writing" at the point where
the reading happens.

### 5.1 The `litreview` widget (notebook canvas, Phase 2)
Data on the item: `{ title, query:{ terms:[…], text }, sections:[{ id, title, paperIds:[…],
notes_html, keyPoints:[{ text, paperIds }] }], papers:{ itemId:{ addedAt, why, highlightIds,
source:'library'|'ss' } }, keyPoints:[…], usedBy:[paperId…] }`.
- **Search.** A term or free text runs against the library first: title, keywords, abstract
  and authors on the cached `items.json` list, plus `terms[]` stamps (§5.4) and the reader's
  highlights (`textQuote.exact` across `papers/{itemId}/annotations`, lab and own). Title and
  keyword hits rank above abstract-only hits; each row shows *why* it matched (the phrase or
  the highlight). **Outside the library**, the same box searches Semantic Scholar through the
  existing `functions/semantic-scholar.js` proxy; a result is one tap from *Add to library +
  review* (the V3.497 import path, so PDF fetch and enrichment run as usual).
- **Papers as links.** A paper in the review is a **paper card** inside the widget (title ·
  first author · year · venue · ⤓ PDF · 📖 open in the reader) with the person's *why* line,
  and optionally a free-standing *Paper card* widget wired `related` to the review so the
  canvas shows the map.
- **Highlights into the notebook.** A card's ▾ lists the paper's highlights (own + lab);
  *Add* drops a `paperquote` widget (the From-paper text card from V3.830) wired to the
  review, with the p. N back-link that reopens the reader at the passage.
- **Sections.** A review has sections (*Methods we might reuse*, *Contradicting results*…);
  a paper can sit in several; each section has a notes box.
- **Distil to key points.** A section's *Distil* opens its key-points list: bullets, drag to
  reorder, each bullet cites papers in the section by chip. Fill it by hand, or **Suggest**: a
  `litDistill` Cloud Function sends the section's highlights and notes to Claude (same
  `ANTHROPIC_API_KEY` secret and pattern as `equationOcr`) and returns candidate bullets the
  person accepts one at a time. Nothing is written without an accept. The review's key points
  are the ordered union of its sections'.
- Collapsed, the widget shows the title, the paper count and the first three key points.

### 5.2 Adding a lit review to a paper's figure board (Phase 2)
- The figure board's `+ Insert` gets **Lit review…**: a picker over the author's reviews
  (and a mentee's, for a mentor; the read rules already allow it). It places a
  `litreview-ref` widget `{ ownerUid, boardId, itemId }`, rendered live from the source and
  showing **only the key points as a bullet list** (collapsed = title + count). *Open in
  notebook* jumps to the source.
- **Association is automatic.** On placement, every library item in the review is linked to
  the paper with `LIBRARY_LINKS.toggleDraftLink(itemId, paperId, true)`, the single
  concurrency-safe writer of `items/{id}.meta.library.linked_drafts`, so the builder's
  References tab, the reader's draft pills, the Evidence Inbox and the grant editor all see
  the papers at once. Papers added to the review later are linked by a small `onWrite`
  function on the source item, so it does not depend on someone reopening the board.
  Removing the ref widget asks whether to unlink the papers it brought (open decision).
- A review placed on a board is marked *in use by <paper>* in the notebook (`usedBy`), and the
  paper builder lists the reviews feeding it beside the References tab.

### 5.3 Why this beats a bare term lens
The term is still the entry point, but the unit the student works with is the review: a
curated, sectioned, annotated set with a distilled summary that travels to the paper. The lens
from the first draft of this plan survives as the **Search** panel inside the widget (results
grouped by source, co-occurring terms as pivots), not as a separate page.

### 5.4 Terms underneath (the plumbing)
`terms/{termId}` lab-scoped with forms; `terms[]` stamped on entries, library items,
protocols and inventory at write time (array-contains reads, no full-text search); a backfill
function when a term is created; `termWeights` 3/2/1 on library items so title and keyword
hits rank first. Marking a word in any Note widget (Alt+W) offers *Start a lit review for
"…"*.

### 5.5 Phasing
Phase 2: the widget with library search, paper cards, highlights-in, sections, manual key
points, the figure-board ref widget and automatic linking. Phase 3: Semantic Scholar search
with add-to-library, `litDistill` suggestions, `terms[]` stamping and the backfill, the mentor
view of mentees' reviews, review-in-use marks in the builder.
