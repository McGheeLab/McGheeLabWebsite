# V3.342 — Scheduler Page Upgrade: fix, paint UX, mobile, notifications

> First implementation step: copy this plan to `CodeLog/ClaudesPlan/V3.342_scheduler_upgrade.md` (repo ritual).

## Context

The scheduler page (`rm/pages/scheduler.html`) is a two-tab tool: **My Schedulers** (shareable invite links for talks/meetings, V3.47 port) and **My Schedule** (weekly personal availability grid, V3.55 lift). Alex reports it needs a significant upgrade: features must actually work, and any lab member should find it easy to use. Exploration confirmed:

- **🔴 Production bug:** the V3.55 lift calls `esc(...)` at `rm/js/scheduler.js:628`, `:655`, `:1167` but the file only defines `escHTML` (line 203). The My Schedule tab renders **blank** for anyone with ≥1 block or calendar event; "+ Custom Event" never opens. Only an empty schedule works.
- Time selection is clunky on three surfaces: the My Schedule drag-grid (drag → modal every time), the guest availability picker, and the admin session/slot setup.
- Mobile is bad — one lone `@media (max-width:600px)` breakpoint at `rm/css/scheduler.css:1266`; 7-day grid cells are too small to touch.
- UI is confusing — unlabeled tab purposes, three availability modes with no legend, no affordance hints.
- A `scheduler` notification toggle exists in settings but nothing ever fires it.

**User decisions (locked):** fix + polish (keep two-tab architecture); paint/toggle (when2meet-style) selection everywhere; 3-day view on phones; new capabilities = dashboard card, guest-response overview, team availability view; notifications = push on guest-submitted + slot-assigned, mailto compose for external guests; **deferred** = persistent OAuth tokens, upcoming-slot reminders, month view, redesign.

## Key facts (verified)

- Root `/scheduler.js` (1,382 lines) is the shared engine, loaded by **both** `index.html:64` (public SPA — guests use invite links there) and `rm/pages/scheduler.html:58`. Engine changes must stay backward-compatible with the public guest flow.
- The engine **already paints** via pointer events: builder freeform at `scheduler.js:511-535`, guest picker `wireFreeformDrag` at `:663-694`. The clunkiness is polish (lost drags via `pointerleave`, no `pointercancel` commit, small touch targets, weak visual feedback), not a missing interaction model.
- Participant docs: "responded" = `availability.length > 0` (see engine `:208`); assignment = `assignedSlot` field, written via `onSaveSpeaker` (engine `:1142`, `:1195`, `:1204` → `SDB.updateSpeaker` in `rm/js/scheduler.js:181-199`).
- Push harness: `functions/helpers/notify.js` → `sendToUsers(db, messaging, uids, {title, body, url, tag}, appKey)`. Per-domain trigger files follow `functions/equipment.js` pattern (v2 `onDocumentCreated`/`onDocumentUpdated`), exported through `functions/index.js:61+`.
- **No email infrastructure exists** in functions/ — hence mailto compose.
- Team overlap primitive exists: `McgheeLab.ScheduleService.resolveAvailabilityOverlap` (`rm/js/schedule-service.js:247-282`), already used by huddle (`rm/js/huddle.js:2379-2393`).
- Dashboard card helper: `card(title, count, body, link)` at `rm/js/dashboard.js:71`.
- Firestore rules: `schedules` public-read, `participants` public-read + update-by-invite-key — **no rules changes needed**. New queries (`participants where scheduleId ==`, `where speakerUid ==`) are single-field, **no new indexes**.
- Next plan number: V3.342 (V3.332 exists). `sw.js` CACHE_VERSION currently 303.

## Approach

### 1. Bug fixes (do first — independently shippable)
`rm/js/scheduler.js`: add `const esc = escHTML;` alias next to line 203 (one line, fixes all three call sites); remove duplicate comment at 874-875.

### 2. Paint interaction — My Schedule grid (`rm/js/scheduler.js`)
Replace drag-then-modal with direct painting driven by the existing mode selector (lines 668-679):

- The three modes (General availability / Special available / Special unavailable) become a segmented control with color swatches matching block colors; the active mode is what painting creates.
- `pointerdown` on a cell starts painting (`setPointerCapture` + `elementFromPoint` tracking, same technique as engine `:686`); painting over cells already covered by a block of the **current mode** erases/trims instead (when2meet toggle semantics). Handle `pointercancel` by committing, not dropping, the paint.
- On `pointerup`, merge contiguous painted cells per day into one block and persist via existing `ScheduleService` calls: General mode → template block (`saveScheduleTemplate`), Special modes → this-week override (`addScheduleOverride`) — same semantics the modal encodes today.
- Erase = delete block if fully covered, trim edges / split if partially covered (client-side block-list math, then save the updated set).
- No modal on create. Details (reason, rigidity) remain editable by tapping a block → existing `showScheduleBlockEditor` (line 1038) unchanged. `showNewScheduleBlockModal` (926-1035) is retired; keep a small "+ Block" button that opens the old modal path for keyboard/precision entry.
- Custom events keep the existing button + modal flow.

### 3. Paint polish — engine surfaces (`/scheduler.js`, shared with public SPA)
Additive/behavior-preserving changes only:

- `wireFreeformDrag` (:663) and builder freeform (:511): commit on `pointercancel` (currently drops), don't end drag on `pointerleave` while pointer is captured, add `touch-action:none` where missing, add a "painting" visual state and a selected-count live readout ("12 slots selected").
- Sessions-mode guest picker: convert the checkbox list to tappable slot chips (larger targets), same data flow.
- Admin session/slot setup (builder): larger cells + paint-preview highlight; day selection becomes tap-to-toggle chips.
- Guest form: clearer step headers ("1. Pick your times → 2. Your details → 3. Save"), bigger Save button, saved-state confirmation.

### 4. Mobile — 3-day window + responsive pass (`rm/js/scheduler.js`, `rm/css/scheduler.css`)
- `renderMyScheduleHTML` (:544) gains a day-window state: on `matchMedia('(max-width: 700px)')`, render 3 of 7 days with ‹ › arrows and swipe to shift; desktop unchanged (7 days). Window offset lives in module state alongside `_weekOffset`.
- Standardize the stray 600px breakpoint to 700px; add responsive rules for tabs, mode selector, modals (full-width sheets on phones), and engine grids (min touch cell size 40px, horizontal scroll where days overflow).

### 5. UI clarity (`rm/js/scheduler.js`, `rm/css/scheduler.css`)
- Tab relabels with one-line subtitles: **"My Availability"** ("When are you free? Paint your weekly schedule.") and **"Scheduling Links"** ("Create a link, collect availability from guests, assign slots.").
- Mode legend chips (color → meaning) above the grid; one-line paint hint ("Tap or drag to paint. Tap a block to edit.") shown until dismissed (flag stored in `userSettings.{uid}.scheduleLayer`, same doc the layer config already uses).
- Empty states on both tabs with a 3-step "how it works".
- Keep it a focused tool — hints are one line each, no reference text (per feedback_focused_tools_not_references).

### 6. Guest-response overview + copy-link (`rm/js/scheduler.js` — My Schedulers list)
- In `paintList` (:263-354), for each scheduler query `participants where scheduleId == id` (public-read, small N), count responded (`availability.length > 0`) and assigned (`assignedSlot`) → badge per row: "4 / 7 responded · 2 assigned".
- Add a per-row "Copy invite link" button reusing the `buildInviteURL` logic (:492-495) so owners don't have to open the editor.

### 7. Team availability — third tab "Team" (`rm/js/scheduler.js`)
- New tab reusing `resolveAvailabilityOverlap` (`schedule-service.js:247-282`) and huddle's rendering approach (`huddle.js:2379-2393`): member multi-select (from `users` lab members), pick a day/week, show overlap windows read-only. Reuses the same week-navigation controls as My Availability.
- Read-only; no new collections (reads `huddleScheduleTemplates`/`huddleScheduleOverrides`, already auth-readable).

### 8. Dashboard card (`rm/js/dashboard.js`)
- New "Scheduler" card via the `card()` helper (:71): count = pending responses across schedulers you own (participants not yet responded); body = your next assigned slot if any (`participants where speakerUid == uid` with `assignedSlot`); link → `/rm/pages/scheduler.html`. Wrap in try/catch like the Library card (:184).

### 9. Notifications (`functions/scheduler.js` NEW, `functions/index.js`)
New trigger file mirroring `functions/equipment.js`:

- `onParticipantUpdated` — `onDocumentUpdated('participants/{key}')`:
  - **Guest submitted/updated availability:** `before.availability` differs from `after.availability` (compare sorted-join) → read `schedules/{after.scheduleId}` → `sendToUsers(..., [ownerUid], {title: 'Availability received', body: '<name> responded to <schedule title>', url: '/rm/pages/scheduler.html', tag: 'sched-avail-<key>'}, 'scheduler')`. Skip if the writer is the owner (no self-notify — compare `after.speakerUid`/owner where derivable; acceptable to notify on admin-entered availability edits, low volume).
  - **Slot assigned:** `before.assignedSlot !== after.assignedSlot && after.assignedSlot && after.speakerUid` → push to `after.speakerUid` ("You've been scheduled: <slot label> — <schedule title>").
- Export via `functions/index.js` require + `module.exports` (pattern at :23, :61+).
- The `scheduler` appKey toggle already exists in settings — respected automatically by `sendToUsers`.
- **Mailto for external guests:** in the engine admin roster (near the assign `<select>` handler, engine `:1139-1146`), when a speaker has `email` + `assignedSlot`, render an "✉️ Email guest" `mailto:` link prefilled with subject (`Your <schedule title> slot is confirmed`) and body (slot day/time + invite link). Pure HTML, additive, safe for the public SPA.

## Data model changes

None. No new collections, no `firestore.rules` changes, no new composite indexes. New client queries are single-field on public-read collections.

## Out of scope (deferred)

Persistent OAuth token storage (tokens stay sessionStorage), upcoming-slot reminder function, month view, page redesign, equipment tie-in, block-edit modal rework, automated guest email (mailto only).

## Release ritual

1. `firebase deploy --only functions` **first** (new triggers are inert until participant writes occur; deploying first means no window where UI implies notifications that can't fire).
2. Bump `sw.js` CACHE_VERSION; update CHANGELOG + ARCHITECTURE.
3. FTP push via Cyberduck (root `scheduler.js` + `index.html`-served assets AND `rm/` tree — remember the engine is served from site root).
4. `python3 scripts/version_push.py` for branch/version bookkeeping.

## Rollback

- Static: git revert + re-FTP (engine + rm/ tree together).
- Functions: `firebase functions:delete onParticipantUpdated` or redeploy previous index.js.
- No data migrations; nothing irreversible.
