# V3.979 — Scientia: a link a site keeps from the app opens in your browser; the page you save comes in by itself

Gabe, 11 Nov 2026, on V3.977's saved-page route: "If given a website link, it should do that pipeline automatically."

## Choice
Three ways were put to Gabe after an app-driven browser window was stopped as getting past the sites' checks for robots:
(1) allow that window, (2) open the link in his own browser and take the page he saves from his Downloads folder,
(3) a browser extension. He chose (2): the browser stays entirely his (his sign-ins, his answers to the sites); the app only
opens a link, as a click does, and reads the file he saved.

## Approach
1. `webcap.py`: `Blocked` marks a refusal that this route can take. `saved_page` + `from_mhtml` make the copy from the saved
   file by the capture's own rules (`_Capture.page` with `_Parts` instead of the network; `has` picks the picture the browser
   showed). `saved_folders`, `watch_start` / `watch_poll` / `watch_stop` find the file: saved since the wait began, settled,
   its saved address's host the link's (or, with one wait, any — a DOI link lands elsewhere), taken once, left in place.
2. `serve.py`: `/api/capture` says `blocked`; `/api/capture/watch` starts (opening the link for a request from this computer),
   polls (the copy written to `images/` server-side — large answers from serve.py are unreliable on Windows), stops.
   `keep_capture` is shared with `/api/capture`, so the standalone's notebook lock changes one place.
3. `13zzs-webcap.js`: `waitSaved` — a card in the corner, not a dialog; polls; makes the component or the next version.

## Decisions
- Only this computer's own requests open a browser (a paired device's person is not at the computer).
- The saved file stays in Downloads; the copy lives in the notebook.
- 20 minutes of waiting; × stops it.
- Under `SIS_NOBROWSER` no browser opens (tests); `SIS_SAVED_DIRS` sets the folders watched.
