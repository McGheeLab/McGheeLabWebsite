# V3.226 — Silent page-time tracker, retire confirm-hours popup

**Date:** 2026-05-15
**Branch:** Version-3.226 (planned)

## Problem

V3.160 set up an "auto-create a pending tracker entry per work-event" model. Every notebook save fired `ActivitySignals.recordWork({...})`; every protocol create fired the same; tasks-buckets fired `recordSchedule` for forward-dated subtasks; etc. Each fire surfaced a toast popup in the bottom-right corner that read *"Logged to tracker — confirm hours"* with "Open tracker" and "Undo" buttons.

User feedback:

> there is a popup that asks to track time whenever the user does an activity on a page, it currently overpopulates this popup and is annoying. we need to silently track the users active time on a page which is defined by the user doing something on the page at least once per 10 minute window. for example if the user types in some words on the page from 0-10 minutes they log 10 minutes of activity for that page, then form 10-20 minute window they do nothing active on the page they don't get the active track on that page. there should no longer be a popup confirming activity. instead the student will just edit the hours logged on the activity tracker page while they confirm the activity.

## Goal

Replace the per-action popup with a silent, time-based tracker:

1. **No more popup** — no in-page toast on any work signal.
2. **10-minute-window page-time** — listen for user activity (keydown, click, input, etc.) on every RM page; any event in a window counts the window as active; idle windows don't count.
3. **One row per page per day** in the tracker, accumulating 10 minutes per active window. User adjusts hours on the activity tracker page; the existing pending-banner UX handles confirmation.

## Decisions (asked the user)

- **Replace per-action triggers**, don't run them alongside. The new time-window tracker becomes the sole driver of auto-logged work. The `recordSchedule` triggers (tasks, meetings with due dates) stay so the Coming-up lane keeps working.
- **Entries land as `status: 'pending'`** so they show up in the existing waiting-on-hours banner on `activity-overview.html`. The user edits hours there.

### 2. Remove per-action work hooks

### 3. New module — [`rm/js/page-time-tracker.js`](../../rm/js/page-time-tracker.js)

Self-installing IIFE.

- **Page slug derivation:** `location.pathname` → `lab-notebook` from `/rm/pages/lab-notebook.html`; `/rm/index.html` → `dashboard`. Slug is stable across reloads, so the doc ID stays the same per page per day.
- **`SKIP_SLUGS`:** `activity-overview` (the tracker UI itself — pointless to track time spent confirming entries) and `pmr` (the heavy reviewer surface — admins skimming a student's PMR shouldn't accumulate hours).
- **`PAGE_LABELS`:** slug → display name map. Unknown slugs fall through to title-cased slug ("foo-bar" → "Foo Bar").
- **Window indexing:** `Math.floor((hours * 60 + minutes) / 10)` → 0..143 from local midnight. Date rollover resets `_lastLoggedWindow`.
- **Events listened:** `keydown`, `mousedown`, `touchstart`, `input`, `change`, `wheel`. `mousemove` and `pointermove` excluded — too noisy. `wheel` covers reading-only sessions (e.g., scrolling through a paper).
- **Throttle:** 1-second debounce on the activity handler. Cheap; real dedupe happens at the (window-idx, doc) level.
- **Visibility:** `document.hidden` short-circuits the activity handler. `visibilitychange` listener fires the handler when coming back from another tab.
- **Auth gate:** `firebridge.onAuth` waits for a signed-in non-guest. Skip when no user.
- **Doc shape** at `trackerEntries/{uid}/entries/auto-pagetime-<slug>-<date>`:
  ```js
  {
    date: '2026-05-15',
    text: 'Active on Lab Notebook',
    categoryPath: [],                       // user adds on tracker page
    duration: N * 10,                       // minutes
    milestone: 0,
    source: 'rm-page-time',
    source_ref: { kind: 'page-time', id: slug, path: pathname },
    status: 'pending',
    scheduled_for: null,
    auto_hours_estimate: N * 10 / 60,
    logged_windows: [0, 12, 13, 47, ...],   // deduped + sorted
    updatedAt: serverTimestamp,
    createdAt: serverTimestamp,             // first write only
  }
  ```
- **Write path:** read-then-write rather than transaction. Single client per uid (multi-tab is uncommon); even with two tabs the worst case is one window double-counted between read and write, which the dedupe on `logged_windows` mostly handles. If the user has confirmed (status != 'pending') the doc, we freeze for the day so confirmed hours aren't overwritten.
- **Public API:** `window.PageTimeTracker.{slug(), pageName(), currentWindow(), flush()}` for console debugging.

### 4. Wire-up — [`rm/js/nav.js`](../../rm/js/nav.js)

Append a small IIFE at the end of `nav.js` that creates `<script src="/rm/js/page-time-tracker.js" async>` and inserts it into `document.head`. Idempotent via `window.__rmPageTimeTrackerInjected`. Every RM page already loads `nav.js`, so the tracker now runs everywhere without per-page edits.

The async load means the tracker script may execute after Firebase SDK + firebridge are already loaded; it doesn't matter, because the script uses `firebridge.onAuth` (which is also async).

## What this doesn't do (future)

- The `rm/css/activity-signals.css` file still contains `.activity-signals-toast-*` styles. These are now dead but harmless. A future tidy-up could prune them.
- Categorization. The new entries land with `categoryPath: []`. User picks a category on the activity tracker page during the same edit pass where they adjust hours. Auto-category-per-page is a candidate follow-up if it turns out users always pick the same category for a given page.
- Admin / shared-time view. The new entries are per-user; cross-user reads work through the existing `shareActivity` flag + admin override.
- Window-by-window evidence. The doc stores `logged_windows` so the tracker page could in principle render which 10-min slots were active. Not exposed in the UI yet.

## Risks + mitigations

- **Over-counting passive page-views.** Visiting a page and leaving the tab open is fine (no events fire), but if the user is actually reading without scrolling we don't catch it. We accept this: reading-without-scroll is rare; `wheel` covers most reading patterns.
- **Multi-tab race.** Two tabs on the same page racing to write the same window. `logged_windows` dedupes; worst case is a redundant write. No data corruption.
- **Confirmed-then-resume.** User confirms an entry at 2h, then keeps working on the page. The writer freezes for that date — new windows are NOT counted toward a new entry, so the additional time goes unlogged. We accept this; user can re-edit hours on the existing entry if needed, or the next day's entry captures the next session.
- **`SKIP_SLUGS` coverage.** The list is hand-curated. If new "meta-surface" pages get added (admin dashboards, etc.) that shouldn't accumulate time, append them.
