# Plan — ELN safety + location surfacing (next: DOE)

## Context

Two follow-ups to the Lab Notebook (V3.110 → V3.118 already shipped) come
directly from grad-student bench reality:

1. **Hazard warnings on chemical chips.** A student picks a reagent and the
   chip renders without any indication that it's flammable / corrosive /
   acutely toxic. The data is already in inventory — `safety.signal_word`
   ("Danger" / "Warning"), `safety.ghs_pictograms[]` (GHS01–09),
   `safety.hazard_statements[]` (H-codes), `safety.precautionary_statements[]`,
   `safety.exposure_routes[]`, `safety.ppe_required[]`, `safety.nfpa_ratings`,
   `safety.first_aid` — and **65 of 158 chemicals are hazardous**, so this is
   a daily-bench surface, not a rare edge case. The pictogram→symbol→color
   mapping is already implemented at [rm/js/chemicals.js](rm/js/chemicals.js)
   `ghsPictograms()`; reuse it.

2. **Location info on every inventory chip.** Students need to *find* the
   item they're using. The schema is `locations: [{name, quantity, notes}]`
   on every inventory doc, but **0/935 items are populated today.** Surface
   the field anyway with a graceful "location not set" hint that points
   admins to [rm/pages/inventory.html](rm/pages/inventory.html) to populate.
   No bespoke admin tool needed in the notebook for this version — that page
   already has location editing.

DOE (LHS + Full Factorial + CCD with structured `state.doc.design`) is the
**next** version — see Brainstorm at the bottom for the ranked next-up list.

## Phase 1 (this ship — V3.119): Hazard + Location

### Files to modify

- [rm/js/lab-notebook.js](rm/js/lab-notebook.js) — extend the chip insert
  pipeline, the Materials panel render, and the body sanitizer's
  `ALLOWED_ATTRS` for SPAN.
- [rm/css/lab-notebook.css](rm/css/lab-notebook.css) — pictogram badge
  styling, location row styling, safety-details modal styling.

### Files to create

None. This is an additive change to the existing chip + Materials surface;
it stays inside the two files above.

### Chip data-attr additions (lab-notebook.js)

`insertInventoryChip(item)` already stamps `data-inv-id`, `data-inv-kind`,
`data-inv-name`, `data-inv-vendor`, `data-inv-cat`, `data-inv-cas`. Add at
insert time, sourced from the picker entry's full record (we already have
`safety` and `locations` on `inventoryState.list[i]`):

- `data-inv-hazard-signal` — `"Danger"` / `"Warning"` / `""`
- `data-inv-hazard-pictos` — comma-joined GHS codes, e.g. `"GHS02,GHS05,GHS07"`
- `data-inv-locations` — JSON-stringified array of `{name,quantity,notes}` (single attr is simpler than fanning out per-row attrs; sanitizer treats it as opaque text)
- `data-inv-storage` — `safety.storage_conditions` (free-text, plain string)

Project these onto each row in `state.doc.inventory_refs[]` too, so the
post-save derivation pass keeps them queryable later (e.g. "every entry
that touched a flammable").

`_projectInventoryEntry` already pulls `safety` from chemicals; extend it
to also project `signal_word`, `ghs_pictograms`, `storage_conditions`, and
the full `locations` array onto the searchable record.

### Sanitizer extension (lab-notebook.js)

`ALLOWED_ATTRS.SPAN` already permits the V3.114 inventory chip data-attrs.
Add the new keys: `data-inv-hazard-signal`, `data-inv-hazard-pictos`,
`data-inv-locations`, `data-inv-storage`. No change to URL-safety logic.

### `collectInventoryRefs()` extension (lab-notebook.js)

The existing walker rebuilds `state.doc.inventory_refs[]` from chips on
every keystroke. Extend the projected ref shape with the new fields so
re-rendering after a remote sync round-trip stays correct:

```js
{
  id, kind, name, vendor, cat, cas,
  hazard_signal,        // "Danger" | "Warning" | ""
  hazard_pictos,        // ["GHS02","GHS05",...]
  locations,            // [{name,quantity,notes}]
  storage_conditions,   // string
}
```

### Chip render (lab-notebook.js)

After the chip's closing tag, conditionally render a sibling
`<span class="ln-inv-hazard">…</span>` containing:

- A small signal-word pill (`Danger` red, `Warning` amber, hidden when empty)
- Compact pictogram badges (one per code, ~14×14 px)

Whole hazard sibling is omitted when the chemical is non-hazardous
(`signal_word === ""` AND `ghs_pictograms.length === 0`). Items
(`kind === "item"`) get no hazard surface — equipment doesn't carry
GHS data.

Click any pictogram or the signal-word pill → opens the safety-details
modal (next).

### Safety-details modal (lab-notebook.js)

New `openSafetyDetailsModal(invRef)` — reuses the V3.118 `.ln-modal-back`
/ `.ln-modal-{head,body,foot}` chrome unchanged. Body sections:

- **Header**: chemical name + signal-word pill + CAS · formula
- **Pictograms**: full row with labels (e.g. "🔥 Flammable")
- **Hazard statements**: bulleted H-codes
- **Precautionary statements**: bulleted P-codes
- **Exposure routes**: chip row
- **PPE required**: chip row
- **NFPA**: 4-quadrant diamond (health / flammability / instability / special), color-coded
- **First aid**: 4 short paragraphs (inhalation / skin / eye / ingestion)
- **Storage**: `storage_conditions`
- **MSDS**: link to `safety.msds.url` if present

Footer: a single "Close" button. No save. Read-only modal.

### Materials panel enhancements (lab-notebook.js)

`renderMaterialsHtml(refs)` already renders one row per ref. Each row
gains:

1. **Hazard column**: signal-word pill + inline pictogram badges (same
   compact size as the chip's hazard sibling). Hidden for items.
2. **Location row**: secondary line under the name reading
   `📍 Room 101, Shelf A · Room 304, -80 freezer` (joining `locations[i].name`).
   When `locations[]` is empty: italic gray "📍 location not set" with a
   small admin-only `(set)` link to `/rm/pages/inventory.html?focus=<id>`.
3. **Storage conditions**: when present and chemical is non-empty, append
   a third line `🌡 Flammable storage cabinet, RT`.
4. **Click-to-open** safety modal: clicking the pictogram column on a
   chemical row opens the same modal as the chip's hazard click.

### Inventory popover row enhancements (lab-notebook.js)

The picker popover currently shows `name · vendor · cat. # · CAS · category`.
Add a small `data-inv-kind`-aware suffix:

- For chemicals with non-empty `signal_word`: append a `Danger` / `Warning`
  pill in the meta line so the student sees the warning **before** picking.
  This is the most valuable place for the warning to live — it prevents
  the careless "I'll just stick TEMED in here" flow.

### CSS additions (lab-notebook.css)

- `.ln-inv-hazard` — flex row, gap 4px, vertical-align baseline, margin-left 4px.
- `.ln-hazard-signal-{danger,warning}` — small pill, 9 px, uppercase, white-on-red and white-on-amber.
- `.ln-ghs` — base badge: 14×14 px, rounded, centered emoji, font-weight 700.
- `.ln-ghs.ln-ghs-{01..09}` — per-code bg + fg.
- `.ln-material-loc` — 11 px, gray, italic when empty.
- `.ln-material-storage` — 11 px, gray, prefixed with 🌡.
- `.ln-loc-set-link` — 10 px, blue, underline on hover, only renders for admins.
- `.ln-safety-modal-body` — uses `.ln-modal-body` plus dl/dt/dd for the H-code / P-code lists.
- `.ln-nfpa` — 4-quadrant diamond, ~64×64 px, fixed colors (red/blue/yellow/white).

## Brainstorm — what else a biomed grad student wants (ranked, ship next)

These came out of the user's open question "what else would a student want
for an experimental lab notebook?" Listed in priority order — pick the
next 1–2 to scope into a follow-on version.

### High-value (next 2 versions)

1. **DOE builder** — Latin Hypercube + Full Factorial + Central Composite
   per the user's request. Toolbar `🧮 DOE` button → modal: pick design type
   → enter factors (name, low, high, levels) → generate matrix → preview
   → insert. Stored as a structured field `state.doc.design = {type, factors[], runs[], created_at}`. Renders as a sortable table panel below
   Protocols followed; "Download CSV" button on the panel. Algorithms
   in-house (~150–200 LOC for all three). Plan: `V3.120_eln_doe.md` (next).

2. **Lot number + expiry on chemical chip** — when picking a chemical,
   prompt for lot number and expiry date (inline mini-form on the picker
   row). Stored on `inventory_refs[i].lot` / `.expiry`. Reagent chip text
   becomes `Agarose · lot A23-118 · exp 2027-06`. Provides forensic
   traceability when results vary across lots — a common biomed
   troubleshooting need. Small (~80 LOC).

### Medium-value

3. **Inline calculators** — molarity / dilution / pH / unit conversion
   pickers. One-click insert with values stored as data-attrs so the user
   can edit later and the calculated result re-derives. Reuse mathjs
   (already lazy-loaded by protocols).

4. **Templates** — already in the original Phase 2 plan: cell culture day,
   microscopy session, bioprinting run, reagent prep, meeting notes. `+ New entry` becomes a split-button.

5. **Timer / stopwatch widgets** — embed countdown timers in the body
   ("incubate 30 min"). Notify when done via Web Notifications API. Tiny
   per-widget state; persist `started_at` on the entry doc.

6. **CSV / data import → inline preview** — paste a CSV, get a sortable
   table with a small auto-chart for numeric columns. Reuses existing
   attachment Storage path; the table renders from the parsed CSV.

7. **Sample lineage tree** — every entry can declare `derived_from: [entryId]`. A new "Lineage" panel shows ancestor + descendant entries
   as a small graph. Critical for cell-culture work.

### Lower-value / speculative

8. **Equipment booking shortcut** — an entry can link a calendar booking
   from `/rm/pages/scheduler.html`; calendar shows the linked entry on
   click.

9. **Voice dictation** — Web Speech API for hands-free logging while
   gloved. Browser-native, no backend.

10. **Barcode / QR scan** — phone camera reads a label, auto-fills the
    inventory chip or sample id. Uses `BarcodeDetector` API where
    supported, fallback to a JS lib.

11. **Cross-day continuation** — "this entry continues from yesterday's
    entry X". A small ↻ button copies the previous entry's title /
    project / tags / materials into a new entry.

12. **Failed-experiment archive view** — filter by `status === 'archived'`
    AND tag includes `failed`. Useful for end-of-rotation retros.

13. **AI summarize last N entries on Project X** — Anthropic API call,
    streams a markdown summary into a new entry. Already authenticated
    per [CLAUDE.md](CLAUDE.md) (Anthropic API key path exists in
    cv-builder.js).

14. **Pre-registration / hypothesis lock** — designate an entry as a
    pre-reg: locks `body_html` after the user clicks "Lock hypothesis";
    subsequent edits go into a sibling "results" entry. Useful for
    high-rigor experiments and easy to demonstrate good practice.
