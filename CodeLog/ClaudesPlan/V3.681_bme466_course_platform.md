# V3.681 — BME466 course platform: Homeworks page, assignment management, student dashboard, sections

Date: 2026-08-28 · builds on V3.674–675 (hwProgress cloud-save, usage dashboard,
roster) and respects V3.679 (`classAdminEmails` deliberately empty).

Instructor request: *"a new page called homeworks, and on the dashboard I want to
be able to assign homework to students. I also want students to have a dashboard
… pending, completed … a basic user profile … make requests/communicate to the TA
and Teacher. From the csv file the course section the student is in should be
imported. there are 4 sections to choose from, and it is important for us to know
the difference."* Built as one delivery.

## The section problem, and what was done instead

The four "sections" are the cross-listed catalog lines — **BME 466, AME 466,
BME 566, AME 566** (department × level), not D2L sections 001–004. D2L merges all
four into one org unit, so **the classlist export has no section column**
(verified against the real FA26 file: `Name, Pronouns, OrgDefinedId, Email, Role,
LastAccessed`, 51 rows = 50 students + 1 Instructor). Section therefore **cannot
be imported**, and the instructor chose: students self-declare, staff can always
assign/reassign, and the staff value wins.

Only the **level** (466 vs 566) has functional consequences — HW1's `[566 only]`
parts, grad rubrics, the 566-only BME566 QE, project team composition. The
**BME/AME axis has no functional effect anywhere** and is captured for reporting
only. Assignment targeting is by level, never by department.

## Narrow TA role — the V3.679 answer

V3.679 emptied `classAdminEmails` because an `@arizona.edu` address there hands
out the whole instructor view (page-edit chrome, the roster with every student's
name, `hwProgress` delete) to the same kind of account a student signs in with.
That left "assign a user to be a TA" with no safe answer.

V3.681 adds a **second, narrower list**: `schedules/bme466.courseStaffEmails`.
It grants exactly the new surfaces — assign homework, status matrix, extensions,
answer requests, set sections — and nothing else. The dashboard's **"Make TA"
button now writes this list** instead of `classAdminEmails`.
`firestore.rules`' `bme466CourseStaff()` is deliberately **absent** from the
roster block, the `schedules/{id}` update rule and `hwProgress` delete; the rules
suite asserts each of those denials, so the guarantee is tested rather than
documented.

## Data model (4 new shapes)

| Path | Writers | Holds |
|---|---|---|
| `schedules/bme466/assignments/{slug}` | staff | title, kind, `audience` (all/466/566), `published`, `dueAt`, `opensAt`, `moduleUrl`, `d2lLink`, `progressKey`, notes, order |
| `hw466Status/{slug}_{uid}` | student ∪ staff, key-pinned per side | student: `selfMarked`, `selfMarkedAt`, `note`; staff: `ackBy`, `ackAt`, `feedback`, `dueOverrideAt`, `extensionNote` |
| `schedules/bme466/profiles/{uid}` | student ∪ staff, key-pinned | student: name/pronouns/major/year/interests + **`sectionClaim`**; staff: **`sectionAssigned`** (+by/at), `staffNote` |
| `schedules/bme466/threads/{id}` + `messages/{id}` | author ∪ staff; messages immutable | thread: author, subject, topic, status, function-written `lastMessageAt`/`messageCount`/`lastMessagePreview`/unread flags; message: author, **proven** `authorRole`, body |

Why these and not the obvious alternatives:

- **Assignments are a subcollection, not an array on the schedule doc.** Writing
  that doc requires `classAdminEmails` = the full instructor view, which a TA must
  not have. A subcollection also gets rules-enforced shape validation and
  free-form ids, so **creating an assignment never needs a rules redeploy**.
- **Profiles live under `schedules/bme466/`, not `users/{uid}.bme466`**, because a
  `role:'guest'` TA cannot read another guest's `users` doc — a TA could never
  have seen a student's section there.
- **No roster rules change.** A student's own section reaches them through their
  `profiles` doc and their extension through their `hw466Status` doc, so the
  roster subcollection stays FERPA-sealed and staff-only exactly as its V3.675
  comment promises.
- **`authorRole` is proven, not claimed**: the rule requires
  `authorRole == (bme466Staff() ? 'staff' : 'student')`, so neither side can
  post as the other, and messages are `allow update, delete: if false`.
- **No grades anywhere.** Key whitelists reject `grade`/`score`/`points`, and a
  published assignment doc (world-readable) additionally rejects `dueOverrides`
  and any per-student field. D2L stays the gradebook and the deadline authority.

## Two bugs the rules tests caught before deploy

1. **`authorRole` was required by the thread-create rule but missing from its own
   `keys().hasOnly()` whitelist** — every thread create would have been denied in
   production.
2. **`bme466Staff()` was not total.** `isAdmin()` dereferences `users/{uid}`
   unguarded, so it *errors* (→ denies the whole rule) for a signed-in user with
   no users doc. Everywhere else that is harmless because `isAdmin()` sits at the
   end of an `||` chain a real user already satisfied — but here it is evaluated
   **eagerly** inside `authorRole == (bme466Staff() ? …)`, so an un-bootstrapped
   student could not open a thread at all. Fixed with `bme466IsGlobalAdmin()`:
   email lists first (they cannot error), the admin lookup guarded by `exists()`.

## Other rules work

- `bme466RosterEnforced()` / `bme466Rostered()` hoisted out of the `hwProgress`
  match block so the new blocks share them.
- `hwProgress` **read** widened to `bme466Staff()` (a TA needs the status matrix);
  **delete** deliberately stays classAdmin-only — destroying a student's saved
  work is not a TA affordance.
- The `hwProgress` assignment enum is now **data**: `hwAssignmentAllowed()` checks
  the nine legacy keys inline **first** (so `||` short-circuits and they keep
  working even if the schedule doc read errors), then
  `schedules/bme466.hwProgressKeys`. Adding a homework module no longer needs a
  rules deploy; the dashboard derives that list from the assignments'
  `progressKey` fields.
- Assignment slugs are pinned to `^[a-z0-9][a-z0-9-]{0,59}$` — **no underscore**,
  because both `hwProgress` and `hw466Status` recover the uid from
  `docId.split('_')[1]`.

## Client (`class-builder.js`)

Three new `SECTION_REG` keys (`homeworks` was already taken by an unrelated
classFiles uploader labelled "Assignments"):

| key | audience | surface |
|---|---|---|
| `hwList466` | public | Homeworks page — published assignments, type, due, module/D2L links |
| `hwMine466` | `studentOnly` | Pending / Completed, self-mark, own module progress, profile + section claim, private requests |
| `hwAssign466` | `staffOnly` | assignment manager + editor, status matrix (section/progress/self-report/extension/ack), requests inbox, sections card + CSV |

- `tabIsVisible()` replaces the inline `adminOnly` filter and adds `staffOnly`
  (instructor **or** TA) and `studentOnly` (any signed-in `@arizona.edu`, staff
  included — a tab that vanishes when you sign in as staff is worse than an empty
  one). Mirrored at the section level in `buildSectionBlockHTML()` so a section
  dropped onto a hand-built public tab cannot leak the staff surface.
- **`bme466Section(profile)` is the single section accessor** — `sectionAssigned`
  beats `sectionClaim` (inverted vs `bmeEffectiveCampus`, where the student wins;
  the comment says why), unrecognized values warn, and `source:'unknown'` **fails
  open**: the student sees every assignment plus a nudge, the matrix shows a
  "no section" chip and drops them from per-level denominators. No silent default
  to 466 — hiding a 566-only assignment from a 566 student is the worst available
  failure.
- A student may `get` but never `list` `hwProgress`/`hw466Status`, so the student
  view reads its own docs **by id** — which is why an assignment carries
  `progressKey`.
- All queries sort client-side, so **no composite index is needed** anywhere in
  this feature (and `firestore.indexes.json`, which has uncommitted work from
  other sessions, is untouched).
- Migrations (idempotent, admin visit): append the three tabs before the
  admin-only Dashboard tab; add `courseStaffEmails: []`; seed the 14-item F26
  assignment inventory as **unpublished drafts** with dates blank (D2L is the
  authority and no repo file holds real F26 dates); derive `hwProgressKeys`.

## `functions/bme466-notify.js` (new, 2 triggers)

Reuses `notifyUsers()` from `functions/helpers/notify.js`, which already writes
both the push and the `userData/{uid}/notifications` feed item.

- `onBme466MessageCreated` — denormalizes the thread (`lastMessageAt`,
  `lastMessagePreview`, `messageCount`) and raises the unread flag for the side
  that did *not* write; notifies the other side. No client rule grants those
  fields, which is what makes "unread" and "last reply" unfakeable.
- `onBme466AssignmentWrite` — only the transition **into** `published` fans out
  (same policy as `class-notify.js`), audience filtered by level, idempotent via
  a `notifiedFor` stamp. Email→uid ladder: `users` query → `getUserByEmail()` →
  log and skip; global admins always included so a request cannot vanish because
  a TA has not signed in yet.

## Course repo (V2.45)

`scripts/hw1_grade.py --sections FILE` — the concrete payoff. The grader had no
roster, so it scored the two 566-only fields (`t2_alpha`, `t5_nrec`) for everyone
and left a human to interpret an extra line. It now reads the dashboard's sections
CSV (`level`/`section` column + `sid`/`netid`/`email` key, normalized through
`hw1_keygen.normalize`) and reports the 566 block as required for 566 students and
"not required" for 466 ones. **HW0/post-test are NetID-seeded so the export joins
as-is; HW1 uses minted course IDs, so for HW1 the CSV needs a `sid` column** from
the Synology ID map. Students the file does not cover are level `?` and keep the
old behavior, with a closing summary naming them — a partial map degrades loudly
instead of silently mis-scoring.

## Rollback

Most reversible first: clear `courseStaffEmails` (revokes TA access instantly, no
deploy) · set every assignment `published:false` (empties the Homeworks page) ·
re-FTP the previous `class-builder.js` (the new collections go inert) · delete the
V3.681 rules blocks (clients fail soft to empty states) · delete the two
functions (notifications stop; threads still work, minus denormalized counters).
Nothing pre-existing depends on the four new collections; `hwProgress`, the roster
and the pretest module are untouched apart from the enum becoming data-driven
with the legacy list first.
