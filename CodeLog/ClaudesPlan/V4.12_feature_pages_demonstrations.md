# V4.12 — A page for every feature, with a demonstration

## Goal
Gabe (17 Nov 2026): "Each feature deserves a full page when clicked on, with a demonstration of what it can be used for, described by the user. Claude then creates a test note, screen records the process of using the feature, and embeds that video in the Settings tab for that feature page. Make sure to update the skill associated with Settings and Features with this new workflow."

Until now (V3.995) a feature's tile unfolded inside the Features board, with its description and settings, and the live preview stood beside the board. There was nothing that showed a feature being *used*.

## Approach
- **The page.** `#/settings/feature/<id>` (`SettingsView.render(a0, a1)` → `featurePage`). A click on a tile goes there; the tile no longer unfolds. The page has the whole width: a line back to the board and to the features before and after, the head (name, presets, tab, needs / goes with, the switch), the whole description, then two columns — What it is for and Settings on the left, the live preview sticky on the right (above them under 1100 px). Coming back, the board scrolls to the tile and marks it.
- **The demonstration** is data beside the register, not part of `FEAT.def`: `FEAT.demo(id, entry)` in a file of its own, `src/20b-demos.js`, which the recorder writes. `FEAT.audit()` is unchanged, so the 63 features without a recording do not fail the tests; `FEAT.undemoed()` lists them, and their pages say "No demonstration has been recorded for this feature yet".
- **"Described by the user".** The `use` text is what the feature is for in the words of whoever asked for it. For the two first recordings these are Gabe's own requests (V4.7 Floats; this request). It is never invented: a feature with no description waits for one.
- **Nothing plays uninvited.** A still and a Play button; the video is not fetched before Play. The steps under it are buttons that play from their second; the current one is lit and written under the picture.
- **Playing on the desktop.** `serve.py` answers static files without byte ranges, where Chrome cannot seek. So the file is fetched whole (they are under about 1 MB) and played from a blob URL; if the fetch fails, the address is used directly; if that fails, one sentence says the recording is not on this device.
- **The recorder** (`scientia/demokit/record.mjs`) lives in `scientia/` so it travels to the standalone repository with the app.
  - Chrome headless on an empty profile; the app served as files from the folder above; the lab layer's `<!--sis-desktop-->` blocks cut out as it is served, so the recording shows the app itself (`--lab` keeps them).
  - `Page.startScreencast` gives a frame whenever the page changes; `--force-device-scale-factor` makes them 1.5× (the screencast ignores an emulated scale). Each frame is kept until the next came (ffmpeg concat with durations), 15 frames a second, H.264 `yuv420p` with `+faststart`: it plays everywhere, iPad included.
  - A pointer, a click ring and the pressed keys are drawn into the page (the screencast has no pointer). The pointer moves eased, 16 ms a step.
  - The script's steps are `[caption, async (R, ctx) => …]`; the caption's second is taken when the step starts, minus the time before the first frame.
  - The entry is written between `/* demo:<id> */` markers with the file's hash (`v`), used as `?v=` on both files.
- **Where the files go.** `scientia/demos/` (tracked) → `rm/scientia/demos/` by `scripts/scientia_build.py` (`COPY`; git-ignored like `rm/scientia/scientia.html`, and `deploy.py` rebuilds whenever `src/` is newer, which a new entry in `20b-demos.js` always makes it) → and `app/demos/` in the desktop download. `serve.py` serves the folder as it is.
- **Its own feature**, as every feature must be: `FEAT.def` `demos` in Tabs & overview, in every preset — speed, the step under the recording, stop / start again — with a preview that follows them.

## Decisions
- **MP4 (H.264), not WebM:** Safari on the iPad plays it; the essentials ffmpeg build has libx264.
- **Captions as text under the video, not burnt in:** sharp at any size, selectable, and they are the step list anyway. The pointer and keys are burnt in, since they are part of what happened.
- **One recording for both builds:** the lab's pills change where a note's tools sit, but not what a feature does; recording the app itself keeps the standalone and the website on the same file.
- **Size:** about 20 KB a second at 1560 × 975. Sixty features of half a minute are about 40 MB in the repository and the phone app's bundle (`sync-rm.mjs` takes all of `rm/`): worth telling Alex before the set is complete.
- **Not done here:** recordings for the other 63 features — each needs Gabe's description of its use first.
