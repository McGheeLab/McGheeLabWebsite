# V3.869 — Phase 1 of the Scientia + RM unification: the web app is RM-native (the library mirror, lab mode)

**Date:** 2026-10-23
**Request (Alex):** *"continue to phase 1"* — of [V3.866_scientia_rm_unification.md](V3.866_scientia_rm_unification.md) §3:
the web Scientia replaces its own Library, Activity, Data and Tasks page with RM's, in the order the plan set —
**library mirror first** (cites and Phase 3 depend on it), then materials, then tasks/activity.

## What this version does

| Scientia tab (web build only) | Now | How |
|---|---|---|
| **Library** | the lab's library, from RM | the hub mirrors RM `items` into the person's `library` rows (id = the RM item id); `lab-mode.js` replaces the Library view: lab papers with *Read in RM* / *Open in RM*, a *Refresh from RM* button, no DOI/paste adders (papers are added in RM); desktop-only papers stay in a second list with Gabe's own card |
| **#/read/\<RM paper\>** | RM's reader | the in-app reader is bypassed for mirrored rows (no "attach the PDF" prompt) |
| **Activity** | gone → pointer to RM's tracker | tab removed; `#/activity` renders a pointer page |
| **Data** | gone → "desktop only" | tab removed; `#/data` explains why |
| **Tasks page** | gone → pointer to RM tasks | `#/tasks` renders a pointer page; the task *component* in notes stays (V3.870 makes it an RM task) |
| Materials, Today, Portfolio, Review, Terms, Canvas, Settings | unchanged | Materials is V3.870 (the inventory picker) |

The desktop app is untouched: `scientia/src` did not change. Everything is in the web build's lab layer.

## Design

### The library mirror (hub side)

`functions/scientia-hub-core.js`:
- `rmItemToLibraryRow(item)` — RM `items/{id}` (`type: paper`, `meta.library.is_library_entry`) → Scientia's library
  record: `{ id, rm: true, rmId, kind: 'paper', doi, cslType, title, authors[{family, given}], container, publisher,
  year, volume, issue, page, issn, url, isPreprint, csl (built, `_source: 'rm'`), rmPdf, added, rmUpdated }`; `pdf` is
  the sentinel `rm:<id>` when RM holds a PDF, so Gabe's "has a PDF" branches route to `#/read/<id>` (which lab mode
  answers with RM's reader).
- `planMirror({state, rows, items})` — ops for the hub's `push`: new papers added, unchanged skipped (`MIRROR_FIELDS`
  compared), changed updated **keeping the fields the mirror does not own** (a desktop-attached `pdf`, notes),
  papers gone from RM tombstoned; non-RM rows never touched. `base` = the current seq, `prev` = the current row, so
  the ordinary merge rules apply and nothing conflicts.
- `route()`: `hello` and `state` call `hub.mirrorLibrary({})` first (quietly — a mirror failure never breaks hello);
  `POST api/rm/library/refresh` forces it; `GET api/rm/library/pdf?id=` mints a download URL for an RM PDF (the same
  token scheme as the hub's own media), for Phase 3's desktop pull.
- `MemoryHub.mirrorLibrary` mirrors `hub.rmItems` (fixtures, the dev hub).

`functions/scientia-hub.js` `FirestoreHub.mirrorLibrary({force})`: throttled by `mirrorAt` on the hub doc (5 min);
reads `items` where `type == 'paper'` and `meta.library.is_library_entry == true` (equality-only, no composite index),
the hub's `library` rows, plans, pushes as device `rm` named **RM library**, stamps `mirrorAt / mirrorN /
mirrorWritten`. `rmPdfUrl(id)` reads the item's `storage_path`, reuses or sets the object's download token.
**Deployed** before the client (`firebase deploy --only functions:scientiaHub`).

Why the hub and not the browser: every device of the hub — the web app, Gabe's desktop through the bridge — receives
the lab's papers through the sync it already runs, and Phase 3 (desktop ↔ RM) starts from rows that already exist.

### Lab mode (client side) — `rm/scientia/lab-mode.js`

`scripts/scientia_build.py` now writes `window.SIS_TARGET = 'web'` before the cloud layer and appends
`<script src="lab-mode.js?v=<hash>">` after the app (before `</body>`). The app's globals (`TABS`, `VIEWS`, `App`,
`DB`, `M`, `LIB`, `h`, `plural`, `debounce`) are top-level `const`s of the classic script that precedes it — same
realm, same global lexical scope — so lab mode reshapes the running app without a line in `scientia/src`:
- `TABS.splice` removes `activity` and `data` **before the first render** (the shell builds the nav once);
- `VIEWS.activity / tasks / data` become pointer pages; `VIEWS.library` becomes the lab library (`title: true` so
  `App.refresh()` leaves its meta line alone); `VIEWS.read` is wrapped: an RM row renders *Read in RM*, anything else
  falls through to Gabe's reader (`after` / `update` guarded the same way);
- `openRM(href)` opens the RM page in a new tab (`noopener`) and posts `{sis, type: 'rm-open', href}` to the notebook
  host (`notebook-scientia.js` records it — the hook for an in-notebook reader later);
- `window.SIS_LAB = { version, RM, opened, openRM, refresh }` for the harness.

### Verification

- `node functions/test/scientia-hub.test.js` — 36/36 (4 new: the row mapping, the plan, the hub flow — hello mirrors
  once per 5 min, refresh forces, a device pulls the rows as ops from device `rm`, the PDF route is 404 off Firestore;
  a hub without a mirror still answers).
- `scripts/tests/v3869-scientia-lab-mode-harness.html` — **30/30 headless against Gabe's real web build**: the built
  file loaded into an iframe with a prelude (a stub Firebase signed in as `u1`, the gstatic SDK loads short-circuited,
  the function answered in-page with a record of 2 RM papers + 1 desktop-only paper + 1 note + a `settings` row).
  Checks: the target flag, boot to `__ready`, tabs, the store holds the rows, `M.lib()` / `LIB.search()` resolve RM
  papers, the Library page (cards, Read/Open in RM, the desktop-only list, no adders), opening goes to RM, the filter,
  Refresh (signed POST + the status line), `#/read/<rm>`, the three pointer pages, a note made through `M.createDoc`
  opens in the editor and pushes, no popups / rejections / errors.
- `v3864-notebook-scientia-harness.html` — 31/31 and 6/6 (no regression with lab-mode in the build).
- `python3 scripts/merge_check.py worktree` — clean.

Three facts the harness taught (kept in the file): a `srcdoc` document resolves relative URLs against the parent, so
the two lab script tags are rewritten to absolute paths; `page.evaluate` runs in an isolated world and cannot see the
frame's page globals (read the DOM, or let the page world write diagnostics into it); the second boot after a full
load needs `settings.dataEpoch` in the record or the app tries to wipe, which the sync layer refuses off the desktop.
